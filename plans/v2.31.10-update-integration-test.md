# v2.31.10 — Auto-Update Integration Test (Windows)

## Триггер

v2.31.7-r10 helper.cmd `set /a SVC_TRIES` parser bug пролежал в `main` ~7
дней до появления у пользователя. Симптом — 100% v2.31.7 → v2.31.8
upgrades silently failing с `"20 was unexpected at this time"` в
`update.log`. Поймали вручную через probe-driven trace.

Корневая причина вне самого бага: **ни один автотест не запускал
helper.cmd через cmd.exe**. Все unit-тесты видят C# string template, не
runtime поведение CMD-парсера. CMD имеет свой interpreter и pre-expanded
`%VAR%` substitution в parenthesized blocks — поведение, которое .NET
тестами не воспроизвести в принципе.

## Симптом

User clicks "Update" → app exits → helper.cmd запускается через cmd.exe
→ `if !SVC_TRIES! gtr 20` (где SVC_TRIES не expand'ed) превращается в
`if  gtr 20` → CMD parser aborts → xcopy не запускается → файлы не
копируются → перезапущенный App запускается на той же версии.

CLAUDE.md rule 1a ("MCP test после каждого ship — обязательно") уже
предписывает ручную проверку, но a) на CI нет MCP, b) человек может
забыть, c) это reactive а не proactive.

## Root cause (тестовой инфраструктуры)

```
VPNRouter.Core.Services.UpdateChecker.ApplyUpdateWindows
    └── string.Join("\r\n", new[] { ... })  ← 50+ lines of cmd.exe DSL
            └── File.WriteAllText(helperPath, cmd)
                    └── Process.Start("cmd.exe", "/c \"" + helperPath + "\"")
                            └── ┌─────────────────────────────────────┐
                                │ cmd.exe parser sees the script for  │
                                │ the FIRST time at runtime. Bugs in  │
                                │ EnableDelayedExpansion / %VAR% vs   │
                                │ !VAR! usage / quoting / escaping    │
                                │ surface ONLY here.                  │
                                └─────────────────────────────────────┘
```

Юнит-тесты валидируют что `string.Join` produces a string. Они не
запускают cmd.exe. Никакая степень покрытия generator-кода не поймает
parser-баг в produced output.

## Fix strategy

Полный end-to-end test, который реально запускает helper.cmd через
cmd.exe и assert'ит что он отработал чисто. Состоит из трёх кусков:

### 1. CI-only CLI команда — `vpnrouter test-update`

`VPNRouter.CLI/Commands/TestUpdateCommand.cs`. Hidden command (не в
`--help`), gated behind `VPNROUTER_CI=1` env var. Принимает:

- `--target <VERSION>` — version label (для assertions / receipt)
- `--staged-dir <DIR>` — pre-extracted update payload, skip GitHub
  download. Используется CI чтобы не зависеть от published release.
- `--repo <OWNER/REPO>` — для тестирования forks (default
  `PavelLizunov/VPNRouter`).

Поток:
1. Verify VPNROUTER_CI=1 (refuse otherwise).
2. Construct `UpdateChecker(Channel = "experimental")` so prerelease tags eligible.
3. If `--staged-dir`: skip GitHub, use payload directly.
4. Otherwise: `CheckForUpdateAsync` → verify `LatestVersion == --target` → `DownloadAndStageAsync`.
5. `ApplyUpdate(extractedDir)` → запускает реальный helper.cmd через cmd.exe.
6. CLI exits → helper.cmd waits for parent exit → копирует файлы →
   logs to `%ProgramData%\VPNRouter\logs\update.log`.

Exit codes (для CI assertion):
- `0` — dispatched OK (helper.cmd will run async)
- `2` — CI gate / arg validation
- `3` — staged dir not found
- `4` — `CheckForUpdateAsync` threw
- `5` — no update available (current >= target on GitHub)
- `6` — latest published version != requested target
- `7` — download / extract failed
- `8` — `ApplyUpdate` threw

### 2. Tiny Core change — VPNROUTER_CI=1 skip-relaunch in helper.cmd

`VPNRouter.Core/Services/UpdateChecker.cs::ApplyUpdateWindows`. The
helper.cmd template has a `start "" "{guiExe}"` line at the end that
launches VPNRouter.GUI.exe. On a CI runner this would:

- Spawn an Avalonia window the test can't close cleanly (windows-latest
  has a desktop session — it doesn't fail, but the window stays around).
- Trigger the Go stub's integrity check, which on mixed-version damage
  invokes SelfRepair → downloads `install.ps1` → reinstalls. Bad for CI.

Fix is a 5-line conditional: when `VPNROUTER_CI=1` is in the calling
process's env (which `cmd.exe` inherits via UseShellExecute), substitute
the `start` line with a `rem CI mode: relaunch suppressed` no-op. Helper
still does the full file copy + Service stop/restart dance — only the
final relaunch is skipped. **Crucially** the parser bugs we want to
catch surface BEFORE the relaunch line, so we still catch them.

### 3. CI workflow — `.github/workflows/test-windows-update.yml`

Triggers:
- `workflow_dispatch` — for manual re-runs
- `release: published` — auto-runs after every published prerelease/stable
- `push: tags: v*-r*` — runs on every -rN tag push (before release upload)

Steps:
1. Checkout + setup .NET 8 + Go 1.21.
2. Read AppVersion.cs literal (build.ps1's hard-guard requires they match).
3. `./build.ps1 -Version <ver>` — generates install + update ZIPs.
4. Extract install ZIP to `C:\TestVPNRouter\install\` (NOT Program Files
   — avoids ACL / lock issues, easy cleanup).
5. Extract update ZIP to `C:\TestVPNRouter\staged\`.
6. Wipe `%ProgramData%\VPNRouter\.update-installed-version` and
   `update.log` so post-update assertions see only this run's output.
7. Capture pre-update Core.dll mtime.
8. `& cliExe test-update --target <ver> --staged-dir C:\TestVPNRouter\staged`
   with `VPNROUTER_CI=1`.
9. Poll `update.log` up to 5 min for `helper done`. Fail-fast on
   `was unexpected at this time` (the v2.31.7-r10 signature).
10. Assert: Core.dll mtime advanced (proves xcopy ran).
11. Assert: sing-box.exe present.
12. Assert: install receipt exists with ≥2 lines.
13. Capture logs as workflow artifact (14-day retention).
14. Cleanup: kill processes, remove test dirs.

### Why local-build-as-FROM, not "previous-stable → latest-prerelease"

The bug we want to catch is in the **CURRENT branch's helper.cmd
generation code**, not in some previously-shipped binary. Using a
prev-stable as the FROM only tests its already-frozen helper.cmd —
it won't catch a bug freshly introduced into `main`'s `UpdateChecker.cs`.

Local-build-as-FROM is also network-independent: works on tag push
before the release is uploaded, works on PRs, works on dispatch from
any branch. Robust to GitHub API rate limits.

The "real upgrade path" test (download prev stable, update to latest
published prerelease) is a complementary value-add and lives in the
follow-up section below.

## Оценка

- Code: ~250 lines of CLI command + ~10 lines of UpdateChecker change.
- Workflow: ~220 lines of YAML.
- Dev time: ~3 hours (includes CI iteration).
- Risk: low. Only NEW code; helper.cmd generation logic untouched
  except for the relaunch-skip toggle, which is gated by env var
  defaulting to off. Real users see no change.
- Recurring CI cost: ~10 minutes per run, only on tag push / release
  publish / manual dispatch.

## Known limitations

- **Windows only.** macOS + Linux update flows have their own
  helper-script bugs class (e.g. `ditto` invocation, polkit policy
  paths). Follow-up: extend to mac-runner and ubuntu-runner with
  matching `test-update` command path. Today's CLI command is portable
  C#; the cmd.exe-equivalent shell scripts are platform-specific
  inside `ApplyUpdate{Mac,Linux}`.
- **Doesn't catch download-side bugs.** Because we use `--staged-dir`
  to skip GitHub. A separate "real upgrade path" workflow would
  download an actually-published asset and test the full
  `CheckForUpdateAsync → DownloadAndStageAsync → ApplyUpdate` chain.
  That's valuable but not the regression we just suffered. Worth
  adding once this stable.
- **Self-build only.** FROM = TO = current branch's build. Doesn't
  catch "v2.31.8's helper can't apply v2.31.10's update layout" type
  cross-version regressions. Would need the published-release flow to
  catch that.
- **GUI relaunch suppressed.** We exercise the file copy + Service
  dance, but not the relaunch path (Go stub integrity check, App.exe
  startup AppVersion read). Those have their own SelfRepair tests
  (`VPNRouter.GUI/integrity_test.go`) but the integration is untested.

## How to extend

### Add Linux

1. New job in same workflow file: `runs-on: ubuntu-22.04`.
2. Build via `dotnet publish`, package as tar.gz.
3. Stage as `--staged-dir` on `/tmp/staged/`.
4. Run `dotnet bin/Release/net8.0/linux-x64/VPNRouter.CLI.dll test-update`
   (Linux CLI, when it exists — currently CLI is win-x64-only;
   needs porting; see VPNRouter.CLI.csproj target).
5. Assert via `~/.config/vpnrouter/logs/update.log`.

### Add macOS

Same pattern, runner `macos-13`. macOS update flow runs `ditto` so
assertions become "did ditto exit 0" + "is the .app bundle's
Info.plist version updated". Helper script is bash, not cmd.exe, so
the bug class is different but the test pattern is identical.

### Add cross-version test (separate workflow)

`.github/workflows/test-windows-update-published.yml`:
- Runs on `release: published` only.
- Downloads PREVIOUS stable's install ZIP via `gh release download`.
- Uses CLI without `--staged-dir` — i.e. real GitHub download.
- Asserts `LatestVersion == github.event.release.tag_name`.

Skipped from this PR because it's network-dependent (GitHub API rate
limits during a CI burst could make it flaky). Worth adding once
self-build CI is stable.
