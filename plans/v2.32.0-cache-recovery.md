# v2.32.0 — Cache Recovery (schema-versioned wipe + rebuild)

## Триггер

Каждый JSON-кеш в `%ProgramData%\VPNRouter\` сегодня проваливается тихо когда
фит:
- truncated mid-byte (disk full, kernel panic во время `Save`)
- partial JSON (`{"schema_version":1,"items":[…` без закрывающего `]}`)
- schema-drift между версиями (поле переименовали, enum значение убрали)
- кто-то вручную поправил файл и закрыл `}` не в том месте

Существующий код во всех трёх load-сайтах одинаков: `try { Deserialize } catch
{ return null/empty }`. Симптом для пользователя — фича сломана, без
диагностики:
- `free_configs.json` corrupt → Free Configs tab пустая, refresh не
  триггерится автоматически
- `profiles.json` corrupt → ProfileManager падает на BuiltIn даже когда HTTP
  до GitHub отвечает (сценарий: повредили кеш + потом потеряли сеть)
- `state.json` corrupt → `vpnrouter stop` думает что VPN не запущен, оставляет
  процесс живым

## Симптом

«Я обновился — Free Configs показывает 0 серверов» / «у меня sing-box
работает, а CLI status пишет not running». Без логирования, без backup
файла, без рестора.

## Root cause

**Единственный шаблон recovery** во всех load-сайтах:
```csharp
try { return JsonSerializer.Deserialize<T>(File.ReadAllText(path)); }
catch (Exception ex) { _logger.Warning("…"); return null; }
```

Проблемы:
1. **Возвращаемый `null`** не отличает «файла нет» от «файл порченый».
   Caller не знает: подожди и попробуй ещё раз? Удалить и пересоздать?
   Хорошо ли это что мы потеряли pinged latency на 25k серверов?
2. **Никакой schema_version** — нельзя поймать drift при апгрейде.
   `FreeConfigCache` уже два раза переживал тихие миграции (v2.31.3-r1
   sub-5ms heal, v2.31.5-r2 keep-policy) и каждый раз heal-логика сидела
   inline в `Load()`.
3. **Никакого backup файла** — operator не может проиграть corruption case
   через support: оригинальный payload пропал.
4. **Один inline catch на каждый callsite** — при добавлении 4-го кеша
   придётся снова копировать.

## Fix strategy

### Stage 1: `CacheRecovery` helper (Core)

Новый `VPNRouter.Core.Services.CacheRecovery.LoadOrRecover<T>(filePath,
expectedSchemaVersion, deserialize, structuralCheck?, logger?)`:

1. file missing → return `(null, NotFound)` (clean first-launch — не warning)
2. file present, JSON read failed → backup + return `(null, IoError)`
3. probe `schema_version` через System.Text.Json:
   - `null` или `<= 0` → backup + return `(null, SchemaMissing)`
   - `< expected` → backup + return `(null, SchemaMismatch)`
   - `>= expected` → forward через caller deserialiser
4. caller's `deserialize` throws → backup + return `(null, JsonMalformed)`
5. caller's `deserialize` returns null → backup + return `(null, JsonMalformed)`
6. caller's `structuralCheck` returns false → backup + return
   `(null, StructurallyInvalid)`
7. otherwise → return `(value, Success)`

`backup` = rename файла на `<file>.corrupt-{yyyyMMdd-HHmmss}` (с counter
suffix если две corruption события в одной секунде). Если rename не
сработал — fallback на `Delete` чтобы не оставить hot loop.

`CacheLoadResult<T>` запись:
- `Loaded` — true только при `Success`
- `ShouldRebuild` — true для всех 4 corruption причин (`SchemaMissing`,
  `SchemaMismatch`, `JsonMalformed`, `StructurallyInvalid`)

### Stage 2: миграция трёх load-сайтов

| Файл | Cache class | Schema | Refactor |
|---|---|---|---|
| `cache/free_configs.json` | `FreeConfigCache.CacheFile` | v1 | `[JsonPropertyName("schema_version")] int SchemaVersion`. `Save()` всегда штампит. `Load()` через `CacheRecovery`. v2.31.3 sub-5ms heal остаётся в-памяти после Load. |
| `cache/profiles.json` | новый `ProfileCacheFile` wrapper | v1 | Wrapper {schema_version, cached_at, upstream_url, profiles}. `GitHubProfileSource.LoadAsync` пишет wrapper после успешного HTTP. На HTTP fail — fallback читает wrapper через CacheRecovery (это новая фича: offline cache read, раньше cache был write-only). |
| `state.json` | `RunState` | v1 | `[JsonProperty("schema_version")] int`. `Write()` штампит, `Read()` через `CacheRecovery`. На corruption — `Read()` возвращает `null` ⇒ `stop` / `status` ведут себя как «no running instance». |

### Stage 3: миграция старых файлов (one-time)

`free_configs.json` без `schema_version` → wipe + backup → `FreeConfigAggregator.RefreshAsync`
пересобирает из network (next refresh trigger). Empty cache не ломает
UI — просто показывает «pool empty», как при первом запуске.

`profiles.json` без `schema_version` → wipe + backup → CacheRecovery
возвращает `null` → `GitHubProfileSource.LoadAsync` re-throws на HTTP
exception → `ProfileManager` идёт к Local, потом BuiltIn. Когда HTTP
снова работает — `GitHubProfileSource.LoadAsync` пишет fresh wrapper.

`state.json` без `schema_version` → wipe + backup → `Read()` returns
`null`. Worst case — `stop` команда не убьёт sing-box (нечего убивать
по их данным). Mitigation: пользователь убивает через Task Manager или
`sc stop VPNRouter`. Trade-off acceptable — alternative было бы fail-open
читать legacy state, что нарушает контракт «no schema_version → не
доверяем».

## Оценка

- **Часов**: ~4 (helper + 3 callsite refactor + 21 тест + plan doc)
- **Risk**: Low. CacheRecovery — pure new code, только Load() сайтов
  поменялся. Save() сторона — добавлена единственная строка
  `state.SchemaVersion = CurrentSchemaVersion;` штамповки.
- **Dependencies**: System.Text.Json (BCL), Newtonsoft.Json (уже dep
  через Core .csproj), Serilog (уже dep).

## WFP / network safety

Все изменения — file ops + JSON. Нет нового сетевого surface. Free
Configs refresh-from-source использует существующие endpoints. State.json
— локально. Profiles.json fallback читает только локальный файл.
