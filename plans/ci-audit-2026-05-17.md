# CI/CD Audit (v2.32.3 baseline)

Audit date: 2026-05-17. Scope: `.github/workflows/*.yml` (7 files). Read-only.

## Summary

- **Total workflows**: 7 (`build-mac`, `build-linux`, `build-android`, `build-free-pool`, `test-windows-update`, `verify-release-integrity`, `publish-apt`)
- **Required-for-stable workflows**: 5 (mac + linux + android + verify-integrity + test-windows-update). `publish-apt` runs post-publish on every release, but is not blocking.
- **Avg release CI wall-clock (parallel)**: ~10 min (longest leg = Android ~8 min on cold runner; Mac 1–2 min; Linux 2–3 min; verify ~1 min; test-windows-update ~5 min)
- **Top 5 optimization wins**:
  1. Add NuGet + dotnet workload caching (Android cold workload install is 3–4 min every run)
  2. Pin third-party actions to commit SHAs (currently all use floating `@v3/@v4/@v5` tags)
  3. Fix verify-release-integrity auto-draft trap (release never re-undrafts on success) — spawned fix in progress
  4. Add `paths-ignore:` on tag-triggered builds so docs-only releases don't re-burn 8 min Android CI
  5. Cache sing-box upstream tarball (re-downloaded ~12 MB on every Linux build) and the AppImage `appimagetool` ELF

## §2 Stable-cut required workflows

A clean `vX.Y.Z` stable cut requires ALL of:

1. **build-linux** (push v* tag) → `.deb`, `.AppImage`, `.tar.gz` + sha256
2. **build-mac** (push v* tag) → DMG + ZIP; dispatches Homebrew tap on stable
3. **build-android** (push v* tag) → APK + sha256 (currently 12 assets when keystore unconfigured; 14 when signed). MEMORY.md notes Android signing is still gated on private wgturn-core for some builds.
4. **verify-release-integrity** (release published) → asset count check (expects 14), embedded `AppVersion` scan, sha256 sidecar verification
5. **test-windows-update** (release published OR `v*-r*` tag) → end-to-end Windows helper.cmd test (catches CMD parser bugs class — v2.31.7-r10 class)
6. **publish-apt** (release published) — required for APT users to receive update; not blocking for "stable cut" technically, but mandatory for Linux update path

Note: `build.ps1` (local) produces Windows ZIPs out-of-band — not a workflow.

## §3 Redundancy & inefficiency

### `build-mac` / `build-linux` / `build-android` all trigger on `push tag v*`
Three independent runs per tag, parallel. Not redundant per se, but no shared bootstrap (each runs `actions/checkout` + `setup-dotnet` independently). Each is also doing its own `dotnet publish` of the App project. Could consolidate setup via reusable composite workflow.

### `build-linux` re-downloads sing-box 1.13.10 every run
~12 MB curl from upstream every Linux build. No `actions/cache` key. Same for Mac (via `build-mac.sh`). Cache key on `SINGBOX_VER` would save ~15s per Linux build + Mac.

### `build-android` re-installs `dotnet workload install android` every run
3–4 min cold install on every Android build per the comment. Workload payload is large but cacheable.

### `test-windows-update` does full `build.ps1` every run
Full Release publish + sing-box download + Go stub build on every PR touching update path. Acceptable cost since the workflow is the only catch-net for CMD parser bugs, but NuGet cache would shave 1–2 min.

### `verify-release-integrity` runs on `release: edited` AND `release: published`
The `edited` trigger fires on EVERY notes edit, including the workflow's own banner-prepend. Echo-loop guard exists (`if draft + FAILED marker → skip`) but the workflow still spins up a runner for ~10s every time. Minor cost.

### `build-free-pool` cron every 6h
Reasonable for fresh pool data. Concurrency group prevents pile-up. No redundancy.

### `publish-apt` wipes & rebuilds APT repo on every release
Intentional (comment explains the half-broken reprepro state). Costs ~30s of reprepro work but is acceptable for correctness. Re-downloads .deb from last 30 stable releases when triggered without an explicit tag.

## §5 Security review

### Third-party action pinning
ALL third-party actions are pinned to **floating major tags**, not commit SHAs:
- `actions/checkout@v4`
- `actions/setup-dotnet@v4`
- `actions/setup-java@v4`
- `actions/setup-go@v5`
- `actions/upload-artifact@v4`
- `android-actions/setup-android@v3`

GitHub-hardening recommendation: pin to commit SHAs (e.g. `actions/checkout@b4ffde6...`) with version comment. `android-actions/setup-android` is third-party and warrants SHA pin most urgently.

### Secrets inventory
| Secret | Used by | Scope |
|---|---|---|
| `GITHUB_TOKEN` | all (auto) | default `contents:write` where declared |
| `HOMEBREW_TAP_DISPATCH_TOKEN` | `build-mac.yml` | PAT, fine-grained `contents:write` on `homebrew-vpnrouter` only |
| `APT_SIGNING_KEY` | `publish-apt.yml` | GPG private key (armored block) |
| `APT_SIGNING_KEY_ID` | `publish-apt.yml` | key ID |
| `ANDROID_KEYSTORE_BASE64` | `build-android.yml` | base64 keystore |
| `ANDROID_KEYSTORE_PASSWORD` | `build-android.yml` | keystore password |

### `permissions:` declarations
All 7 workflows declare `permissions:` block (good). Mostly `contents: write` (required for releases / gh-pages). `test-windows-update` uses `contents: read` (minimal).

### Concerns
- `publish-apt` echoes the first/last line of the PGP private key during diagnostics — only the BEGIN/END markers, not key bytes. Acceptable but technically logs a fragment of the secret blob structure.
- No `id-token: write` anywhere — no OIDC usage. Fine; nothing requires it.
- `build-android`'s `KS_PASS` passed through `-p:AndroidSigningStorePass=` on the dotnet CLI — visible in process listings on the runner momentarily. Standard for Android signing; acceptable but `-p:` form is preferable over env var passthrough for keystore pass.

## §6 Known issues

- **verify-release-integrity auto-draft trap** (HIT BY USER 2026-05-17): when the check fails it `gh release edit --draft=true` + prepends FAILED banner. On a subsequent successful re-run (via dispatch or re-published edit), the workflow never undrafts the release. Result: release stuck in draft after fix lands. The echo-loop guard at lines 89–118 actually causes this — it short-circuits BEFORE the success path could undraft. The success branch has no `gh release edit --draft=false` step at all. **Fix being spawned in separate task.**
- **`build-android` historic "failure" rows** (v2.32.1, v2.32.2-r1): old behaviour exited 1 when keystore secret was absent. Fixed in v2.32.2-r2 (graceful skip with `skip=true` output flag), but historical run history still shows red.
- **`build.ps1` is OUT-OF-BAND from CI**: Windows ZIPs are produced locally on the dev VM, not by any workflow. This is by design (Windows code-signing infra lives locally) but means the FROM-binary for `test-windows-update` is a fresh CI build, not the same binary users download. Acceptable per the workflow comment, but worth flagging — Windows artifacts have NO automated provenance other than `verify-release-integrity`'s post-publish scan.
- **Mac CI smoke test is `continue-on-error: true`** (build-mac.yml line 70): a sing-box config-shape regression won't fail the build, only log a warning. Intentional — comment explains it's a soft signal — but flagged for awareness.

## §7 Refactor enablement (v3.0 project restructure)

If projects move:
- **No `paths:` filters in tag-triggered workflows** — they all run on every `v*` push regardless of which files changed. Restructuring projects WILL NOT break these triggers.
- **`test-windows-update`** has explicit `paths:` filter on the PR trigger:
  ```yaml
  - "VPNRouter.Core/Services/UpdateChecker.cs"
  - "VPNRouter.CLI/Commands/TestUpdateCommand.cs"
  - "VPNRouter.CLI/Program.cs"
  - "VPNRouter.Core/AppVersion.cs"
  - "build.ps1"
  ```
  Any restructure that moves `UpdateChecker.cs` out of `VPNRouter.Core/Services/` (or splits CLI) will silently disable PR coverage. **Critical to update in sync with refactor.**
- **`build-linux.yml`** publishes only `VPNRouter.App` and notes that CLI/Service are `net8.0-windows`-only. A refactor that splits Core into a platform-agnostic sub-project would need to update the linux publish line.
- **`build-android.yml`** hardcodes `VPNRouter.Android/VPNRouter.Android.csproj` and APK basename `com.ninitux.vpnrouter-Signed.apk`. Both must move in sync.
- **`verify-release-integrity.yml`** hardcodes filename patterns (`VPNRouter-v${VERSION}-win.zip`, etc.) and DLL name `VPNRouter.Core.dll`. A core-namespace rename would invalidate the embedded-version scan.
- **Tests workflow**: NONE EXISTS. `dotnet test` is not run in any workflow. The 731-test suite mentioned in MEMORY.md is only exercised locally. This is the single biggest gap for the v3.0 refactor — restructuring without an automated test gate is high-risk.

## §8 Recommendations

### Quick wins (1–2 PRs each)

1. **Fix verify-release-integrity auto-draft trap** — add `gh release edit --draft=false` to the success branch (or post-job step). Spawned task in progress.
2. **Pin all `actions/*` and `android-actions/*` to commit SHAs** — single PR; takes ~10 min with the `gh api` SHA-lookup approach.
3. **Add `actions/cache@v4` for NuGet** in all 5 build workflows. Single cache key `${{ hashFiles('**/*.csproj') }}`.
4. **Cache the sing-box tarball** in `build-linux.yml` keyed on `SINGBOX_VER`.
5. **Add a dedicated tests workflow** (`test.yml`) that runs `dotnet test VPNRouter.Tests/...` on PR + push to main. Currently a glaring hole.

### Medium (one focused effort)

6. **Cache Android workload** — biggest single time-suck. Key on .NET SDK version + Android workload manifest. ~3 min savings per build.
7. **Consolidate setup steps via reusable workflow** (`.github/workflows/_setup-dotnet.yml`) — eliminates triplicated checkout + setup-dotnet across mac/linux/android. ~50 lines saved.
8. **Add `paths-ignore:` for tag triggers** — e.g. tag pushes that only touch `*.md` or `plans/**` should skip the 8-min Android build. Currently every tag re-burns full CI.

### Long-term

9. **Migrate Windows build into CI** — eliminate the out-of-band `build.ps1` step. Requires code-signing infra setup in Actions (KMS or imported cert). Closes the provenance gap.
10. **Composite "release" workflow** that fans out to mac/linux/android via `workflow_call` so a single dispatch can rebuild a release end-to-end. Replaces the current "push tag → three independent workflows" model.
11. **Automated stable-cut gate workflow** — after `test-windows-update` + `verify-release-integrity` PASS on a `-rN`, auto-comment readiness on the release. Currently manual per CLAUDE.local.md "live update gate".
