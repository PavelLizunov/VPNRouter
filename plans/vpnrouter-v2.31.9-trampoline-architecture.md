# VPNRouter v2.31.9+ — Production-Grade Auto-Update Architecture

**Status**: Draft, 2026-05-05. Planning phase post v2.31.8 stable cut.
**Author**: Claude (continuing) + Pavel (steering).
**Context budget**: this doc is the persistence layer — read it whole on
every new session that touches auto-update.

## 1. Problem statement

The v2.31.8 cycle (10 iterations r1..r10) closed multiple bugs in the
auto-update flow but exposed a fundamental architectural weakness:

> **The thing that updates the app IS the app itself.**

If `helper.cmd` (generated by `VPNRouter.Core/Services/UpdateChecker.cs`)
has a bug, every user with the broken version is locked in — clicking
Update reruns the same broken helper. That's exactly what happened to
v2.31.7 users hitting the CMD parser bug fixed in r10. Their only
recourse is `https://vpn.ninitux.com/repair.cmd` — manual, requires
a download + UAC + double-click.

**User feedback (2026-05-05)**:
> Это нормальная практика, чтобы в дальнейшем не натыкаться на баги
> обновления? Типа мы будем «VPNRouter Self-Repair Tool» перед
> скачкой обновления, если вдруг новый баг появится. Как это в
> производственной практике делается?

Yes — production VPN / antivirus / browser apps don't update themselves
in-process. They have a separate **trampoline** + **update agent**
that's immune to bugs in the main app. Examples: Chrome's Goopdate,
Office Click-to-Run, Microsoft Edge Update, Squirrel.Windows,
Sparkle (Mac).

## 2. Goal

After v2.31.9+:

- **A bug in App.exe / Core.dll / helper.cmd CANNOT block future
  updates** — separate code paths handle the update flow.
- **User intervention frequency**: zero in steady-state. The first
  upgrade from a pre-trampoline version still requires `repair.cmd`
  (one-time recovery), but every subsequent transition is invisible.
- **Mean time to recovery on broken state**: < 60 seconds, zero user
  action — the trampoline detects + repairs at next launch.
- **No new failure modes**: the trampoline's own code must be
  bulletproof. Native, no .NET dependency, < 200 LOC, simple state
  machine.

## 3. Architecture overview

```
┌─────────────────────────────────────────────────────────┐
│  Start Menu shortcut → C:\Program Files\VPNRouter\app\  │
│                       VPNRouter.GUI.exe                  │
│                       (Go native, ~2 MB)                 │
└──────────────────────┬──────────────────────────────────┘
                       │
                       ▼
        ┌──────────────────────────────────┐
        │ Phase A — integrity check         │
        │   - Read App.dll PE metadata     │
        │   - Read Core.dll PE metadata    │
        │   - Read Service.dll PE metadata │
        │   - Compare commit hashes         │
        │     (InformationalVersion '+sha')│
        └──────────────┬───────────────────┘
                       │
            ┌──────────┴──────────┐
            │                     │
     all match                 mismatch
            │                     │
            ▼                     ▼
    ┌───────────────┐    ┌────────────────────────┐
    │ Phase C       │    │ Phase B — auto-repair  │
    │ launch App.exe│    │   - spawn install.ps1  │
    │ detached, exit│    │     (silent, hidden)   │
    └───────────────┘    │   - wait for completion│
                         │   - then Phase C       │
                         └────────────────────────┘
```

The Go stub is **already** the entry point for every install path
(Start Menu shortcut, install.ps1 runs `Start-Process` on it
post-install, helper.cmd does `start "" {guiExe}` post-update). All
existing install layouts work unchanged.

## 4. Why Go stub specifically

Already shipped (~2 MB native binary), already the entry point. Pre-r9
its only job was forwarding launch + a v2.29.0-r6 «bootstrap» mode
for legacy broken updaters. We're adding integrity check + auto-repair
as a third mode.

Native code advantages over doing this in App.exe:
- ✅ No .NET runtime dependency — App.exe could fail to load due to
  ABI mismatch, mixed DLL versions, broken yaml; Go stub doesn't care.
- ✅ Tiny (~2 MB), zero recurring runtime cost.
- ✅ Doesn't read user config — no parser bugs to introduce.
- ✅ Standalone — never needs to load any of our .NET assemblies.
- ✅ Already always-runs-first via Start Menu shortcut and
  install.ps1's Launch step.

## 5. Phase plan

### Phase 1 — Go stub trampoline integrity check (r1)

**Effort**: ~200 LOC Go + Go toolchain setup if missing.
**Files changed**:
- `VPNRouter.GUI/main.go` — extend with integrity check
- `build-vpnrouter-gui.ps1` — new build script (or extend existing)
- Pre-built `.exe` checked into `VPNRouter.GUI/`

Implementation outline:

```go
package main

import (
    "debug/pe"
    "encoding/binary"
    // ... existing imports ...
)

const (
    expectedDlls = []string{
        "VPNRouter.App.dll",
        "VPNRouter.Core.dll",
        "VPNRouter.Service.dll",
    }
)

func main() {
    // ... existing dir/self resolution ...

    // NEW: integrity check before launching App.exe.
    if mismatched, err := detectMixedVersion(dir); err == nil && mismatched {
        runRepairAndWait(dir)
    }

    // existing: launch App.exe detached
}

// detectMixedVersion reads InformationalVersionAttribute from each
// DLL's PE resources and compares the +commit suffix. Returns true
// if any DLL's commit differs.
func detectMixedVersion(dir string) (bool, error) {
    hashes := make(map[string]string)
    for _, name := range expectedDlls {
        h, err := readCommitHash(filepath.Join(dir, name))
        if err != nil { continue }  // missing/unreadable counts as healthy
        if h == "" { continue }
        hashes[name] = h
    }
    // need 2+ to compare
    seen := map[string]bool{}
    for _, h := range hashes {
        seen[h] = true
    }
    return len(seen) > 1, nil
}

// runRepairAndWait spawns install.ps1 silently and blocks until done.
func runRepairAndWait(dir string) {
    cmd := exec.Command("powershell.exe",
        "-NoProfile", "-WindowStyle", "Hidden",
        "-ExecutionPolicy", "Bypass",
        "-Command",
        `$ProgressPreference = 'SilentlyContinue'; ` +
        `$tmp = Join-Path $env:TEMP 'vpnr-trampoline-repair.ps1'; ` +
        `Invoke-WebRequest -Uri 'https://vpn.ninitux.com/install.ps1' -OutFile $tmp -UseBasicParsing; ` +
        `& $tmp -Prerelease -NoLaunch`,
    )
    cmd.Run()  // block — no Start, we want to wait for repair done
}
```

**Key design decisions**:

1. **Native PE metadata read**, no Windows API calls. Works on any
   Windows version, no admin needed for read.
2. **Block on repair (`cmd.Run`)** vs current SelfRepair (which
   exits app after spawn). Stub blocks → user sees one progress
   window → app launches when repair done. No multi-process race.
3. **`-NoLaunch`** flag on install.ps1 — prevents install.ps1 from
   spawning App.exe. The stub itself launches App.exe in Phase C.
   Avoids double-launch.
4. **Loop prevention** — stub writes a marker; if marker is recent
   (<10 min), don't re-trigger repair. Same logic as
   `SelfRepair.Plan()`.
5. **Channel awareness** — read existing AppVersion from any single
   DLL we can; if ANY contains `-r`, pass `-Prerelease`. Even on
   total mismatch we have channel info.

**Build process**:

```powershell
# Add to build-vpnrouter-gui.ps1
cd VPNRouter.GUI
go build -ldflags="-s -w" -o VPNRouter.GUI.exe main.go
upx --best VPNRouter.GUI.exe   # optional — reduce ~2 MB to ~700 KB
```

Verify size sanity check in `build.ps1` — if GUI.exe > 5 MB, fail
the build (someone forgot to strip).

### Phase 2 — Scheduled Task daily integrity check (r2)

**Effort**: ~50 LOC C# in install.ps1 + repair.cmd.
**Files changed**:
- `packaging/windows/install.ps1` — register Task Scheduler entry
- `packaging/windows/uninstall.ps1` — clean up Task on uninstall

Concept: a Windows Scheduled Task that runs `VPNRouter.GUI.exe` daily
at user logon with a `--integrity-check-only` flag. If integrity is
healthy → exit 0, no app launch. If mismatched → trigger repair, then
exit. User never sees this; runs in background.

```powershell
# install.ps1 — add after Service install
schtasks /Create /TN "VPNRouter Integrity Check" `
    /TR "\"$AppDir\VPNRouter.GUI.exe\" --integrity-check-only" `
    /SC ONLOGON /F /RL HIGHEST
```

Stub recognizes the flag:

```go
if hasFlag("--integrity-check-only") {
    if mismatched, _ := detectMixedVersion(dir); mismatched {
        runRepairAndWait(dir)
    }
    os.Exit(0)  // no App.exe launch in this mode
}
```

This catches the case where user doesn't open VPNRouter for a while
but it's installed, then opens it after damage. Without daily check,
damage sits until user notices. With check, repaired silently in
background overnight.

**Effort**: ~40 LOC C# + small XAML.
**Files changed**:
- `VPNRouter.App/Views/AboutWindow.axaml` — new button

Useful when:

- Power-user troubleshooting
- Support telling them «click About → Repair install» instead of

### Phase 4 — atomic-replace upgrades (deferred, big refactor)

**Effort**: weeks. Defer unless Phase 1+2+3 prove insufficient.

Concept (Chrome / Edge pattern): install layout becomes:

```
C:\Program Files\VPNRouter\
├── app\           ← junction → versions\v2.31.8\
└── versions\
    ├── v2.31.7\
    │   └── (full app folder)
    └── v2.31.8\
        └── (full app folder)
```

Updates: download v2.31.9 → extract to `versions\v2.31.9\` → atomically
swap junction `app\` to point to v2.31.9 → done. No file locks ever
matter because v2.31.9 dir was always isolated.

**Why deferred**:
- Junctions / symbolic links require admin OR Developer Mode on Win10+
- Significant change to install layout
- Existing v2.31.x users would need migration step
- Phase 1+2+3 should solve the practical problem without this

If we ever do Phase 4, consider it for v3.0 when we're already
breaking compatibility for Android port etc.

## 6. Compatibility / migration

### Existing v2.31.7 users (broken helper)

Don't change. After v2.31.8 stable cut they:
- Click Update in app → still fails (their helper is broken)
- One-time recovery via `vpn.ninitux.com/repair.cmd`
- Land on v2.31.8+ → trampoline + scheduled task work going forward

### Existing v2.31.8 users (clean install)

After v2.31.9-r1 trampoline ships:
- In-app Update → v2.31.8's helper.cmd works fine (r10 fix) → installs v2.31.9
- v2.31.9's GUI.exe stub now has integrity check
- Future updates: trampoline catches any subsequent damage

### Existing v2.31.6 / earlier users

After v2.31.8 stable cut:
- See v2.31.8 update offer → their simple helper works → land on v2.31.8
- Trampoline arrives in v2.31.9 — same as above

**No more «catch-22»** scenarios after v2.31.9 because the trampoline
runs INDEPENDENTLY of the buggy app code.

## 7. Risks + mitigations

### R1 — Go stub bug becomes the new chokehold

If trampoline itself has a bug, every user is stuck (since trampoline
is the entry point). Mitigations:
- Keep stub MINIMAL (< 200 LOC). Single responsibility: integrity
  check + launch.
- Pure stdlib Go — no third-party deps to maintain.
- Comprehensive tests (Go's `go test` for unit + integration tests
  with synthetic mixed dirs).
- Stub is updated rarely — most version bumps don't touch it. New
  binary signed only when stub itself changes.

### R2 — PE metadata reading fragility

`debug/pe` package can fail on some files (e.g. self-contained AOT
binaries, binaries without proper InformationalVersion attribute).
Mitigation:
- Fallback: if hash can't be read for ANY DLL, treat as healthy
  (don't trigger repair on inability-to-read).
- Test against all our build outputs — Avalonia's various Skia
  variants, signed vs unsigned, etc.

### R3 — Trampoline blocks during long-running repair

If install.ps1 runs 60+ seconds, user clicked shortcut and waited 60s
seeing nothing. UX is sub-par.

Mitigation:
- Hidden powershell window flicker is OK for short repair.
- For long repair (>5 s), spawn a small **native** Windows MessageBox
  «Repairing VPNRouter...» from the stub before running repair. Close
  on completion. Tiny Go addition.
- Don't use system tray or Avalonia for this — that brings .NET
  back into the loop.

### R4 — Recursive update loop

Trampoline detects damage → repair → relaunch. New launch's stub
detects damage AGAIN (e.g. install.ps1 itself failed silently) →
repair again. Infinite loop.

Mitigation:
- Marker file with timestamp (already designed in `SelfRepair.Plan`).
- Trampoline checks: if marker exists AND age < 10 min, **skip
  repair** and fall through to launch App.exe. App.exe will see
  damaged install + show banner with «contact support» message.
- No third-attempt logic — by now user needs human intervention.

### R5 — Scheduled Task accidentally fires mid-update

User initiates Update → in-progress xcopy → background task fires →
runs trampoline → trampoline sees mismatch → triggers ANOTHER repair.

Mitigation:
- helper.cmd writes a `.update-in-progress` lock file before xcopy,
  removes after. Trampoline + scheduled task check for lock; if
  present, exit 0 (no integrity check).
- 10-min marker also limits damage if locks are missed.

### R6 — Network unavailable during repair

User's stuck install + offline. Trampoline tries install.ps1 from web
→ fails. App can't launch.

Mitigation:
- **Embed install.ps1 as a resource** in VPNRouter.GUI.exe (or
  alongside as `repair.ps1`). Trampoline tries embedded version
  first if web fails.
- Won't help if user installed broken VERSION and never had network
  to download install.ps1's dependencies (sing-box, etc.). But for
  pure file-replacement repair (no dependency download needed if all
  files exist somewhere on disk) — embedded script is enough.

## 8. Testing strategy

### Unit tests (Go)

- `detectMixedVersion` with synthetic mixed dirs (mock PE files)
- `readCommitHash` with various PE inputs (valid, invalid, malformed)
- Marker file creation / reading / age check

### Integration tests (Windows VM)

- T1: fresh install → launch GUI.exe → no repair triggered, App.exe runs
- T2: synthetic damage → launch GUI.exe → repair window flashes, install.ps1 runs, App.exe runs at end with all DLLs matching
- T3: scheduled task fires when no app session → repair runs in background, no UI
- T4: «Repair install» button in About → confirms → silent repair

### Real-world test (release candidate)

- Install pre-r9 stable with deliberate Service running
- Trigger update via in-app Update button to v2.31.9-r1
- Helper.cmd runs (v2.31.8's, has r10 fix) → succeeds
- v2.31.9's GUI.exe stub takes over → integrity check passes
- App launches normally
- → Verify: no flicker, no «did not take effect» banner, version 2.31.9

### Probe-driven verification

Same approach that **discovered** r10 bug: write a small probe that
invokes UpdateChecker programmatically + monitors helper.cmd execution
+ examines all logs. Run on every -r bump.

## 10. Decision points (need user input)

1. **Go toolchain**: do we install Go on the dev VM + GitHub Actions
   runner, or precompile + check in `VPNRouter.GUI.exe`? Currently
   precompiled. **Recommendation**: keep precompiled, add build
   workflow that rebuilds on tag push.

2. **Phase 4 atomic-replace** — defer to v3.0 or earlier? Earlier
   ensures it's available before more features ship. **Recommendation**:
   defer to v3.0, Phases 1-3 should be sufficient.

3. **Scheduled task frequency** — daily at logon, hourly background,
   or on-demand only? **Recommendation**: at logon (already most
   reliable trigger). Skip if user is offline.

4. **Embedded vs network repair script** — if internet down, embedded
   script may not have access to fresh install zip. Worth shipping
   embedded script + small repair-only zip locally? **Recommendation**:
   ship embedded `repair.ps1` (same content as web `install.ps1`)
   as fallback. Web version always preferred if network up.
