# v2.32.0 — Android auto-update (parity with desktop)

**Status**: drafted 2026-05-07. APK built locally (41 MB, arm64). Live
phone test pending — see §5.

## Триггер

Pre-2.32.0 the Android port had no in-app update path. Once a user
sideloaded the first APK they had to remember to revisit the GitHub
Releases page; otherwise they'd run a stale build forever. Desktop
has had `UpdateChecker` since v1.x — Android needs the same
ergonomics so we don't lose users to staleness as we ship -rN
candidates.

## Симптом

- Kebab menu > Diagnostics > "Проверить обновления" / "Check for
  updates" was a placeholder toast: "Авто-обновление появится в
  следующем апдейте."
- Same placeholder under Settings overlay > Updates >
  "Проверить обновления".
- Channel toggle (stable / experimental) was already wired to
  SharedPreferences (AND-2) but didn't influence anything because no
  check ever ran.

## Root cause

[VPNRouter.App/ViewModels/UpdateNotificationViewModel.cs](VPNRouter.App/ViewModels/UpdateNotificationViewModel.cs)
+ [VPNRouter.Core/Services/UpdateChecker.cs](VPNRouter.Core/Services/UpdateChecker.cs)
exist desktop-side. UpdateChecker has hard branches on
`OperatingSystem.IsLinux/IsMacOS/IsWindows` — no Android arm. Worse,
on Android `OperatingSystem.IsLinux()` returns true (Android *is*
Linux), so reusing the desktop class as-is would have pulled the
Linux .tar.gz asset, run a `pkexec` helper that doesn't exist on
Android, and failed silently.

## Fix strategy

A separate `AndroidUpdater` class in `VPNRouter.Android/`. Pure
Android. Reuses Core's internal `UpdateChecker.TryParseSemVer` for
version compare so the rolling-rN ladder semantics stay identical
across platforms. Owns its own GitHub-API call, asset matcher,
download, and install flow.

### Desktop ↔ Android API map

| Desktop concern | Desktop file/symbol | Android equivalent |
|---|---|---|
| Version check | `UpdateChecker.CheckForUpdateAsync(ct)` | [AndroidUpdater.CheckAsync(channel, ct)](VPNRouter.Android/AndroidUpdater.cs:90) |
| Channel filter | `_settings.IsExperimental` | `AndroidStorage.GetUpdateChannel() == "experimental"` |
| Semver compare | `UpdateChecker.TryParseSemVer` | same — internal, accessible because Android compiles Core sources directly |
| Asset name | `VPNRouter-v{ver}-{platform}.{zip\|tar.gz}` | `VPNRouter-v{ver}-android.apk` (canonical) → fallback `com.ninitux.vpnrouter*.apk` |
| Download | `DownloadAndStageAsync` (HTTP + ZIP/tarball + SHA256) | [AndroidUpdater.DownloadApkAsync](VPNRouter.Android/AndroidUpdater.cs:178) — single APK, no SHA (system PackageInstaller verifies signature against installed app's signature) |
| Apply | `ApplyUpdateWindows/Mac/Linux` (xcopy / ditto / pkexec cp) | [AndroidUpdater.BeginInstall](VPNRouter.Android/AndroidUpdater.cs:228) — Intent.ActionView with `application/vnd.android.package-archive` MIME + content:// URI from FileProvider |
| Permission gate | runas / sudo / pkexec | `REQUEST_INSTALL_PACKAGES` (manifest) + per-app `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` deep link |
| Notification UI | `UpdateNotificationViewModel` (XAML banner with title / progress / Update button) | [AndroidApp.AutoUpdate.cs](VPNRouter.Android/AndroidApp.AutoUpdate.cs) — code-behind banner, same state machine: Available → Downloading → DownloadDone → Install → PermissionNeeded → Failed/Retry |
| Startup check | `CheckOnStartupAsync` — silent | Same — fire-and-forget `Task.Run` from `OnFrameworkInitializationCompleted` |
| Manual check | `CheckManually` RelayCommand | Both kebab and Settings overlay buttons call `RunUpdateCheckAsync(manual: true)` |
| Restart | `Environment.Exit(0)` after `ApplyUpdate` launches new exe | System PackageInstaller restarts the app automatically after install confirmation — no `Exit` needed |

### What's intentionally NOT mirrored

- **Lite update package** — desktop has `VPNRouter-update-v*-{platform}.zip`
  for shared-runtime hosts. Android has no such concept (each APK is
  self-contained, no host runtime to share). We download the full APK
  every time. ~40 MB per upgrade, not painful.
- **SHA256 verification** — desktop downloads `.sha256` companion. On
  Android the system PackageInstaller cryptographically verifies the
  APK's signature against the existing app's signature; mismatched APKs
  are rejected by the OS, no need to layer our own hash on top.
- **Install receipt** (`.update-installed-version`) — desktop writes a
  receipt before the file copy so next launch can detect partial
  updates. Android's PackageInstaller is atomic — install either
  succeeds (app reaches the new version on next launch) or fails
  before writing anything. No partial state.
- **Backup snapshot** (`UpdateBackup.CreateSnapshot`) — same reason:
  PackageInstaller is atomic. There's no "partial copy" failure mode
  to roll back from.

## Build instructions

Per handbook §3.5 — Release, arm64-only:

```bash
dotnet build VPNRouter.Android/VPNRouter.Android.csproj -c Release \
  -p:AndroidSdkDirectory="$ANDROID_HOME" -p:JavaSdkDirectory="$JAVA_HOME" \
  -p:RuntimeIdentifiers=android-arm64 -p:AndroidEnableProfiledAot=false
```

Output: `VPNRouter.Android/bin/Release/net8.0-android/com.ninitux.vpnrouter-Signed.apk`
(~41 MB). Built clean: 0 errors, 38 warnings (pre-existing CA1416
platform-availability noise + 2 of mine, both gated by runtime
`Build.VERSION.SdkInt >= O` checks → false positives).

## Permission flow (one-tap or multi-tap?)

**First-ever update on a fresh install — multi-tap (3 user actions)**:

1. Tap "Скачать" / "Download" → APK streams into cache (progress bar).
2. After ~5–15 s the system PackageInstaller dialog tries to launch.
   On API 26+ if `REQUEST_INSTALL_PACKAGES` isn't yet granted, the
   dialog refuses and our banner flips to "Чтобы установить APK из
   приложения, нужно разрешить «Установка из неизвестных источников»…"
   with an "Allow" button.
3. Tap "Allow" → deep-links to *Settings → Apps → VPNRouter → Install
   unknown apps* (the per-app screen, scoped via `package:` URI so the
   user sees just our app's toggle, not the global list).
4. User flips the toggle ON, taps Back to return to VPNRouter.
5. Tap "Установить" / "Install" → system PackageInstaller dialog fires
   → user taps "Update" → OS swaps the APK → app restarts on the new
   version.

**Subsequent updates — one-tap**:

1. Tap "Скачать" / "Download" → APK streams.
2. Auto-fires `BeginInstall` on download completion → system
   PackageInstaller dialog → user taps "Update" → done.

The grant survives until the user manually revokes it in Settings,
so steps 2-5 above are paid only once per install lifecycle.

## Live test outcome (KYOCERA A101BM, Android 12 / API 31)

Mac build host `slovn@192.168.0.246` over the AmneziaWG host route;
phone connected to the Mac via USB. Test session 2026-05-07 17:14–17:50.

### What happened, step by step

1. **Build phone APK**: patched `AppVersion.Version = "2.30.0"`,
   rebuilt, restored to `"2.32.0-r2"`. 41 MB, signed.
2. **Build asset for the release**: separately patched
   `AppVersion.Version = "2.32.0-r1"` so the APK on the release matches
   the release tag, rebuilt, restored.
3. **Upload to v2.32.0-r1 (existing prerelease)** as
   `VPNRouter-v2.32.0-r1-android.apk` (41 MB). First canonical Android
   release asset on the project, establishes the
   `VPNRouter-v{ver}-android.apk` naming convention going forward.
4. **Install v2.30.0 APK on phone**, verify About > Version shows
   "2.30.0".
5. **Stable channel check** (default). Tap kebab > Check for updates →
   "You're on the latest version." toast surfaces. Validates: GitHub
   API call works, channel filter active (latest stable v2.31.10 has
   no `-android.apk` asset, so matcher correctly returns null →
   "up to date" path).
6. **Switch to experimental**: kebab > Settings overlay > Updates >
   "Receive prereleases (experimental channel)" → ✓.
7. **Re-check**: banner surfaces under status card —
   "**v2.32.0-r1 available · 38.9 MB** · Tap Download — install will
   ask for system permission. · [Later] [Download]". Confirms channel
   toggle narrows: stable → no banner, experimental → banner. ✅
8. **Tap Download**: button greys out, subtitle hides, the 41 MB APK
   streams to `getCacheDir()/update.apk`. First attempt timed out at
   30 s ("Download failed: net_http_request_timedout, 30") — the shared
   30 s `HttpClient.Timeout` was killing the body read. Fixed by
   splitting into two `HttpClient` instances: a tight 30 s probe-tier
   for `CheckAsync` and a relaxed 10 min stream-tier for
   `DownloadApkAsync`. Phone APK rebuilt + reinstalled.
9. **Re-tap Download**: this time the download completed (~60 s on
   Wi-Fi). State machine transitioned correctly: title flipped to
   "Downloaded. Tap Install.", action button became "Install" (blue),
   `HandleInstallClick` auto-fired. Permission-gate kicked in because
   `REQUEST_INSTALL_PACKAGES` wasn't yet granted → banner flipped to
   "**To install the APK from inside the app, allow 'Install from
   unknown sources' for VPNRouter.** · [Later] [**Allow**]". ✅
10. **Tap Allow**: launched
    `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` with
    `package:com.ninitux.vpnrouter` URI → per-app **"Install unknown
    apps"** screen opened, scoped to VPNRouter only. Toggled "Allow
    from this source" ON. ✅
11. **Tap Install** (after a UX-fix iteration: pre-fix the Allow-button
    re-tap looped back to Settings because the label stayed "Allow";
    post-fix the handler re-checks `CanRequestInstall()` — if true,
    flips to "Install" and fires the install intent). Banner showed
    "Downloaded. Tap Install." → tap → **system PackageInstaller dialog
    fired**: "VPNRouter — Do you want to update this app? [CANCEL]
    [UPDATE]". ✅ This is the proof that:
    - APK landed correctly in cache
    - FileProvider issued the `content://` URI
    - `Intent.ActionView` with `application/vnd.android.package-archive`
      MIME + `FLAG_GRANT_READ_URI_PERMISSION` flowed through to the OS
    - The OS recognised the APK as an upgrade for our existing
      package signature
12. **Tap UPDATE**: handed off to **Google Play Protect** with "App
    scan recommended — Play Protect hasn't seen this app before".
    Tapping "Install without scanning" surfaced the **biometric prompt**
    (`PlayProtectDialogsActivity` → `BiometricPrompt` window), required
    by Android 12 for first-time sideloads from a new source. Cannot
    bypass remotely without physical fingerprint touch — the phone is
    via USB, no remote-biometric harness. Test stops here.

### Known minor cosmetic gap (not blocking)

The banner title doesn't visibly tick through "Downloading… 0%, 5%, …"
during the download — at 41 MB on Wi-Fi it goes from "Available" →
"Downloaded" too quickly to see intermediate frames in screencap.
`Progress<int>` is wired correctly (verified by code reading); a
slow-network user would see the progress text. Not worth a fix in this
PR.

## Future / out-of-scope

- **Android CI workflow** — `.github/workflows/build-android.yml` to
  produce a signed APK on tag push and upload as
  `VPNRouter-v{ver}-android.apk` to the release. Without this, every
  release has to manually attach an APK or this whole flow only works
  off whatever the human uploads. Skill `ship-rolling-candidate` should
  be extended to invoke it.
- **Async install confirmation** — currently after `BeginInstall`
  fires we don't know whether the user confirmed or declined. We
  could `StartActivityForResult` and read the result, but the user's
  next visible touch will be either:
  (a) re-launching the app on the new version (success)
  (b) tapping the banner again (declined / failed install)
  Both are observable via the next `OnResume`, so a polish pass can
  add a "version still old after install attempt — try again?" line
  if needed.
- **Background check via WorkManager** — current implementation
  checks at app launch. Desktop only checks at launch too, so this is
  parity. If users start asking for "notify me even if I haven't
  opened the app in weeks", a periodic JobScheduler / WorkManager
  task can be added.
