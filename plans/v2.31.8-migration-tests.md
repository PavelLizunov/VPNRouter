# v2.31.8 migration test plan — autonomous run

Run while user sleeps, document every iteration.

## Goal

Verify the user-traced migration path actually works:

```
Old version (v2.31.5 / v2.31.6) + Service installed
  ↓ in-app auto-update (broken helper)
  ↓ mixed-version DLL state
  ↓ NEW v2.31.8 App.exe launches
  ↓ InstallHealthCheck detects mismatch
  ↓ SelfRepair → install.ps1 → clean v2.31.8
```

The deeper question: would a real user *actually* get to v2.31.8 with
zero manual intervention? Or would something break along the way?

## Test scenarios

### T1 — Synthetic damaged install → SelfRepair fires (most controlled)

Setup:
- Install v2.31.8-r1 fresh to `C:\Program Files\VPNRouter\app`
- Replace `VPNRouter.Core.dll` with v2.31.7 Core.dll (different commit hash)
- Verify mixed state via `Get-Item .VersionInfo.ProductVersion`

Run:
- Stop any running VPNRouter.App
- Launch `VPNRouter.App.exe`
- Capture stderr
- Watch for "[health] mixed-version" log line
- Watch for `powershell.exe` process spawning install.ps1

Expected:
- App.exe exits early (because health check failed, returned)
- New PowerShell window appears running install.ps1
- install.ps1 stops Service (if any), extracts latest stable to install dir
- New App.exe launches automatically (install.ps1 -NoLaunch is NOT set)
- After install.ps1 done: install dir has consistent commit hash
- `repair-marker` file exists with timestamp

PASS criteria:
- All 3 DLL hashes match after install.ps1 finishes
- App is reachable

### T2 — Real broken-update simulation from v2.31.6 with Service

Setup:
- Install v2.31.6 stable from GitHub release (clean install over current)
- Install Windows Service: `vpnrouter service install + start`
- Verify Service is RUNNING via `sc query VPNRouter | find "RUNNING"`

Run:
- Trigger in-app update check OR manually simulate the update flow:
  a. Download v2.31.7 update zip
  b. Manually invoke the v2.31.6's update flow (via UI button click)
  c. OR: simulate by manually running `xcopy` of v2.31.7 over v2.31.6 install
     while Service is RUNNING — this gives us the SAME result as the
     broken helper would
- After "broken update": observe mixed state in install dir

Switch to v2.31.8-r1:
- Manually overwrite App.exe + App.dll only with v2.31.8-r1 versions
  (simulating that those DLLs got through the broken xcopy)
- Leave Core.dll + Service.dll at v2.31.6 (Service-locked, not replaced)
- Stop running app, relaunch

Expected:
- v2.31.8-r1 App.exe runs InstallHealthCheck
- Detects v2.31.6 Core.dll vs v2.31.8 App.dll mismatch
- Triggers SelfRepair
- install.ps1 runs, stops Service, replaces ALL DLLs cleanly
- After: all DLLs at consistent v2.31.7 stable (since install.ps1 default = stable)

PASS criteria:
- Auto-recovery works without user input
- Final state: clean install at v2.31.7+

### T3 — User-mode install (no Service) — no repair needed

Setup:
- Install v2.31.8-r1 fresh
- DO NOT install Service
- Verify Service not installed

Run:
- Launch app

Expected:
- InstallHealthCheck = healthy
- No repair triggered
- No PowerShell repair window
- No marker file
- App proceeds normally

PASS criteria:
- App functional in user mode without any side effects

### T4 — Loop prevention

Setup:
- Trigger SelfRepair (via T1 setup)
- Wait for repair to start
- Kill PowerShell window mid-install (so repair doesn't actually fix DLLs)
- Verify mixed state still present
- Relaunch App.exe immediately

Expected:
- Second launch detects mixed state (still damaged)
- Plan() returns ShouldRun=false (marker is recent)
- App falls through, doesn't loop
- Surfaces failure to user (e.g., crash from mixed DLLs caught by CrashReporter)

PASS criteria:
- No infinite loop of repair attempts

### T5 — install.ps1 actual download + Service-aware

Setup:
- Install v2.31.7 stable + Service running
- Save current state of Service settings + autostart flags

Run:
- Run `iwr install.ps1 | iex -Prerelease` → should land v2.31.8-r1

Expected:
- install.ps1 stops Service
- xcopy succeeds (no locked files)
- Service restarted
- App launches

PASS criteria:
- v2.31.8-r1 installed correctly
- Service preserved (still installed + running if was)

## Iteration order

1. **T3 first** (least destructive) — confirm baseline
2. **T1** (semi-controlled) — confirm core mechanism
3. **T4** (after T1) — confirm loop guard
4. **T5** (longer flow) — install.ps1 web full path
5. **T2** (most realistic) — actual old-version-with-service migration

## Recovery strategy between tests

After each test:
- Snapshot install dir to `C:\tmp\snapshots\{test}\`
- Document what state we landed in
- If broken: restore via known-good install (re-run install.ps1 -Prerelease)
- Stop sing-box, kill VPNRouter.App, uninstall Service if needed

## Logs to capture per test

- `C:\ProgramData\VPNRouter\logs\vpnrouter*.log` (latest)
- `%TEMP%\vpnr-repair.ps1` (if repair fires)
- `%TEMP%\vpnrouter-update-*.log` (if update helper runs)
- App stderr output (Console.Error)
- Get-Process snapshots before / after each step

## What this means for users

### Migration scenario (full closure)

1. User on old version (v2.31.5 / v2.31.6) with Service installed
2. Triggers in-app auto-update (UI button or background check)
3. OLD update helper (.cmd) tries to xcopy while Service holds DLL locks
4. Mixed-version DLLs land in install dir
5. NEW v2.31.8 App.exe launches (this part of xcopy succeeded)
6. **InstallHealthCheck detects mismatched commit hashes**
7. **SelfRepair spawns elevated install.ps1 from web**
8. install.ps1:
   - Snapshots Service running state BEFORE killing processes (r2 fix)
   - Gracefully stops Service
   - Kills any leftover VPNRouter.App / sing-box processes
   - SHA256-verifies install ZIP
   - Cleanly extracts new version (no locked files anymore)
   - Restarts Service if was running pre-update
   - Launches new VPNRouter.App.exe (unless -NoLaunch)
9. App.exe relaunches, InstallHealthCheck PASSES, normal startup
10. User sees clean install at latest stable, Service preserved

**Zero user intervention required.**

### Recovery from r1 → r2

Users on r1 will get the install.ps1 r2 fix automatically the next time
SelfRepair fires (since install.ps1 is downloaded from the web each time,
not bundled). r1 binary's SelfRepair → r2 install.ps1 → correct Service
preservation.
