# VPNRouter v3.0 Refactor Roadmap

**Authored**: 2026-05-17 (post-v2.32.3-r1 ship)
**Baseline**: v2.32.3-r1, ~94k LOC C# across 233 files in 7 projects
**Synthesizes**: 6 parallel audits — see `plans/{dead-code,feature-catalog,nuget-audit,test-coverage,ci-audit}-2026-05-17.md` + `plans/v3.0-architecture-roadmap.md`

---

## Executive summary

VPNRouter is in **good architectural shape**. Layering is clean (Core has zero UI deps), test discipline is strong (765 tests, well-covered placeholder defense), security posture is clean (0 CVEs in 31 dependencies). The refactor isn't about fixing rot — it's about **paying down velocity-tax**: god-files that take 3× longer to safely modify, missing test seams that block confident change in critical paths, CI workflows that re-download tools every run.

**Headline numbers:**

| Metric | Value | Notes |
|---|---:|---|
| Total C# LOC | 93,702 | 233 files across 7 projects |
| Dead/removable LOC | ~1,678 | 1.8% of codebase (mostly duplicate L_X wrappers + App/Strings.cs dedup) |
| Pure relocation (god-file splits) | ~17,000 | 18% reshuffle, no deletes |
| Test count | 765 | 9 services untested (1,851 LOC, leak-class risk) |
| NuGet packages | 31 | 0 CVEs, 1 minor drift, 5 modernization candidates |
| God-files | 6 | ~21,800 LOC concentrated in 6 files (23% of codebase) |
| Estimated refactor duration | **8-10 weeks** | 3 phases, no behind-flag rollout needed |

## Phase 2 — Mediums (Weeks 2-4)

**Goal**: split god-files + introduce test seams for v3.0 enablement. No behaviour changes; verify via existing test suite + new characterization snapshots.

### 2A — Localization dedup (1 day, -1,400 LOC)

**`VPNRouter.App/Localization/Strings.cs` → pass-through to Core**.

Audit A found 547 of 589 keys (93%) are byte-identical to Core. Android already uses the pass-through pattern:

```csharp
public static string SmpScanQrButton => global::VPNRouter.Core.Localization.Strings.SmpScanQrButton;
```

Apply same to App's Strings.cs. Keep ONLY the 42 App-specific keys (desktop-only menu items, etc.).

**Risk**: low. xUnit test count stays identical, headless screenshot tests catch any glyph regression.

### 2B — `MainWindowViewModel.cs` split (completed 2026-08-02)

Completed as a behavior-neutral relocation guarded by the existing public-surface
characterization hash. The 7,692-line main file became a ~1,710-line state /
constructor / orchestration file plus six concern partials:

```
MainWindowViewModel.cs                    (~1,710 LOC)
  ├── MainWindowViewModel.Connection.cs   (~1,216 LOC)
  ├── MainWindowViewModel.CustomRules.cs  (~1,650 LOC)
  ├── MainWindowViewModel.Servers.cs      (~290 LOC)
  ├── MainWindowViewModel.SettingsPersistence.cs (~606 LOC)
  ├── MainWindowViewModel.TgProxy.cs      (~557 LOC)
  └── MainWindowViewModel.Zapret.cs       (~1,829 LOC)
```

All 20 `MainWindowViewModel*.cs` files are below ~24k approximate tokens. See
`plans/phase2b-mvm-partial-split-2026-08-02.md` for the verification record.

### 2C — `AndroidApp.axaml.cs` split (completed in evolved form 2026-05-18)

Wave 9 extracted Notifications, Permissions, VpnLifecycle and UiBindings; later
work added more concern files. `AndroidApp` now spans 19 source partials and the
main file is ~2,330 LOC. The live inventory is maintained in
`VPNRouter.Android/CLAUDE.md`; the originally proposed Theme/SimplePage filenames
were not needed as separate abstractions.

### 2D — Test seam introduction (5 days)

Audit E identifies 4 missing abstractions blocking 9 untested services:

| Interface | Replaces | Untested services unlocked |
|---|---|---|
| `IProcessRunner` | `System.Diagnostics.Process` direct calls | `EtwProcessMonitor`, `ZapretActions`, helper.cmd parser |
| `IFileSystem` | `File.*`, `Directory.*` static calls | `HostsManager`, `WindowsDnsHardening`, `LockFile` |
| `IHttpClient` | `static readonly HttpClient` (6 fields) | `UpdateChecker`, `SubscriptionFetcher`, `VlessDeepVerifier` |
| `ISingBoxApi` | `SingBoxManager` direct calls | `HealthMonitor` hot-reload path |

Each abstraction is a 1-day task: extract interface + concrete impl + inject + update 1-3 services + 5-10 new tests.

### 2E — `UnitTest1.cs` extraction (2 days)

6169 LOC / 42 test classes / 313 tests in a single file. Mechanical extraction: each class becomes its own file matching the class name. Zero logic change, just `cs` files split. **Audit E lists which 42 to create.**

### 2F — `HealthMonitor.GenerateConfigJson` consolidation (1 day)

Audit D found this duplicates `VpnEngine` config-pipeline logic — root cause of v2.28.2 silent-leak. Extract `Services/ConfigPipeline.cs`:

```csharp
internal static class ConfigPipeline
{
    public static string Generate(AppSettings settings, IReadOnlyList<VlessServerEntry> servers, string activeServerName)
    {
        // Single canonical path: Resolve → Validate → Generate → LeakProtection
    }
}
```

Both `VpnEngine.StartAsync` + `HealthMonitor.GenerateConfigJson` route through it. Closes the entire bug class.

### 2G — Test untested services (3 days, ~2,750 LOC of tests)

Audit E's "v3.0 enablement budget":
- `WindowsDnsHardening` — 15 tests (highest priority, leak risk)
- `HostsManager` — 12 tests (system hosts file write, leak risk)
- `EtwProcessMonitor` — 10 tests
- `VpnEngine.StartAsync` characterization — 15 tests
- `UpdateChecker` (SemVer + URL parsing already tested via CI workflow, add 10 unit tests)
- `VlessDeepVerifier` — 12 tests
- Plus 8 misc

**Phase 2 total**: ~3 weeks, -1,400 LOC, +17,000 LOC pure reshuffle, +82 tests, 4 new abstractions, 1 critical bug class closed.

## Phase 3 — Majors (Weeks 5-10)

**Goal**: modernization + structural improvements. Each item is shippable independently.

### 3A — Avalonia 11 → 12 upgrade (1-2 weeks)

Audit C identifies as P1. Requires:
- SkiaSharp 2 → 3 (transitive bump)
- Re-baseline `VisualDiffTests` PNG fixtures (3 baselined pages)
- Verify headless Avalonia harness still works
- API breaks: check Avalonia 12 migration guide

**Risk**: medium. Behind a branch + full QA pass.

### 3B — Newtonsoft.Json → System.Text.Json (1 week)

Audit C: 2-5× faster, AOT-friendly for Android. Touches:
- `AndroidStorage.cs` (heaviest user, 15+ serialize calls)
- `SubscriptionFetcher.cs`, `FreeConfigCache.cs`, `UpdateChecker.cs`, `ProfileManager.cs`

**Gotchas**: STJ requires `[JsonInclude]` on private setters where Newtonsoft auto-handles them; YAML escape conventions differ slightly.

**Risk**: medium. New unit tests per migrated type to catch round-trip drift.

### 3C — `VpnEngine.StartAsync` extraction → `StartupPipeline` (1 week)

Audit B+D: 880 LOC monolith with 16 service touches. Extract a `StartupPipeline` orchestrator (analogous to `ConfigPipeline` from 2F):

```csharp
public sealed class StartupPipeline
{
    public async Task<StartupResult> ExecuteAsync(StartupContext ctx, CancellationToken ct) { ... }
}
```

Phases: ResolveProfile → ResolveServers → GenerateConfig → ValidateConfig → SetupFirewall → StartSingBox → StartMonitors. Each step a static helper, tested in isolation.

### 3D — F-A..F-E placeholder defense consolidation (1 week)

Audit B+D: 5 layers (Phase 2a/b/c migrator/runtime), 65 tests, 8 files. They share placeholder fingerprint sets via `PlaceholderGuard` (we added in v2.32.3). Consolidate into single `Services/PlaceholderDefense.cs` with internal sub-classes for each layer. Stops drift between Core/Android lists.

### 3E — `Free Configs` pipeline stages (1 week)

Audit B: 5-stage pipeline (fetch → parse → dedupe → GeoIP → test → cache) lives in one orchestrator. Split into composable stages with explicit contracts:

```csharp
interface IFreeConfigStage { Task<StageResult> RunAsync(StageContext ctx, CancellationToken ct); }
```

Enables: per-stage retry policy, stage replay for debugging, optional stages (e.g. skip GeoIP if offline).

### 3F — Android `IUpdateSource` per-platform (3 days)

Audit B: Android currently downloads update APK via `UpdateChecker` shared with desktop. Add `IUpdateSource` interface; concrete impls: `GitHubReleaseSource` (desktop), `PlayStoreSource` (future Android), `SideloadSource` (current Android).

Lets us add Play Store distribution later without forking `UpdateChecker`.

### 3G — Service architecture polish (1 week)

Audit D:
- `SettingsLoader.Load/Save` static in 17 call sites → inject `ISettingsStore`
- 6 `static readonly HttpClient` fields → single shared `IHttpClient` with policy
- Fix `.Result` blocking call in `VpnEngine.cs:461`
- `PlatformServices.CreateVpnEngine` factory enforcement (some sites bypass it)

**Phase 3 total**: ~6 weeks, modernization complete, infrastructure ready for 4.x.

## Phase 4 — Defer

Items intentionally NOT in this roadmap:

| Item | Why deferred |
|---|---|
| .NET 8 → 9 / 10 migration | LTS until Nov 2026; no compelling reason yet |
| DI container (Microsoft.Extensions.DI etc.) | Static + nullable is fine for this codebase size |
| Clean Architecture rewrite | Over-engineering. Current 4-layer split (Core / App / Service / CLI) works |
| Rewrite Android in Compose / Kotlin | Avalonia.Android works. Maintenance vs greenfield calc says stay |
| Tauri / Electron rewrite of desktop | Avalonia performance + size is BETTER than either. No win |

## Out-of-roadmap follow-ups (track separately)

These came up during audits but don't fit the refactor narrative:

- **Android port future**: source-link Core via `<Compile>` works today; once .NET 9's multi-target story matures, switch to `ProjectReference` (Audit D).
- **APT repo signing automation**: currently manual `reprepro` invocation in workflow. Could move to `aptly` or upstream `reprepro` action.
- **Homebrew tap testing**: cask installation succeeds in CI but no smoke-test that the binary actually launches. Add `brew install --cask --verbose` + verify `vpnrouter --version` returns expected string.
- **Free Configs pool format v2**: current `pool.json` is 25k entries / ~30 MB. Could add per-region shards to cut Android download by 80%.
