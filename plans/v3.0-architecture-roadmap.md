# v3.0 Architecture Roadmap (v2.32.3 baseline)

Read-only audit produced 2026-05-17. Repo: `C:\Project\VPNRouter`. Numbers are
LOC for `.cs` files in source tree only (`bin/` and `obj/` excluded).

## Executive summary

- **Layering: MOSTLY CLEAN.** `VPNRouter.Core` has **zero** `Avalonia.*` /
  `System.Windows.*` / `Mono.Android.*` `using`s. Platform branches live behind
  `#if PLATFORM_WINDOWS` / `#if PLATFORM_ANDROID` constants, and there's a
  proper `PlatformServices` factory at `VPNRouter.Core/Platform/PlatformServices.cs`
  that fans out to Windows vs macOS implementations. One small leak: tests
  project (`VPNRouter.Tests`) references both `Core` and `App`, so App-layer
  changes break Core tests in the same run. Not a layering violation per se,
  just a coupling note.
- **God classes: 6 identified, ~21 800 LOC ripe for split.** Top offenders are
  `AndroidApp.axaml.cs` (7177), `MainWindowViewModel.cs` (6753), `VpnEngine.cs`
  (1658), `AndroidApp.ServerList.cs` (1499), `UpdateChecker.cs` (1387),
  `ConfigGenerator.cs` (1353), `AndroidApp.FreeConfigs.cs` (1330),
  `AndroidApp.SubscribePage.cs` (1320), `CustomConfigInjector.cs` (1254),
  `MainActivity.cs` (1223), `AndroidStorage.cs` (1511).
- **DI: ad-hoc, no framework.** `new VpnEngine(...)` is wired manually in three
  places (`Program.cs` for App, `StartCommand.cs` for CLI, `VPNRouterService.cs`
  for Service). `PlatformServices.CreateVpnEngine` factory exists but isn't
  used by all three — Service still constructs raw `ProcessScanner` /
  `FirewallManager` / `EtwProcessMonitor` (file-locked to Windows).
- **`SettingsLoader.Load/Save` is called statically from 17 files** (Core +
  App + CLI + Service + Android + Tests). Mutation paths are scattered.
  This is the single largest "missing seam" for unit testing.
- **Top 5 refactor priorities** (detailed in §7):
  1. Split `MainWindowViewModel.cs` along its 24 section comments into ~6
     page-VMs. Highest reward, highest risk — main lifeline of GUI.
  2. Extract `UpdateChecker` into 4 collaborators (Checker / Downloader /
     PlatformApplier / SemVer). Linear win, low risk.
  3. Split `AndroidApp.axaml.cs` into a `Pages/` folder under `VPNRouter.Android`
     mirroring `VPNRouter.App/Views/Pages/`. Largest LOC win.
  4. Promote `PlatformServices.CreateVpnEngine` everywhere — wire CLI + Service
     through it. 1-hour change.
  5. Extract `HealthMonitor.GenerateConfigJson` (duplicates `VpnEngine` logic)
     into a shared `ConfigPipeline` static helper. Closes the v2.28.2 silent-
     leak class of bug at the call-site level.

## §3 Service architecture

- 60+ services under `VPNRouter.Core/Services/` plus `FreeConfigs/` and
  `EmergencyChannel/`. No `Singleton` static-instance fields in Core.
- **Static methods on Core classes are pervasive** (≥66 `static readonly` /
  `public static` in the first 20 service files). For pure helpers this is
  fine, but it means callers can't substitute fakes. Concrete examples:
  - `SettingsLoader.Load(string path)` — pure static, called from 17 sites.
    No `ISettingsStore` interface → tests poke real `%ProgramData%` files
    (the Tests/CLAUDE.md flags this as a known parallel-test hazard).
  - `VlessServersResolver.Resolve(settings, logger)` — pure static helper.
    Fine, but `MutateInPlace` semantics on `settings.Vless.Servers` is the
    v2.28.2 silent-leak class of bug — flagged also in App/CLAUDE.md "Rule F2".
  - `FreeConfigCache.{Load,Save}` — static singleton-style.
- **No circular service deps observed.** `VpnEngine` owns `SingBoxManager`
  and `HealthMonitor`. `HealthMonitor` holds back-reference to `SingBoxManager`
  (constructor-injected). No A→B→A.
- **Missing seams:**
  - `SettingsLoader` — wrap behind `ISettingsStore` for testability + future
    mutation tracking.
  - `FreeConfigCache` — same.
  - `HttpClient` is `static readonly` in `UpdateChecker`, `SubscriptionFetcher`,
    `FreeConfigFetcher`, `FreeConfigPoolFetcher`, `GeoDataDownloader`,
    `WgturnUpdater`, `ZapretUpdater`. Centralize on an injected
    `IHttpClientFactory`-style provider so retries / proxy bypass / test
    fakes can be wired uniformly.
- **Duplicate logic**: `HealthMonitor.GenerateConfigJson` (line 494) duplicates
  the resolve-then-generate sequence from `VpnEngine`. CLAUDE.md flags this
  as the "every caller of ConfigGenerator.Generate must call Resolve first"
  pattern.  **One`ConfigPipeline.Build(settings)` static helper would close
  this class of bug at the call-site level.**

## §4 Cross-cutting issues

### Logging — Serilog, mostly consistent
- Serilog package referenced in every project that needs it. Most services
  take `ILogger?` in constructors and use null-conditional logging.
- `ILogger` instances are usually passed in (good). A few services (e.g.
  some `FreeConfigs/*` files) use `Serilog.Log.Logger` static directly —
  ~10 sites worth tidying.

### Configuration — direct mutation is the norm
- `AppSettings` is mutated in-place from VMs (`_settings.Vless.Servers = ...`)
  in multiple paths, then `SettingsLoader.Save(_settings)` persists. There's
  no transactional / immutable wrapper. The v2.28.2 silent-leak + v2.30.0-r8
  subscription-leak are both rooted in this pattern (App/CLAUDE.md Rule F2).
- Proposal (Phase 2): introduce `ISettingsMutator` with a "session change-set"
  + atomic apply. Out of scope for v3.0 but worth a separate plan doc.

### Error handling — mixed
- 7 files contain an empty `catch (Exception) { }` block. Most are
  intentional swallows in disposal paths (`HealthMonitor`, `MacProcessMonitor`,
  CLI cleanup). Two in `MainWindowViewModel.cs` are debatable — review.
- No custom exception hierarchy beyond `ConflictingVpnException` (typed) +
  `WgturnDownloadException` (typed). The lack of typed exceptions for
  e.g. config-validation failures forces stringly-typed Warning event traffic.

### Async hygiene
- **`async void` count: 9 — all in `VPNRouter.Android`** (UI event handlers,
  expected for Avalonia/Android). Zero in Core/App/CLI/Service. **PASS.**
- **`.Result` blocking call count: 1** — `VpnEngine.cs:461` (`_scanResult =
  scanTask.Result`). Inside a sync helper called during start sequence.
  Worth a follow-up to `await` it.

## §5 Android port future

**Current state (v2.32.x):**
- `VPNRouter.Android.csproj` source-links Core via `<Compile Include="..\VPNRouter.Core\**\*.cs"/>`.
- The dead `<Compile Include="..\VPNRouter.UI\**\*.cs"/>` and matching
  `<AvaloniaResource>` lines (91-95) point at a directory that no longer
  exists. **Remove these immediately** (1-line fix in Phase 1 quick wins).
- Cross-platform packages are duplicated in Android csproj (matching Core
  csproj). Maintenance burden — adding a new transitive in Core requires
  remembering to add it here.

**.NET 9 multi-target story**: source-linking is a workaround for the .NET 8
limitation where a multi-target Core (net8.0 + net8.0-android) trips on
restore-graph RID inconsistencies. .NET 9 with `RuntimeIdentifiers` aware
multi-target restore should make ProjectReference the natural choice.

**Proposal**: defer the source-link → ProjectReference migration to .NET 9
upgrade (no benefit doing it now). Keep two-line block in Android csproj
that mirrors Core packages — annotate it as "mirror VPNRouter.Core.csproj
PackageReference block; sync when adding/removing".

## §6 UI architecture

### ViewModels
- Page-level VMs exist for `FreeConfigsPage` (`FreeConfigsPageViewModel`).
- Most other pages bind directly to `MainWindowViewModel` — there's no
  per-page VM. That's why `MainWindowViewModel` is 6.7k LOC.
- Sub-VMs that are well-factored: `ServerViewModel` (366), `SubscriptionViewModel`,
  `AppGroupViewModel`, `AppItemViewModel`, `CustomConfigViewModel`,
  `CustomRuleViewModel`, `UpdateNotificationViewModel`. These are item-level
  and used correctly.

### Code-behind
- `View.axaml.cs` files are thin (most under 80 LOC). `MainWindow.axaml.cs`
  is **69** LOC. `AboutWindow.axaml.cs` 143. `NetworkPage.axaml.cs` 80.
  **Healthy.** Most logic is in the VM, where it belongs.

### Bindings
- `<AvaloniaUseCompiledBindingsByDefault>true` in App csproj — good.
- Mix of `OneWay` (read state) and `TwoWay` (form inputs) — appropriate.

### Memory / leaks
- `MainWindowViewModel` implements `IDisposable` (since v2.31.6-r12 per
  comment on line 31-41). Disposes timers + engine events + sub-VMs.
- `Dispatcher.UIThread` used 12 times in MainWindowViewModel.cs — all in
  cross-thread post-back-to-UI paths. Reasonable.
- 5 CancellationTokenSource fields in MainWindowViewModel are disposed in
  the Dispose path. Good.
- One leak risk identified: `MainWindowViewModel.Dispose` is wired to
  `Quit()` but **not yet wired to `MainWindow.Closed`** (per VM comment).
  X-button close still leaks timers. Trivial fix.

## Things deliberately NOT recommended

- **No DI container** (Autofac / Microsoft.Extensions.DependencyInjection.Hosting).
  The codebase uses 3 composition roots (App, CLI, Service) and the manual
  wiring is 5-10 lines each. A container would add ~50 KB of complexity
  for negative net value. `PlatformServices` factory is enough.
- **No abstraction over `FileSystemWatcher`**, `Process.Start`, `Registry`.
  These are leaf concerns and tests gate on `OperatingSystem.IsWindows()` —
  fine for a Windows-first product.
- **No moving Strings.cs to a `.resx`** despite its 1631 LOC. The custom
  `static getter Ru ? "..." : "..."` pattern is idiomatic for this project,
  fast, and avoids the .resx satellite-assembly tax. Keep as-is.
- **No "Clean Architecture" / "Hexagonal" rewrite.** The 3-project split
  (Core / App / Service) is already a sound 2-layer domain/presentation
  split. Adding ports/adapters/use-cases would be over-engineering.
