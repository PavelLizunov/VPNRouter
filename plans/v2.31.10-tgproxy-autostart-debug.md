## Failure mode 1 — empty secret silent skip (probable root cause)

**Repro on this VM**:

```bash
sed -i "s/tg_proxy_secret: 8ad281bf2e2c9be7b4a62857336936a0/tg_proxy_secret: ''/" config.yaml
sc start VPNRouter
```

Service log:

```
[2026-05-07 03:54:25] [INFOR] [Startup] VPNRouter Service starting (mode: WindowsService)
[2026-05-07 03:54:25] [INFOR] [Service] AutostartVpn=false, skipping VPN
[2026-05-07 03:54:25] [WARNI] [Service] TgProxy secret not configured, skipping
```

No tg-ws-proxy spawned. No port 1443 listener. Event Log got an auto-bridged `Microsoft.Extensions.Logging` entry but it's tagged with category `VPNRouter.Service.VPNRouterService` and zero actionable copy. **From the user's perspective this looks identical to "Service didn't react to autostart_tgproxy=true".**

**User path that produces this state**: Open Settings → Autostart sub-tab → tick "Auto launch with Windows for tgproxy" → reboot. Without ever clicking *Start* on the Telegram tab once, `tg_proxy_secret` stays as `string.Empty` (its default in `AppSettings.cs:299`). Secret is currently lazy-generated only on the first `StartTgProxyCommand` press (`MainWindowViewModel.cs:4354-4358`).

### Fix shipped — split between App and Service

**App** ([VPNRouter.App/ViewModels/MainWindowViewModel.cs:1587](VPNRouter.App/ViewModels/MainWindowViewModel.cs:1587)) — auto-generate secret when toggling autostart on:

```csharp
partial void OnAutostartTgProxyChanged(bool value)
{
    if (_isLoadingUI) return;

    if (value && string.IsNullOrWhiteSpace(TgProxySecret))
    {
        var bytes = System.Security.Cryptography.RandomNumberGenerator.GetBytes(16);
        TgProxySecret = Convert.ToHexString(bytes).ToLowerInvariant();
        TgProxyLink = TgProxyManager.BuildProxyLink("127.0.0.1", TgProxyPort, TgProxySecret);
    }

    SaveSettings();
}
```

Same RNG + format as `StartTgProxyCommand`. Property setters fire `PropertyChanged` automatically (CommunityToolkit.Mvvm `[ObservableProperty]`), so the Telegram tab's secret field + tg://proxy link reflect the new value immediately.

**Service** ([VPNRouter.Service/VPNRouterService.cs:336-365](VPNRouter.Service/VPNRouterService.cs:336-365)) — surface skip reasons to Event Log so users hitting legacy installs can debug via Event Viewer:

```csharp
if (!TgProxyUpdater.IsInstalled())
{
    _logger.LogWarning("[Service] TgProxy not installed, skipping autostart");
    WriteEventLog(
        "TgProxy autostart skipped: tg-ws-proxy is not installed. " +
        "Open the Telegram tab in the desktop app and click Install.",
        EventLogEntryType.Warning);
    return;
}
// ...
if (string.IsNullOrWhiteSpace(secret))
{
    _logger.LogWarning("[Service] TgProxy secret not configured, skipping");

```

Both hooks were already there in the file-log path — the gap was Event Log + actionable copy. Pre-fix, debugging this required tail-grepping `vpnrouter*.log` files and noticing the rolling-suffix-per-process pattern.

## Failure mode 2 — port 1443 held, no liveness check (deferred)

**Discovered in iteration 1** of this debug session: I had a leftover python.exe on port 1443 from a manual standalone test. When Service tried to autostart tg-proxy, it logged success but the spawned python died in <1 second with exit code 1. Service did not retry.

```
[03:50:17] [TgProxy] Starting: python.exe -m proxy.tg_ws_proxy --port 1443 ...
[03:50:17] [TgProxy] Started (PID 9248)
[03:50:17] [Service] TgProxy started on port 1443 (PID 9248)   ← claims success
[03:50:17] [TgProxy] Process exited (exit code: 1)             ← actually dead
```

### Why this happens

`TgProxyManager.Start` ([VPNRouter.Core/Services/TgProxyManager.cs:67-86](VPNRouter.Core/Services/TgProxyManager.cs:67-86)) calls `Process.Start(psi)` and returns the moment the OS hands back a PID. There is no post-spawn liveness window. The `_process.Exited` event fires when python dies, but the only handler is a `_logger.Warning` — no signal back to ResilientStarter, no auto-restart, no Event Log.

`ResilientStarter` ([VPNRouter.Core/Services/ResilientStarter.cs:67-74](VPNRouter.Core/Services/ResilientStarter.cs:67-74)) sees `startFn` return without exception → returns `true` → no retry.

### Why this is low-severity in practice

The leftover python in iter 1 was created by *me* during this debug session. In a real cold boot:
- Service starts before any other VPNRouter process
- Port 1443 is free
- python spawns and binds successfully

In a warm-restart-only-Service scenario, the App's `OrphanCleanup` (v2.31.7+) handles process cleanup via `SingleInstance` mutex — App's tg-proxy is owned via a `Process` handle and gets killed on App `Stop`. The python orphan we'd worry about (App killed via Task Manager / power loss) would be cleaned up at Service start by the same orphan-handling path that covers sing-box (Program.cs:48-69) — except that path is sing-box-specific and would not currently target python.

### Fix not shipped here — recommendation for future r-iteration

Add a minimal liveness check in `TgProxyManager.Start`:

```csharp
_process = Process.Start(psi);
// ... existing event wiring ...

// Brief probe: tg-ws-proxy binds within ~150 ms in tests. If it died
// in the first 1.5 s, surface the failure so ResilientStarter retries.
Thread.Sleep(1500);
if (_process.HasExited)
{
    var code = _process.ExitCode;
    _process.Dispose();
    _process = null;
    throw new InvalidOperationException(
        $"tg-ws-proxy exited immediately (code {code}). " +
        "Likely cause: port {port} already in use, or proxy module failed to import.");
}
```

Plus, in `Program.cs`, extend the orphan cleanup to include zombie python processes whose CommandLine matches `proxy.tg_ws_proxy`. That covers the warm-restart scenario without the 1.5 s sleep penalty on cold boot.

Held off shipping in this iteration because:
1. Probability is low for the user's reported symptom (cold boot path is fine)
2. The 1.5 s wait inflates Service start time noticeably
3. The orphan path needs a conservative `Get-CimInstance ... -Filter "CommandLine LIKE ..."` ACL test on LocalSystem before it can ship safely
4. Out-of-scope for the «Service-mode autostart_tgproxy works?» yes/no question in this branch

Recommend tracking as a separate r-iteration item.

## Code-review checklist for the Service-mode autostart path

For future debug:

1. `settings.App.AutostartTgProxy == true` in config.yaml → required
2. `TgProxyUpdater.IsInstalled()` → `python.exe` exists at `%ProgramData%\VPNRouter\tg-proxy\python\python.exe` AND `proxy/` subdirectory exists
3. `settings.App.TgProxySecret` non-whitespace → required
4. `settings.App.TgProxyPort` (default 1443) → port must be free at Service-start time
5. tg-ws-proxy must bind successfully (depends on Python + cryptography wheels + proxy/ source intact)
6. Event Viewer → Application log → Source `VPNRouter` → look for Warning entries

If all of 1-5 pass, child python.exe will be visible via `Get-CimInstance Win32_Process` with `ParentProcessId == VPNRouter.Service.exe.ProcessId`.
