# Module C01 Audit Report — Core Interfaces & Settings Store Seam (Batch B014_C01)

## 1. SUMMARY & PURPOSE

Module `C01` (Batch `B014_C01`) defines the core dependency-inversion contracts in `VPNRouter.Core/Interfaces/` together with the settings persistence abstraction in `VPNRouter.Core/Services/ISettingsStore.cs`. These interfaces decouple the platform-agnostic orchestration engine (`VpnEngine`, `StartupPipeline`, `HealthMonitor`, `ProfileManager`, `AutoFailoverEngine`, ViewModels, CLI commands, and the Windows Service) from OS-specific subsystem implementations (`netsh` / `nftables` / `pfctl`, Windows ETW / Unix `ps` polling, WMI / `ps -eo`, filesystem / HTTP profile stores, and YAML disk persistence).

## 3. DATA FLOWS & STATE MACHINES

### 3.1 Firewall Kill-Switch State Machine (`IFirewallManager` & `ICommittedFirewallConfig`)

The firewall contract supports two distinct lifecycle paths depending on whether the concrete implementation implements `ICommittedFirewallConfig`:

#### Path A: Legacy Per-Process Firewall (`FirewallManager` on Windows, `NullFirewallManager`)
1. **Instantiation (Phase 6 of `StartupPipeline`)**: `_host.FirewallFactory()` creates a new `IFirewallManager` and registers it on `VpnEngine` via `_host.SetFirewallManager(firewall)`.
2. **Rule Creation (Disabled)**: Because `firewall is not ICommittedFirewallConfig`, Phase 6 checks `if (profile.BlockOnVpnFail)` and invokes `firewall.CreateBlockRules(scanResult.ProcessNames, isFullTunnel)`. On Windows, `FirewallManager` sweeps orphaned `VPNRouter_Block_*` / `VPNRouter-DnsLockdown-*` rules, stores exact process names in `_requestedNames`, resolves running/known executable paths via `ProcessImagePath`, and creates outbound `netsh advfirewall` block rules with `enable=no`.
3. **Crash Activation (`EnableBlockRules`)**: When `SingBoxManager.Crashed` fires (`HealthMonitor.OnSingBoxCrashed`) or before a debounce-driven full restart (`HealthMonitor.OnDebounceElapsed`), `HealthMonitor` calls `_firewall.EnableBlockRules()`. Windows late-creates enabled rules for any previously unresolved `_requestedNames` now running and sets `enable=yes` on all `_managedRules`.
4. **Recovery Deactivation (`DisableBlockRules`)**:
   - After an in-place Clash API hot-reload in `AttemptRestart`, `HealthMonitor` immediately calls `_firewall.DisableBlockRules()`.
   - After a full `sing-box` restart, `HealthMonitor` sets `_deferredBlockRuleDisable = 1` and waits until a subsequent `OnHealthTick` confirms the Clash API is serving (`GET /version`) or `DeferredDisableMaxWait` (30s) elapses before calling `_firewall.DisableBlockRules()`.
5. **Teardown (`DisableBlockRules` -> `DeleteAllRules` -> `Dispose`)**: `VpnEngine.TeardownInternal()` calls `DisableBlockRules()`, `DeleteAllRules()`, and `Dispose()`.

#### Path B: Capability-Driven Global Kill-Switch (`LinuxFirewallManager`, `MacFirewallManager`)
1. **Instantiation (Phase 6 of `StartupPipeline`)**: `_host.FirewallFactory()` instantiates the manager (whose constructor sweeps any orphaned `inet vpnrouter_ks` table or `com.vpnrouter` `pf` anchor left by a prior crash if the marker file exists). Phase 6 **skips** `CreateBlockRules` because `firewall is ICommittedFirewallConfig`.
2. **Initial Commit (Phase 7 of `StartupPipeline`)**: Immediately after `StartSingBoxPhaseAsync` succeeds, `StartupPipeline.ExecuteAsync` checks `if (firewall is ICommittedFirewallConfig committedFirewall)` and calls `committedFirewall.UpdateCommittedConfig(configJson, profile.BlockOnVpnFail && isFullTunnel)`. The manager extracts server IPs from `configJson` in memory and sets `_armed = enabledForFullTunnel`.
3. **Runtime Hot-Reload / Restart Commit (`VpnEngine.ApplyGatedAsync`)**: Only after `_singBox.TryReloadConfigJson` or `_singBox.ReloadConfigJsonWithResult` succeeds does `VpnEngine` call `UpdateFirewallCommittedConfig`, which invokes `committed.UpdateCommittedConfig(configJson, (profile?.BlockOnVpnFail == true) && isFullTunnel)`. If the kill-switch is currently loaded in the kernel (`_loaded == true`), the ruleset is atomically reloaded in-place with the new server IPs. If the reload/restart failed, `UpdateCommittedConfig` is never called, preserving the active baseline.
4. **Crash / Recovery / Teardown**: Same `EnableBlockRules()` -> `DisableBlockRules()` -> `DeleteAllRules()` / `Dispose()` transitions as Path A.

### 3.3 Settings Persistence & Live-Reload Data Flow (`ISettingsStore`)

1. **Startup Load**: Consumers call `_store.Load(path)`. `RealSettingsStore` delegates to `SettingsLoader.Load`, which reads YAML, runs `SettingsMigrator.Migrate`, prunes placeholder credentials (recording count/timestamp for `ConsumePlaceholderPruneNotice`), runs `EnsureSane()`, and validates via `SettingsValidator.Validate` (backing up bad files and populating `LastRecoveryNotice` for `ConsumeRecoveryNotice()`).
2. **Runtime Save (Atomic Rename & Subscription Isolation)**:
   - Direct UI mutations call `_settingsStore.Save(_settings)`.
   - Background self-healing (`StartupPipeline.PersistSanitizedActiveProfile`) and server failover (`AutoFailoverEngine.PersistActiveServerSelection`) must **not** save the live in-memory `AppSettings` directly because `VlessServersResolver.Resolve` populates `settings.Vless.Servers` with transient subscription-expanded entries. Instead, they call `var fresh = _store.Load(AppPaths.ConfigYamlPath);`, mutate only the target field (`ActiveProfile` or `ActiveServer`), and call `_store.Save(fresh, AppPaths.ConfigYamlPath);`.
3. **External Write Watching (`VPNRouter.Service`)**: `VPNRouterService` calls `_store.StartWatching(onReload: ...)`. When the desktop UI writes `config.yaml`, `FileSystemWatcher` triggers a 2s debounce timer in `SettingsLoader`, which re-parses `config.yaml` via `Load` and invokes `onReload`.

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1 `IFirewallManager` Concurrency & Lifecycle
- **Instance-Per-Session Factory**: `VpnEngine` holds `Func<IFirewallManager> _firewallFactory` and creates a fresh `IFirewallManager` instance during each `ColdStart` (`StartupPipeline.DeployAndSetupFirewallPhaseAsync`), disposing it during `TeardownInternal()`.
- **Synchronization Disparity Across Implementations**:
  - `LinuxFirewallManager` and `MacFirewallManager` synchronize all `IFirewallManager` and `ICommittedFirewallConfig` methods with a private `lock (_gate)`.
  - Windows `FirewallManager` has **no internal lock** protecting `_managedRules` (`List<string>`) or `_requestedNames` (`List<string>`). If `HealthMonitor.OnSingBoxCrashed` (`_firewall.EnableBlockRules()` on a threadpool thread) races with `VpnEngine.Stop()` -> `TeardownInternal()` (`_firewall.DisableBlockRules()` / `DeleteAllRules()` on the caller thread, because `_singBox.Dispose()` or an earlier crash callback can overlap before `_healthMonitor` finishes an in-flight `OnSingBoxCrashed` invocation), `_managedRules` can be enumerated and mutated concurrently.

### 4.2 `IProcessMonitor` Threading & Teardown Guarantees
- **Event Threading**: Both `EtwProcessMonitor` and `MacProcessMonitor` invoke `ProcessStarted` and `ProcessStopped` synchronously on their dedicated background thread (`VPNRouter-ETW` or `VPNRouter-MacPollMonitor`). Subscribers must be thread-safe and non-blocking:
  - In `StartupPipeline.StartMonitorsPhase` (`StartupPipeline.cs:1395–1420`), the `ProcessStarted` handler runs `ProcessScanner.MatchesPattern` (bounded to 250ms per pattern), calls `_host.OnProcessDetected(procName, e.ProcessId)`, and calls `healthMonitor.OnNewProcessDetected(procName)` (which uses `Interlocked.Exchange(ref _debounceTimer, newTimer)` for lock-free thread safety).
- **Start/Stop Race & Handle Disposal**:
  - `EtwProcessMonitor` uses `ManualResetEventSlim _sessionReady` (CO-6 fix) so a rapid `Start()` -> `Stop()` waits up to 1s for `RunSession` to assign `_session` before calling `session.Stop()`, then joins `_sessionThread` with a 2s timeout.
  - `VpnEngine.TeardownInternal` (`VpnEngine.cs:1074`) calls `_etw?.Dispose()` (not merely `Stop()`), which is required to dispose `EtwProcessMonitor._sessionReady`'s kernel `WaitHandle`.
  - `MacProcessMonitor.Stop()` cancels `_cts` and nulls `_pollThread` and `_cts` **without** joining `_pollThread` or disposing `_cts`. Furthermore, `MacProcessMonitor.Start()` checks `if (_pollThread != null) return;` without synchronization.

### 4.3 `IProcessScanner` Synchronous Blocking & Uncancellable Background Tasks
- `IProcessScanner.ScanForProfile(Profile)` is a synchronous method with no `CancellationToken` parameter.
- In `StartupPipeline.ScanProcessesPhaseAsync` (`StartupPipeline.cs:862–888`), the scan is offloaded via `Task.Run(() => _host.Scanner.ScanForProfile(profile), ct)` and raced against `Task.Delay(TimeSpan.FromSeconds(30), ct)`. If the scan exceeds 30s (e.g., a stalled WMI service on Windows), `StartupPipeline` continues with an empty `ScanResult`, while the timed-out `ScanForProfile` call remains running on a ThreadPool thread until WMI returns.
- Both `ProcessScanner` and `MacProcessScanner` use a `static readonly ConcurrentDictionary<string, Regex> _regexCache` (`StringComparer.OrdinalIgnoreCase`) to cache compiled wildcard regexes thread-safely across scans.

### 4.4 `ISettingsStore` / `RealSettingsStore` Concurrency
- **`RealSettingsStore` Singleton Aliasing**: `RealSettingsStore.Instance` is stateless, delegating to static fields in `SettingsLoader` (`LastRecoveryNotice`, `_watcher`, `_debounceTimer`, `_reloadCallback`).
- **`InMemorySettingsStore` Locking**: Uses `lock (_lock)` around its internal `_snapshots` dictionary, `_recoveryNotice`, `_watcherCallback`, `SaveCount`, and `LastSave`, verified by `ISettingsStoreContractTests.InMemory_ParallelSaveLoadReset_IsRaceFree` (200 concurrent tasks).
- **Static `SafeMode.Enabled` Contention**: Both `RealSettingsStore` and `InMemorySettingsStore` read the global static `SafeMode.Enabled` flag (`SettingsLoader.cs:518`, `InMemorySettingsStore.cs:105`), requiring xUnit test classes that toggle `SafeMode.Enabled` to join `[Collection(SafeModeStateCollection.Name)]`.

## 5. SECURITY & PRIVILEGE BOUNDARIES

- **Kill-Switch Routing Intent Boundary (`IFirewallManager.CreateBlockRules` & `ICommittedFirewallConfig.UpdateCommittedConfig`)**:
  - On Linux and macOS, the firewall kill-switch blocks all host egress except loopback, RFC1918/link-local LAN, DHCP, and the VPN server IP(s). Arming it in split-tunnel mode would break all non-VPN applications if `sing-box` crashes.
  - Passing explicit `bool isFullTunnel` (and `bool enabledForFullTunnel` on `ICommittedFirewallConfig`) enforces that the global kill-switch is armed only when `RoutingMode == "full"` and `profile.BlockOnVpnFail == true`.
- **Privilege Boundaries in `IFirewallManager` Implementations**:
  - Windows `FirewallManager` requires Administrator privileges to execute `netsh advfirewall firewall`; failures are logged and fail open.
  - Linux `LinuxFirewallManager` executes `/usr/bin/sudo -n nft` (non-interactive NOPASSWD sudoers grant); if privileges are missing, it logs a warning and fails open without blocking the caller.
  - macOS `MacFirewallManager` executes `/usr/bin/sudo -n /sbin/pfctl`.
- **ETW Privilege Boundary (`IProcessMonitor`)**:
  - Windows `EtwProcessMonitor` requires Administrator privileges to open the kernel trace session (`KernelTraceEventParser.Keywords.Process`). When run unelevated, `RunSession` catches `UnauthorizedAccessException` and logs `[ETW] Session failed`, degrading gracefully (initial connect-time `IProcessScanner` rules still apply, only dynamic process-start hot-reloads are inactive).
- **ReDoS Protection on Untrusted Profile Patterns (`IProcessScanner`)**:
  - `Profile.Processes[].ScanPatterns` can originate from remote GitHub profile URLs (`GitHubProfileSource` has priority 10). Both `ProcessScanner` and `MacProcessScanner` compile wildcard patterns with a hard 250ms `Regex` match timeout (`TimeSpan.FromMilliseconds(250)`) and catch `RegexMatchTimeoutException` so catastrophic backtracking cannot stall ETW callbacks or startup scans.
- **JSON Depth Guard on Profile Sources (`IProfileSource`)**:
  - Implementations of `IProfileSource` deserialize profile JSON using `ProfileManager.SafeJsonOptions`, which enforces `MaxDepth = 32` to prevent stack-overflow DoS from deeply nested JSON payloads.
- **File Permission Hardening on Settings Persistence (`ISettingsStore`)**:
  - Because `AppSettings` contains VLESS UUIDs, Reality keys, Subscription URLs, and Clash API secrets, `RealSettingsStore.Save` -> `SettingsLoader.Save` writes to `{configPath}.tmp` using `AppPaths.CreatePrivateFile(tmp)` (mode `0600` on Linux/macOS) inside `AppPaths.EnsurePrivateUnixDirectory(AppPaths.DataDir)` (`0700`) before atomically renaming over `config.yaml`.

## 6. SUSPICIOUS PATTERNS / DEFECT CANDIDATES

### 6.1 `ISettingsStore` Doc-Comment Contract Violation: `RealSettingsStore.Save` and `ResetToDefaults` Do Not Swallow I/O Exceptions (`ISettingsStore.cs:41–43`, `127–132`)
- **Evidence**: `ISettingsStore.cs:41–43` explicitly states:
  > *"Implementations MUST swallow all transient I/O failures and return defaults rather than throwing — matches the Load() / Save() pre-3G contract documented on `SettingsLoader`."*
  However, while `SettingsLoader.Load` wraps `LoadCore` in a catch-all `try/catch`, `SettingsLoader.Save` (`SettingsLoader.cs:509–566`) and `SettingsLoader.ResetToDefaults` (`SettingsLoader.cs:670–684`) contain **no `catch` block**. Any `IOException` (e.g., locked target `config.yaml` on Windows during `File.Move(tmp, configPath, overwrite: true)`, disk full, or concurrent writers colliding on the fixed `{configPath}.tmp` filename) or `UnauthorizedAccessException` propagates directly out of `RealSettingsStore.Save` and `RealSettingsStore.ResetToDefaults`.
- **Impact**: Callers relying on the documented `ISettingsStore` no-throw contract (such as `AutoFailoverEngine.PersistActiveServerSelection` or CLI commands) will experience unhandled exceptions if `config.yaml` or `config.yaml.tmp` is transiently locked by an external process or concurrent writer.

### 6.2 Windows `FirewallManager` Rules Never Refresh on Runtime `ApplyAsync` or Debounced Process Rescan (`IFirewallManager.cs:18–31`, `VpnEngine.cs:957–965`, `HealthMonitor.cs:1126–1208`)
- **Evidence**:
  - `VpnEngine.ApplyGatedAsync` runs `StartupPipeline` in `StartupMode.HotReload` (which executes Phases 1–4 and skips Phase 6 `DeployAndSetupFirewallPhaseAsync`), then calls `UpdateFirewallCommittedConfig` (`VpnEngine.cs:957–965`), which only updates `if (_firewall is ICommittedFirewallConfig committed)`.
  - `LinuxFirewallManager` and `MacFirewallManager` implement `ICommittedFirewallConfig`, so they receive runtime config updates. Windows `FirewallManager` implements only `IFirewallManager` and is **never** called during `ApplyAsync`.
  - Similarly, when `HealthMonitor.OnDebounceElapsed` (`HealthMonitor.cs:1134–1202`) rescans processes via `_scanner.ScanForProfile(_activeProfile)` and discovers newly launched child processes (`include_children`) or wildcard-matched executables (`scan_patterns`), it hot-reloads `sing-box` with the expanded process list but **never** calls `_firewall.CreateBlockRules(newScan.ProcessNames, ...)`.
- **Impact**: On Windows with `block_on_vpn_fail: true`, any application added via the UI while connected (`ApplyAsync`), or any child/wildcard process discovered dynamically after initial connect (`OnDebounceElapsed`), has no Windows Firewall block rule in `_managedRules` or `_requestedNames` and will leak direct traffic if `sing-box` crashes.

### 6.3 Dangerous Default Parameter `bool isFullTunnel = true` on `IFirewallManager.CreateBlockRules` (`IFirewallManager.cs:18`)
- **Evidence**: `void CreateBlockRules(IEnumerable<string> processNames, bool isFullTunnel = true);` defaults `isFullTunnel` to `true` *"for the many Windows/HealthMonitor/VpnEngine test call sites where it's irrelevant"* (`IFirewallManager.cs:16–17`).
- **Impact**: On Linux and macOS, `isFullTunnel: true` arms the host-wide global egress kill-switch. Defaulting a safety-critical boolean parameter to the most destructive state (`true` = global host block) means any new call site that invokes `firewall.CreateBlockRules(processNames)` without explicitly passing `isFullTunnel` will silently arm a full-host kill-switch even in split-tunnel mode—the exact P1 bug class that parameter was introduced to prevent.

### 6.4 `InMemorySettingsStore` Violates Its Own Cloning Contract (`ISettingsStore.cs:35–36`, `InMemorySettingsStore.cs:33–35`, `88–114`)
- **Evidence**: `InMemorySettingsStore`'s class summary (`VPNRouter.Tests/Fakes/InMemorySettingsStore.cs:33–35`) states:
  > *"it stores object references directly and clones on Save so subsequent mutations to the in-memory tree don't leak back into the store."*
  In reality, `Save` (`InMemorySettingsStore.cs:110`) executes `_snapshots[key] = settings; // store by reference — Load returns the same instance.`, and `Load` (`InMemorySettingsStore.cs:93–94`) returns `snapshot.EnsureSane()` without cloning.
- **Impact**: Any service under test that mutates the `AppSettings` instance returned by `_store.Load()` in-place (for example, `VlessServersResolver.Resolve` mutating `settings.Vless.Servers` in memory) silently mutates the "persisted" snapshot inside `InMemorySettingsStore` even if `_store.Save()` was never called, masking persistence bugs in unit tests.

### 6.5 Non-Atomic Static State in `RealSettingsStore` Delegates (`ISettingsStore.cs:135–147`, `SettingsLoader.cs:34–39`, `590–660`)
- **Evidence**:
  - `RealSettingsStore.ConsumeRecoveryNotice()` delegates to `SettingsLoader.ConsumeRecoveryNotice()` (`SettingsLoader.cs:34–39`), which performs a non-atomic read-then-clear (`var notice = LastRecoveryNotice; LastRecoveryNotice = null; return notice;`) despite its XML doc claiming it *"atomically returns the current notice and clears it"*.
  - `RealSettingsStore.StartWatching` / `StopWatching` delegate to `SettingsLoader.StartWatching` / `StopWatching` (`SettingsLoader.cs:590–660`), which mutate static `_watcher`, `_debounceTimer`, and `_reloadCallback` fields without any lock. Concurrent `FileSystemWatcher` events on threadpool threads running `ScheduleReload` can race with `StopWatching()` or with each other when disposing/replacing `_debounceTimer`.

### 6.6 Synchronous Uncancellable `IProcessScanner.ScanForProfile` Signature (`IProcessScanner.cs:12`)
- **Evidence**: `ScanResult ScanForProfile(Profile profile);` is synchronous and accepts no `CancellationToken`.
- **Impact**:
  1. When `StartupPipeline.ScanProcessesPhaseAsync` times out after 30s (`StartupPipeline.cs:862–888`), the underlying ThreadPool task running `ScanForProfile` cannot be cancelled and continues executing in the background.
  2. `HealthMonitor.AttemptRestart` (`HealthMonitor.cs:883`, `943`) and `HealthMonitor.OnDebounceElapsed` (`HealthMonitor.cs:1134`) invoke `_scanner.ScanForProfile(_activeProfile)` synchronously without any timeout guard, allowing a hung WMI query on Windows to block crash recovery or debounce reloads indefinitely.

### 6.7 Architectural Layer Inversion in `IProcessScanner.cs` (`IProcessScanner.cs:2`)
- **Evidence**: `VPNRouter.Core/Interfaces/IProcessScanner.cs` imports `using VPNRouter.Core.Services;` (line 2) because its return type `ScanResult` is declared inside `VPNRouter.Core/Services/ProcessScanner.cs` (lines 280–290) rather than in `VPNRouter.Core.Models` or `VPNRouter.Core.Interfaces`.
- **Impact**: Creates a circular namespace dependency (`VPNRouter.Core.Interfaces` <-> `VPNRouter.Core.Services`).
