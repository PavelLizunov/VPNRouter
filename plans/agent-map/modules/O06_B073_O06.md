## 1. SUMMARY & PURPOSE

`setup` is an unprivileged, offline lifecycle management, packaging, and validation script written in Bash with embedded Python 3 subprograms. It governs the staging, verification, installation, status inspection, and uninstallation of the `VPNRouter.Headless` backend payload within the `omarchy-vpnrouter` plugin directory.

### Core Invariants & Architectural Responsibilities

1. **Zero Privilege Escalation**:
   The script executes entirely in user space. It never prompts for root credentials, invokes `sudo` or `pkexec`, generates or alters `sudoers` files, or spawns privileged helper shells. All privileged firewall filtering operations (such as nftables kill-switch and DNS lockdown) are explicitly flagged as pending an external privileged broker.

2. **Zero Unauthorized Remote Fetching**:
   The script does not download code, query GitHub release feeds, or fetch remote archives. It strictly enforces local offline installation (`--backend-dir <PATH>`) from an explicit build directory. Legacy archive and hash options (`--artifact`, `--sha256`) are rejected fail-closed.

3. **Zero Implicit Activation or Network Modification**:
   Installation does not register system services, alter desktop network routing tables, or enable the plugin in the Omarchy desktop shell. Enabling the plugin requires explicit user action (`omarchy plugin enable io.github.pavellizunov.vpnrouter`).

4. **Refusal of Active Backend Update**:
   The script never sends signals (`SIGTERM`, `SIGKILL`) to running processes. If an active `VPNRouter.Headless` or framework-dependent `dotnet` daemon is running, `setup` refuses to install or remove files, requiring the operator to terminate the daemon beforehand.

5. **Strict User Data Preservation**:
   All user-generated configuration files, cryptographic keys, and connection profiles stored in `~/.config/vpnrouter` (or `$XDG_CONFIG_HOME/vpnrouter`) are strictly preserved and untouched across setup, upgrade, and removal (`--remove`).

6. **Single Payload Directory & Transactional Rollback**:
   The Omarchy plugin validator forbids any symlinks within the plugin hierarchy. `setup` installs binaries into a single directory (`bin/backend/`). It stages build materials into a sibling directory (`bin/.stage_backend.XXXXXX`), validates the staged binary, renames the old payload to `bin/.backend_backup_$$`, moves the staging directory into place, and performs post-install manifest validation. If any validation step or signal interruption occurs prior to commit, the transaction rolls back cleanly.

7. **Fail-Closed Session Lock Verification**:
   On live desktop hosts running `omarchy-shell`, `setup` queries the desktop lock state (`timeout 3s omarchy-shell lock status`). If the shell is locked, requesting a lock, operating in secure mode, or if the lock state is unparseable or times out, the script fails closed and aborts installation.

8. **Strict Wire Protocol Handshake**:
   Prior to installation, candidate backend executables undergo a bounded handshake over standard I/O (`--stdio --data-dir <probe_dir>`). The probe operates with non-blocking selectors, a 3.0-second deadline, a strict 256 KiB frame ceiling checked prior to accumulator allocation, discarded stderr without disclosure, and strict Omarchy Protocol v1 validation (verifying integer `v: 1`, exact matching request ID `"setup-probe"`, and fail-closed error detection).

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Concurrency Patterns & Synchronization

1. **Subprocess Management with Monotonic Timeouts**:
   The protocol handshake helper (`validate_backend_executable`) avoids blocking indefinitely by employing Python's `selectors.DefaultSelector` on non-blocking pipe file descriptors. Timeouts are calculated against `time.monotonic()` with a maximum 3.0-second ceiling.

2. **Deterministic Subprocess Teardown**:
   In `validate_backend_executable`:
   - Standard input is closed immediately after sending the single snapshot frame (`proc.stdin.close()`), instructing the backend to exit after completing the snapshot.
   - If the backend stalls, floods stdout, or times out, the `finally:` block executes `proc.kill()` and waits up to 1.0 second.
   - All standard I/O streams are explicitly closed in the `finally:` block to release file descriptors.

3. **Multi-Instance Mutual Exclusion Limitation**:
   The script does not acquire an exclusive advisory file lock (`flock`) on `$plugin_dir/bin/.setup.lock`. While individual staging and backup directory names are randomized or include the PID (`.stage_backend.XXXXXX`, `.backend_backup_$$`), concurrent execution of `./setup` by two processes on the same checkout will race during the directory swap phase.

### 4.2. Signal Handling & Teardown Guarantees

- **Trap Registration**: `trap cleanup EXIT INT TERM` at line 49.
- **Rollback Guarantee**:
  If the script receives `SIGINT` (Ctrl+C) or `SIGTERM` while in the `SWAPPED_UNCOMMITTED` or `VALIDATING_POST_INSTALL` states (where `install_committed == 0`), the trap handler deletes the unverified `$target_backend_dir` and restores `$backup_tmp` to `$target_backend_dir`.
- **Interruption Scope**:
  `SIGHUP` and `SIGQUIT` are not caught in the trap specification, which could leave a temporary backup in place if a controlling terminal disconnects.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. Privilege Elevation & Identity
- Runs strictly under the invoking unprivileged user ID (`UID != 0`).
- No calls to `sudo`, `pkexec`, `su`, or `doas`.
- Explicitly warns that privileged Linux firewalling (`nftables` rules for kill-switch and DNS lockdown) cannot be operated directly by the unprivileged plugin and requires a dedicated external broker.

### 5.2. File Path Traversal & Injection Defenses
1. **Zero Symlinks Invariant**:
   - Staging loop inspects `[[ -L "$item" ]]` and immediately aborts if any symlink is detected in build materials.
   - Post-install validation executes `find "$plugin_dir" -type l 2>/dev/null` across the entire plugin tree; detection of any symlink triggers an immediate transaction rollback.
2. **Path Traversal in Catalogs**:
   - Profile copy uses `os.open` with `O_NOFOLLOW | O_CLOEXEC` on the directory and `dir_fd` relative file descriptors to prevent symlink hopping or `../` path traversal.
3. **Option Injection Defense**:
   - Basenames are validated against leading hyphens (`[[ "$item_base" == -* ]]`) to prevent command-line option injection into `cp` or `chmod`.
   - Trailing dots are rejected (`[[ "$item_base" == *\. ]]`).
   - All `cp` and `chmod` commands explicitly use the `--` double-hyphen argument terminator (e.g. `cp -- "$item" "$stage_dir/$item_base"`).

### 5.3. Memory Exhaustion & Denial of Service Protection
1. **Bounded Buffer Allocation**:
   - In `validate_backend_executable`, stdout chunk sizes are checked before buffering:
     ```python
     if total_stdout_bytes + len(chunk) > MAX_FRAME_BYTES:
         frame_overflow = True
         stdout_open = False
         break
     ```
   - If a malfunctioning backend produces an unbounded byte stream (e.g. `/dev/zero` or infinite log loops), the reader breaks immediately without accumulating memory and terminates the child process.
2. **Stderr Discarding**:
   - Standard error is read in 64 KiB chunks and discarded (`pass`) without accumulation, preventing memory exhaustion from massive stderr debug output.

### 5.4. Information Disclosure & Redaction
- Stderr from candidate backend execution is completely suppressed and never printed to the console or log files.
- Exit statuses are reported generically (`backend process exited with status {proc_returncode}`) without leaking exception stack traces, internal paths, tokens, or environment variables.

## 6. SUSPICIOUS PATTERNS / DEFECT CANDIDATES

### Defect Candidate 1: Deployment Gap — Sing-Box Co-Location vs Core Hardcoded Resolution
- **Severity**: MEDIUM / OPERATIONAL
- **Lines**: `setup:441-449`
- **Description**: `setup` installs `sing-box` into `$plugin_dir/bin/backend/sing-box` when present in the build directory. However, `VPNRouter.Core` (`AppPaths.SingBoxExePath`) strictly resolves `sing-box` at `~/.config/vpnrouter/bin/sing-box`.
- **Evidence**: `setup` acknowledges this gap with a notice:
  ```bash
  local app_singbox="${XDG_CONFIG_HOME:-$HOME/.config}/vpnrouter/bin/sing-box"
  if [[ ! -x "$app_singbox" ]]; then
    printf '%s\n' "  [NOTICE] Deployment gap: upstream VPNRouter.Core resolves sing-box strictly at:"
    printf '%s\n' "           $app_singbox"
  ...
  ```
- **Impact**: After running `setup --backend-dir ...`, the backend reports `capabilities.connect: false` in the protocol snapshot and cannot establish tunnels until the user manually copies or symlinks `sing-box` to `~/.config/vpnrouter/bin/sing-box`.

### Defect Candidate 2: Probe Temporary Directory Leak on Signal Interruption
- **Severity**: LOW / HYGIENE
- **Lines**: `setup:201`, `setup:35-49`
- **Description**: In `validate_backend_executable`, `probe_dir="$(mktemp -d "$plugin_dir/bin/.probe_tmp.XXXXXX" 2>/dev/null || mktemp -d)"` creates a directory in `bin/`. `cleanup()` does not track `probe_dir`.
- **Evidence**: If `SIGINT` or `SIGTERM` interrupts the probe while Python is running, `cleanup()` executes but only removes `$install_tmp` and rolls back `$backup_tmp`. The `.probe_tmp.XXXXXX` directory is left on disk until `setup --remove` is run.
- **Impact**: Interrupted probes leave orphaned temporary directories in `bin/`.

### Defect Candidate 3: Unhandled Signals in Cleanup Trap (`SIGHUP`, `SIGQUIT`)
- **Severity**: LOW / RELIABILITY
- **Lines**: `setup:49`
- **Description**: `trap cleanup EXIT INT TERM` omits `SIGHUP` and `SIGQUIT`.
- **Evidence**: If an SSH session disconnects (`SIGHUP`) or a terminal sends `SIGQUIT` (`Ctrl+\`) during the directory swap, the trap does not trigger, leaving `bin/.backend_backup_$$` un-restored and the plugin in an uncommitted state.
- **Impact**: Operator terminal disconnects during installation can leave the plugin broken without triggering automatic rollback.

### Defect Candidate 4: Missing Inter-Process Mutual Exclusion Lock (`flock`)
- **Severity**: LOW / CONCURRENCY
- **Lines**: `setup:580-698`
- **Description**: No lockfile is used to serialize multiple concurrent `./setup` invocations.
- **Evidence**: If two instances of `setup --backend-dir` execute simultaneously, their staging directories are unique, but the physical rename of `$plugin_dir/bin/backend` can race, corrupting the target directory or orphaning backup directories.
- **Impact**: Race hazard during concurrent automated setup calls.

### Defect Candidate 5: System-Wide Process Name Collision in `check_no_active_backend`
- **Severity**: MEDIUM / FALSE-POSITIVE REJECTION
- **Lines**: `setup:137-179`
- **Description**: `check_no_active_backend` inspects all `/proc` entries on the system for processes named `VPNRouter.Headless` or arguments referencing `VPNRouter.Headless` / `VPNRouter.Headless.dll`.
- **Evidence**: It does not verify whether the running process was launched from `$plugin_dir/bin/backend`. If another user on a multi-user machine or a background test suite in an independent workspace is running `VPNRouter.Headless`, `setup` will refuse to install or update.
- **Impact**: False-positive installation refusal in shared or multi-workspace environments.

### Defect Candidate 6: Hardcoded Profile Filenames Silently Ignore New Profiles
- **Severity**: LOW / EXTENSIBILITY
- **Lines**: `setup:599-600`
- **Description**: The profile extraction logic explicitly iterates over `("default.json", "default-linux.json")`.
- **Evidence**: If upstream introduces additional profile catalogs in `profiles/` (e.g. `streaming.json` or `vpn-profiles.json`), `setup` silently ignores them. Conversely, if upstream renames either file, `setup` fails closed and refuses installation.
- **Impact**: Tightly coupled to specific profile filenames; cannot install expanded profile catalogs without updating `setup`.

### 7.2. End-to-End Integration Check (`tests/check-published-backend.py`)

Validates real-world installation from a live build directory against `setup`:
- Runs `./setup --backend-dir <publish_dir>`.
- Verifies catalog bytes for `default.json` and `default-linux.json` match source.
- Executes `bin/vpnrouter-headless --stdio --data-dir <temp_dir>`.

- Validates read-only data guarantees (asserts no files are written to user config or test data directory during query).

### 7.3. Untested Boundaries & Gaps

1. **Probe Interruption Cleanup**: Tests do not simulate sending `SIGINT` or `SIGTERM` during the 3-second `validate_backend_executable` window to check for `.probe_tmp.XXXXXX` leaks.
2. **Terminal Disconnect (`SIGHUP`)**: Tests do not verify behavior under `SIGHUP` or `SIGQUIT`.
3. **Multi-Instance Concurrency**: No test exercises two concurrent `setup` processes attempting simultaneous installation into the same directory.
4. **Foreign Process Collision**: No test asserts whether a running `VPNRouter.Headless` in an unrelated directory causes false-positive rejection of a local installation.
5. **Additional Profile Files**: No test verifies behavior when `profiles/` contains more than the two hardcoded files.
