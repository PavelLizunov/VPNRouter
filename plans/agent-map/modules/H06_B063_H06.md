> **TL;DR:** Module H06 (`VPNRouter.Headless/Lifecycle`) delivers the process management, capability verification, and session state coordination foundation for VPNRouter's headless daemon. It enforces strict two-phase connection readiness (Phase A launch budget 60s, Phase B warmup budget 20s), bounded teardown guarantees (5s stop deadline preventing zombie processes), multi-layered fail-closed process ownership validation (`TunOwnershipLock`, `runtime-owner.json` v2/v1 with PID+start-time tick matching, and `ProcessOwnership`), zero-secret-leak exception scrubbing, and runtime policy scoping across all operations.

# Exhaustive Code Inventory & Audit: VPNRouter Headless Lifecycle Layer (Module H06 / Batch B063_H06)

## 1. SUMMARY & PURPOSE

The Headless Lifecycle module (`VPNRouter.Headless/Lifecycle/*`) provides the execution lifecycle, platform capability verification, process ownership protection, and state machine coordination for the `VPNRouter.Headless` daemon and Omarchy Quattro desktop shell plugin (`omarchy-vpnrouter`). It bridges the UI-agnostic protocol and backend layer (`RouterSession`, `RouterBackend`) to the underlying core VPN engine (`VPNRouter.Core.Services.VpnEngine`), sub-process orchestrators (`SingBoxManager`), and cross-platform kernel tun locks (`TunOwnershipLock`).

### Component Roles & Responsibilities

- **`BoundedTeardown.cs`**:
  - Enforces bounded time execution for stopping VPN engines (`StopBoundedAsync`) with a default 5-second deadline.
  - Prevents zombie process leaks by validating that `IsRunning` is `false` and `SingBoxPid` is `null` post-stop before allowing a transition to a disconnected state.
  - Scrubs secret-bearing data (URIs, credentials, UUIDs, passwords) from exception messages via `CrashReporter.ScrubSecrets` before logging or returning error descriptions.

- **`ILifecycleEngine.cs`**:
  - Core engine abstraction decoupling `RouterSession` from the concrete, OS-dependent `VpnEngine`.
  - Enables deterministic unit and integration testing without spawning live child processes, opening network connections, or requiring administrator/root privileges.
  - Declares the engine-scoped readiness guard contract (`CaptureReadinessGuard`) and optional capability probe (`CapabilityReadinessFunc`).

- **`LinuxOwnershipGuard.cs`**:
  - Safeguards process exclusivity and mutual exclusion on Linux and Windows where standard semaphore locks can fail open.
  - Employs a multi-layered verification strategy: native kernel lock (`TunOwnershipLock` / `LinuxTunOwnership`), durable filesystem records (`runtime-owner.json` v2 and legacy v1), and authoritative process identity cross-validation (`ProcessOwnership`).
  - Detects active foreign owners, active foreign child `sing-box` processes, and self-owned sessions using exact PID, start time (`StartedAtUtcTicks`), and executable image paths to eliminate PID recycling false positives.
  - Fails closed (`Unavailable`) on corrupt records, unknown schema kinds, or inspection errors.

- **`PlatformCapabilityVerifier.cs`**:
  - Implements the Omarchy Protocol v1 rule: *"Capabilities reflect verified availability, not optimistic platform detection."*
  - Verifies firewall kill-switch availability across operating systems: Windows returns `true` (via `netsh`); Linux returns `false` unless verified through an injected protected adapter, failing closed against unverified root or `NOPASSWD` assumptions.
  - Verifies DNS lockdown capability: returns `true` on Windows and macOS, but `false` on Linux due to firewall/namespace parity limitations.
  - Probes system connect readiness (`VerifyCanConnect`) by combining binary existence or `SingBoxRuntimePolicy` authorization with positive `OwnershipStatus.Free` checks.

- **`SessionStates.cs`**:
  - Single source of truth for canonical session state strings defined by Omarchy Headless Protocol v1: `disconnected`, `connecting`, `connected`, `disconnecting`, `error`, `unavailable`.
  - Provides strict schema validation (`IsValid`) to ensure no illegal or intermediate state strings enter the state event pipeline.

- **`TwoPhaseConnectCoordinator.cs`**:
  - Implements a resilient two-phase connection coordinator:
    - **Phase A**: Process launch and initial PID assignment (`SingBoxStarted` event) bounded by default 60-second budget.
    - **Phase B**: TUN adapter warmup and typed routability confirmation (`Connected` event) bounded by default 20-second budget.
  - Enforces typed readiness: captures engine readiness guards upon receiving the `Connected` event and evaluates the guard delegate before declaring the outcome `Connected`, preventing false-positive or optimistic string-based state promotions.
  - Subscribes to events *before* initiating the start task to eliminate event-before-subscription race conditions.

- **`VpnEngineAdapter.cs`**:
  - Production adapter implementing `ILifecycleEngine` by wrapping `VPNRouter.Core.Services.VpnEngine`.
  - Binds and latches `SingBoxRuntimePolicy` to prevent privilege escalations or untrusted binary execution across asynchronous operations.
  - Bridges concrete engine lifecycle events (`SingBoxStarted`, `Connected`, `StatusChanged`, `Warning`) to the headless event model.

                     │     │        ▼              │               │

        ┌────────────────────────────────────────┘

        ├── connectedTcs receives Connected ─────┐
        │                                        │
        ├── Phase B Timer expires ───────────────┼──> Outcome: PhaseBTimeout

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Concurrency Synchronization Primitives

| Primitive | Location | Scope / Purpose |
|---|---|---|
| `TunOwnershipLock` (`flock` on Linux, `Global\VPNRouter-SingBox-Owner` on Windows) | `LinuxOwnershipGuard.cs` (via Core) | Cross-process exclusivity over the physical TUN device. |
| `TaskCompletionSource<int>` | `TwoPhaseConnectCoordinator.cs:66` | Asynchronous wait for `SingBoxStarted` with `RunContinuationsAsynchronously` to prevent threadpool starvation or continuation deadlocks. |
| `TaskCompletionSource<(int, Func<bool>?)>` | `TwoPhaseConnectCoordinator.cs:67` | Asynchronous wait for `Connected` event + readiness guard capture with `RunContinuationsAsynchronously`. |
| `CancellationTokenSource.CreateLinkedTokenSource` | `TwoPhaseConnectCoordinator.cs:114, 153` | Links caller cancellation tokens to phase budget timeouts (`budgetA`, `budgetB`). |
| `Interlocked.CompareExchange` CAS Loop | `SingBoxRuntimePolicy.Capture` (called by `VpnEngineAdapter`) | Thread-safe atomic latching of runtime policy; guarantees production policy dominance without lock contention. |
| `AsyncLocal<SingBoxRuntimePolicy?>` | `SingBoxRuntimePolicy.EnterScope` (used by `VpnEngineAdapter`) | Thread-local and async-flow contextual policy scoping across asynchronous operations. |

### 4.2. Asynchronous Patterns & Deadlock Prevention

- **`RunContinuationsAsynchronously`**: Both `startedTcs` and `connectedTcs` in `TwoPhaseConnectCoordinator` explicitly specify `TaskCreationOptions.RunContinuationsAsynchronously`. This ensures event-handler callbacks executing on background engine threads do not synchronously run long coordinator continuations on the publisher thread.
- **`ConfigureAwait(false)`**: Used universally throughout `BoundedTeardown` and `TwoPhaseConnectCoordinator` on all awaits (`Task.WhenAny`, `Task.Delay`, `stopTask`), ensuring continuations run on thread pool threads and avoid UI or synchronization context deadlocks.
- **Event-Before-Task Subscription**: In `TwoPhaseConnectCoordinator`, `engine.SingBoxStarted` and `engine.Connected` event handlers are wired *before* the start task or delegate is initiated. This prevents a race condition where a fast or synchronously executing engine fires events before listeners are registered.

### 4.3. Teardown Guarantees & Zombie Prevention

- **Strict State Invariant**: A session or engine stop is forbidden from claiming `SessionStates.Disconnected` if the engine reports `IsRunning == true` or `SingBoxPid != null`.
- **Bounded Teardown Deadline**: `BoundedTeardown.StopBoundedAsync` executes `engine.Stop()` with an enforced timeout (default 5s). If the timeout is exceeded, the method returns `false`, and `RouterSession` transitions the session to `SessionStates.Error` (with error code `stop_failed`), refusing to report `Disconnected` while processes remain alive.
- **Foreign Session Protection**: `RouterSession` consults `LinuxOwnershipGuard.CheckOwnership()` before calling teardown on disposal or disconnect; if another process owns the tunnel and the current instance is not the recorded owner, the foreign session is left untouched.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. Elevation & Privilege Boundaries

- **Refusal to Assume Root**: `PlatformCapabilityVerifier.ProbeLinuxNftWithoutPassword` refuses to inspect `Environment.UserName` or assume `sudo NOPASSWD` capability. If an explicit verified protected operation adapter is not injected, firewall capability checks fail closed (`return false`).
- **Restricted Runtime Policy (`SingBoxRuntimePolicy`)**:
  - Headless Linux runs under `SingBoxRuntimePolicy.DefaultProduction`, which is initialized as `IsAvailable = false` (untrusted) until a cryptographically verified, pinned binary artifact is authorized.
  - Startup copies from bundle locations, colocation workarounds, and sudo/pkexec fallbacks are strictly rejected by policy.
  - Mere physical file presence at `AppPaths.SingBoxExePath` does not grant launch authority.

### 5.2. Secret Scrubbing & Data Redaction

- **Mandatory Exception Sanitization**:
  - `BoundedTeardown.SanitizeExceptionMessage(Exception? ex)` is the centralized sanitizer for lifecycle errors.
  - Delegates to `CrashReporter.ScrubSecrets`, which systematically strips:
    - VLESS / Trojan / Shadowsocks / VMess URIs (`vless://...`, `vmess://...`).
    - HTTP / HTTPS URLs containing user credentials, query strings, and auth tokens.
    - UUIDs and bearer tokens (`[a-f0-9-]{36}`).
    - Passwords and private keys.
  - Fail-safe fallback: If an exception is thrown inside `SanitizeExceptionMessage`, it catches the failure and returns `"An internal error occurred during teardown."`, ensuring unscrubbed raw text never reaches logs or protocol outputs.

### 5.3. Process Identity & PID Recycling Protection

- **PID + Timestamp + Executable Path Triple**:
  - Relying solely on PIDs on POSIX systems is susceptible to PID recycling attacks or false collisions.
  - `LinuxOwnershipGuard` inspects `StartedAtUtcTicks` (process start time ticks) and `ExecutablePath` in addition to `Pid`.
  - If a foreign owner record in `runtime-owner.json` references a PID that is now held by a recycled process whose start timestamp differs, the stale owner record is rejected, preventing false ownership attribution.

## 6. SUSPICIOUS PATTERNS / DEFECT CANDIDATES

### 6.1. Synchronous Scope Disposal in Asynchronous Methods (`VpnEngineAdapter.cs`)

- **Location**: `VpnEngineAdapter.cs`, lines 62–72:
  ```csharp
  public Task StartAsync(AppSettings settings, CancellationToken ct)
  {
      using var _ = SingBoxRuntimePolicy.EnterScope(EffectivePolicy);
      return _engine.StartAsync(settings, ct);
  }

  public Task<bool> ApplyAsync(AppSettings settings, CancellationToken ct)
  {
      using var _ = SingBoxRuntimePolicy.EnterScope(EffectivePolicy);
      return _engine.ApplyAsync(settings, ct);
  }
  ```
- **Nature of Defect**: `StartAsync` and `ApplyAsync` are not declared `async` and do not `await` the returned tasks. Consequently, the `using var _` scope holder is disposed **synchronously** as soon as the method returns the pending task to the caller, *before* the asynchronous pipeline inside `_engine.StartAsync` or `_engine.ApplyAsync` has executed its background work and continuations!
- **Consequence / Risk**: Any asynchronous operation or callback inside `_engine.StartAsync` that relies on `SingBoxRuntimePolicy.Current` across `await` points or on threadpool threads will see the scope already exited and `SingBoxRuntimePolicy.Current` reverted to its prior value. While `VpnEngine` internally re-enters its own policy scope in some methods, this wrapper construct is an anti-pattern that fails to protect asynchronous execution within the adapter itself.
- **Recommended Remediation**: Declare the methods `async Task` and `await` the engine call:
  ```csharp
  public async Task StartAsync(AppSettings settings, CancellationToken ct)
  {
      using var _ = SingBoxRuntimePolicy.EnterScope(EffectivePolicy);
      await _engine.StartAsync(settings, ct).ConfigureAwait(false);
  }
  ```

### 6.2. Orphaned Background Thread on Stop Timeout (`BoundedTeardown.cs`)

- **Location**: `BoundedTeardown.cs`, lines 29–36:
  ```csharp
  var stopTask = Task.Run(() => engine.Stop());
  var completed = await Task.WhenAny(stopTask, Task.Delay(budget)).ConfigureAwait(false);

  if (completed != stopTask)
  {
      logger?.Warning("[BoundedTeardown] Engine stop exceeded timeout of {Budget}s; process remains active.", budget.TotalSeconds);
      return false;
  }
  ```
- **Nature of Defect**: If `engine.Stop()` hangs (e.g. blocked inside a native driver P/Invoke, hung unkillable process, or kernel mutex deadlock), `Task.WhenAny` returns when `Task.Delay(budget)` fires, and `StopBoundedAsync` returns `false`. However, the thread executing `engine.Stop()` on the .NET thread pool cannot be cancelled or aborted; it remains running indefinitely in the background.
- **Consequence / Risk**: If `engine.Stop()` eventually wakes up or finishes minutes later, it may attempt to mutate engine fields or dispose resources concurrently while a subsequent connect attempt is in progress, leading to state corruption. Furthermore, if `stopTask` eventually faults, the exception is unobserved on the completed task.
- **Recommended Remediation**: Attach an observe-continuation to `stopTask` to catch and log late-arriving faults, and consider an uncooperative kill fallback (e.g. process termination) if the managed stop task fails to settle within an extended grace window.

### 6.3. Uncancelled `Task.Delay` Timers and CTS Lifetime (`TwoPhaseConnectCoordinator.cs`)

- **Location**: `TwoPhaseConnectCoordinator.cs`, lines 114–117 and 153–156:
  ```csharp
  using var phaseACts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
  phaseACts.CancelAfter(budgetA);
  var phaseATimer = Task.Delay(budgetA, phaseACts.Token);
  ```
- **Nature of Defect**:
  1. When `startedTcs.Task` completes well before `budgetA` (e.g. within 200ms), Phase A terminates and `phaseACts` is disposed at the end of the `using` block. However, `phaseATimer` remains active in the runtime timer queue. While .NET handles cancellation token registrations reasonably well, leaving pending timers without cancelling them incurs unnecessary timer queue pressure.
  2. Disposing a `CancellationTokenSource` while an uncompleted `Task.Delay` holds a reference to its token can occasionally surface `ObjectDisposedException` on certain runtime versions if timer callbacks fire during cleanup.
- **Recommended Remediation**: Cancel `phaseACts` when Phase A succeeds to cleanly terminate `phaseATimer`, or cancel timers explicitly.

### 6.4. Unscoped Fallback to Disk Existence in `PlatformCapabilityVerifier.VerifyCanConnect`

- **Location**: `PlatformCapabilityVerifier.cs`, lines 77–88:
  ```csharp
  var policy = SingBoxRuntimePolicy.Current;
  if (policy != null)
  {
      if (!policy.IsAvailable)
          return false;
  }
  else
  {
      var exePath = AppPaths.SingBoxExePath;
      if (!File.Exists(exePath))
          return false;
  }
  ```
- **Nature of Defect**: If `VerifyCanConnect` is invoked outside an active `SingBoxRuntimePolicy.EnterScope` context, `SingBoxRuntimePolicy.Current` is `null`. In this case, instead of defaulting to `SingBoxRuntimePolicy.DefaultProduction` (which fails closed on Linux as `IsAvailable = false`), the method falls back directly to `File.Exists(exePath)`.
- **Consequence / Risk**: Under Linux Headless, rule #7 mandates: *"Default production policy is strictly unavailable (`untrusted`) because no trusted artifact is yet authorized. Mere file existence on disk at `AppPaths.SingBoxExePath` does not establish readiness, integrity, or authority to launch code."* If an unauthorized binary exists on disk and `VerifyCanConnect` is called without an active scope, it will report `true`, violating the fail-closed policy.
- **Recommended Remediation**: Replace `var policy = SingBoxRuntimePolicy.Current;` with:
  ```csharp
  var policy = SingBoxRuntimePolicy.Current ?? (OperatingSystem.IsLinux() ? SingBoxRuntimePolicy.DefaultProduction : null);
  ```

### 6.5. Synchronous Blocking Teardown in `VpnEngineAdapter.DisposeAsync`

- **Location**: `VpnEngineAdapter.cs`, lines 97–101:
  ```csharp
  public ValueTask DisposeAsync()
  {
      Dispose();
      return ValueTask.CompletedTask;
  }
  ```
- **Nature of Defect**: `ILifecycleEngine` implements `IAsyncDisposable`. However, `VpnEngineAdapter.DisposeAsync()` simply invokes synchronous `Dispose()` and returns `ValueTask.CompletedTask`.
- **Consequence / Risk**: Calling `await engine.DisposeAsync()` synchronously blocks the caller's thread during process termination and resource cleanup rather than executing an asynchronous, non-blocking drain.
- **Recommended Remediation**: If `_engine` provides asynchronous disposal, await it; otherwise offload synchronous cleanup to the thread pool with timeout bounds.

### 6.6. Point-in-Time TOCTOU in `LinuxOwnershipGuard.CheckOwnership`

- **Location**: `LinuxOwnershipGuard.cs`, lines 38–42 and 52–55.
- **Nature of Defect**: The method probes `TunOwnershipLock`, inspects `runtime-owner.json`, and scans PIDs at a discrete point in time without holding a mutual exclusion lock across the probe sequence.
- **Consequence / Risk**: Another process can start sing-box or write `runtime-owner.json` immediately after `CheckOwnership` returns `OwnershipStatus.Free` but before the current process acquires `TunOwnershipLock`.
- **Assessment**: The author explicitly documented this limitation in comments: *"Point-in-time PID, process name, and file probing is inherently non-atomic and vulnerable to race conditions (TOCTOU). True concurrency guarantees require a shared synchronization lock; this probe does NOT claim an atomic concurrency guarantee."* The downstream `RouterSession` relies on this probe only as an admission gate, with true exclusion enforced at actual engine start.

### 7.2. Test Gaps & Uncovered Scenarios

1. **Linux nftables Live Verification Adapter**:
   - `PlatformCapabilityVerifier.VerifyKillSwitchSupport` delegates to `linuxNftChecker`. Existing tests pass `null` (failing closed) or `() => true` / `() => throw`. There is no test exercising a live nftables process runner or checking for exit codes / permission denials under real Linux non-root environments.
2. **PID Recycling High-Frequency Stress Test**:
   - While `LinuxOwnershipGuard` checks `StartedAtUtcTicks` to differentiate recycled PIDs, there is no multi-process test simulating rapid Linux PID wrap-around to empirically verify that tick comparison rejects false owners under sub-millisecond process recycling.
3. **`VpnEngineAdapter` Unawaited Policy Scope Leak**:
   - As identified in Defect 6.1, `VpnEngineAdapter.StartAsync` disposes the policy scope synchronously upon returning the pending task. No current test asserts that `SingBoxRuntimePolicy.Current` remains intact at the final completion continuation of an asynchronous `VpnEngineAdapter.StartAsync` execution.
4. **macOS Parity for Kill-Switch Verification**:
   - `PlatformCapabilityVerifier.VerifyKillSwitchSupport` currently returns `false` on macOS. While Core provides `MacFirewallManager` (pf), Headless capability verification does not yet wire macOS pf capabilities into `PlatformCapabilityVerifier`.
