> **TL;DR:** The `VPNRouter.GUI` module (Module G01 / Batch B059_G01) is a lightweight, zero-.NET-dependency native Go launcher, bootstrap updater, and self-repair trampoline. It safeguards Windows installations by resolving in-process update lockouts via `_bootstrap/` stage copying, detecting mixed-assembly version drift across `VPNRouter.App.dll`, `Core.dll`, and `Service.dll` via Win32 `version.dll` syscalls, enforcing a 10-minute cooldown loop guard, and safely executing detached PowerShell repairs formatted to evade Defender ClickFix heuristics.

# Exhaustive Code Inventory & Audit: Go Launcher & Repair Helper (Module G01 / Batch B059_G01)

## 1. SUMMARY & PURPOSE

The `VPNRouter.GUI` module is a standalone, native Go binary compiled to `VPNRouter.GUI.exe` (~2 MB). It resides in the application root directory and serves three critical architectural functions in the VPNRouter desktop lifecycle:
1. **Backwards-Compatibility Launcher Stub**: Provides continuity for legacy desktop shortcuts, Start Menu entries, and legacy auto-updaters (such as v2.3.x WinForms updaters) that expect an executable named `VPNRouter.GUI.exe`. It transparently forwards CLI arguments and detaches execution to `VPNRouter.App.exe`.
2. **Post-Update Bootstrap Host (v2.29.0-r6+)**: Solves the Windows in-process binary-locking limitation where earlier .NET-based auto-updaters failed when overwriting mapped DLLs. Staged payloads extracted to `_bootstrap/` are atomically walked and copied over the application root once the parent .NET process terminates.
3. **Integrity Verifier & Self-Repair Trampoline (v2.31.9-r1+)**: Validates that all core .NET assemblies share identical build commit hashes (extracted from `AssemblyInformationalVersionAttribute` / `ProductVersion` via native Win32 `version.dll` APIs). If a mixed-version condition is confirmed, it initiates a silent, hidden background repair via PowerShell using a 10-minute file-based cooldown marker to prevent bootloops.

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Concurrency Primitives & Goroutines
- **Repair Timeout Execution (`repair.go:63-78`)**:
  - `RunRepair` launches a dedicated goroutine:
    ```go
    done := make(chan error, 1)
    go func() {
        done <- cmd.Run()
    }()
    ```
  - The channel `done` has a buffer capacity of 1. This guarantees that if the outer select hits `time.After(deadline)` and exits, the goroutine will not leak on channel send when `cmd.Run()` eventually completes.
- **Process Teardown on Timeout**:
  - On deadline expiry, `cmd.Process.Kill()` is invoked.
  - *Risk*: `cmd.Process` may be nil if `cmd.Run()` has not completed `cmd.Start()` inside the goroutine, though over a 5-minute deadline this race is theoretical.
  - *Teardown Limitation*: `cmd.Process.Kill()` terminates the top-level `powershell.exe` process. On Windows, child processes spawned by `install.ps1` (e.g. background installers or curl) are not assigned to a Windows Job Object (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) and can become orphaned.

### 4.2. File Locking & Kernel Deallocation Delays
- **Kernel Memory Mapping Window**:
  - When .NET assemblies terminate, Windows unmaps executable PE pages asynchronously.
  - To prevent file access violations (`ERROR_SHARING_VIOLATION` / `0x20`), `runBootstrap` introduces an explicit delay:
    ```go
    time.Sleep(time.Duration(bootstrapPostParentDelayMs) * time.Millisecond) // 750ms
    ```
- **Transient Contention Mitigation**:
  - `copyFileWithRetry` implements a 5-iteration retry loop with a 500ms fixed backoff (total window 2.5s) to outlast antivirus background scanners (Defender, CrowdStrike) holding transient read locks.

### 4.3. Process Lifecycle & Detachment
- **`DETACHED_PROCESS` Flag (`0x00000008`)**:
  - Passed via `syscall.SysProcAttr.CreationFlags` when launching `VPNRouter.App.exe`.
  - Ensures the child application does not inherit console attachment, allowing `VPNRouter.GUI.exe` to exit immediately without blocking shortcut dispatchers or keeping desktop console windows open.
- **`os.Exit` vs `defer` Unwinding**:
  - In `main.go`, `logFile.Close()` is deferred (`main.go:90`). However, all termination paths in `main.go` exit via `os.Exit(0)`, `os.Exit(1)`, `os.Exit(2)`, or `os.Exit(3)`.
  - In Go, `os.Exit` terminates the process immediately without running deferred functions. The file handle is closed by the OS kernel upon process destruction, but in-memory runtimes buffers are not formally flushed via Go's runtime.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. Antivirus / AMSI Evasion & ClickFix Mitigation
- **Defender ClickFix Heuristic Workaround**:
  - Microsoft Defender heuristic `Trojan:Win32/ClickFix.DCW!MTB` aggressively flags `powershell.exe -Command "<download and invoke>"`.
  - To maintain zero false-positive signatures, `repair.go` formats the invocation strictly:
    1. Writes the script to a physical disk file (`%TEMP%\vpnr-trampoline-repair-<nano>.ps1`).
    2. Executes PowerShell strictly via `-File <path>` (`repairArgs()`).
    3. Test `TestRepairArgs_UsesFileNotCommand` asserts that `-Command` is never introduced.
- **AMSI Clean Shape & TLS 1.2 Enforcement**:
  - Script output uses canonical CRLF line endings (`\r\n`) and explicit `[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12` to prevent execution failures on legacy Windows 10/Server environments lacking default TLS 1.2 in PowerShell 5.1.

### 5.2. File System Security & Predictable Paths
- **Fixed File Name in Temp Directory (`repair.go:91`)**:
  - In `repairScript()`, the download target is hard-coded:
    `$tmp = Join-Path $env:TEMP 'vpnr-trampoline-install.ps1'`
  - *Risk*: A low-privileged or malicious local process running in the same user session can pre-create or watch for `vpnr-trampoline-install.ps1` and inject payload code prior to execution (TOCTOU race).
- **Marker File Hijack / Denial of Service (`marker.go:26`)**:
  - The marker file `%TEMP%\vpnrouter-trampoline-repair-marker` is located in `%TEMP%` without strict DACLs. Any local process in the user session can touch this file to suppress auto-repairs indefinitely.

### 5.3. Network Egress & Integrity Verification
- **Unverified Remote Script Execution**:
  - `repair.go` downloads `https://vpn.ninitux.com/install.ps1` and immediately dot-executes it (`& $tmp`).
  - The downloaded payload is not verified against a pre-compiled SHA256 checksum or an embedded Authenticode digital signature.
  - While protected in transit by TLS 1.2, any compromise of the hosting endpoint (`vpn.ninitux.com`) or corporate TLS inspection certificate directly results in arbitrary PowerShell code execution at the integrity level of the launcher.

### 5.4. Privilege & Elevation Boundaries
- **Un-Elevated Execution**:
  - Neither `VPNRouter.GUI.exe` nor the spawned `powershell.exe` in `RunRepair()` request UAC elevation (`runas`).
  - If the application is installed in `C:\Program Files\VPNRouter`, replacing files in `runBootstrap()` or modifying binaries via `install.ps1` will fail with `Access Denied` unless the launcher itself was started from an elevated context.

## 6. SUSPICIOUS PATTERNS / DEFECT CANDIDATES

### 6.1. Defect Candidate 1: Unconditional Destruction of `_bootstrap/` on Partial Copy Failure
- **File & Line**: `VPNRouter.GUI/main.go:244`
- **Pattern**:
  ```go
  if err := copyFileWithRetry(srcPath, destPath); err != nil {
      failed++
      logf("copy %s -> %s: %v", relPath, destPath, err)
  } else {
      copied++
  }
  ...
  // Phase 3: cleanup _bootstrap/.
  if err := os.RemoveAll(bootstrapDir); err != nil {
      logf("cleanup _bootstrap/: %v", err)
      return err
  }
  ```
- **Analysis**: If one or more files fail to copy during `runBootstrap` (e.g. `failed > 0` due to a locked secondary file or disk full condition), `os.RemoveAll(bootstrapDir)` is still called. This permanently wipes out the staged update directory, destroying the recovery source and leaving the install in a corrupted, mismatched state without the ability to retry on subsequent boots.
- **Recommended Remediation**: Abort directory removal if `failed > 0`:
  ```go
  if failed > 0 {
      return fmt.Errorf("bootstrap incomplete: %d files failed to copy; retaining _bootstrap", failed)
  }
  ```

### 6.2. Defect Candidate 2: Inaccurate & High-Overhead Process Polling in `isProcessRunning`
- **File & Line**: `VPNRouter.GUI/main.go:296-305`
- **Pattern**:
  ```go
  func isProcessRunning(name string) bool {
      cmd := exec.Command("tasklist", "/FI", "IMAGENAME eq "+name, "/NH", "/FO", "CSV")
      out, err := cmd.Output()
      if err != nil {
          return false
      }
      return strings.Contains(strings.ToLower(string(out)), strings.ToLower(name))
  }
  ```
- **Analysis**:
  1. Spawning `tasklist.exe` every 200ms for up to 30s can launch up to 150 short-lived processes, causing significant CPU spikes and disk I/O contention during startup.
  2. If `tasklist` fails due to environment issues (missing from PATH or permission errors), `err != nil` causes `isProcessRunning` to return `false`. `runBootstrap` then assumes the parent has terminated and attempts to overwrite locked files immediately.
  3. `strings.Contains` on CSV output matches substrings. If another process named `OldVPNRouter.App.exe` or `VPNRouter.App.exe.bak` is running, it will match.

### 6.3. Defect Candidate 3: Temporary Script Removal Failure Due to Process Sharing Violation
- **File & Line**: `VPNRouter.GUI/repair.go:52, 75`
- **Pattern**:
  ```go
  defer os.Remove(scriptPath)
  ...
  case <-time.After(deadline):
      if cmd.Process != nil {
          _ = cmd.Process.Kill()
      }
      return elapsed, fmt.Errorf("repair timed out after %v", deadline)
  ```
- **Analysis**: On Windows, deleting a file held open by a process returns an `ERROR_SHARING_VIOLATION`. If `RunRepair` times out and calls `cmd.Process.Kill()`, Windows process cleanup is asynchronous. When `RunRepair` returns immediately, the deferred `os.Remove(scriptPath)` executes while PowerShell may still hold the file handle, causing `os.Remove` to fail silently and leaking `.ps1` scripts in `%TEMP%`.

### 6.4. Defect Candidate 4: Read-Only File Overwrite Failure in `copyFile`
- **File & Line**: `VPNRouter.GUI/main.go:281`
- **Pattern**:
  ```go
  d, err := os.OpenFile(dst, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)
  ```
- **Analysis**: On Windows NTFS, opening an existing file marked with the `FILE_ATTRIBUTE_READONLY` attribute with `O_TRUNC` or `O_WRONLY` fails with `os.ErrPermission`. If an assembly or configuration file in the target directory was marked read-only, `copyFile` will fail on every retry attempt.
- **Recommended Remediation**: Remove read-only attributes before opening: `_ = os.Chmod(dst, 0666)`.

### 7.2. Test Coverage Gaps & Untested Paths

1. **Bootstrap Copy Pipeline Untested**:
   - `runBootstrap`, `copyFileWithRetry`, and `copyFile` have **0% unit test coverage**.
   - No mock test exists to verify behavior when files are locked, directories are nested, or permissions fail.
2. **Main Function & CLI Argument Forwarding Untested**:
   - `main()` is entirely unexercised by test fixtures. Forwarding of `os.Args[1:]` to the child `VPNRouter.App.exe` is not verified.
   - Missing executable exit code (`os.Exit(2)`) and start failure exit code (`os.Exit(3)`) are untested.
3. **`RunRepair` Timeout and Process Killing Untested**:
   - `RunRepair` execution, goroutine dispatch, and `cmd.Process.Kill()` on timeout are not tested.
4. **Synthetic Version Mismatch Injection**:
   - While `TestCheckIntegrity_EmptyDir` tests the zero-DLL path, there are no tests that feed real PE binaries with deliberately mismatched `ProductVersion` hashes to verify that `Mismatched = true` is set.
5. **Cross-Compilation Limitations**:
   - Tests in `integrity_test.go` and `repair_test.go` rely on Windows-specific `syscall.SysProcAttr` fields (`CreationFlags`) and Win32 DLLs, meaning tests cannot be executed on Linux/macOS developer machines without setting `GOOS=windows` and using a Windows test runner (such as WINBRAT).
