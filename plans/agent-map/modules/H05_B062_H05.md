> **TL;DR:** Module H05 (`RouterBackend` and `RouterSession`) forms the authoritative headless core for VPNRouter under Omarchy Protocol v1, responsible for serializing feature endpoint dispatch, enforcing atomic configuration persistence with guarded CAS rollback, managing two-phase VPN startup with typed connected readiness, and guaranteeing bounded teardown without process or secret leaks. This audit documents all symbols, state machines, and concurrency primitives, identifying a dead in-flight request cancellation dictionary in `RouterBackend` and an unsynchronized semaphore disposal race during `DisposeAsync`.

## 1. SUMMARY & PURPOSE

Module H05 constitutes the core orchestration backend of `VPNRouter.Headless`. It acts as the bridge between external transport layers (NDJSON protocol server/handlers in module H02) and low-level VPN lifecycle/storage engines (`ConfigStorage`, `VpnEngine`, `SingBoxManager`).

### Component Responsibilities

1. **`RouterBackend.cs`**:
   - **Protocol v1 Request Router**: Validates method names and arguments via allowlists, routing 37 distinct protocol methods across 9 specialized feature handlers (`ServerFeature`, `SubscriptionFeature`, `FreeConfigFeature`, `AppRoutingFeature`, `ProfileFeature`, `RulesFeature`, `CustomConfigFeature`, `SettingsFeature`, `DiagnosticsFeature`) and session lifecycle commands (`connect`, `disconnect`, `snapshot`, `cancel`).
   - **Operation Concurrency Arbiter**: Implements an atomic compare-exchange concurrency gate (`_busyState`). Strictly serializes all ordinary operations (rejecting concurrent calls with error code `busy`), while granting non-blocking bypass to urgent control operations (`cancel`, `disconnect`, `snapshot`).
   - **Guarded Settings Mutation Engine (`ExecuteMutationAsync`)**: Ensures candidate configuration mutations are validated, saved atomically with Compare-And-Swap (CAS) revision tracking, and applied to active VPN connections. If live apply fails, executes guarded compensation rollback to prior settings only if no concurrent external edits modified the configuration file.
   - **Event & State Snapshot Broker**: Bridges session state transitions and background feature progress notifications to client listeners (`StateChanged`, `ProgressChanged`).
   - **Policy Scoping**: Wraps all invocations, snapshots, and disposal within `SingBoxRuntimePolicy.EnterScope` to enforce headless runtime integrity rules.

2. **`RouterSession.cs`**:
   - **Authoritative Session State Machine**: Implements `IRouterSession` with explicit protocol states (`disconnected`, `connecting`, `connected`, `disconnecting`, `error`, `unavailable`).
   - **Two-Phase Connection Coordinator**: Orchestrates asynchronous start sequences (Phase A: sing-box process launch; Phase B: TUN interface warmup and routability probe) via `TwoPhaseConnectCoordinator`.
   - **Typed Connected Readiness Guard**: Prevents false/stale connected states by requiring an engine-scoped readiness probe (`CaptureReadinessGuard(pid)`). Evaluates the retained guard on every `State` property read and during post-crash recovery.
   - **Linux Exclusive Ownership Enforcement**: Queries `LinuxOwnershipGuard` (`_ownershipProbe`) before initiating connections or teardowns. Refuses to stop or corrupt foreign sessions owned by another GUI or CLI instance.
   - **Fail-Closed Capability Verifier**: Truthfully gates DNS leak lockdown (`SupportsDnsLockdown`: false on Linux) and firewall kill-switch (`SupportsKillSwitch`: requires verified nftables adapter). Fails closed when an unsupported security configuration is requested.
   - **Bounded Teardown & Leak-Free Cleanup**: Enforces a strict 5-second deadline (`BoundedTeardown.StopBoundedAsync`) for engine shutdown. Replaces raw exception strings with scrubbed error codes to eliminate secret/credential leakage.

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Synchronization Primitives

1. **`RouterBackend._busyState` (`int`)**:
   - Primitive: Atomic `Interlocked.CompareExchange(ref _busyState, 1, 0)` and `Interlocked.Exchange(ref _busyState, 0)`.
   - Purpose: Enforces single-operation ordinary concurrency across all 34 ordinary protocol methods.
   - Behavior: If an ordinary operation is running, any concurrent ordinary operation immediately throws `RouterException("busy", ...)`. Urgent methods (`cancel`, `disconnect`, `snapshot`) bypass this gate.
2. **`RouterSession._gate` (`SemaphoreSlim(1, 1)`)**:
   - Primitive: Asynchronous mutual exclusion semaphore.
   - Purpose: Coordinates execution of `ConnectAsync`, `ApplyAsync`, and `DisconnectAsync`.
   - Behavior:
     - `ConnectAsync` and `ApplyAsync` use non-blocking acquisition: `_gate.WaitAsync(0, ct)`. If another session operation is active, they immediately throw `RouterException("busy", ...)`.
     - `DisconnectAsync` uses blocking acquisition: `_gate.WaitAsync(ct)`. This ensures that urgent disconnect waits for in-flight operations to cancel or drain before stopping the engine.
3. **`RouterSession._stateLock` (`object`)**:
   - Primitive: Synchronous CLR monitor lock (`lock (_stateLock)`).
   - Purpose: Protects internal state variables: `_state`, `_errorCode`, `_ownsConnection`, `_disconnectStarted`, `_connectedPid`, and `_retainedReadinessGuard`.
   - Invariant: Guard checks and PID comparisons are performed under lock to eliminate race conditions between background event promotions and active disconnects.

### 4.2. Two-Phase Connect & Startup Synchronization
The connection sequence executes through `TwoPhaseConnectCoordinator.RunAsync`:
- **Phase A (Startup & PID Capture)**:
  - Subscribes to `_engine.SingBoxStarted(int pid)` before initiating `_engine.StartAsync`.
  - Enforces a 60-second budget (`DefaultPhaseABudget`).
- **Phase B (TUN Warmup & Typed Readiness)**:
  - Awaits `_engine.Connected(int pid)`.
  - Enforces a 20-second budget (`DefaultPhaseBBudget`).
  - Calls `_engine.CaptureReadinessGuard(pid)` immediately upon receiving the event.
  - Evaluates the captured guard function. If the guard returns `false` or throws, the connection is aborted with `TwoPhaseOutcome.ReadinessGuardFailed`.

### 4.3. Async/Await Patterns & Threading Invariants
- **Non-Blocking UI/Protocol Thread**: All network, process management, and storage calls are asynchronous and configured with `.ConfigureAwait(false)` in `RouterSession`.
- **Decoupled Event Invocation**: `RouterSession.TransitionState` calculates whether the state or error code changed under `_stateLock`, assigns the delegate to a local variable `changedHandler`, releases `_stateLock`, and then invokes `changedHandler?.Invoke()`. This prevents deadlocks if event subscribers call back into `RouterSession.State` or `ErrorCode`.
- **Policy Scoping Across Async Boundaries**: Both `RouterBackend` and `RouterSession` utilize `SingBoxRuntimePolicy.EnterScope(EffectivePolicy)`, which preserves the active security policy across async continuation hops via `AsyncLocal<SingBoxRuntimePolicy?>`.

### 4.4. Cancellation & Preemption Mechanics
- **Urgent Preemption**: When `DisconnectAsync` is invoked while `ConnectAsync` is running, `_disconnectStarted` is set to `true` and `_activeConnectCts?.Cancel()` is immediately signalled. This unblocks the waiting `TwoPhaseConnectCoordinator` or `_engine.StartAsync`, releasing `_gate` so `DisconnectAsync` can proceed.
- **Pre-Mutation Cancellation Enforcement**: `RouterBackend.ExecuteMutationAsync` invokes `ct.ThrowIfCancellationRequested()` *before* calling the mutation delegate. This prevents disk I/O or settings corruption if cancellation occurred while queued.

### 4.5. Teardown Guarantees & Deadlines
- **Bounded Engine Stop**: `BoundedTeardown.StopBoundedAsync` runs `_engine.Stop()` in a `Task.Run` worker bounded by a 5-second deadline (`DefaultStopTimeout`).
- **Fail-Closed Engine Process Invariant**: If `StopBoundedAsync` times out or if `_engine.IsRunning` or `_engine.SingBoxPid != null` remains true after stop, `RouterSession` refuses to transition to `Disconnected`. It transitions to `SessionStates.Error` with `ErrorCode = "stop_failed"`. Under no circumstances will `RouterSession` report `disconnected` while an owned sing-box process remains running on the host.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. `SingBoxRuntimePolicy` Scoping & Fail-Closed Enforcement
- Headless execution operates under `SingBoxRuntimePolicy.DefaultProduction` (on Linux), which defaults to strictly `untrusted`.
- The backend enforces fail-closed policy checks: if the runtime policy is unavailable, calls to `ExecuteAsync` map `SingBoxRuntimePolicyException` to `RouterException("unavailable", "VPN runtime is unavailable")`.
- `CanConnect` inspects `SingBoxRuntimePolicy.Current` and returns `false` if `policy.IsAvailable` is false, even if a sing-box binary exists on disk.

### 5.2. Cross-Process Ownership Verification & Foreign Session Protection
- Headless operations must coexist safely with GUI instances (`VPNRouter.App`) or CLI runs without hijacking or killing active tunnels.
- Before `ConnectAsync`, `RouterSession` checks `_ownershipProbe()` (or `LinuxOwnershipGuard.CheckOwnership(_logger)`). If the status is `OwnershipStatus.HeldByAnother`, it refuses to connect and throws `RouterException("conflict", ...)`.
- Before `DisconnectAsync` or `DisposeAsync`, `RouterSession` verifies `_ownsConnection`. If the session does not own the active connection, it logs information and leaves the foreign process untouched. If an owned session attempts disconnect but ownership has since been claimed by another process, disconnect throws `RouterException("conflict", ...)` and refuses to kill the foreign tunnel.

### 5.3. Truthful Capability Gating (Killswitch & DNS Lockdown)
- In accordance with Protocol v1 rules ("Capabilities reflect verified availability, not optimistic platform detection"):
  - `SupportsDnsLockdown`: Returns `false` on Linux because Linux DNS lockdown lacks complete firewall parity with Windows WFP and macOS pf.
  - `SupportsKillSwitch`: Returns `false` on Linux unless an injected nftables checker demonstrates verified root/capability permissions without guessing or assuming `NOPASSWD`.
  - If a user configuration requests `settings.App.DnsLeakLockdown == true` on Linux, `ConnectAsync` and `ApplyAsync` throw `RouterException("unavailable", "DNS leak lockdown is not supported on this platform.")`.
  - If a profile specifies `BlockOnVpnFail == true` when kill-switch is unsupported, connection is refused with `RouterException("unavailable", "Firewall killswitch is not supported without verified privileges.")`.

### 5.4. Input Validation & Parameter Allowlists
- Strict parameter filtering is enforced via `RouterBackend.EnsureAllowedProperties` and `RouterBackend.EnsureEmptyParameters`.
- Any unmapped, unexpected, or misspelled parameter triggers an immediate `RouterException("invalid_argument", "Unexpected parameter '...'")`.
- Revisions are validated against storage CAS via `_storage.ValidateRevision(revProp.GetString())`, preventing stale configuration overwrites.

### 5.5. Secret Sanitization & Error Code Redaction
- Exception messages are processed through `BoundedTeardown.SanitizeExceptionMessage` (which utilizes `CrashReporter.ScrubSecrets`).
- Under no circumstances are raw URIs, passwords, private keys, subscription tokens, or server addresses logged or returned in protocol error responses.
- `RouterException` mappings guarantee fixed, safe strings for all error codes (`conflict`, `unavailable`, `busy`, `stop_failed`, `connect_failed`, `storage_error`, `internal_error`).

## 6. SUSPICIOUS PATTERNS & DEFECT CANDIDATES

### 6.1. Finding 1 (P2 - Medium): Dead `_inFlightRequests` Map in `RouterBackend`
- **Location**: `VPNRouter.Headless/RouterBackend.cs:47, 88-90, 337-358, 423-428`
- **Code**:
  ```csharp
  private readonly ConcurrentDictionary<string, CancellationTokenSource> _inFlightRequests = new();
  ...
  if (method == "cancel")
      return HandleCancel(parameters);
  ...
  private object HandleCancel(JsonElement parameters)
  {
      ...
      if (_inFlightRequests.TryRemove(id, out var cts))
      {
          try { cts.Cancel(); } catch { }
          try { cts.Dispose(); } catch { }
          return new { id, cancelled = true };
      }
      return new { id, cancelled = false };
  }
  ```
- **Analysis**:
  - `RouterBackend` declares `_inFlightRequests`, but `_inFlightRequests.TryAdd(...)` is NEVER called anywhere in the codebase.
  - `RouterBackend.ExecuteAsync` does not take a request ID parameter (its signature is `ExecuteAsync(string method, JsonElement parameters, CancellationToken ct)`).
  - When `ProtocolDispatcher` in module H02 handles client cancellations, it tracks cancellation tokens in its *own* internal dictionary. It never populates `RouterBackend._inFlightRequests`.
  - *Impact*: Any programmatic consumer calling `RouterBackend.ExecuteAsync("cancel", ...)` directly will always receive `{ id, cancelled = false }`. Furthermore, `_inFlightRequests` represents dead allocations and cleanup code in `DisposeAsync`.
  - *Recommendation*: Either remove `_inFlightRequests` from `RouterBackend` and document that cancellation is managed exclusively by `ProtocolDispatcher`, or accept request IDs in `RouterBackend.ExecuteAsync` to register tokens.

### 6.2. Finding 2 (P2 - Medium): Unsynchronized Concurrent Engine Stop During `DisposeAsync`
- **Location**: `VPNRouter.Headless/RouterSession.cs:517-586`
- **Code**:
  ```csharp
  public async ValueTask DisposeAsync()
  {
      ...
      if (_ownsConnection)
      {
          ...
          var stopped = await BoundedTeardown.StopBoundedAsync(_engine, timeout: _stopTimeout, logger: _logger).ConfigureAwait(false);
          ...
      }
      ...
      finally
      {
          ...
          _gate.Dispose();
      }
  }
  ```
- **Analysis**:
  - `DisposeAsync` does NOT acquire `_gate` (`SemaphoreSlim`) before invoking `BoundedTeardown.StopBoundedAsync(_engine)`.
  - If `ConnectAsync` or `ApplyAsync` is currently executing inside `_gate` (e.g. running an asynchronous sing-box apply or probe), `DisposeAsync` concurrently runs `_engine.Stop()`.
  - Furthermore, in the `finally` block at line 584, `_gate.Dispose()` is called unconditionally.
  - When the concurrent `ConnectAsync` or `ApplyAsync` reaches its `finally { _gate.Release(); }` block, calling `Release()` on a disposed `SemaphoreSlim` throws `ObjectDisposedException`.
  - *Recommendation*: `DisposeAsync` should attempt to acquire `_gate` (with a short timeout, e.g. 1 second) or signal an internal disposal CTS before tearing down the engine and disposing the semaphore.

### 6.3. Finding 3 (P3 - Low): Arbitrary Delegate Invocation Inside `_stateLock` in `EvaluateRetainedGuard()`
- **Location**: `VPNRouter.Headless/RouterSession.cs:88-107, 137-152`
- **Code**:
  ```csharp
  public string State
  {
      get
      {
          lock (_stateLock)
          {
              if (_state == SessionStates.Connected && !EvaluateRetainedGuard())
              {
                  return SessionStates.Error;
              }
              ...
          }
      }
  }

  private bool EvaluateRetainedGuard()
  {
      ...
      try
      {
          return _retainedReadinessGuard();
      }
      catch { return false; }
  }
  ```
- **Analysis**:
  - `_retainedReadinessGuard` is an external delegate provided by `ILifecycleEngine` (e.g. `VpnEngineAdapter`).
  - It is invoked synchronously inside `lock (_stateLock)`.
  - If the engine's readiness guard implementation acquires internal locks or performs blocking I/O while another thread is attempting to transition state via `TransitionState` (which also acquires `_stateLock`), there is a risk of lock inversion / lock contention.
  - Furthermore, on every read of `State` and `ErrorCode` (such as in `GetSnapshot()`), `_retainedReadinessGuard()` is invoked twice in rapid succession under lock.
  - *Recommendation*: Cache the guard result for a small duration (e.g. 500ms) or invoke `_retainedReadinessGuard` outside `_stateLock` before validating state under lock.

### 6.4. Finding 4 (P3 - Low): `State` and `ErrorCode` Dynamic Property Read Divergence from `_state`
- **Location**: `VPNRouter.Headless/RouterSession.cs:91-94, 118-121`
- **Code**:
  ```csharp
  if (_state == SessionStates.Connected && !EvaluateRetainedGuard())
  {
      return SessionStates.Error;
  }
  ```
- **Analysis**:
  - When the getter detects that `!EvaluateRetainedGuard()`, it dynamically returns `SessionStates.Error`.
  - However, it does NOT update the underlying `_state` field (it remains `SessionStates.Connected`), nor does it trigger `Changed?.Invoke()`.
  - As a result, listeners subscribed to `Changed` are not notified of the degradation until another operation (or engine event) triggers `TransitionState`.
  - *Recommendation*: If `EvaluateRetainedGuard()` returns false in the property getter, dispatch an asynchronous state transition to formally transition `_state` to `SessionStates.Error` and fire `Changed`.

### 6.5. Finding 5 (P3 - Low): Disconnect Race with Running Long Feature Probes (Bypass of `_busyState`)
- **Location**: `VPNRouter.Headless/RouterBackend.cs:91-95` & `RouterSession.cs:474`
- **Code**:
  ```csharp
  if (method == "disconnect")
  {
      EnsureEmptyParameters(parameters);
      return await HandleDisconnectAsync(ct);
  }
  ```
- **Analysis**:
  - In `RouterBackend`, `disconnect` bypasses `_busyState` so urgent disconnect requests are never blocked by busy errors.
  - In `RouterSession`, `DisconnectAsync` acquires `_gate` (`await _gate.WaitAsync(ct)`).
  - However, feature endpoints like `servers.verify` or `free.verify` hold `_busyState` in `RouterBackend`, but do NOT hold `_gate` in `RouterSession` (only `connect`, `apply`, and `disconnect` hold `_gate`).
  - Therefore, if a client triggers `servers.verify` and then immediately calls `disconnect`, `DisconnectAsync` will stop the live sing-box process while `servers.verify` is still actively probing endpoints through the proxy socket.
  - *Impact*: The verification probe will experience network connection drops and report failures, but process stability is preserved. This is an intentional protocol tradeoff (urgent disconnect prioritizes tearing down network tunnels over ongoing diagnostic tasks).

### 6.6. Finding 6 (P3 - Low): Unhandled Cancellation During Mutation Action in `ExecuteMutationAsync`
- **Location**: `VPNRouter.Headless/RouterBackend.cs:298-300`
- **Code**:
  ```csharp
  // 1. Execute mutation (validates candidate, writes atomic CAS to storage)
  await mutationAction();
  var committedRevision = _storage.CurrentRevision;
  ```
- **Analysis**:
  - `ct.ThrowIfCancellationRequested()` is executed prior to `await mutationAction()`.
  - However, if `mutationAction()` is asynchronous (e.g. `_subscriptionFeature.RefreshAsync` or `_profileFeature.SelectAsync`) and cancellation token `ct` is triggered *during* the execution of `mutationAction()`, `mutationAction()` may throw `OperationCanceledException`.
  - `await mutationAction()` is outside the try/catch block (which only wraps `_session.ApplyAsync`).
  - If `mutationAction()` wrote partial changes to disk or updated files before being cancelled, no guarded rollback runs.
  - *Mitigation in place*: Feature mutations perform internal validation before atomic CAS file replacement in `ConfigStorage`, minimizing partial write risks.

### 7.2. Test Coverage Gaps

1. **Concurrent `DisposeAsync` While `ApplyAsync` In-Flight**:
   - There is no test simulating `RouterSession.DisposeAsync()` being called concurrently while `_engine.ApplyAsync(...)` is suspended or awaiting network/IPC responses, which would exercise the `_gate.Dispose()` race identified in Finding 6.2.
2. **Readiness Guard Lock Inversion Stress Test**:
   - Tests evaluate simple boolean lambdas for readiness guards. There is no stress test where `_retainedReadinessGuard()` attempts to acquire cross-thread synchronization primitives or perform simulated disk/network operations during concurrent `State` reads.
3. **Dead `_inFlightRequests` Map Verification**:
   - While tests verify cancellation through `ProtocolDispatcher`, there is no unit test asserting the behavior of direct calls to `RouterBackend.ExecuteAsync("cancel", ...)` with arbitrary request IDs.
4. **`OnSessionChanged` Event Emission Exception Handling**:
   - `RouterBackend.EmitStateChanged` swallows exceptions from `StateChanged?.Invoke()`. There is no test asserting that an exception thrown by an external subscriber does not disrupt backend operations or corrupt `_busyState`.
5. **Simulated Crash During Two-Phase Phase B Warmup**:
   - While Phase A and Phase B timeouts are tested, an immediate process death (PID exit) occurring precisely between `SingBoxStarted` and `Connected` during Phase B is not explicitly tested.
