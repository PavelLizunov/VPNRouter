> **TL;DR:** The `VPNRouter.Headless` Protocol subsystem provides a hardened, zero-dependency NDJSON RPC server operating over standard I/O for the Omarchy Quattro shell plugin. It strictly enforces strict framing limits (256 KiB pre-accumulation frames, JSON depth â¤ 32, universal duplicate key detection), single-ordinary-operation concurrency with urgent `cancel`/`disconnect` preemption, bounded 8-frame output queue with state event coalescing, and fail-closed 3-second write/flush/disposal stall deadlines to prevent process hangs and secret leaks.

# Exhaustive Code Inventory & Audit: VPNRouter Headless Protocol Layer (Module H02 / Batch B061_H02)

## 1. SUMMARY & PURPOSE

The Headless Protocol layer (`VPNRouter.Headless/Protocol/*`) implements the bidirectional, newline-delimited JSON (NDJSON) communication protocol (Omarchy Protocol v1) between the Omarchy Quattro QML desktop shell plugin (`omarchy-vpnrouter`) and the `VPNRouter` headless daemon.

### Component Roles & Responsibilities
- **`IProtocolHandler.cs`**: Transport-agnostic abstraction defining asynchronous method execution (`ExecuteAsync`) and decoupled backend notifications (`StateChanged`, `ProgressChanged`).
- **`ProtocolConstants.cs`**: Single source of truth for protocol boundaries: Protocol Version 1, 256 KiB input/output frame limits, max JSON depth 32, max queue capacity 8 frames, pagination limit 100, bounded execution deadlines (2â3 seconds), and the 37 known protocol v1 method names.
- **`ProtocolRequest.cs`**: Immutable representation of an incoming validated request (`v`, `id`, `method`, `params`) and strict identifier validator (`1-64` alphanumeric/hyphen characters).
- **`ProtocolFrame.cs`**: Wire-level frame hierarchy (`ProtocolResponseFrame`, `ProtocolStateEventFrame`, `ProtocolProgressEventFrame`) ensuring all serializations are strictly bounded to 256 KiB and exceptions are safely converted to generic error frames.
- **`ProtocolLineReader.cs`**: Streaming chunk-based input reader (8 KiB buffer) enforcing the 256 KiB frame limit *before* memory accumulation to prevent denial-of-service/OOM attacks. Implements non-cancellable OS file descriptor 0 (`Console.OpenStandardInput()`) task isolation.
- **`ProtocolParser.cs`**: Zero-allocation streaming `Utf8JsonReader` parser enforcing strict root schema rules (`v: 1`, non-empty `id`, known `method`, object/null `params`), JSON depth restrictions (â¤ 32), and duplicate key rejection at all nesting depths.
- **`ProtocolOutputQueue.cs`**: Bounded 8-frame output queue with status coalescing, response eviction priority, backpressure pausing, and a 3-second write/flush stall timeout callback.
- **`ProtocolDispatcher.cs`**: Concurrency coordinator ensuring at most one ordinary operation executes at a time (rejecting concurrent requests with `busy`), while providing priority handling for non-blocking urgent controls (`cancel`, `disconnect`).
- **`ProtocolServer.cs`**: Central orchestrator coordinating line reading, parsing, dispatching, queueing, in-flight task tracking, and graceful teardown on EOF, SIGTERM, or write stalls.
- **`RouterBackendHandler.cs`**: Thin adapter implementing `IProtocolHandler` by forwarding calls and events to/from `RouterBackend`.

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Synchronization Primitives
1. **`ProtocolDispatcher._sync` (`object`)**:
   - Guards: `_activeOperationId`, `_activeOperationCts`, and `_activeUrgentCount`.
   - Invariant: Admission decisions are strictly atomic; no task or threadpool invocation occurs under lock.
2. **`ProtocolOutputQueue._sync` (`object`)**:
   - Guards: `_queue` (`List<ProtocolFrame>`), `_queueNotFullTcs`, `_isCompleted`, `_isStalled`, `_inFlightWriteTask`.
   - Invariant: Queue modifications, state coalescing, and backpressure signals are strictly atomic.
3. **`ProtocolOutputQueue._signal` (`SemaphoreSlim(0)`)**:
   - Producer-consumer signal between frame enqueuers and `WriterLoopAsync`.
   - Kept strictly in sync with `_queue.Count`. State event replacement does not increment semaphore permits.
4. **`ProtocolServer.inFlightLock` (`object`)**:
   - Guards `inFlightTasks` (`HashSet<Task>`).
   - Caps total asynchronous in-flight tasks at `1 + MaxUrgentOperations` (5).
5. **`ProtocolServer._teardownSync` (`object`)**:
   - Guards `_teardownTask` ensuring `PerformTeardownAsync()` runs exactly once even if `RunAsync` and `DisposeAsync` race.

### 4.2. Asynchronous Patterns & Deadlock Avoidance
- **Decoupled Synchronous Handlers**: `ProtocolDispatcher` schedules admitted operations via `Task.Run(() => _handler.ExecuteAsync(...))` on the threadpool. This ensures a buggy or blocking synchronous implementation of `ExecuteAsync` (e.g. disk I/O before returning `Task`) never blocks the NDJSON reader loop or prevents urgent `cancel` processing.
- **Console fd 0 OS Sycall Non-Cancellability**: Operating system Console reads (`Console.OpenStandardInput()`) block in native kernel syscalls that cannot be cancelled via managed cancellation tokens. `ProtocolLineReader` starts a read on the stream with `CancellationToken.None` and awaits it via `.WaitAsync(cancellationToken)`. If cancelled, `_isCancelled = true` prevents the buffer from ever being reused, avoiding data corruption upon later unmanaged completion.
- **Per-Frame Output Write Stall Timeout**: Standard output writes (`Console.OpenStandardOutput()`) block in native kernel `write(1)` syscalls when the pipe buffer is full and the peer stops reading. `ProtocolOutputQueue` isolates each write/newline/flush sequence in `Task.Run` with a strict `OutputWriteTimeoutSeconds` (3s) deadline. If a stall occurs, the queue self-terminates and cancels the server.

### 4.3. Teardown Guarantees & Deadlines
Graceful shutdown is initiated when:
1. Standard input signals `EOF`.
2. A cancellation token is fired (Console SIGTERM / SIGINT / SIGQUIT / Ctrl+C).
3. Standard output stalls (> 3s) or breaks (EPIPE / broken pipe).

**Teardown Sequence**:
1. `serverCts.Cancel()` cancels all linked in-flight operation tokens.
2. `_dispatcher.CancelActiveOperation()` signals the active operation CTS immediately.
3. In-flight tasks drain with a bounded deadline of 2 seconds (`InFlightDrainTimeoutSeconds`).
4. Event handlers (`StateChanged`, `ProgressChanged`) are unhooked.
5. Remaining tasks drain with a fallback 1-second deadline.
6. `PerformTeardownAsync` executes:
   - Handler disposal (`_handler.DisposeAsync()`) is launched bounded by 3 seconds (`HandlerDisposalTimeoutSeconds`).
   - Output queue disposal (`_outputQueue.DisposeAsync()`) is launched concurrently (3s drain + 1s cancel).
   - Both tasks run concurrently via `Task.WhenAll`. This ensures uncooperative stdout readers never delay backend engine stop or lock file release.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. Input Validation & DoS Protections
- **Pre-Accumulation Buffer Cap**: Lines exceeding 256 KiB are rejected and drained without memory growth in `ProtocolLineReader`. The buffer is fixed-size (256 KiB) and never reallocated.
- **Nesting Depth Cap**: JSON recursion is restricted to 32 levels (`MaxJsonDepth`). Payloads exceeding depth are rejected with `depth_limit_exceeded`.
- **Universal Duplicate Key Rejection**: `ProtocolParser` validates every object at every nesting depth using a depth-indexed stack of `HashSet<string>`. Any repeated key triggers `duplicate_key`, eliminating parser differential attacks.
- **Root Property Allowlist**: The root request object accepts *only* `v`, `id`, `method`, `params`. Extra fields trigger `invalid_request`.
- **Method Allowlist**: Only the 37 statically recognized methods in `ProtocolConstants.IsKnownMethod` are accepted; unknown methods trigger `unknown_method`.
- **Strict Identifier Sanitization**: Request `id` must be 1 to 64 ASCII characters matching `^[a-zA-Z0-9-]+$`. Special characters, spaces, and control codes are rejected with `invalid_id`.

### 5.2. Output Sanitization & Secret Leak Prevention
- **Generic Safe Error Messages**: `RouterException.SafeMessage` uses a static string mapping for all error codes. Under no circumstances are raw exception messages, inner exceptions, stack traces, host paths, or configuration values reflected back in error frames.
- **Output Frame Cap**: If any response or event frame serializes to more than 256 KiB, `ProtocolFrame.SerializeWithLimit` discards the payload and replaces it with an internal error: `{"v":1,"id":...,"error":{"code":"internal_error","message":"Response size exceeds limit."}}`.
- **Dedicated NDJSON Stdout**: Standard output is reserved strictly for valid newline-delimited protocol JSON frames. Unhandled exceptions in `Program.Main` print to `Console.Error` (`stderr`) and never pollute `stdout`.

### 5.3. Privilege Boundaries
- The headless protocol daemon executes in standard user space (unprivileged, UID > 0).
- Linux headless operates under `SingBoxRuntimePolicy.DefaultProduction` (fail-closed, untrusted unless explicitly verified).
- No network operations or subprocess elevations are permitted in protocol constructors.

## 6. SUSPICIOUS PATTERNS & DEFECT CANDIDATES

### 6.1. Defect Candidate: Dead Code and Inconsistent Intent in `ProtocolConstants.IsUrgentOrReadOnlyMethod`
- **Location**: `VPNRouter.Headless/Protocol/ProtocolConstants.cs:62`
- **Code**:
  ```csharp
  public static bool IsUrgentOrReadOnlyMethod(string method) => method is "cancel" or "disconnect" or "snapshot";
  ```
- **Analysis**:
  - `ProtocolConstants.IsUrgentOrReadOnlyMethod` includes `"snapshot"`.
  - However, `ProtocolDispatcher.DispatchAsync` explicitly treats `"snapshot"` as an ordinary operation:
    ```csharp
    // All non-control methods, including snapshot, are ordinary operations.
    ```
  - `IsUrgentOrReadOnlyMethod` is completely unreferenced across the entire codebase.
  - *Impact*: While the behavior in `ProtocolDispatcher` matches the approved contract (snapshot is ordinary and subject to `busy` rejection), the helper method in `ProtocolConstants` is dead code and creates architectural ambiguity.
  - *Recommendation*: Remove `IsUrgentOrReadOnlyMethod` or align it with the exact set of urgent controls (`cancel`, `disconnect`).

### 6.2. Architecture Tradeoff: Reader Loop Suspends During Output Backpressure
- **Location**: `VPNRouter.Headless/Protocol/ProtocolServer.cs:143` & `ProtocolOutputQueue.cs:71`
- **Code**:
  ```csharp
  if (dispatchTask.IsCompleted)
  {
      ...
      await _outputQueue.EnqueueResponseAsync(response, serverCts.Token).ConfigureAwait(false);
  }
  ```
- **Analysis**:
  - Synchronous responses (such as `busy` errors or fast `cancel` responses) are enqueued directly on the `ProtocolServer` reader loop using `EnqueueResponseAsync`.
  - If the client sends requests rapidly while refusing to read from `stdout`, the 8-frame queue fills with responses.
  - `EnqueueResponseAsync` awaits `_queueNotFullTcs.Task`, which halts the stdin reader loop.
  - *Impact*: While reading is suspended, an urgent `cancel` or `disconnect` frame sent on `stdin` will not be parsed or executed until the client drains the output pipe or the 3-second output write stall deadline fires. As recorded in `plans/omarchy-transport-security-review.md`, this is an accepted tradeoff (no delivery guarantee to a dead transport), but consumers should be aware that unread stdout stalls stdin command processing.

### 6.3. Concurrency Subtlety: Progress Event Stamping Race
- **Location**: `VPNRouter.Headless/Protocol/ProtocolDispatcher.cs:54-65`
- **Code**:
  ```csharp
  string? activeId;
  lock (_sync)
  {
      activeId = _activeOperationId;
  }

  object enriched = progressData;
  if (activeId != null && progressData is not null)
  {
      enriched = EnsureProgressId(progressData, activeId);
  }
  ```
- **Analysis**:
  - `activeId` is read under lock, but the dictionary mutation in `EnsureProgressId` occurs outside lock.
  - If `progressData` is a shared or reused `Dictionary<string, object>` across concurrent operations, modifying `dict["id"] = activeId` can throw `InvalidOperationException` or suffer dictionary mutation races.
  - *Mitigation in place*: Feature handlers currently create fresh dictionaries for each progress report. However, `EnsureProgressId` assumes exclusive ownership of `dict`.

### 6.4. Event Handler Memory Retention on Disposal
- **Location**: `VPNRouter.Headless/Protocol/RouterBackendHandler.cs:28-33`
- **Code**:
  ```csharp
  public async ValueTask DisposeAsync()
  {
      _backend.StateChanged -= OnStateChanged;
      _backend.ProgressChanged -= OnProgressChanged;
      await _backend.DisposeAsync().ConfigureAwait(false);
  }
  ```
- **Analysis**:
  - `RouterBackendHandler` detaches itself from `_backend`, but does not clear its own event invocation lists (`StateChanged = null; ProgressChanged = null;`).
  - *Impact*: Minor; `RouterBackendHandler` is disposed during server teardown immediately prior to process termination.

### 7.2. Test Coverage Gaps
1. **Direct Unit Test for `RouterBackendHandler`**:
   - `RouterBackendHandler` is only exercised indirectly via end-to-end subprocess tests (`TestSubprocessStdoutStallAsync`, etc.). There is no isolated unit test verifying event unsubscription and disposal delegation using a mocked/faked `RouterBackend`.
2. **Progress Frame Drop Under Queue Saturation**:
   - `EnqueueProgressEvent` returning `false` when the 8-frame queue is full is not explicitly asserted in `ProtocolTests.cs`.
3. **CRLF Split Across Chunk Boundary**:
   - `ProtocolLineReader` chunk boundary tests do not explicitly simulate a `\r\n` where `\r` falls on index 8191 and `\n` falls on index 0 of the subsequent chunk read.
4. **Invalid JSON Escape Sequences**:
   - `ProtocolParser` has tests for duplicate keys, depth, and schema fields, but lacks explicit unit tests for malformed UTF-8 byte sequences or truncated JSON escape characters (`\uXXXX`).
