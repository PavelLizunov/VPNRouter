> **TL;DR:** Module C27 (`AutoFailoverEngine`, `HealthCheck`, `HealthMonitor`) provides VPNRouter's core resilience, diagnostic observability, and self-healing lifecycle. It implements intelligent multi-pool failover with intent guards and anti-leak fresh persistence, comprehensive environment and path MTU health verification, crash recovery with exponential backoff and deferred kill-switch lifting, Windows TUN hang/wedge killing, and dynamic Strict DNS fail-open reconciliations. Key defect candidates include synchronous threadpool blocking via `.GetAwaiter().GetResult()` in timer callbacks, long synchronous freezes in `HealthCheck.RunAll()` from sequential ping probing, dead dependency injection of `ConfigSanityCheck` in `AutoFailoverEngine`, and unhandled exception exposure in public event handler invocations.

# Exhaustive Code Inventory & Audit: Core AutoFailoverEngine, HealthCheck, HealthMonitor (Module C27 / Batch B029_C27)

## 1. SUMMARY & PURPOSE

Module C27 sits in `VPNRouter.Core/Services/` and delivers the active fault-tolerance, health diagnostics, and self-healing supervision for the VPNRouter core engine. It comprises three foundational services:
- `VPNRouter.Core/Services/AutoFailoverEngine.cs` (429 lines)
- `VPNRouter.Core/Services/HealthCheck.cs` (898 lines)
- `VPNRouter.Core/Services/HealthMonitor.cs` (1312 lines)

### Subsystem Roles & Responsibilities

1. **`AutoFailoverEngine`**:
   - Manages stateful server failover when the active configuration is diagnosed as dead by `ConfigSanityCheck` or when `HealthMonitor` exhausts its restart ceiling.
   - Enforces a strict candidate selection hierarchy: enabled Subscription servers (priority 1) $\rightarrow$ manual VLESS servers (priority 2).
   - Filters out already-attempted endpoints (`_tried`), the currently failing active server, and known malicious/invalid placeholder fingerprints via `PlaceholderDefense`.
   - Protects user intent: suppresses automatic server swapping in `custom` mode, or in `generated` mode when the user explicitly picked a legitimate manual server despite having active subscriptions (Bug-r10-F / Brat regression fix).
   - Implements two-phase commit: in-memory mutation occurs before invoking the restart delegate (`VpnEngine.StartAsync`), while disk persistence occurs **only after** restart confirmation (`committed == true`).
   - Prevents configuration file pollution (the P1 subscription-leak bug class): disk persistence reloads a fresh copy of `AppSettings` via `ISettingsStore.Load()`, updating only `Vless.ActiveServer` and `App.ActiveSubscriptionServer` without flushing the transient subscription aggregate in `_settings.Vless.Servers`.

2. **`HealthCheck`**:
   - Serves as the central multi-vector diagnostic "doctor" for the CLI (`vpnrouter doctor`) and UI ("Run Health Check").
   - Performs read-only inspection of application configurations (`config.yaml`), profile catalogues (`default.json`), sing-box executables, update receipts, PID/state files (`state.json`), and lock files (`running.lock`).
   - Audits process and service ownership to detect multi-owner conflicts (e.g. Windows Service and GUI running concurrent sing-box instances).
   - Inspects recent sing-box logs (`sing-box.log`) and active JSON configurations (`current.json`) for dial timeouts (`i/o timeout`), Discord DNS stalls, and game traffic patterns (Roblox UDP sensitivity on TCP/VLESS).
   - Executes active ICMP Path MTU discovery on Windows via `ping.exe` with Don't Fragment (`-f`) flags across standard payload thresholds (1240–1420 bytes) to detect MTU black holes.
   - Evaluates True Split kernel driver readiness on Windows by querying `mullvad-split-tunnel`, `AmneziaVPNSplitTunnel`, and `AmneziaVPN-service` via `sc.exe`.

3. **`HealthMonitor`**:
   - Oversees the end-to-end lifecycle of the sing-box process during active VPN connections.
   - Periodically polls sing-box health via `System.Threading.Timer` (30s default, or 5s in `StrictMode`).
   - Integrates with Windows power and session events via `PowerEventListener` to trigger immediate out-of-band health ticks (`ProbeNow()`) upon wake, logon, or session unlock.
   - Executes automatic restart loops upon crash detection (`SingBoxManager.Crashed`) or health check failure with exponential backoff ($5\text{s} \times 2^{\text{attempt}-1}$, capped at `MaxRestartAttempts`).
   - Solves the Windows Wintun black-hole hang condition (W0.1 wedge kill): detects when sing-box is alive in the OS process table but its Clash API has stopped serving, terminating the hung process via `_singBox.KillWedgedForRecovery()` so Windows restores adapter routes.
   - Implements deferred kill-switch lifting (`_deferredBlockRuleDisable`): defers disabling firewall block rules after a full sing-box restart until the Clash API actually confirms the fresh Wintun adapter is routing, eliminating the ~16s startup leak window.
   - Reconciles runtime DNS failovers:
     - `DnsLeakLockdown`: lifts firewall DNS blocks when the tunnel goes down (fail-open) and restores them when healthy.
     - `StrictDns`: dynamically suppresses `dns.final = vpn-dns` to `local-dns` when proxy probe (`/proxies/proxy/delay`) times out, preventing endless loading states during server degradations.
   - Manages debounced process rescans (5-second window) triggered by ETW or polling, hot-reloading routes without full tunnel bounces unless a 60-second cooldown has elapsed.
   - Hands off control to `AutoFailoverEngine` via the `FailoverRequested` event once the restart attempt ceiling is reached.

### 3.1. Auto-Failover State Transition Flow

```
[ConfigSanityCheck / HealthMonitor] 
          │ (Dead config reason)
          ▼
 AutoFailoverEngine.HandleDeadConfigAsync()
          │
          ├── IsIntentCurrent() == false? ───────────► [Abort: Switched=false, Silent]
          │
          ├── ConfigMode == "custom"? ───────────────► [Abort: Custom JSON warning]
          │
          ├── Generated + Legitimate Manual? ────────► [Abort: Manual server warning]
          │
          ├── _tried.Count >= MaxAttempts? ──────────► [Abort: All servers dead warning]
          │
          ▼
 PickNextCandidate()
   ├── 1. SubscriptionPool (Enabled, !Tried, Usable)
   └── 2. ManualPool (!Tried, Usable)
          │
          ├── Candidate is null? ─────────────────────► [Abort: Pool empty warning]
          │
          ▼
 Record oldActive in _tried
 Mutate _settings in-memory (Vless.ActiveServer & App.ActiveSubscriptionServer)
          │
          ▼
 Invoke _restart(ct) [VpnEngine.StartAsync]
          │
          ├── Cancelled / Threw? ─────────────────────► Rollback in-memory settings
          │                                            _tried.Add(failedCandidate)
          │                                            [Abort: Switched=false, Silent]
          │
          ▼ (committed == true)
 Reload fresh settings from disk: _store.Load()
 Update ActiveServer & ActiveSubscriptionServer
 Persist to disk: _store.Save(onDisk)
          │
          ▼
 Return FailoverOutcome(Switched: true, NewActiveServer)
```

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Concurrency Primitives & Invariants

1. **`HealthMonitor._attemptRestartLock` (`object`)**:
   - Serializes concurrent entries to `AttemptRestart()` from two distinct threadpool sources:
     - `OnSingBoxCrashed` (fired from `Process.Exited` on threadpool).
     - `OnHealthTick` (fired from `System.Threading.Timer` on threadpool).
   - Encloses attempt counter increment (`_restartAttempts++`), cancellation token swap (`_restartCts = new()`), and `_failoverRequested` latching.
   - Prevents off-by-one race conditions on `MaxRestartAttempts` and eliminates `CancellationTokenSource` disposal leaks.

2. **`HealthMonitor._onHealthTickInProgress` (`int` Interlocked Gate)**:
   - Guards `OnHealthTick`: `Interlocked.CompareExchange(ref _onHealthTickInProgress, 1, 0) != 0` immediately aborts re-entrant ticks.
   - Critical because `OnHealthTick` performs cross-process HTTP calls (Clash API `/version`, `/proxies/proxy/delay`) that may take up to 3 seconds.
   - Cleared in `finally` via `Interlocked.Exchange(ref _onHealthTickInProgress, 0)`.

3. **`HealthMonitor._deferredBlockRuleDisable` (`int` Interlocked Gate)**:
   - Synchronizes deferred kill-switch lifting across the restart continuation threadpool thread (writer: sets `1`) and the periodic timer tick thread (consumer: checks `1` and clears to `0` via `Interlocked.Exchange`).
   - Ensures kill-switch block rules remain active during TUN initialization and are lifted only once.

4. **Volatile Variables**:
   - `_isStopping` (`volatile bool` in `HealthMonitor`): Set on the UI thread during `Stop()`; read inside threadpool `Task.Delay` continuations (M-9 audit fix) before reviving sing-box.
   - `_strictDnsFailedOver` (`volatile bool` in `HealthMonitor`): Read during config generation to determine DNS override.
   - `_failoverRequested` (`volatile bool` in `HealthMonitor`): Ensures latch visibility across threads.

5. **Atomic Timer Swaps**:
   - `_healthTimer`, `_debounceTimer`, and `_powerListener` use `Interlocked.Exchange(ref field, null)?.Dispose()` during `Stop()` and `OnNewProcessDetected`, preventing race conditions where late callbacks observe partially disposed objects.

### 4.2. Sync-over-Async Call Sites

The module contains multiple synchronous blocking calls on async methods (`.GetAwaiter().GetResult()`):
- `HealthMonitor.cs:594`: `_api.GetVersionAsync().GetAwaiter().GetResult()` (inside `ClashApiResponds`)
- `HealthMonitor.cs:646`: `_api.GetProxyDelayAsync(...).GetAwaiter().GetResult()` (inside `ProxyReachable`)
- `HealthMonitor.cs:1038`: `TunAdapterDiagnostics.TryDisableAdapterViaNetshAsync(...).GetAwaiter().GetResult()`
- `HealthMonitor.cs:1054`: `Task.Delay(500, ct).GetAwaiter().GetResult()`
- `HealthMonitor.cs:1112`: `_api.ReloadConfigAsync(path).GetAwaiter().GetResult()` (inside `TryHotReloadViaApi`)
- `HealthCheck.cs:694`: `proc.StandardOutput.ReadToEndAsync().GetAwaiter().GetResult()` (inside `PingOk`)

*Contextual Safety*: In `HealthMonitor`, these execute on .NET ThreadPool worker threads without a `SynchronizationContext`, which avoids classic GUI dispatch deadlocks. However, they block worker threads for the duration of the HTTP/network timeout (up to 3,000ms), which can contribute to threadpool starvation under sustained high load or slow network conditions.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. Privilege Elevation & External Processes
- **Windows Firewall (`netsh.exe`)**:
  - `HealthMonitor` orchestrates `_firewall.EnableBlockRules()` and `DisableBlockRules()`. On Windows, modifying firewall rules requires elevated administrative privileges (UAC elevation or LocalSystem service execution).
- **Windows Adapter Reset (`netsh.exe`)**:
  - `RunTunOrphanRecoveryCleanup` calls `TunAdapterDiagnostics.TryDisableAdapterViaNetshAsync` to force-disable `VPNRouter-TUN`. Requires administrator rights.
- **Service Control (`sc.exe`)**:
  - `HealthCheck.RunSc` invokes `%SystemRoot%\System32\sc.exe` with `query` and `qc` verbs. `WindowsServiceCommand.GetSystemScPath()` uses `Environment.GetFolderPath(SpecialFolder.System)` to prevent DLL/binary hijacking via search-path manipulation.
- **ICMP Ping (`ping.exe`)**:
  - `HealthCheck.PingOk` executes system `ping.exe` with strict argument validation (`-n 1 -w 1000 -f -l <int> 8.8.8.8`).
- **Linux Privilege Boundary**:
  - `HealthCheck.RunAll()` audits Linux execution context: checks `LinuxRuntimeEnvironment.GetTunPrivilegeBlocker()` and `ResolvePkexec()`. Flags AppImage/bubblewrap sandbox restrictions where `TUNSETIFF` is blocked.
  - `HealthMonitor.OnSingBoxCrashed` detects `_singBox.LastCrashWasLinuxTunPermissionFailure` and permanently disarms auto-restart (`_shouldBeRunning = false`) to avoid infinite restart loops when root privileges are missing.

### 5.2. File System Boundaries & Redaction
- **Paths**:
  - All configuration and log paths route through `AppPaths` (`%ProgramData%\VPNRouter` on Windows, `~/.config/vpnrouter` on Linux, `~/Library/Application Support/VPNRouter` on macOS).
  - `AutoFailoverEngine` persists strictly through `ISettingsStore` (backed by `SettingsLoader`), which performs atomic `.tmp` writes with 0600 POSIX permissions.
- **Data Redaction & Sanitization**:
  - `AutoFailoverEngine` logs server names and `server:port` endpoints, never passwords, UUIDs, or Reality private keys.
  - In `HealthCheck.cs`, proxy endpoints extracted from `current.json` for timeout analysis redact credentials, extracting only `server:port`.
  - In `HealthMonitor.cs`, Clash API bearer secret (`clashApiSecret`) is passed in memory to `ClashSingBoxApi` and omitted from diagnostic logs.

## 6. SUSPICIOUS PATTERNS / DEFECT CANDIDATES

### 6.1. Defect Candidate 1: Unused Dependency Injection in `AutoFailoverEngine`
- **Location**: `VPNRouter.Core/Services/AutoFailoverEngine.cs:36, 75`
- **Pattern**:
  ```csharp
  private readonly ConfigSanityCheck _sanity;
  ...
  _sanity = sanity ?? throw new ArgumentNullException(nameof(sanity));
  ```
- **Evidence**: `_sanity` is stored in a private field and guarded by null checks, but is **never referenced** anywhere in `AutoFailoverEngine.cs`.
- **Impact**: Dead dependency. Callers are forced to instantiate and supply `ConfigSanityCheck` even though `AutoFailoverEngine` never uses it.

### 6.2. Defect Candidate 2: Heavy Synchronous Thread Freeze in `HealthCheck.RunAll()`
- **Location**: `VPNRouter.Core/Services/HealthCheck.cs:653-664, 667-698`
- **Pattern**:
  ```csharp
  foreach (var payload in new[] { 1420, 1400, 1380, 1360, 1350, 1340, 1332, 1320, 1310, 1300, 1280, 1260, 1240 })
  {
      if (PingOk(payload)) return new(payload, false);
  }
  ```
- **Evidence**: `ProbePathMtuPayload()` executes sequential `ping.exe` processes. Each invocation has a 1,000ms wait (`-w 1000`) and a 2,000ms `WaitForExit(2000)`. If ICMP is dropped by an ISP or local firewall, the method tests plain ping (up to 2s) + up to 13 payloads (up to 26s).
- **Impact**: Calling `HealthCheck.RunAll()` from the UI thread completely freezes the GUI for up to 28 seconds. Must always be offloaded to `Task.Run`.

### 6.3. Defect Candidate 3: Unhandled Exception Exposure in Public Event Invocations
- **Location**: `VPNRouter.Core/Services/HealthMonitor.cs:533, 720, 736, 854, 858, 989`
- **Pattern**:
  ```csharp
  VpnStarted?.Invoke(this, EventArgs.Empty);
  StrictDnsFailoverChanged?.Invoke(this, failOpen);
  VpnStopped?.Invoke(this, EventArgs.Empty);
  FailoverRequested?.Invoke(this, "max restart attempts reached");
  RestartAttempted?.Invoke(this, attempt);
  ```
- **Evidence**: Events are raised directly on threadpool threads (inside timer callbacks or `Task.Delay.ContinueWith`).
- **Impact**: If any external subscriber (UI ViewModel, notification handler) throws an unhandled exception, it terminates the process immediately via the threadpool unhandled exception handler.

### 6.4. Defect Candidate 4: Potential Deadlock / Buffer Hang in `HealthCheck.RunSc`
- **Location**: `VPNRouter.Core/Services/HealthCheck.cs:842`
- **Pattern**:
  ```csharp
  var output = proc.StandardOutput.ReadToEnd() + proc.StandardError.ReadToEnd();
  proc.WaitForExit(3000);
  ```
- **Evidence**: Synchronously reading standard output to end before reading standard error.
- **Impact**: If a queried service or tool outputs sufficient data to fill the standard error pipe buffer (typically 4KB) before standard output closes, `sc.exe` blocks writing to stderr while the C# process blocks reading stdout, creating an OS pipe deadlock. While `sc.exe` output is typically small, this is a dangerous I/O antipattern.

### 6.5. Defect Candidate 5: ThreadPool Starvation Risk via Sync-Over-Async in `HealthMonitor`
- **Location**: `VPNRouter.Core/Services/HealthMonitor.cs:594, 646, 1112`
- **Pattern**: Synchronous `.GetAwaiter().GetResult()` invocations on `ISingBoxApi` methods inside periodic timer ticks.
- **Evidence**: `ClashApiResponds` and `ProxyReachable` synchronously block the threadpool timer thread for up to 3,000ms.
- **Impact**: When network interfaces are wedged or sing-box is unresponsive, timer callbacks stall threadpool threads, causing thread pool growth and delayed execution of other tasks.
