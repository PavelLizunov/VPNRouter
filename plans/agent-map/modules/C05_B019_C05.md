# Module C05 Audit Report — Core VpnEngine and StartupPipeline (Batch B019_C05)

## 1. SUMMARY & PURPOSE

Module `C05` (`StartupPipeline.cs` and `VpnEngine.cs`) forms the core VPN connection orchestration and session lifecycle management spine in `VPNRouter.Core.Services`.

- **`StartupPipeline.cs` (1,444 LOC)**: Extracted in Phase 3C as the single source of truth for the 8-phase VPN startup sequence (`Preflight` -> `ResolveProfile` / `ResolveServers` -> `ScanProcesses` -> `GenerateConfig` -> `PreStartChecks` -> `DeployAndSetupFirewall` -> `StartSingBox` -> `StartMonitors`). It operates in three modes (`ColdStart`, `HotReload`, and `AutoFailover`) and interacts with `VpnEngine` exclusively through the `IStartupHost` / `StartupHostInternal` callback surface rather than mutating engine fields directly.
- **`VpnEngine.cs` (1,908 LOC)**: Owns the stateful runtime session (`_singBox`, `_healthMonitor`, `_etw`, `_firewall`, `_slipstream`, `_splitDriver`, `_sanityCheck`, `_failover`, `_connHealth`, `_connHealthStream`), lifecycle concurrency gates (`_lifecycleGate`, `_sessionCts`, `_probeCts`, `_failoverGeneration`), public API entry points (`StartAsync`, `ApplyAsync`, `Stop`, `Dispose`, `RestartTrueSplitAsync`), structural change detection on hot-reload, true-split kernel driver lifecycle hooks, Unix DNS hardening, profile source resolution, user customization merging, and the private nested `VpnEngineStartupHost` adapter.

## 3. DATA FLOWS & STATE MACHINES

### 3.1 ColdStart Data Flow (`VpnEngine.StartAsync` -> `StartupPipeline.ExecuteAsync`)

1. **Authorization & Gate Acquisition**: `StartAsync` checks `SingBoxRuntimePolicy.Authorize(Start)`, acquires `_lifecycleGate`, checks `HasLiveOrStartingSingBox()`, creates `_sessionCts = CreateLinkedTokenSource(ct)`, and calls `ResetFailoverContext(settings)` (incrementing `_failoverGeneration`).
2. **Pre-Pipeline Reset**: `StartAsyncInternal` sets `_skipVpnConflictCheck`, `_warmupConfirmed = false`, `_postStartPhase = false`, and runs `_splitDriver.SweepStaleStateAsync(ct)`.
3. **Phase 0 (Preflight)**: Ensures `AppPaths` directories, checks `ConflictingVpnDetector` (throws `ConflictingVpnException` on hard conflicts, logs warning on coexisting WG/AWG), flushes DNS if `FlushDnsOnStart`, and downloads GeoIP/GeoSite files if `BypassRussianTraffic` is enabled.
4. **Phases 1 & 2 (Profile & Server Resolution)**:
   - Custom mode: reads and validates custom JSON file, extracts server address.
   - Generated mode: validates `AppSettings` invariants (`LeakProtection.ValidateAppSettings`), mutates `settings.Vless.Servers` in-place via `VlessServersResolver.Resolve`, sets `ActiveServerAddress`.
   - Quarantines stale user `default.json` catalogue, loads `ProfileCollection` from prioritized sources, merges `CustomGroupApps` and `CustomCategories` (unless `SafeMode.Enabled`), resolves `activeProfile` (self-healing `ActiveProfile` on disk via fresh load/save if partial profile names were missing), adds `CustomApps`, and strips `ExcludedApps`.
5. **Phase 3 (Process Scan & Subnet Auto-Exclusion)**:
   - Runs `_host.Scanner.ScanForProfile(profile)` with a 30s timeout; falls back to empty `ScanResult` on timeout/error.
   - Runs `NetworkInterfaceDetector.DetectWireGuardSubnets` and overwrites `settings.Tun.AutoDetectedExcludeAddress` (runtime-only, never persisted).
6. **Phase 3.5 (RB1 Naive UDP Probe)**: If an active server uses Naive protocol, probes UDP-capable sibling servers (3s timeout) to produce an `isServerAlive` filter predicate.
7. **Phase 4 (Config Generation)**: Produces final `sing-box` JSON via `CustomConfigInjector.Inject` (custom mode) or `ConfigPipeline.Generate` in `Strict` validation mode (generated mode).
8. **Phase 5 (PreStartChecks / F-E)**: Runs `ConfigSanityCheck.CheckBeforeStart(configJson)`. If dead, runs `AutoFailoverEngine.HandleDeadConfigAsync`, which swaps the active server and re-enters `StartAsyncInternal`. When switched, outer `ExecuteAsync` returns `StartupResult(Success: true, EarlyReturn: true)` so the outer frame exits cleanly without double-starting.
9. **Phase 6 & 6.5 (Binary Deploy, Firewall & DNS-Tunnel Transport)**:
   - Deploys bundled `sing-box` if missing or file size differs (skipped when `EffectivePolicy != null`).
   - Instantiates `IFirewallManager` and creates disabled block rules if `profile.BlockOnVpnFail && firewall is not ICommittedFirewallConfig`.
   - If active server protocol is `dns-tunnel`, starts `SlipstreamManager` and verifies local port listening within 5s.
10. **Phase 7 (Start `sing-box`, Warmup & Post-Start Probe)**:
    - Starts `SingBoxManager.StartWithJson(configJson)` (`OnSingBoxStarted` transitions `_postStartPhase = true`).
    - Polls `IsRunning()` every 500ms up to 5s.
    - Spawns background warmup probe (`ScheduleWarmupProbe`, 15 attempts x 1s to `https://www.gstatic.com/generate_204`) and post-start Clash API probe (`SchedulePostStartProbe`, 15s delay).
    - Updates `ICommittedFirewallConfig.UpdateCommittedConfig` if supported by the platform firewall manager.
11. **Phase 8 & Post-Pipeline Hooks**:
    - Starts `IProcessMonitor` (ETW) and `HealthMonitor`, applies Windows DNS hardening (`_dnsHardening.Apply`).
    - Back in `StartAsyncInternal`: computes `ActiveAppRoutingFingerprint`, applies Unix DNS hardening (`_unixDns.Apply`) if `DnsLeakLockdown` is set, and engages the Windows true-split kernel driver (`TryEngageSplitDriverAsync`).

### 3.2 HotReload Data Flow (`VpnEngine.ApplyAsync`)

1. Acquires `_lifecycleGate`, verifies `_sessionCts` is active and `_singBox.IsRunning()`.
2. Snapshots current live baseline (`oldConfigMode`, `oldRoutingMode`, `oldTunFingerprint`, `oldAppRoutingFingerprint`, `oldServerAddress`, `oldProfile`, `oldScanResult`).
3. Runs `StartupPipeline.ExecuteAsync` with `StartupMode.HotReload` (executes Phases 1–4 only; skips Phase 0 and Phases 5–8) and receives candidate `configJson` and `Profile`.
4. Computes structural change flags via `DetectStructuralChanges`. Escalates `forceRestart = true` if any of `ConfigMode`, `RoutingMode`, `TunFingerprint`, or `AppRoutingFingerprint` changed.
5. Attempts `_singBox.TryReloadConfigJson(configJson)` if `!forceRestart`, otherwise calls `_singBox.ReloadConfigJsonWithResult(configJson, forceRestart)`.
6. If reload/restart fails, restores the snapshotted live baseline and returns `false`.
7. If reload/restart succeeds, commits new metadata, calls `ResetFailoverContext(settings)`, updates `ICommittedFirewallConfig`, and reconciles the true-split driver via `TryEngageSplitDriverAsync(settings, CancellationToken.None)`.

## 4. CONCURRENCY, LOCKS & LIFECYCLE

- **Primary Synchronization Primitive (`_lifecycleGate`)**: `SemaphoreSlim(1, 1)` on `VpnEngine` (line 70) serializes all top-level state transitions:
  - `StartAsync` (line 358)
  - `ApplyAsync` (line 750)
  - `Stop` (line 982)
  - `ExecuteProbeFailoverRestartAsync` (line 645)
- **Non-Reentrant Gate Avoidance (`_postStartPhase`)**: Because `SemaphoreSlim` is not re-entrant, a pre-start failover triggered inside Phase 5 of `StartupPipeline` runs while `StartAsync` already holds `_lifecycleGate`. `ExecuteFailoverRestartAsync` inspects `volatile bool _postStartPhase` (line 602):
  - When `_postStartPhase == false` (pre-start), it calls `StartAsyncInternal` directly without re-acquiring `_lifecycleGate`.
  - When `_postStartPhase == true` (set by `OnSingBoxStarted` in Phase 7), it routes through `ExecuteProbeFailoverRestartAsync`, which acquires `_lifecycleGate`.
- **Two-Tier Cancellation (`_sessionCts` vs `_probeCts`)**:
  - `_sessionCts` represents user session intent. Created in `StartAsync` (line 371) and cancelled at the very start of `Stop()` (line 976) *before* waiting on `_lifecycleGate`. This guarantees that an in-flight failover restart holding `_lifecycleGate` observes cancellation via `_sessionCts.Token` and aborts instead of resurrecting the VPN after user disconnect.
  - `_probeCts` is linked to the startup token and cancelled in `TeardownInternal()` (line 1027). Crucially, `ExecuteProbeFailoverRestartAsync` ignores `probeCt` during bring-up and uses `_sessionCts.Token` (line 664) so `TeardownInternal()` cancelling `_probeCts` does not self-cancel the failover restart.
- **Generation Fencing (`_failoverGeneration`)**: Incremented on every `ResetFailoverContext` (called in `StartAsync` and `ApplyGatedAsync`) and `Stop()`. Checked by `ExecuteFailoverRestartAsync`, `ExecuteProbeFailoverRestartAsync`, `AutoFailoverEngine.IsCurrentIntent`, `VpnEngineStartupHost.OnConnected`, and `CaptureReadinessGuard` to fence off stale background callbacks from prior sessions or configs.
- **Teardown Ordering (`Stop` & `TeardownInternal`)**:
  1. `Stop()` cancels `_sessionCts` and calls `_healthMonitor?.Stop()` *before* `_lifecycleGate.Wait()` (lines 976–981) so the 30s health timer cannot trigger a false restart while waiting for the gate.
  2. Inside `TeardownInternal()` (lines 1027–1081): `_probeCts?.Cancel()` -> `_warmupConfirmed = false` -> `_healthMonitor?.Dispose()` -> `_singBox?.Dispose()` -> `_slipstream?.Dispose()` -> `_splitDriver?.DisengageAsync().Wait(5s)` -> `_connHealthStream?.Stop()/Dispose()` -> `_dnsHardening.Restore()` -> `_unixDns.Restore()` -> `_etw?.Dispose()` -> `_firewall?.DisableBlockRules()/DeleteAllRules()/Dispose()`.

## 5. SECURITY & PRIVILEGE BOUNDARIES

- **Runtime Execution Policy (`SingBoxRuntimePolicy`)**: Both `VpnEngine.StartAsync`, `VpnEngine.ApplyAsync`, `VpnEngine.Stop`, `VpnEngine.TeardownInternal`, and `StartupPipeline.ExecuteAsync` enter `SingBoxRuntimePolicy.EnterScope(EffectivePolicy)` and enforce `policy.Authorize(SingBoxRuntimeOperation.Start)` on start/apply paths. When `EffectivePolicy != null` (restricted/headless policy), `StartupPipeline.DeploySingBoxBinary` (line 1129) explicitly skips copying the bundled `sing-box` binary over the target path.
- **Binary Deployment & Path Expansion**: `DeploySingBoxBinary` (lines 1135–1156) expands environment variables in `settings.SingBox.ExecutablePath` on Windows (`AppPaths.SingBoxExePath` on Unix) and overwrites the target binary whenever the bundled binary in `AppContext.BaseDirectory` has a different byte length (`installedSize != bundledSize`). No cryptographic hash or signature comparison is performed during this size-based copy check (tracked in `OPEN-DEFECTS.md` as `OMARCHY-RUNTIME-TRUST-CONTRACT`).
- **Pre-Generation & Post-Generation Leak Validation**:
  - Phase 1 validates `AppSettings` via `LeakProtection.ValidateAppSettings(settings)` (line 646) before `VlessServersResolver` mutates `settings.Vless.Servers`.
  - Phase 4 runs `ConfigPipeline.Generate` with `ConfigPipeline.ValidationMode.Strict` (line 1032) or validates custom JSON via `CustomConfigInjector.Validate` (line 629).
- **Kill-Switch Arming Invariant**:
  - For legacy `IFirewallManager` implementations (`firewall is not ICommittedFirewallConfig`), Phase 6 passes explicit `isFullTunnel` to `firewall.CreateBlockRules(scanResult.ProcessNames, isFullTunnel)` (lines 1106–1115) so an empty `ProcessNames` list in split mode (e.g., after a 30s scan timeout) never arms a global host kill-switch on Linux/macOS.
  - For `ICommittedFirewallConfig` implementations, `UpdateCommittedConfig(configJson, profile.BlockOnVpnFail && isFullTunnel)` is called in Phase 7 after `sing-box` starts (lines 492–498) and after hot-reload commits in `ApplyGatedAsync` (lines 906, 936, 957–965).
- **Deferred DNS Lockdown (BR-7)**: Windows firewall DNS port lockdown (`_dnsHardening.EnableLockdownIfConfigured`) is deferred until `ScheduleWarmupProbe` confirms `gstatic.com` reachability through the tunnel (line 1322), preventing a bootstrap deadlock where DNS queries needed to warm up the tunnel are blocked on physical NICs before the TUN route is active. If warmup fails all 15 attempts, the lockdown is left unarmed (fail-open for internet availability, logged at `Warning` level on lines 1337–1341).
- **Clash API Secret Propagation**: Both `HealthMonitor` (line 1389), `ConfigSanityCheck.ProbeAsync` (line 1870), and `ClashLogStream` (line 1226) receive `settings.SingBox.ClashApiSecret`, and `ClashLogStream` is bound strictly to loopback (`http://127.0.0.1:{clashPort}`, line 1222).

## 6. SUSPICIOUS PATTERNS / DEFECT CANDIDATES

1. **`SafeMode.Enabled` Semantic Mismatch Between Profile Resolution and `ConfigGenerator` (`StartupPipeline.cs:710–728` vs `GenerateConfigPhase:1028`)**:
   - **Evidence**: When `SafeMode.Enabled` is `true`, `ResolveProfileAndServersAsync` sets local `isFullTunnel = true` (line 713) and creates `activeProfile = new Profile { Name = "FullTunnel", DnsMode = "vpn_only", ... }` (line 727), skipping process rules. However, `settings.App.RoutingMode` is *not* mutated, and Phase 4 (`ConfigPipeline.Generate`) and Phase 7 (`committedFirewall.UpdateCommittedConfig` at line 495) read `settings.App.RoutingMode ?? "split"` directly. If `settings.App.RoutingMode` is `"split"`, `ConfigGenerator` generates a split-tunnel config with an empty process list (`route.final = "direct"`), and `isFullTunnel` at line 495 evaluates to `false`. (Corresponds to `NIGHT-FOLLOWUP-02` in `plans/OPEN-DEFECTS.md`).
2. **`RestartTrueSplitAsync` Does Not Acquire `_lifecycleGate` (`VpnEngine.cs:583–584`)**:
   - **Evidence**: `public Task RestartTrueSplitAsync(AppSettings settings, CancellationToken ct = default) => TryEngageSplitDriverAsync(settings, ct);` invokes `TryEngageSplitDriverAsync` directly without acquiring `_lifecycleGate` or checking `_sessionCts.IsCancellationRequested`. If called concurrently with `Stop()` or `ApplyAsync()`, it can race with `TeardownInternal()`'s `_splitDriver.DisengageAsync()` (line 1048) and leave the kernel split-tunnel driver engaged after the VPN has stopped, or mutate `CurrentTrueSplitState` concurrently.
3. **Unawaited Fire-and-Forget Warmup Task Not Tracked by Dedicated CTS (`StartupPipeline.cs:1250–1352`)**:
   - **Evidence**: `ScheduleWarmupProbe` launches `_ = Task.Run(async () => ... , ct)` using the `ct` passed into `ExecuteAsync` (which is `_sessionCts.Token` from `StartAsync`). Unlike `SchedulePostStartProbe` (which links `_probeCts` cancelled in `TeardownInternal()`), `ScheduleWarmupProbe` does not link to `_probeCts`. During a post-start failover restart (`ExecuteProbeFailoverRestartAsync`), `TeardownInternal()` cancels `_probeCts` (line 1027) but does *not* cancel `_sessionCts`. Consequently, the warmup probe task from the *first* (failed) server keeps running for up to 15 seconds concurrently with the replacement server's startup. While `VpnEngineStartupHost.OnConnected` (lines 1658–1667) guards against stale `_singBoxManager` and `_startedHandle`, the old task continues to emit `_host.OnStatus($"Connected (PID {pidSnapshot})")` (lines 1293 and 1342) and can call `_dnsHardening.EnableLockdownIfConfigured` (line 1322) out of band because `OnStatus` and `_dnsHardening` in `ScheduleWarmupProbe` are called *outside* `OnConnected`'s staleness check!
4. **Size-Only Binary Deployment Check (`StartupPipeline.cs:1143–1156`)**:
   - **Evidence**: `DeploySingBoxBinary` decides whether to overwrite the installed `sing-box` binary solely by comparing `new FileInfo(exePath).Length != new FileInfo(bundledPath).Length`. A modified or same-size binary of identical byte length will not be refreshed, and no digest check is performed (`OMARCHY-RUNTIME-TRUST-CONTRACT`).
5. **Timed-Out Process Scan Continues Running in Background (`StartupPipeline.cs:862–888`)**:
   - **Evidence**: When ` _host.Scanner.ScanForProfile(profile)` exceeds 30 seconds in `ScanProcessesPhaseAsync`, `Task.WhenAny` returns `timeoutTask` and the pipeline proceeds with an empty `ScanResult`, while `scanTask` continues executing on a ThreadPool thread because `IProcessScanner.ScanForProfile(Profile)` is synchronous and accepts no `CancellationToken`.
