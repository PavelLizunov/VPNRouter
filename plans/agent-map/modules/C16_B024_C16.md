## 1. SUMMARY & PURPOSE

Module C16 serves as the primary network defense-in-depth and leak-prevention layer for VPNRouter. While traffic routing during normal operation is handled by the sing-box TUN adapter, this module provides fail-closed guarantees during connection setup, configuration mutation, daemon crash windows, and abnormal process termination.

### Component Roles & Responsibilities

1. **`FirewallManager.cs` (`IFirewallManager`, `IDisposable`)**:
   - **Per-Process Kill-Switch (`block_on_vpn_fail`)**: Operates on the key architectural insight that firewall rules are *not* required during normal VPN execution because the sing-box TUN interface captures all targeted traffic. It pre-creates outbound block rules in a **DISABLED** state at VPN connect. When `HealthMonitor` detects a sing-box crash, it rapidly flips the rules to **ENABLED** to prevent direct cleartext egress over physical adapters. Upon sing-box restart, rules are disabled; on clean shutdown, they are deleted.
   - **Late Resolution of Off-PATH Apps**: Re-resolves executable paths on crash for applications that were launched after VPN connection was established or reside outside standard PATH (e.g., Discord in `%LocalAppData%`, Telegram), preventing fail-open kill-switch bypasses.
   - **DNS Leak Lockdown (Wave 39 / BR-8 / BR-9 / r10 #6)**: Static platform helpers that install Windows Firewall rules blocking outbound UDP/53, TCP/53, and TCP/853 on all interfaces, while allowing loopback (`127.0.0.1`) and scoping IPv4 blocks to the mathematical *complement* of the TUN CIDR range (`ComputeBlockExclusionRange`). Also enforces parallel public IPv6 blocks on `2000::/3`.
   - **Orphan Cleanup (`CleanupOrphanedRules` / `TryCleanupOrphanedRulesSafe`)**: Enumerates and purges stale VPNRouter firewall rules left behind by abnormal termination, power loss, or ungraceful crashes on application startup and `AppDomain.ProcessExit`.
   - **Process Execution & Argument Marshalling**: Bridges commands to `netsh.exe` via `IProcessRunner` using a custom quote-aware argument splitter (`SplitShellArgs`).

2. **`LeakProtection.cs` (`ValidationResult`, `LeakProtection`)**:
   - **Pre-generation Model Validation (`ValidateAppSettings`)**: Inspects `AppSettings` before sing-box JSON generation to catch invalid combinations of `ConfigMode`, `Subscriptions`, and `Vless.Servers`. Defends against silent fail-to-direct leaks (e.g., F-12 parity audit regression where empty proxy outbounds fall through to direct routing).
   - **Pre-flight Config Sanity Validation (`ValidateConfig`)**: Analyzes fully instantiated `SingBoxConfig` structures prior to engine launch or hot-reload. Validates:
     - Strict `ipv4_only` DNS strategy (defeats dual-stack IPv6 DNS leaks).
     - TUN inbound configuration (`strict_route == false`, non-empty address).
     - Complete mapping between routed process rules and DNS resolution rules.
     - Outbound server scope checking (`ValidateOutboundServersScopeAware`): Ensures proxy outbounds match allowed subscription or manual server pools (defeating stas-class placeholder override leaks).
     - Protocol schema conformance: VLESS, Hysteria2, TUIC, Shadowsocks, Shadowsocks-2022 multi-key length validation, and AmneziaWG (AWG) endpoint peer schemas.
     - Polarity alignment: Verifies `Route.Final` matches the expected direction for full tunnel ("proxy") vs split tunnel ("direct").

### 3.2. DNS Leak Lockdown Flow & IP Exclusion Range Math

When `WindowsDnsHardening` activates `EnableDnsLockdownAsync`:
1. `NormalizeTunAllowIp(tunCidr)` parses `settings.Tun.Ipv4Address` (e.g., `"172.19.0.1/30"`), masks host bits, and derives `"172.19.0.0/30"`.
2. `ComputeBlockExclusionRange("172.19.0.0/30")` computes:
   - Network integer: `172.19.0.0` (`0xAC130000`)
   - Broadcast integer: `172.19.0.3` (`0xAC130003`)
   - Lower complement: `0.0.0.0` to `172.18.255.255`
   - Upper complement: `172.19.0.4` to `255.255.255.255`
   - Emits: `"0.0.0.0-172.18.255.255,172.19.0.4-255.255.255.255"`
3. Injected Netsh rules:
   - Allow Rule: `remoteip=127.0.0.1 protocol=UDP remoteport=53`
   - IPv4 Block Rules: Scoped with `remoteip={exclusionRange}` across UDP/53, TCP/53, and TCP/853.
   - IPv6 Block Rules: Scoped with `remoteip=2000::/3` across UDP/53, TCP/53, and TCP/853.

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Concurrency Analysis
- **`FirewallManager` Thread Safety**:
  - `FirewallManager` is **not thread-safe**.
  - `_managedRules` (`List<string>`) and `_requestedNames` (`List<string>`) are unsynchronized mutable collections. Concurrent calls across `CreateBlockRules`, `EnableBlockRules`, `DisableBlockRules`, or `DeleteAllRules` (e.g., a race between `HealthMonitor` detecting a crash and `VpnEngine` executing `Stop`) can throw `InvalidOperationException` or corrupt collection state.
  - The static test seam `Runner` (`internal static IProcessRunner Runner { get; set; }`) is shared across all instances. If tests or background workers mutate `Runner` concurrently, execution routes can cross-contaminate.
- **`LeakProtection` Thread Safety**:
  - Fully static and stateless. Safe for concurrent invocations across arbitrary threads, provided caller-supplied `AppSettings` and `SingBoxConfig` instances are not concurrently mutated during inspection.

### 4.2. Synchronous Blocking on Async Paths (Sync-over-Async)
- In `FirewallManager.cs`:
  - `RunNetsh`: Calls `_runner.RunAsync(...).GetAwaiter().GetResult()` synchronously, blocking the caller for up to `NetshTimeoutMs` (5,000 ms).
  - `FindRulesByPrefixes`: Calls `_runner.RunAsync(...).GetAwaiter().GetResult()` synchronously, blocking the caller for up to 10,000 ms.
  - `RunNetshStatic`: Calls `Runner.RunAsync(...).GetAwaiter().GetResult()` synchronously inside `Task.Run` with a 3,000 ms timeout.
- *Impact*: In UI threads or thread-pool constrained environments, these synchronous blocks risk thread pool starvation. When multiple rules are processed sequentially in loops, total blocking time scales linearly with rule count.

### 4.3. Cancellation Token Disassociation
- `EnableDnsLockdownAsync` and `DisableDnsLockdownAsync` accept a `CancellationToken ct`.
- They construct `timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct)` and set a 5-second deadline.
- They invoke `Task.Run(..., timeoutCts.Token)`.
- **Defect**: The delegate passed to `Task.Run` executes 7 (in enable) or 9 (in disable) sequential blocking calls to `RunNetshStatic`. The cancellation token is *never passed* to `RunNetshStatic` and is *never checked* between loop iterations.
- If the 5-second timeout expires, `Task.Run` throws `OperationCanceledException` to the awaiter, but the background thread-pool worker *continues executing all remaining netsh commands to completion*.

### 4.4. Teardown Guarantees
- `FirewallManager.Dispose()` calls `DeleteAllRules()`, protected by `if (_disposed) return; _disposed = true;`.
- `TryCleanupOrphanedRulesSafe()` creates a temporary `FirewallManager` and invokes `CleanupOrphanedRules()`, swallowing all exceptions. This is hooked into `AppDomain.ProcessExit` and startup paths in `VPNRouter.App` and `VPNRouter.Service`.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. Elevation Requirements
- Modifying the Windows Firewall via `netsh advfirewall` requires elevated privileges (Administrator / High Integrity Level / `SeSecurityPrivilege`).
- On non-elevated executions, `netsh` exits with code 1 (`"The requested operation requires elevation"`). `FirewallManager` logs warnings on non-zero exit codes but does not throw. Consequently, in non-elevated contexts, the firewall manager **fails open**.

### 5.2. Cross-Session Process Path Resolution
- When running as a Windows Service in Session 0, calling standard .NET `Process.MainModule.FileName` on user-session processes returns `null` due to WOW64 and session isolation boundaries.
- `FirewallManager` invokes `ProcessImagePath.ResolveRunningPath(processName)` which uses native P/Invoke `QueryFullProcessImageName` with `PROCESS_QUERY_LIMITED_INFORMATION`. This succeeds across Session 0 -> User Session boundaries, closing a critical fail-open vulnerability where the Windows Service previously generated zero firewall rules.

### 5.3. Shell Argument Splitting & Injection Hardening
- `SplitShellArgs(string arguments)` implements custom quote-aware splitting to pass arguments safely via `ProcessStartInfo.ArgumentList`.
- Outer double quotes surrounding values (e.g., `program="..."` or `description="..."`) are stripped so that .NET's runtime argument serializer can re-quote them safely for the Windows kernel (`CreateProcessW`).
- Limitation: It does not support escape sequences (`\"`). If a process path or rule name contains embedded double quotes, tokenization will split unpredictably.

### 5.4. Scope-Aware Leak Prevention (Stas-Class Defenses)
- Stas-class leaks occur when a user switches to subscription mode or generated mode, but legacy `vless.servers[]` containing stale or placeholder IPs shadow live subscription entries.
- `LeakProtection.ValidateOutboundServersScopeAware` isolates authority:
  - In `subscribe` mode: Allowed servers derive strictly from enabled subscriptions. Any outbound targeting a manual VLESS server emits a fatal `Error`.
  - In `generated` mode: Outbounds may target subscription servers or valid manual servers, but known placeholder entries (`VlessServersResolver.IsPlaceholderEntry`) are filtered out.
  - In `custom` mode: Server IPs are not checked against `config.yaml`, but the JSON is validated to ensure a functioning `proxy` outbound exists with non-empty host and valid port.

  - Line 265 evaluates safely (`settings.App?.ConfigMode` would be null, but `settings.App.ConfigMode` is evaluated directly! Wait: line 265 actually accesses `settings.App.ConfigMode` without null conditional operator `?.`).
  - Line 267 unconditionally dereferences `settings.App.RoutingMode`.
  - Line 269 unconditionally dereferences `settings.App.RoutingAppsMode`.
- **Impact**: Throws `NullReferenceException`, aborting configuration validation unexpectedly.
- **Remediation**: Use null-conditional operators: `settings.App?.ConfigMode`, `settings.App?.RoutingMode`, `settings.App?.RoutingAppsMode`.

### Finding 2: Unhandled Cancellation and Background Thread Leak in `EnableDnsLockdownAsync` / `DisableDnsLockdownAsync`
- **Location**: `VPNRouter.Core/Services/FirewallManager.cs`, lines 724–824 and 873–891.
- **Vulnerability**: The 5-second `timeoutCts` token is passed to `Task.Run(..., timeoutCts.Token)`. However, inside the delegate, 7 to 9 synchronous `RunNetshStatic` calls run sequentially without checking `timeoutCts.Token.IsCancellationRequested` or `ct.IsCancellationRequested`.
- **Impact**: If `netsh.exe` calls run slowly (e.g. 1.5 seconds each), after 3 calls (4.5s) the timeout expires, `Task.Run` throws `OperationCanceledException` to the caller, but the remaining 4 calls continue running on the thread pool in the background. If the user immediately disconnects or triggers teardown, background calls race with teardown rules.
- **Remediation**: Check `timeoutCts.Token.ThrowIfCancellationRequested()` before each `RunNetshStatic` call.

### Finding 3: Synchronous Blocking Sync-over-Async in `RunNetsh` and `FindRulesByPrefixes`
- **Location**: `VPNRouter.Core/Services/FirewallManager.cs`, lines 465, 534, 1034.
- **Code**: `_runner.RunAsync(...).GetAwaiter().GetResult()`
- **Vulnerability**: Synchronously blocks the calling thread waiting for process execution. In `EnableBlockRules()`, this executes sequentially for every managed rule.
- **Impact**: 10 rules with potential 5s timeouts can block the thread for up to 50 seconds during a critical sing-box crash recovery window.
- **Remediation**: Expose asynchronous APIs (`EnableBlockRulesAsync()`, `DeleteAllRulesAsync()`) and await `RunAsync()`.

### Finding 4: Kill-Switch Fails Open for Processes Not Running at Crash Time
- **Location**: `VPNRouter.Core/Services/FirewallManager.cs`, lines 244–249, 283–287.
- **Vulnerability**: Windows Firewall requires an absolute executable path in `program="..."`. If a process is not running when VPN connects and not on PATH (e.g., Discord or Telegram installed in `%LocalAppData%`), `ResolveProcessPath` returns `null`. `EnableBlockRules()` attempts late resolution on crash, but if the application is *still* not running at the exact instant of the crash, resolution fails again.
- **Impact**: If the user launches the application 5 seconds *after* the VPN crashed, no firewall rule exists for it. The application connects directly to the Internet with the user's ISP IP, completely bypassing the kill-switch.
- **Remediation**: Document this fundamental Windows per-app firewall limitation; consider scanning common installation paths (`%LocalAppData%\Programs\*`, `%AppData%\*`) or maintaining a persistent executable path cache.

### Finding 5: Fragile Netsh Block Parsing in `FindRulesByPrefixes`
- **Location**: `VPNRouter.Core/Services/FirewallManager.cs`, lines 471–494.
- **Code**:
  ```csharp
  var inNewBlock = true;
  foreach (var line in output.Split('\n'))
  {
      var trimmed = line.Trim();
      if (trimmed.Length == 0) { inNewBlock = true; continue; }
      if (!inNewBlock) continue;
      inNewBlock = false; // consume this block's first field
      var colonIdx = trimmed.IndexOf(':');
      if (colonIdx < 0) continue;
      var value = trimmed[(colonIdx + 1)..].Trim();
      ...
  ```
- **Vulnerability**: Assumes the *first non-empty line* of every blank-separated block contains the rule name after a colon. If a Windows locale, update, or third-party firewall hook outputs banner text, headers without colons, or multi-line metadata, `inNewBlock` is set to `false` on the header, causing the actual `Rule Name:` line in that block to be completely skipped.
- **Impact**: Orphaned rules are not discovered during cleanup, leaving old block rules active and permanently stranding user traffic.

### Finding 6: Unused Dead Code: `ConsoleEncoding`
- **Location**: `VPNRouter.Core/Services/FirewallManager.cs`, lines 132–152.
- **Observation**: `ConsoleEncoding` resolves the Windows OEM code page via `GetOEMCP()` and `CodePagesEncodingProvider`. However, with the adoption of `IProcessRunner`, `ProcessRequest` does not expose a standard output encoding property. `ConsoleEncoding` is never referenced outside its own declaration.
- **Impact**: Localized Cyrillic/German error output from `netsh.exe` logged in `RunNetsh` is decoded as UTF-8 by default, causing mojibake in `vpnrouter.log`.
