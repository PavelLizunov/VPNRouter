> **TL;DR:** Headless Storage (`ConfigStorage` and `CustomConfigStorage`) implements isolated, fail-closed configuration persistence and revision concurrency control for `VPNRouter.Headless`. `ConfigStorage` provides intra-process monitor locking and cross-process cooperative named Mutex locking (`VPNRouter_ConfigLock_{hash}`) with SHA-256 revision validation (CAS), bounded single-pass reads (1 MiB), strict no-symlink hierarchy traversal, and fail-closed POSIX file/directory permissions (0600/0700). `CustomConfigStorage` provides atomic persistence of raw sing-box JSON configurations with strict size (256 KiB) and depth (32) bounding, pre-commit schema validation via Core's `CustomConfigInjector`, and path sanitization. Key defects identified include global `AppPaths.OverrideDataDir` mutation in `ConfigStorage`'s constructor, raw exception logging in Mutex acquisition violating the zero-secret-leak invariant, unhandled IO exceptions in `CustomConfigStorage.SaveCustomConfig` escalating to `internal_error` instead of `storage_error`, and state divergence on partial failures in custom config removal.

## 1. SUMMARY & PURPOSE

The Headless Storage subsystem provides the persistent data foundation for the `VPNRouter.Headless` daemon (Omarchy Quattro shell plugin daemon). It handles loading, in-memory caching, validation, cooperative and external revision concurrency control, and atomic file system operations for both the primary application configuration (`config.yaml`) and imported custom sing-box JSON configuration files.

### Component Roles & Responsibilities

1. **`ConfigStorage.cs`**:
   - Manages the lifecycle of `AppSettings` mapped to `config.yaml`.
   - **Zero Startup Mutation**: Guarantees that if `config.yaml` does not exist at startup, default in-memory settings are loaded without writing a new file to disk.
   - **Cooperative Named Mutex Synchronization**: Serializes concurrent cross-process backend instances targeting the same data directory using an OS-level named mutex (`VPNRouter_ConfigLock_{hash}`) derived from the SHA-256 hash of the normalized `DataDir` path.
   - **Optimistic Concurrency & Revision CAS**: Every configuration file state is identified by its lower-case hex SHA-256 digest (initial revision `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` representing the SHA-256 of empty content). Writes require matching expected revisions to prevent lost updates.
   - **Pre-Commit External Change Detection**: Re-reads and re-verifies the on-disk file revision immediately before executing atomic file replacements to provide best-effort detection against uncooperative external writers.
   - **Bounded Single-Pass Reading**: Caps stream reads at 1 MiB (`MaxConfigFileBytes = 1024 * 1024`) upfront before memory expansion, deriving both the UTF-8 payload and the revision digest from a single memory buffer to eliminate double-read TOCTOU vulnerabilities.
   - **Strict No-Symlink Hierarchy**: Recursively traverses every ancestor directory up to the filesystem root, verifying that neither the target file nor any parent directory is a symbolic link or reparse point.
   - **Fail-Closed POSIX Permissions**: Strictly verifies and enforces directory mode `0700` (`rwx------`) and file mode `0600` (`rw-------`) on Linux and macOS. Persisting to or leaving files in non-private directories fails closed with `storage_error`.
   - **Detached In-Memory Cloning**: Delivers deep-cloned copies of `AppSettings` via AOT-compatible static YAML serialization (`YamlStaticContext`) to isolate internal cached state from consumer mutations.

2. **`CustomConfigStorage.cs`**:
   - Manages validation, isolated directory creation, atomic writing, and deletion of custom sing-box configuration files (`custom-{safeName}.json`) stored under `AppPaths.ConfigDir`.
   - **Strict Input Bounding**: Rejects configuration names over 128 characters, empty payloads, and payloads exceeding 256 KiB (`MaxConfigBytes = 262,144` bytes).
   - **Structure & Depth Validation**: Parses candidate JSON using `JsonDocumentOptions` with `MaxDepth = 32` and `CommentHandling = JsonCommentHandling.Skip`, requiring a root JSON object.
   - **Core Schema Validation**: Directly invokes `CustomConfigInjector.Validate(rawJson)` prior to disk access to verify required outbound arrays, proxy presence, fork gates (e.g. AWG/xhttp support), and duplicate outbound tags.
   - **Path Traversal Protection & Sanitization**: Strips illegal filename characters via `Path.GetInvalidFileNameChars()` and prepends `custom-` to prevent path traversal outside `AppPaths.ConfigDir`.
   - **Atomic Persistence**: Writes to a temporary file (`custom-{safeName}.json.tmp.{Guid}`) in the target directory, performs durable flush (`stream.Flush(flushToDisk: true)`), and performs atomic replacement via `File.Move(..., overwrite: true)`.
   - **Best-Effort Unix Permissions**: Attempts setting mode `0700` on the configuration directory and `0600` on the file, logging or silently ignoring permission errors without failing closed.

## 3. DATA FLOWS & STATE MACHINES

### 3.1. Settings Lifecycle & Read/Write Pipeline (`ConfigStorage`)

```
[Client / Caller]
       │
       ▼ GetSettings()
  Acquire _syncLock
       │
       ▼ EnsureLoaded()
  ┌───────────────────────────────────────────────┐
  │ ReadExactFileBounded():                       │
  │ 1. AssertNoSymlinksInPath(ConfigPath)         │
  │ 2. If !File.Exists -> return null             │
  │ 3. Open stream (seekable check <= 1 MiB)      │
  │ 4. Chunked read (8 KiB) capped at 1 MiB       │
  │ 5. Compute SHA256 hex + UTF-8 string          │
  └──────────────────────┬────────────────────────┘
                         │
         ┌───────────────┴───────────────┐
    File Missing?                 File Present?
         │                               │
  _cachedSettings =            Has Revision Changed?
    new AppSettings().EnsureSane()       ├── NO ──> Return cached instance
  _cachedRevision = InitialRevision      └── YES ─> SettingsLoader.Parse(yaml)
  (NO DISK MUTATION)                               Update _cachedSettings & _cachedRevision
         │                               │
         └───────────────┬───────────────┘
                         │
       ▼ CloneSettings(_cachedSettings)
  YAML Serialize -> Parse -> Return Detached Copy
```

```
[Client / Caller]
       │
       ▼ SaveSettings(settings, expectedRevision)
  1. Acquire _syncLock
  2. Acquire Named Mutex ("VPNRouter_ConfigLock_{hash}", 5s timeout)
  3. EnsureLoaded()
  4. If expectedRevision != null -> ValidateRevision(expectedRevision)
  5. AssertNoSymlinksInPath(DataDir) & AssertNoSymlinksInPath(ConfigPath)
  6. EnsurePrivateDirectory(DataDir) -> Enforce 0700
  7. SerializeToYaml(settings) -> Bounded to 1 MiB
  8. SettingsLoader.Parse(yaml) -> Pre-write roundtrip validation
  9. Write to tmp file: config.yaml.tmp.{Guid} (mode 0600, flushToDisk: true)
 10. Re-read disk revision: ReadExactFileBounded()
     └── If expectedRevision != diskRevision -> Throw RouterException("conflict")
 11. Atomic Rename: File.Move(tmpPath, ConfigPath, overwrite: true)
 12. Linux/macOS: Enforce mode 0600 on ConfigPath; verify forbidden bits == 0
 13. Update Memory: _cachedSettings = Clone(settings); _cachedRevision = sha256(yamlBytes)
 14. Finally: Cleanup tmpPath; Release & Dispose Mutex; Release _syncLock
```

### 3.2. Custom Config Import & Removal Pipeline (`CustomConfigStorage`)

```
[custom.import Request]
       │
       ▼ CustomConfigFeature.Import
  1. Validate expected revision against _storage.CurrentRevision
  2. SaveCustomConfig(name, text):
     ├── Length check (name <= 128 chars, text <= 256 KiB)
```

```
[custom.remove Request]
       │

  2. Locate CustomConfigEntry by ID
```

### 3.3. Revision CAS State Machine

| Current Disk State | Client Revision | Action | Outcome | State Transition |
|---|---|---|---|---|
| Absent (`InitialRevision`) | `InitialRevision` | `SaveSettings(settings, InitialRevision)` | Success | Disk created, revision becomes `SHA256(yaml)` |
| Absent (`InitialRevision`) | `"stale_hash"` | `SaveSettings(settings, "stale_hash")` | Conflict | Rejected (`RouterException("conflict")`), no disk write |
| Hash A | Hash A | `SaveSettings(settings, Hash A)` | Success | Revision advances to Hash B |
| Hash A | Hash C (Stale) | `SaveSettings(settings, Hash C)` | Conflict | Rejected with `conflict` before writing tmp file |
| Hash A | Hash A (Concurrent write occurs during serialization) | `SaveSettings(settings, Hash A)` | Conflict | Pre-commit disk check detects Hash X != Hash A; rejects with `conflict`; deletes tmp file; disk preserved |

## 4. CONCURRENCY, LOCKS & LIFECYCLE

### 4.1. Concurrency Model & Lock Hierarchy

1. **Intra-Process Monitor Lock (`_syncLock`)**:
   - Private `readonly object _syncLock = new()` in `ConfigStorage`.
   - Protects `_cachedSettings`, `_cachedRevision`, and ensures that `GetSettings()`, `ValidateRevision()`, `SaveSettings()`, and `CurrentRevision` do not race within the same process.
2. **Cross-Process Cooperative Named Mutex (`VPNRouter_ConfigLock_{hash}`)**:
   - Scope: Shared among cooperating `VPNRouter.Headless` or CLI instances accessing the same `DataDir`.
   - Name derivation: `$"VPNRouter_ConfigLock_{Convert.ToHexStringLower(SHA256.HashData(Encoding.UTF8.GetBytes(normalizedDataDir)))}"`.
   - Acquisition deadline: `mutex.WaitOne(TimeSpan.FromSeconds(5))`. If the timeout expires, it throws `RouterException("conflict", "Configuration lock contention: concurrent backend operation timed out")`.
   - Crash resilience: Specifically catches `AbandonedMutexException` and treats the lock as successfully acquired (`acquired = true`), allowing recovery from crashed predecessor processes.
3. **Lock Ordering Guarantee**:
   - Strict lock hierarchy:
     1. Monitor lock `_syncLock` (internal).
     2. Cooperative named Mutex (external).
   - Because `AcquireCooperativeLock()` is only invoked inside `lock (_syncLock)`, lock inversion deadlock cannot occur within the process.
4. **Lack of Locks in `CustomConfigStorage`**:
   - `CustomConfigStorage` possesses no synchronization primitives (`lock`, `SemaphoreSlim`, or `Mutex`).
   - Thread safety relies entirely on external callers: within Headless, `ProtocolDispatcher` enforces a single active ordinary command, and `CustomConfigFeature` synchronizes its overall transaction via `_storage.ValidateRevision` and `_storage.SaveSettings`.
   - Concurrent external processes writing custom configs directly to `AppPaths.ConfigDir` are uncoordinated except for atomic file replacements.

### 4.2. Teardown Guarantees & Resource Cleanup

- **Temporary File Cleanup**:
  - Both `ConfigStorage.SaveSettings` and `CustomConfigStorage.SaveCustomConfig` enclose file creation, writing, and atomic moves in `try ... finally` blocks.
  - In `finally`, if `File.Exists(tmpPath)` is true (e.g. if serialization failed, pre-commit revision check failed, or move failed), `File.Delete(tmpPath)` is invoked within a suppressed catch block to prevent leaking orphaned temporary files.
- **Mutex Handle Lifetime**:
  - Encapsulated in `private sealed class CooperativeLockReleaser : IDisposable`.
  - Disposing the releaser guarantees `_mutex.ReleaseMutex()` followed by `_mutex.Dispose()`.

## 5. SECURITY & PRIVILEGE BOUNDARIES

### 5.1. File Permissions & POSIX Hardening

| Component | Target Path | Target Mode | Enforcement Strategy | Non-Private Behavior |
|---|---|---|---|---|
| `ConfigStorage` | `DataDir` | `0700` (`rwx------`) | Strict `File.SetUnixFileMode` + verify forbidden mask | **Fails closed**: throws `RouterException("storage_error")` |
| `ConfigStorage` | `tmpPath` (file) | `0600` (`rw-------`) | `FileStreamOptions.UnixCreateMode` + `SetUnixFileMode` + verify forbidden mask | **Fails closed**: closes stream, deletes file, throws `storage_error` |
| `ConfigStorage` | `ConfigPath` | `0600` (`rw-------`) | `SetUnixFileMode` + verify forbidden mask post-rename | **Fails closed**: throws `RouterException("storage_error")` |
| `CustomConfigStorage` | `AppPaths.ConfigDir` | `0700` (`rwx------`) | Best-effort `File.SetUnixFileMode` | **Tolerant**: catches and ignores exceptions |
| `CustomConfigStorage` | `tmpPath` (file) | `0600` (`rw-------`) | `FileStreamOptions.UnixCreateMode` + best-effort `SetUnixFileMode` | **Tolerant**: catches and ignores exceptions |
| `CustomConfigStorage` | `destPath` | `0600` (`rw-------`) | Best-effort `SetUnixFileMode` post-rename | **Tolerant**: catches and ignores exceptions |

- **Forbidden Mask**:
  ```csharp
  const UnixFileMode forbiddenMask = UnixFileMode.GroupRead | UnixFileMode.GroupWrite | UnixFileMode.GroupExecute |
                                     UnixFileMode.OtherRead | UnixFileMode.OtherWrite | UnixFileMode.OtherExecute;
  ```
  `ConfigStorage` verifies `(mode & forbiddenMask) == 0`. If any group or world permission bits remain active (such as on filesystems mounted without POSIX permission support like FAT32/exFAT), persistence is refused.

### 5.2. Strict Anti-Symlink Hierarchy

Both storage components implement `AssertNoSymlinksInPath(string path)`:
- Recursively walks from `Path.GetFullPath(path)` up through every parent directory to the filesystem root.
- Probes each directory and file using:
  1. `fileInfo.LinkTarget != null`
  2. `fileInfo.Attributes.HasFlag(FileAttributes.ReparsePoint)`
  3. `dirInfo.LinkTarget != null`
  4. `dirInfo.Attributes.HasFlag(FileAttributes.ReparsePoint)`
  5. `File.ResolveLinkTarget(path, returnFinalTarget: false) != null`
  6. `Directory.ResolveLinkTarget(path, returnFinalTarget: false) != null`
- **Fail-Closed Semantics**: If any exception other than `FileNotFoundException` or `DirectoryNotFoundException` is raised during probing, `IsSymlinkOrReparsePoint` returns `true`, triggering an immediate `RouterException("storage_error", ...)`. Broken symlinks whose targets do not exist are detected via `LinkTarget` and `ResolveLinkTarget` and rejected.

### 5.3. Memory Bounding & Denial of Service Defenses

- **ConfigStorage File Ceiling**: Fixed at 1 MiB (`MaxConfigFileBytes = 1,048,576`).
  - Seekable streams verify length upfront: `if (stream.CanSeek && stream.Length > MaxConfigFileBytes) throw ...`.
  - Non-seekable streams or streaming reads track total accumulation in 8 KiB chunks: `if (totalRead > MaxConfigFileBytes) throw ...`.
  - Outgoing serialized candidate YAML is checked before writing: `if (yamlBytes.Length > MaxConfigFileBytes) throw ...`.
- **CustomConfigStorage Limits**:
  - Maximum raw JSON payload: 256 KiB (`MaxConfigBytes = 262,144`). Checked using UTF-8 byte count: `Encoding.UTF8.GetByteCount(rawJson) > MaxConfigBytes`.
  - Maximum JSON parsing depth: 32 (`MaxDepth = 32`). Prevents stack overflow attacks via deeply nested JSON structures.
  - Maximum configuration name length: 128 characters.

### 5.4. Path Sanitization & Traversal Mitigation

- In `CustomConfigStorage`, paths are generated via `CustomConfigInjector.GetProgramDataPath(configName)`:
  ```csharp
  var dir = AppPaths.ConfigDir;
  var safeName = string.Join("_", configName.Split(Path.GetInvalidFileNameChars()));
  return Path.Combine(dir, $"custom-{safeName}.json");
  ```
  - Prepending `custom-` ensures that even inputs such as `..` or `.` resolve to `custom-...json` within `dir`, preventing directory traversal escapes.
  - Slashes (`/` on Unix, `/` and `\` on Windows) are stripped by `Path.GetInvalidFileNameChars()` and replaced with underscores (`_`).

### 5.5. Diagnostic Logging & Redaction Compliance

- `VPNRouter.Headless/AGENTS.md` mandates zero raw exception messages, inner exceptions, stack traces, subscription URLs, or credentials in logs.
- Most logging adheres to this strictly by logging only `ex.GetType().Name`:
  - `_logger.Warning("[ConfigStorage] Failed to serialize candidate settings: {ErrorType}", ex.GetType().Name);`
  - `_logger.Warning("[ConfigStorage] Persistence failure: {ErrorType}", ex.GetType().Name);`
  - `_logger.Warning("[ConfigStorage] Malformed configuration file: {ErrorType}", ex.GetType().Name);`
  - `_logger.Warning("[ConfigStorage] Failed to read {Path}: {ErrorType}", ConfigPath, ex.GetType().Name);`
  - `_logger.Warning("[CustomConfigStorage] Best-effort deletion failed for custom config: {ErrorType}", ex.GetType().Name);`
- Wire error reporting uses `RouterException.SafeMessage` exclusively, mapping codes to static, fixed strings.

  ```csharp
  }
  ```
- **Analysis**: In all other storage catch blocks (lines 173, 234, 280, 337), the author conscientiously logged `{ErrorType}` using `ex.GetType().Name` without passing `ex` as the first argument, adhering to Invariant #1 in `VPNRouter.Headless/AGENTS.md` ("Errors, log lines, and responses must never echo raw input, exception messages, inner exceptions, stack traces..."). However, in lines 359 and 375, `ex` is passed directly as the primary argument to Serilog (`_logger.Warning(ex, ...)`). If Serilog formats this exception, full exception messages and OS paths may leak into daemon logs.
- **Severity**: Medium (Logging Invariant Violation).
- **Remediation**: Replace `_logger.Warning(ex, ...)` with `_logger.Warning("[ConfigStorage] ...: {ErrorType}", lockName, ex.GetType().Name);`.

### Defect Candidate 2: Global Static Mutation via `AppPaths.OverrideDataDir` in `ConfigStorage` Constructor

- **Location**: `VPNRouter.Headless/Storage/ConfigStorage.cs`, lines 88
- **Code**:
  ```csharp
  if (!string.IsNullOrWhiteSpace(dataDir))
  {
      DataDir = Path.GetFullPath(dataDir);
      AppPaths.OverrideDataDir(DataDir);
  }
  ```
- **Analysis**: `AppPaths.OverrideDataDir` mutates process-wide static state (`AppPaths._dataDir`). If multiple `ConfigStorage` instances are constructed with different directories (such as in unit/integration test suites or multi-daemon worker processes), every new instance alters global path resolution across the entire process. Furthermore, `CustomConfigStorage` does not accept a `dataDir` parameter and relies solely on `AppPaths.ConfigDir`. If `CustomConfigStorage` is used without `ConfigStorage` having overridden `AppPaths`, or if multiple instances race, `CustomConfigStorage` operates on whatever `AppPaths.DataDir` was set to last.
- **Severity**: Medium (Shared Mutable State / Process Bleed).
- **Remediation**: Pass explicit `dataDir` or `configDir` into `CustomConfigStorage`, or avoid mutating static `AppPaths` when an explicit directory is supplied to an instance.

### Defect Candidate 3: Unhandled Filesystem Exceptions in `CustomConfigStorage.SaveCustomConfig`

- **Location**: `VPNRouter.Headless/Storage/CustomConfigStorage.cs`, lines 91–116
- **Code**:
  ```csharp
  try
  {
      using (var stream = CreatePrivateFile(tmpPath))
      using (var writer = new StreamWriter(stream, new UTF8Encoding(false)))
      {
          writer.Write(rawJson);
          writer.Flush();
          stream.Flush(flushToDisk: true);
      }

      File.Move(tmpPath, destPath, overwrite: true);
      ...
      return destPath;
  }
  finally
  {
      try { if (File.Exists(tmpPath)) File.Delete(tmpPath); } catch { }
  }
  ```
- **Analysis**: Unlike `ConfigStorage.SaveSettings` which catches `Exception` and wraps it into `RouterException("storage_error", ...)`, `CustomConfigStorage.SaveCustomConfig` has no `catch` block wrapping file creation, writing, or renaming. If `File.Move` or `writer.Write` throws `IOException` (e.g. disk full, permission denied, destination file locked by another process), the raw .NET exception escapes `SaveCustomConfig`. In `CustomConfigFeature.Import`, this exception is not caught and escapes to `ProtocolDispatcher.DispatchAsync`, which categorizes unexpected exceptions as `"internal_error"` rather than domain `"storage_error"`.
- **Severity**: Low-Medium (Protocol Error Code Inconsistency).
- **Remediation**: Wrap lines 91–116 in `catch (Exception ex) when (ex is not RouterException)` and throw `new RouterException("storage_error", "Failed to persist custom configuration to disk", ex)`.

### Defect Candidate 4: Asymmetric State Divergence on Failed Custom Config Removal

- **Location**: `VPNRouter.Headless/Features/CustomConfigFeature.cs`, lines 152–168
- **Code**:
  ```csharp
  configs.Remove(match);
  _customStorage.DeleteCustomConfig(match.Name); // File deleted from disk here!
  ...
  _storage.SaveSettings(settings, revision);     // Revision check occurs here!
  ```
- **Analysis**: In `CustomConfigFeature.Remove`, `_customStorage.DeleteCustomConfig` deletes the configuration JSON file from disk *before* `_storage.SaveSettings(settings, revision)` is called. If `_storage.SaveSettings` subsequently fails (e.g. due to a concurrent modification triggering revision conflict, lock contention, or disk error), `config.yaml` is NOT updated and still lists the custom configuration in `CustomConfigs`. However, the physical file `custom-{safeName}.json` is already permanently deleted. If the engine later attempts to activate or load this custom config, it will fail because the underlying file is missing.
- **Severity**: Medium (State Inconsistency / Data Loss on Conflict).
- **Remediation**: Defer deleting the underlying file until after `_storage.SaveSettings` successfully commits the updated `config.yaml`, or use a staged rename (e.g. `.trash`) that can be rolled back if `SaveSettings` fails.

### Defect Candidate 5: Symlink Probing TOCTOU Race Condition

- **Location**: `VPNRouter.Headless/Storage/ConfigStorage.cs` (lines 149–199) & `CustomConfigStorage.cs` (lines 82–100)
- **Analysis**: Both classes call `AssertNoSymlinksInPath(...)` prior to file creation, followed later by `File.Move(tmpPath, targetPath, overwrite: true)`. Between the traversal check and the final `File.Move`, a local adversary with directory access could swap a directory or file entry with a symlink. Standard .NET `File.Move` does not support `AT_FDCWD` or `O_NOFOLLOW` descriptor pinning. While `CreatePrivateFile` mitigates temp file creation via `FileMode.CreateNew`, the destination replacement in `File.Move` remains subject to a narrow TOCTOU window.
- **Severity**: Low (Requires local write access to the user's private 0700 configuration directory).

### Defect Candidate 6: `CurrentRevision` Disk Read Under Lock vs In-Memory Stale Cache

- **Location**: `VPNRouter.Headless/Storage/ConfigStorage.cs`, lines 69–79
- **Code**:
  ```csharp
  public string CurrentRevision
  {
      get
      {
          lock (_syncLock)
          {
              var exactRead = ReadExactFileBounded();
              return exactRead?.Revision ?? InitialRevision;
          }
      }
  }
  ```
- **Analysis**: `CurrentRevision` always bypasses `_cachedRevision` and reads `config.yaml` directly from disk. However, `_cachedSettings` and `_cachedRevision` are not refreshed during this property access (they are only refreshed when `EnsureLoaded()` is called). If an external process writes valid or invalid YAML to disk:
  1. `CurrentRevision` immediately reports the new disk hash.
  2. A concurrent `GetSettings()` call will then invoke `EnsureLoaded()`. If the file was written with invalid YAML, `EnsureLoaded()` throws `storage_error`, while `CurrentRevision` previously succeeded.
  While this ensures `CurrentRevision` reflects true disk state, callers should be aware that querying `CurrentRevision` incurs a synchronous disk read on every invocation.
- **Severity**: Informational / Performance Consideration.

## 7. TEST COVERAGE & GAPS

### 7.1. Existing Test Coverage

Storage functionality is tested in `VPNRouter.Headless.Tests`, primarily within `StorageChecks.cs` and `FeatureChecks.cs`:

1. **`StorageChecks.cs`** (Static test suite invoked via `StorageChecks.RunAsync()`):
   - `CheckCorruptConfigFailsClosedAsync`: Verifies corrupt YAML syntax on disk triggers `RouterException("storage_error")`, verifies safe message mapping, verifies `RouterBackend.ExecuteAsync("snapshot")` fails closed, and asserts corrupt content is preserved without being overwritten.
   - `CheckOversizedConfigFileFailsClosedAsync`: Verifies files exceeding 1 MiB fail closed with `storage_error` on both `GetSettings()` and `CurrentRevision`.
   - `CheckSymlinkRejectionAsync`: Validates symlink rejection across three scenarios:
     1. Direct file symbolic links.
     2. Broken symbolic links pointing to non-existent targets.
     3. Parent directory symbolic links.
   - `CheckRevisionConflictDetectionAsync`: Verifies stale revisions passed to `ValidateRevision` and `SaveSettings` throw `conflict`, and asserts external file modifications between validation and save trigger conflict detection.
   - `CheckFailingApplyPreservingExternalNewContentAsync`: Verifies guarded rollback in `RouterBackend` when `IRouterSession.ApplyAsync` fails concurrently with an external edit; asserts rollback detects conflict and preserves the external content.
   - `CheckCooperativeNamedLockingAsync`: Verifies cross-instance synchronization between two `ConfigStorage` objects targeting the same directory.
   - `CheckPrivatePermissionsEnforcedAsync`: Verifies POSIX file modes (`0600` for file, `0700` for directory) on Linux and macOS.
   - `CheckCancelledMutationDoesNotPersistAsync`: Verifies pre-cancelled mutation requests abort without mutating disk contents or revision.

2. **`FeatureChecks.cs`**:
   - `CheckCustomConfigsValidationAndStorageAsync`: Verifies that malformed JSON is rejected with `invalid_argument`, valid custom sing-box JSON is stored, listed via `custom.list`, and deleted via `custom.remove`.

### 7.2. Coverage Gaps & Untested Paths

1. **Direct `CustomConfigStorage` Unit Tests**:
   - `CustomConfigStorage` is tested exclusively through `RouterBackend` / `CustomConfigFeature`. There are no standalone unit tests testing `CustomConfigStorage` in isolation.
2. **Untested `CustomConfigStorage` Boundary Limits**:
   - **Size Limit**: No test verifies that raw JSON exceeding 256 KiB (`MaxConfigBytes`) throws `RouterException("invalid_argument")`.
   - **Depth Limit**: No test verifies that JSON exceeding 32 levels of nesting triggers `invalid_argument`.
   - **Name Limit**: No test verifies that config names exceeding 128 characters throw `invalid_argument`.
   - **Symlink Rejection**: `AssertNoSymlinksInPath` in `CustomConfigStorage` is completely untested (symlink tests in `StorageChecks.cs` only exercise `ConfigStorage`).
3. **Named Mutex Contention Timeout**:
   - `ConfigStorage` mutex contention timeout (5 seconds -> `RouterException("conflict")`) is not exercised by tests.
4. **Abandoned Mutex Handling**:
   - The `catch (AbandonedMutexException)` path in `AcquireCooperativeLock()` is not covered by any test fixture.
5. **Disk Write / IO Failure Paths**:
   - Tests do not cover scenarios where `CreatePrivateFile` or `File.Move` encounters permission denial or full disk conditions.
6. **Permission Forbidden Mask Rejection**:
   - Tests verify that private permissions are set, but do not test the failure path where permissions cannot be enforced (e.g. simulating a filesystem that refuses chmod 0700).
