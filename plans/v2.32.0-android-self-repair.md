# v2.32.0 — Android self-repair (mirror desktop SR-1..SR-4)

## Триггер

Desktop клиент в v2.32.0 получил четырёхуровневую defense-in-depth для
"app can't even reach UI" сценариев:

| Tier | Что | Файл |
|---|---|---|
| SR-1 | Settings semantic validation | `VPNRouter.Core/Services/SettingsValidator.cs` |
| SR-2 | Launch failure counter + graduated recovery | `VPNRouter.Core/Services/LaunchFailureCounter.cs` |
| SR-3 | Schema-versioned cache recovery | `VPNRouter.Core/Services/CacheRecovery.cs` |
| SR-4 | Robust Settings load (outer try/catch + EnsureSane) | `VPNRouter.Core/Services/SettingsLoader.cs` + `Models/AppSettingsSane.cs` |

Android port (v3.0) до сих пор не имел эквивалента — корневая SharedPrefs
с битым JSON, повторяющиеся crash'и в `MainActivity.OnCreate` или
`AndroidApp.OnFrameworkInitializationCompleted`, неизвестное значение
`per_app_mode` после ручной правки `vpnrouter_settings.xml` все
проявлялись либо как тихое возвращение пустого списка серверов либо
как app, который пользователь не может запустить без `Settings > Apps >
VPNRouter > Storage > Clear data`.

## Симптом

User-side: «Серверы пропали после обновления»; «приложение не
открывается, нажимаю иконку — ничего». На phone никакого crash dialog'а
не появляется (для не-system uncaught exceptions Android просто закроет
process), и нет обычного Windows crash log'а.

Internal-side: `adb logcat -s VpnRouter` показывает stack trace, но
recovery нет — каждый launch reset'ит state.

## Root cause

1. AndroidStorage JSON deserialize sites молча catch-и + return пустой
   list (хорошо для робастности, плохо для observability — пользователь
   не понимает, что произошло).
2. Enum getters (`GetRoutingMode`, `GetDnsStrategy`, `GetUpdateChannel`,
   `GetTheme`) принимали raw value без validation — типo `"splut"`
   протекал в маршрутизатор.
3. Нет launch-counter persistence layer — каждый OnCreate fresh start.
4. Нет escalation pattern — не отличаем "первый crash" от "седьмой
   подряд".

## Fix strategy

### Reuse map (handbook §1.3 — desktop is source-of-truth)

| Tier | Desktop service | Android reuse | Android-specific add |
|---|---|---|---|
| SR-1 | `SettingsValidator.Validate` | Reused for Forward-compat: `SettingsLoader.ConsumeRecoveryNotice()` is called from `AndroidApp` even though Android currently doesn't load YAML. | New: `AndroidStorage.ValidateOrDefault` validates enum SharedPrefs values against allowed sets + quarantines bad raw value + stamps recovery notice. |
| SR-2 | `LaunchFailureCounter` | Reused verbatim — pass explicit path under `Application.Context.FilesDir`. | New: `MainActivity.DispatchAndroidLaunchRecovery` switches on the recommended action with Android-meaningful tiers (no Windows installer surface to call). |
| SR-3 | `CacheRecovery.LoadOrRecover<T>` | Reused via `FreeConfigCache` — already platform-neutral; works on Android because `AppPaths.CacheDir` resolves under app sandbox. | New: `StorageBlobRecovery.LoadOrRecover<T>` (Core, platform-neutral) — sibling for in-memory blobs (SharedPreferences string values, not files). |
| SR-4 | `SettingsLoader` outer try/catch + `AppSettingsSane.EnsureSane` | Implicitly reused — `SettingsLoader.LastRecoveryNotice` consumed by `AndroidApp.ConsumeAndSurfaceRecoveryNotice`. | New: `AndroidStorage.QuarantineBadValue` + `StampRecoveryNotice` mirror the same "preserve forensics + surface to UI" contract for SharedPreferences. |

### File changes

#### 1. `VPNRouter.Core/Services/StorageBlobRecovery.cs` (NEW)

Platform-neutral analog of `CacheRecovery`. Operates on a string blob
the caller already pulled out of the storage backend (SharedPreferences,
NSUserDefaults, browser localStorage), classifies parse failure into a
typed `StorageBlobReason`. No file IO — quarantine + recovery notice
are the platform layer's job.

API:

```csharp
public static class StorageBlobRecovery
{
    public static BlobLoadResult<T> LoadOrRecover<T>(
        string? blob,
        Func<string, T?> deserialize,
        Predicate<T>? structuralCheck = null) where T : class;
}

public sealed record BlobLoadResult<T>(T? Value, StorageBlobReason Reason, string? Detail = null);
public enum StorageBlobReason { Success, NotFound, JsonMalformed, StructurallyInvalid }
```

#### 2. `VPNRouter.Android/AndroidStorage.cs` (EDIT)

- Refactored `GetSubscriptions`, `GetServers`, `GetPerAppPackages` to
  use `StorageBlobRecovery.LoadOrRecover` instead of inline try/catch
  with silent empty fallback. On corruption: quarantine the bad value
  to `{key}__corrupt_{ts}` companion key, stamp recovery notice.
- Added enum-validating wrappers:
  - `GetRoutingMode` → `ValidateOrDefault(KeyRoutingMode, raw, AllowedRoutingModes, "split")`
  - `GetDnsStrategy` → `ValidateOrDefault(KeyDnsStrategy, raw, AllowedDnsStrategies, "ipv4_only")`
  - `GetUpdateChannel` → `ValidateOrDefault(KeyUpdateChannel, raw, AllowedUpdateChannels, "stable")`
  - `GetTheme` → `ValidateOrDefault(KeyTheme, raw, AllowedThemes, "light")`
  - `GetPerAppMode` → wraps `PerAppFilterMode.Normalize` with notice-on-coercion.
- Added `LastRecoveryNotice` + `ConsumeRecoveryNotice` (mirror
  `SettingsLoader`).
- Added `QueueSafeModeBannerForUi` + `ConsumeSafeModeBanner` —
  persistent SharedPrefs flag for SR-2 tier-3 (survives crash so the
  banner shows on the launch that finally succeeds).
- Added `ResetUserSettings` — wipes documented user-data keys but
  preserves quarantine companions for forensics.

#### 3. `VPNRouter.Android/MainActivity.cs` (EDIT)

`OnCreate` (BEFORE `base.OnCreate`):

```csharp
var filesDir = FilesDir?.AbsolutePath;
if (!string.IsNullOrEmpty(filesDir))
{
    LaunchCounterPath = Path.Combine(filesDir, "launch-counter.json");
    var action = LaunchFailureCounter.RecommendAction(LaunchCounterPath);
    if (action != "none") DispatchAndroidLaunchRecovery(action);
    LaunchFailureCounter.IncrementOnStartup(path: LaunchCounterPath);
}
```

`DispatchAndroidLaunchRecovery(action)`:

| Action | Threshold | Android effect |
|---|---|---|
| `self-repair` | 3 strikes | Wipe transient cache files (`AppPaths.CacheDir/*.json` — FreeConfig pool, etc.) + clear external sing-box log dump. **Why this tier:** desktop's web-reinstall doesn't translate (Play Store / sideload only). Most chronic crash sources on Android are cache-driven (corrupt subscription pool, malformed `test-uri.txt`, etc.). |
| `config-reset` | 5 strikes | All of `self-repair` + `AndroidStorage.ResetUserSettings()` (wipes user-data SharedPrefs keys, keeps quarantine companions). Equivalent to desktop's `config.yaml.crash-recovery-{ts}` backup + reset. |
| `safe-mode-prompt` | 7 strikes | `AndroidStorage.QueueSafeModeBannerForUi()` — sets persistent flag that AndroidApp surfaces as a banner: «Если проблемы продолжаются: Settings > Apps > VPNRouter > Storage > Clear data». Equivalent to desktop's `--safe` / `repair.cmd` pointer. Persistent because the launch that crashed didn't get to surface in-memory notices. |

The `LaunchCounterPath` static property is exposed so
`AndroidApp.OnFrameworkInitializationCompleted` can pass the same path
to `MarkStable` (counter reset on first successful render).

#### 4. `VPNRouter.Android/AndroidApp.axaml.cs` (EDIT)

`OnFrameworkInitializationCompleted`: subscribe a one-shot
`AttachedToVisualTree` handler on the root view. When the view first
attaches (Avalonia rendering committed at least one frame, dispatcher
pumping):

1. `LaunchFailureCounter.MarkStable(MainActivity.LaunchCounterPath)` —
   zero the strike counter.
2. `ConsumeAndSurfaceRecoveryNotice()` — pulls notices from:
   - `SettingsLoader.ConsumeRecoveryNotice` (forward-compat — currently
     no-op on Android, kept for the day Android adopts the YAML
     backend).
   - `AndroidStorage.ConsumeRecoveryNotice` (this launch's per-key
     recovery stamps).
   - `AndroidStorage.ConsumeSafeModeBanner` (persistent SR-2 tier-3).
   - Combined into one banner via existing `ShowMenuFeedback` helper.

#### 5. `VPNRouter.Tests/StorageBlobRecoveryTests.cs` (NEW)

8 tests covering happy path, null/empty/whitespace, malformed JSON,
deserialiser-returns-null, deserialiser-throws, structural check
failure, ShouldRecover semantics, Loaded gate. Mirrors
`CacheRecoveryTests` shape so a future audit can run the same probe set
against either path.

Android-specific tests (i.e. SharedPreferences-backed) are intentionally
NOT added — VPNRouter.Tests targets `net8.0` (no Android SDK), and the
SR-1/3/4 logic that's Android-specific (the `AndroidStorage` enum
wrapping) calls into `Android.App.Application.Context` which doesn't
resolve on the test host. The Core invariants are pinned via
`StorageBlobRecoveryTests`; the Android wrapper is a thin pass-through
verified manually on phone (acceptance below).

      deferral as repro 1.)

## Оценка

- New code: ~70 lines Core + ~180 lines Android.
- New tests: 9 (StorageBlobRecoveryTests).
- Risk: low — additive on top of existing defensive patterns; no
  behavior change for the happy path. SR-2 dispatch could in principle
  delete data (cache wipe at tier-1, settings wipe at tier-2), but only
  fires after 3-5 chronic launch failures — far from a normal user
  state.
