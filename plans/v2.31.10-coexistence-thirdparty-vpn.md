# v2.31.10 — Coexistence with third-party / commercial VPN clients

**Status**: in flight (Task B v2 testing 2026-05-06).
**Branch**: `claude/blissful-goodall-4a3fcd` (worktree).
**HEAD**: v2.31.10-r1 prerelease.

## Question we're answering

When a user layers VPNRouter (TUN+sing-box+VLESS) on top of a commercial VPN
client (ProtonVPN / NordVPN / Mullvad / Tailscale / Windscribe / ExpressVPN)
that has its own kill-switch enabled, what happens?

Three concrete scenarios per vendor:

1. Commercial KS ON, then VPNRouter starts — does sing-box's outbound succeed,
   or does KS classify it as leak and block?
2. VPNRouter up first, then commercial VPN connects — does the commercial
   client see VPNRouter's wintun adapter as "non-VPN traffic" and block it?
3. Both up for 5 minutes — sustained coexistence test.

## Test environment

- Host: Windows 11 LTSC VM (VirtualBox guest)
- Default route: `10.0.2.2` (NAT) via `Ethernet` (Intel PRO/1000)
- Baseline ipify: `104.194.156.93` (host NAT exit; consistent across reboots)
- VPNRouter installed: `C:\Program Files\VPNRouter\app\` (v2.31.10-r1)
- VPNRouter test profile: `main-brat` (multi-app split-tunnel)

Baseline snapshot saved to `%TEMP%\task-b-baseline.json`. Pre-existing
`WireGuardTunnel$wgtest` service from Task A is Stopped+Manual — safe.

## Safety pattern in use

Every test wrapped:

```powershell
try {
    # ... scenarios ...
} finally {
    # Universal rescue: stop any VPN service, disable wintun/TAP adapters
    Get-Service | Where Name -match '^(WireGuardTunnel|AmneziaWGTunnel|nordvpn|protonvpn|mullvad|tailscaled?|windscribe|openvpn)' |
        ForEach-Object {
            Stop-Service $_.Name -Force -EA SilentlyContinue
            Set-Service $_.Name -StartupType Manual -EA SilentlyContinue
        }
    Get-NetAdapter | Where InterfaceDescription -match 'wintun|TAP-Windows|Tailscale' |
        ForEach-Object { Disable-NetAdapter $_.Name -Confirm:$false -EA SilentlyContinue }
    # Verify-Internet — abort if down
}
```

Internet sanity check between every scenario (`Verify-Internet`).

## Findings

### Tailscale (v1.x via tailscale-setup-latest-amd64.msi)

**Install footprint** (silent MSI install via msiexec /i /qn):

| Resource | Value |
|---|---|
| Service | `Tailscale` (StartType=Automatic, Status=Running after install) |
| Adapter | `Tailscale` (InterfaceDescription="Tailscale Tunnel", wintun-based) |
| Firewall | 1 rule: `Tailscale-Process` (Allow Inbound) |
| Binaries | `C:\Program Files\Tailscale\{tailscale,tailscale-ipn,tailscaled}.exe + wintun.dll` |
| Logs | `C:\ProgramData\Tailscale\logs\tailscale-service-*.txt` |

**Kill-switch model**: Tailscale does NOT have a classic "block-all-traffic-if-tunnel-down" kill-switch. Closest analogues:

- **Exit node mode** (`tailscale up --exit-node=<peer>`): adds default route on Tailscale adapter, all traffic flows through chosen exit peer.
- **`--exit-node-allow-lan-access=false`**: prevents LAN escape when exit node configured.
- **Shields-up** (`tailscale up --shields-up`): drops *inbound* traffic from tailnet, irrelevant for kill-switch comparison.

There is no "block Internet if Tailscale daemon unreachable" mode comparable to ProtonVPN/Mullvad/NordVPN kill-switches. Tailscale is a mesh fabric, not a privacy VPN.

**Coexistence with VPNRouter — observed live**:

VPNRouter sing-box started while Tailscale daemon was Running (logged out, no peer connection). Result captured from `C:\ProgramData\Tailscale\logs\tailscale-service-*.txt`:

```
2026-05-06T17:01:10.294+03:00: Rebind; defIf="VPNRouter-TUN", ips=[172.19.0.1/30 fe80::...]
2026-05-06T17:01:12.599+03:00: monitor: got windows change event after 3.104s: evt=addr
```

Tailscale's daemon detected VPNRouter-TUN becoming the default interface and **automatically rebinded its outbound socket** to that interface. No errors, no panic, no firewall block. Both adapters Up, both wintun-based, peacefully coexisting.

| Scenario | Result |
|---|---|
| 1. KS first, then VPNRouter starts | n/a — Tailscale has no KS to enable |
| 2. VPNRouter first, then Tailscale | Live: Tailscale daemon adapts (rebinds defIf to VPNRouter-TUN). ipify 3/3 samples returned 104.194.156.93. TCP probe to 1.1.1.1:443 succeeded |
| 3. 5-min coexist | Pass — no degradation in 60s+ window observed (full 5min run not extended given KS irrelevance) |

**Verdict**: ✅ Compatible. Tailscale's mesh model means it follows the system default route rather than fighting it. If a user later authenticates Tailscale and configures an exit node, *Tailscale* would attempt to set its own default route — at which point Tailscale's RouteMetric vs VPNRouter-TUN's metric (currently 0) determines who wins. Even in that case, behavior is "one wins, the other follows" — not a kill-switch block.

**Rescue triggered**: No.

### Windscribe (v2.21.7 via deploy.totallyacdn.com)

**Install footprint** (silent install via `Windscribe_2.21.7_amd64.exe -silent`):

| Resource | Value |
|---|---|
| Service | `WindscribeService` (StartType=Automatic, Status=Running) |
| Adapter | None at install (created on connect) |
| Firewall | None at install (added by `firewall on` cmd) |
| Binaries | `C:\Program Files\Windscribe\` — `WindscribeService.exe`, `windscribe-cli.exe`, `WireguardService.exe`, `tunnel.dll`, `amneziawgtunnel.dll`, `windscribeopenvpn.exe`, `windscribewstunnel.exe`, `tapctl.exe`, `devcon.exe`, `wintun.dll`, `wireguard.dll` |

**Note**: Windscribe's standard `/S` NSIS flag is broken (installer hangs ~7min); the documented `-silent` flag (single dash) works. TAP driver popup blocks `/S` but `-silent` apparently auto-confirms it.

**Kill-switch model**: Windscribe has a "**always-on firewall**" feature exposed via `windscribe-cli.exe firewall on|off`. It is **independent of login state** — it can be toggled even when logged out. Firewall-on adds **48 WFP filters** named `WindscribeFirewall` that block all outbound traffic that doesn't traverse Windscribe's chosen VPN adapter.

**🎯 LIVE TEST — Windscribe firewall ON kills VPNRouter's tunnel**:

Captured via `windscribe-cli firewall on` while VPNRouter sing-box was Connected to `vless-is-01 443 main-brat`:

```
Pre-test:  ipify = 93.95.226.167  (sing-box → VLESS → host AmneziaWG → ninitux → out)
firewall on → "Firewall is on."
Post-test: ipify = FAIL: The request was aborted: The request was canceled.
```

Mechanism: Windscribe's WFP filters have a higher priority than sing-box's outbound. sing-box.exe has no allow-rule in Windscribe's filter set, so its outbound TCP to `160.79.104.10:443` (VLESS server) gets dropped at the WFP layer. VPNRouter-TUN adapter remains Up but cannot pass traffic upstream — **the tunnel is alive but stranded**.

**VPNRouter does NOT detect this kind of WFP-based block on short timescales**: HealthMonitor's 30s tick window meant the brief 3s test never tripped the leak protection. sing-box process did not die (TCP just returned RST/timeout), so `[HealthMonitor] VPN is up` continued to log. The VPN appears healthy from VPNRouter's process-liveness perspective, but no traffic flows.

After `windscribe-cli firewall off`, all 48 WFP filters cleared and ipify returned to 93.95.226.167.

| Scenario | Result |
|---|---|
| 1. KS first (firewall on), then VPNRouter starts | Live: simulated — VPNRouter was already running, Windscribe firewall ON. **sing-box outbound blocked at WFP**. ipify FAIL. Recovery: `firewall off` |
| 2. VPNRouter first, then Windscribe firewall on | Live: same as scenario 1 (order-independent — WFP filters apply regardless of which started first). FAIL on connectivity |
| 3. 5-min coexist with KS on | Not viable — VPN would stay disconnected. Skipped |

**Verdict**: ❌ **Incompatible when Windscribe firewall is ON** — not just kill-switch (firewall-on is independent of VPN state). VPNRouter has no exception in Windscribe's WFP allowlist. Compatible when Windscribe firewall is OFF (firewall off + Windscribe daemon running = no interference observed).

**Rescue triggered**: No (firewall off worked cleanly).

**Side finding**: VPNRouter's leak protection created a stale block rule for the *Windscribe installer* EXE path (in TEMP folder). The rule persists after the installer is gone, doing nothing useful. Tracks as F-W1 below.

### NordVPN, Mullvad, ProtonVPN Permanent KS, ExpressVPN — public-KB summary

These vendors require paid accounts and CAPTCHA-gated browser flows for live KS testing. Findings synthesized from official docs + open-source code (Mullvad's `mullvadvpn-app/docs/security.md`, ProtonVPN's `protonvpn.com/support/permanent-kill-switch-windows`, NordVPN/ExpressVPN support KBs).

| Vendor | KS Mechanism | Service Name | Persists at Boot? | Recovery |
|---|---|---|---|---|
| **Mullvad** | WFP filters (always-on, can't disable in app); persistent filters added when service exits in case enforcement is desired | `MullvadVPN` | Yes (atomic transaction model — filters stay if app crashes) | Stop service → filters auto-clear |
| **NordVPN** (NordLynx) | WFP filters via Internet Kill Switch (system-level); blocks all traffic except VPN adapter | `nordvpn-service`, `NordVPN Service` | Yes when System-level KS is on | Stop service → filters clear (per docs) |
| **ProtonVPN** (Standard KS) | WFP filters active only during VPN connection | `ProtonVPN Service` | No | Disconnect VPN → filters clear |
| **ProtonVPN** (Advanced/Permanent KS) | Persistent WFP filters that block at boot until VPN connects, plus on shutdown | `ProtonVPN Service` + persistent provider | Yes | Run `ProtonVPN.RestoreInternet.exe` (ships with installer) — **tool exists explicitly because of this scenario** |
| **ExpressVPN** (Network Lock) | Packet filter driver (PKF) — newer Lightway-UDP variant; older builds use WFP. Installed by default | `ExpressVPNService` | Yes | Stop service. PKF driver may need full uninstall |

**Live confirmation on ProtonVPN install** (without KS enabled — just service running):

| Resource | Value |
|---|---|
| Service | `ProtonVPN Service` (StartType=Manual, started → adapter not created until login+connect) |
| WFP providers registered | `ProtonVPN Permanent Provider` + `ProtonVPN Dynamic Provider` (containers; filters added when KS engages) |
| Recovery tool shipped | `C:\Program Files\Proton\VPN\v4.3.14\ProtonVPN.RestoreInternet.exe` |
| Binaries | OpenVPN, WireGuard (TCP+UDP), TAP installer, all bundled |

The two registered WFP providers (`Permanent` + `Dynamic`) match ProtonVPN's two-mode model: Standard KS uses Dynamic provider (cleared on disconnect), Advanced KS uses Permanent provider (survives reboot). The fact that ProtonVPN ships its OWN `RestoreInternet.exe` is implicit acknowledgement that the Permanent KS can lock users out — same class of incident as Task A's WireGuard scenario.

**Predicted compatibility with VPNRouter**:

| Vendor | Scenario 1 (KS first → VPNR start) | Scenario 2 (VPNR first → KS engages) |
|---|---|---|
| Mullvad | ❌ KS always on → sing-box outbound blocked at WFP, identical to Windscribe live finding | ❌ Same — WFP outranks any user-space tunnel |
| NordVPN System KS | ❌ Same WFP block model | ❌ Same |
| ProtonVPN Standard | ⚠️ Only when ProtonVPN connection drops; filters cleared on disconnect | ⚠️ Conditional |
| ProtonVPN Permanent | ❌ Persistent block → sing-box can't even reach VLESS upstream | ❌ Same |
| ExpressVPN | ❌ Network Lock blocks at PKF driver level; sing-box outbound dropped | ❌ Same |

**Recovery in all five cases**: stop the vendor service → WFP filters auto-clear (or PKF driver releases). Mirrors the WireGuard fix pattern documented in `wireguard_killswitch_wfp.md`.



## Recommendations

### Should we publish a "VPNRouter compatibility guide" for users layering with commercial VPNs?

**Yes — short Markdown page in repo + linked from docs.** Specifically:

1. **`docs/compatibility/commercial-vpn-clients.md`** with sections:
   - "If you have a commercial VPN client with kill-switch enabled, VPNRouter cannot pass traffic through it" — visual diagram of the WFP layer dropping sing-box outbound
   - One-liner per vendor: how to safely run side-by-side (almost always: turn off the vendor's KS while VPNRouter is active)
   - **Recovery commands** if the user gets locked out (mirrors `wireguard_killswitch_wfp.md` pattern):
     - Mullvad: `Stop-Service MullvadVPN -Force; Set-Service MullvadVPN -StartupType Manual`
     - Windscribe: `& 'C:\Program Files\Windscribe\windscribe-cli.exe' firewall off`
     - ProtonVPN: `& 'C:\Program Files\Proton\VPN\v*\ProtonVPN.RestoreInternet.exe'` (vendor ships this)
     - NordVPN: `Stop-Service nordvpn-service -Force` + disable system-level KS in app
     - ExpressVPN: `Stop-Service ExpressVPNService -Force`

This is low-effort, high-value documentation. Most of these recipes are already known patterns; we just collect them in one place keyed off VPNRouter symptoms ("sing-box log shows TCP RST", "VPNRouter-TUN Up but no internet").

### Should we detect known commercial-VPN processes and show user-friendly warning at startup?

**Yes, but only as a soft warning, not a hard block.** Specifically:

Add a `CommercialVpnDetector.cs` (or extend `RuntimeStatusDetector`) to scan for:

| Process pattern | Vendor | Severity |
|---|---|---|
| `MullvadVPN.exe`, `mullvad-daemon.exe` | Mullvad | high (always-on KS) |
| `Windscribe.exe`, `WindscribeService.exe` | Windscribe | medium (only blocks if `firewall on`) |
| `NordVPN.exe`, `nordvpn-service.exe` | NordVPN | medium (only blocks if system KS configured) |
| `ProtonVPN.exe`, `ProtonVPNService.exe` | ProtonVPN | medium (Permanent KS only) |
| `ExpressVPN.exe`, `ExpressVPNService.exe` | ExpressVPN | medium (Network Lock default-on) |
| `tailscaled.exe` | Tailscale | low (mesh, coexists fine) |

When detected at VPNRouter startup, surface a non-blocking yellow toast:

> "Detected ${vendor} running. If its kill-switch / firewall is enabled, VPNRouter will fail silently with no internet for routed apps. [Compatibility guide](link) · [Dismiss]"

Implementation: ~50 lines. Reuse the `Process.GetProcessesByName` machinery already in `RuntimeStatusDetector`. **Critically: dispose Process[] handles** (handle leak fixed in v2.31.1's AU-9 — apply same pattern here).

### Should we whitelist sing-box.exe in commercial VPN kill-switches via WFP API or registry?

**No.** This is fragile and would create more problems than it solves:

1. Vendors change their WFP filter layouts between releases (no documented stable ABI for adding to `MullvadFirewall` provider, etc.).
2. Modifying a vendor's WFP provider would likely violate their TOS and could be flagged as malware.
3. WFP filters require admin + WFP API integration; sing-box doesn't currently use WFP at all — adding this dependency for an edge case is poor cost/benefit.
4. ProtonVPN's `RestoreInternet.exe` exists precisely because *they* know their KS can lock users out — meaning even the vendor doesn't trust modifications to the filter set.

The right level of intervention is **detection + user-facing warning + clear recovery docs**, not silent WFP manipulation.

### F-W1: VPNRouter leak protection adds stale block rules for installer EXEs

**Observed**: When the user runs an installer EXE (Windscribe, ProtonVPN, etc.) whose process name happens to be in a profile's process list (or matches a wildcard), VPNRouter's leak protection adds a Windows Firewall block rule like `VPNRouter_Block_Windscribe_2.21.7_amd64`. After the installer finishes and the EXE is deleted, the rule remains as orphan firewall pollution targeting a non-existent path.

**Impact**: Low — disabled rules don't affect traffic. Cosmetic clutter accumulates over time.

**Fix candidate** (out of scope for v2.31.10 unless user wants to ship `-r2`): in `FirewallManager.SyncRules`, validate that each existing `VPNRouter_Block_*` rule's targeted EXE path still exists; delete rules where the path is gone (TEMP folder cleanups, uninstalled apps).

This is a real but very low-impact bug. Not worth a `-r2` cycle on its own. Bundle with next firewall-related change.

## Bug fix decision for v2.31.10-r2

**No code changes needed for r2.** Findings are documentation + recommendation work, not bugs in shipped behavior. The Windscribe-firewall-blocks-VPNRouter outcome is **expected** Windows networking semantics (WFP outranks user-space tunnels), not a VPNRouter regression. VPNRouter's role here is to *help users diagnose* the situation, not to engineer around the OS.

If the user wants follow-up code work, it would be:
1. Soft "commercial VPN detected" warning (~50 lines)
2. F-W1 stale-rule cleanup (~20 lines)
3. (Optional) Compatibility guide MD file in `docs/`

Each is small enough to land in a single follow-up commit on the next non-emergency cycle. No changes here are urgent enough to delay v2.31.10 stable promotion.
