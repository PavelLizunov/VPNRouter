# v2.31.10 — Autostart UX clarity (per-component status badges)

## Problem

User report 2026-05-07 — "Auto-start with Windows for tgproxy doesn't
work". The Autostart sub-tab in Network → Autostart had three component
toggles (VPN / Zapret / Telegram proxy) with no inline indication of
WHEN/HOW each one would actually fire. A user could tick
`AutostartTgProxy` on a host without the Windows Service installed and
nothing would happen at next boot — silent no-op.

The flag is read by `VPNRouter.Service.AutostartTgProxyAsync` at boot.
Without the service installed, NOTHING reads the flag — there's no
App-side bootstrap that runs `TgProxyManager.StartAsync` at user login
to compensate. The toggle is wired to a YAML field that no live process
ever queries.

## Root cause

Three independent boot/login mechanisms live in the same panel:

| Toggle               | Backed by                    | When fires |
| -------------------- | ---------------------------- | ---------- |
| Master service card  | `sc.exe install` (HKLM)      | Boot, by SCM |
| AutostartVpn/Zapret/TgProxy | YAML flag read by Service | Boot, IF service installed |
| AutostartUi          | HKCU\Run / LaunchAgent / .desktop | User login |

Pre-r1, the per-component sub-toggles became `IsEnabled=false` when the
service wasn't installed (already wired in v2.27 redesign), but a user
could:
1. Reach the sub-tab without scrolling past the master card,
2. Try ticking VPN/Zapret/TgProxy, see no visible response (greyed),
3. Have no idea WHY it's greyed.

Plus, the existing inline "Эти флаги читает служба при boot. Требуется
установленная служба." hint sits BELOW the three toggles, in 9pt italic.
Easy to miss.

## Fix

Inline status badge below each of the three component CheckBoxes. Three
states cover every (Service installed?, App-side bootstrap exists?)
permutation:

| Service | App bootstrap | Badge | Wording (EN) |
| --- | --- | --- | --- |
| ✅ | * | Green ✓ | "✓ Via Windows Service (at boot)" |
| ❌ | ✅ | Amber ⚠ | "⚠ Service not installed — will fire after App login" |
| ❌ | ❌ | Red ⛔ | "⛔ Will not fire without the Windows service" |

`HasAppBootstrap{Vpn,Zapret,TgProxy}` are currently constants
returning `false` for all three. The sister DBG-2 task introduces
App-side bootstrap (App.axaml.cs reads YAML at OnFrameworkInitialization
and runs the appropriate manager) — flipping any of those constants to
`true` switches that component from red ⛔ to amber ⚠ without any other
code change.

Why no current "service installed but stopped" branch: at boot, an
installed delayed-auto service starts via SCM regardless of whether it's
running right now. The user's question is "what happens at next reboot?"
— and for that, only `IsInstalled` matters. `IsRunning` is a transient
runtime signal, not a boot autostart signal.

## Implementation

**Strings (Localization/Strings.cs)**:
- `AutostartStatusBoot` — RU + EN
- `AutostartStatusLoginFallback` — RU + EN
- `AutostartStatusNoBoot` — RU + EN

**VM (MainWindowViewModel.cs)**:
- Three constants `HasAppBootstrap{Vpn,Zapret,TgProxy}` (all `false`
  pre-DBG-2)
- Three `LblAutostart{Vpn,Zapret,TgProxy}Status` getters (status text
  via `ComputeAutostartStatus`)
- Nine `IsAutostart{Vpn,Zapret,TgProxy}Status{Good,Warn,Bad}` flags
  driving per-status `IsVisible` gates in XAML
- `ComputeAutostartStatus(bool isServiceInstalled, bool hasAppBootstrap)`
  — internal static pure-function dispatch; unit-testable without VM
  ctor (no Avalonia, no I/O, no logger)
- `ServiceVm.PropertyChanged` handler extended: on `IsInstalled` flip,
  re-fire `OnPropertyChanged` for all 12 new bindings (3 labels + 9
  flags). The existing v2.27 Bug B handler already fired
  `SmpAutostartChecked` re-notify on the same event; this builds on it.

**XAML (NetworkPage.axaml)**:
- Each of the three component CheckBoxes gets a sibling StackPanel
  containing the CheckBox + three IsVisible-gated `<TextBlock>`s, one
  per status state. The status text reads from the matching
  `LblAutostart{X}Status` binding; the active TextBlock's `Foreground`
  uses semantic tokens (`SuccessFgBrush` / `WarningFgBrush` /
  `DangerFgBrush`).
- 9pt FontSize matches existing card-sub TextBlock baseline; `Margin
  22,0,0,0` lines up the badge under the CheckBox text (24-px
  CheckBox.Glyph.Width minus the 2-px Padding gap).

**Tests**:
- `AutostartStatusComputationTests` (4 plain `[Fact]`s) — pure-function
  dispatch table. Pin all 4 (svc, app) permutations + bilingual parity.
- `AutostartStatusBindingTests` (2 `[AvaloniaFact]`s) — integration:
  flip `vm.ServiceVm.IsInstalled` + assert (a) flag triplets respond
  correctly, (b) PropertyChanged stream contains all 12 expected names,
  (c) labels read the right strings.
- `PageScreenshotTests` — 3 new variants pinning the visual state per
  scenario:
  - `NetworkPage_AutostartTab_ServiceNotInstalled` — red ⛔ branch
  - `NetworkPage_AutostartTab_ServiceInstalled` — green ✓ branch
  - `NetworkPage_AutostartTab_ServiceInstalledStopped` — green ✓
    despite IsRunning=false (pins the "boot-only" semantics)
- Stale-index fix: existing `NetworkPage_Autostart*` tests used
  `SelectedSettingsIndex = 4` which became Updates after the v2.30.0-r2
  Rules section addition shifted indices. Bumped to 5 so the screenshots
  actually capture Autostart.

## Manual repro on a real Windows host

1. Open VPNRouter.App, navigate to Network → Autostart.
2. With the Windows service NOT installed, confirm:
   - Master card "Фоновая служба Windows" has its checkbox unchecked
   - All three component CheckBoxes are greyed out
   - Below each one, RED ⛔ badge reads "⛔ Не сработает без службы
     Windows" (RU) / "⛔ Will not fire without the Windows service" (EN)
3. Click "Установить службу" inline CTA. Wait for install to complete.
4. Confirm:
   - Master card checkbox is now checked
   - All three component CheckBoxes are now interactive
   - Below each one, GREEN ✓ badge reads "✓ Через службу Windows (на
     старте ОС)" / "✓ Via Windows Service (at boot)"
5. Stop the service via PowerShell `sc stop VPNRouter`. Refresh the VM
   (re-open Network → Autostart). Confirm green ✓ stays — the boot
   semantics don't depend on current run state.
