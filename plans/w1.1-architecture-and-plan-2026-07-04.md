# W1.1-W1.4 — production architecture + phased plan: Mullvad split-driver agent

**Дата:** 2026-07-04. **Статус:** design (исполняем против этого дока).
**Родитель:** [`goal-w1-mullvad-split-driver-2026-07-03.md`](goal-w1-mullvad-split-driver-2026-07-03.md)
(W1.0 Outcome = **PASS**, gate зелёный). **ABI (authoritative):**
[`w1-driver-abi-reference-2026-07-03.md`](w1-driver-abi-reference-2026-07-03.md).
**Spike-агент (90% production-кода уже написано и live-proven):** scratch
`w1-spike/spike/Program.cs` — P/Invoke (SCM / DeviceIoControl / Toolhelp32 /
QueryDosDevice / QueryFullProcessImageName / FWPM sublayers), ручные буферы,
полный engage-flow до ENGAGED(4). Spike сознательно пропустил inverted-call
event pump — W1.1 его добавляет (референс: Mullvad `driver.rs`
`parse_event_buffer` + overlapped-хелперы, `defs/events.h`).

**Красная линия (повтор из goal):** fail-open. Любой сбой драйвера на любом
шаге → лог + тихий откат на текущее post-capture поведение (sing-box
`process_name → direct` rules остаются в конфиге как defense-in-depth).
Никогда не бричим сеть. Каждый failure-path в §3 обязан заканчиваться
строкой "fallback: ...".

## 0. Executive summary + refined estimate

W1.0 закрыл ВСЕ feasibility-риски: драйвер грузится bare kernel-service
create, C#-агент драйвит протокол до ENGAGED, sublayers создаём сами,
реальное OS-level исключение работает с TUN sing-box и переживает kill.
Остались только production-инженерия: reshape спайка в sealed-класс,
event pump, fail-open обвязка, wiring, тесты, packaging.

**Оценка: 6-9 рабочих дней суммарно** (было "2-4 недели" ДО спайка, когда
агент был unknown). Разбивка и обоснование — §8. Главный не-code риск —
итерации на live-VM (WinRM-гочи из W1.0), поэтому диапазон, а не точка.

Три ключевых архитектурных решения (детали ниже):

1. **Один exclusive overlapped device handle на всё.** Драйвер требует
   share_mode=0, значит второй handle невозможен — все control-IOCTL идут
   через overlapped+event (по образцу Mullvad `device_io_control_buffer`),
   pump держит собственный OVERLAPPED на том же handle. Control-плоскость
   сериализована одним SemaphoreSlim.
2. **Pump = observability, не correctness.** Splitting происходит в ядре
   независимо от DEQUEUE_EVENT (доказано спайком). Смерть pump'а → лог +
   degraded-флаг, но остаёмся ENGAGED (fail-open в обе стороны: не бричим
   сеть И не выключаем работающий split из-за телеметрии).
3. **Kernel-сервис ставим один раз и не останавливаем.** Disengage = RESET
   (драйвер в STARTED, фильтры сняты, inert). ControlService(STOP) — только
   в uninstall.ps1. Причина: у драйвера известный баг — stop без RESET
   течёт callbacks (Mullvad `service.rs` "must RESET before stopping"), и
   demand-start сервис в состоянии STARTED стоит ~100 KB ядерной памяти.
   Меньше SCM-churn = меньше failure-поверхность.

## 1. `SplitTunnelDriverManager.cs` — architecture

|---|---|---|

| `SplitTunnelDriverProtocol.cs` | **pure static**: IOCTL-коды/GUIDs/константы, buffer builders (порт из спайка), event parser, `SplitTunnelPolicy` decisions (§4) | ~350 |
| `SplitTunnelDriverInterop.cs` | `static class Native` — P/Invoke (порт из спайка + CancelIoEx/GetOverlappedResult/CreateEvent), `SafeDeviceHandle` | ~250 |

Правки существующих: `ProcessImagePath.cs` (+native-form variant + shared
name→path resolver, §1.4), `VpnEngine.cs` (W1.2 hooks, §5),

Все три файла: `#nullable enable`, `[SupportedOSPlatform("windows")]`,

### 1.2 Public API surface (что зовёт VpnEngine)

```csharp
[SupportedOSPlatform("windows")]
internal interface ISplitTunnelDriver : IDisposable   // seam по образцу IWindowsDnsHardening
{
    bool IsEngaged { get; }
    bool IsPumpHealthy { get; }                        // для badge-tooltip / diag
    event Action<bool>? EngagedChanged;                // W1.3 badge
    Task<bool> EngageAsync(SplitTunnelEngageRequest request, CancellationToken ct);
    Task DisengageAsync(CancellationToken ct);         // RESET + снять sublayers; never throws
}

// Всё, что нужно для полного (re)engage. Идемпотентно: повторный Engage =
// Mullvad-style reinitialize (RESET → INITIALIZE → REGISTER_PROCESSES →
// REGISTER_IP_ADDRESSES + SET_CONFIGURATION).
internal sealed record SplitTunnelEngageRequest(
    IReadOnlyList<string> ExcludedDosPaths,   // уже разрезолвленные DOS-пути
    string? TunnelIpv4, string? TunnelIpv6);  // из settings.Tun; internet-NIC ищем сами
```

`SplitTunnelDriverManager : ISplitTunnelDriver` — единственная реализация;
интерфейс нужен ТОЛЬКО как тест-seam для W1.2 lifecycle-тестов (это
устоявшийся паттерн кодовой базы: `IWindowsDnsHardening` +
`NullWindowsDnsHardening`, `IFirewallManager`). Тестовый двойник —
`FakeSplitTunnelDriver` в Tests, не в Core.

Заметки по API:
- **Нет отдельных `RegisterIps` / `SetExcluded` в публичном API.** Любое
  изменение (excluded-список, TUN IP) → повторный `EngageAsync` — драйвер
  переинициализируется за миллисекунды, идемпотентность дешевле двух
  дополнительных публичных методов с частичной инвалидизацией состояния.
  IP-change физического NIC manager обрабатывает САМ (§1.6) — VpnEngine
  об этом не знает.
- `EngageAsync` возвращает `false` (не throws) при любом сбое — caller'у
  не нужен try/catch, fail-open заложен в контракт. Исключений наружу нет
  by design.
- `DisengageAsync` never-throws + идемпотентен (звать при не-engaged — no-op).

### 1.3 Ownership (кто чем владеет)

| Ресурс | Владелец | Создание | Teardown |
|---|---|---|---|
| SCM-сервис `mullvad-split-tunnel` (kernel, demand-start, binPath = `<install>\driver\mullvad-split-tunnel.sys`) | manager | первый `EngageAsync`: OpenService → есть? проверка binPath (collision guard §3 p.3, self-heal через ChangeServiceConfig если наш-но-переехал) : CreateService. StartService (tolerate ALREADY_RUNNING) | НЕ трогаем на Disengage. STOP+DELETE только `uninstall.ps1` (W1.4) |
| Device handle `\\.\MULLVADSPLITTUNNEL` | manager, один `SafeDeviceHandle` | `CreateFileW(GENERIC_READ\|WRITE, share=0, FILE_FLAG_OVERLAPPED)` на Engage | close на Disengage/Dispose (после RESET). Держим открытым пока engaged — exclusive handle заодно блокирует второго агента |
| 2 WFP sublayers (baseline `{21E068A2-...}` w=0xFFFF, dns `{E65841B6-...}` w=0xFFFE) | manager | на Engage ДО INITIALIZE: `FwpmSubLayerAdd0` x2, tolerate `FWP_E_ALREADY_EXISTS` (спайк-код как есть) | на Disengage ПОСЛЕ RESET: `FwpmSubLayerDeleteByKey0` x2, tolerate NOT_FOUND/IN_USE (лог, не fatal) |
| Driver state machine | manager отражает, драйвер владеет | engage-flow строго по ABI-доку: `GET_STATE != STARTED → RESET` → INITIALIZE → REGISTER_PROCESSES → REGISTER_IP_ADDRESSES + SET_CONFIGURATION → verify `GET_STATE == ENGAGED(4)` | Disengage: `RESET` (METHOD_NEITHER, null buffers) → verify STARTED |
| Event pump поток | manager | стартует после успешного engage | §2.4 shutdown |
| `NetworkChange.NetworkAddressChanged` подписка | manager | подписка при engage | отписка при disengage/Dispose |

**Crash-recovery sweep (зеркало `_unixDns.RestoreStrandedIfAny`):** при
первом создании manager'а (lazy, до первого engage) — если device
открывается и `GET_STATE > STARTED`, а мы ещё ничего не engage'или → это
хвост от крэша прошлой сессии со stale IP/конфигом → `RESET` + лог.
Излечивает "excluded-апы биндятся к вчерашнему IP".

### 1.4 Reuse (ponytail — что НЕ пишем заново)

- **name → DOS path**: логика `FirewallManager.ResolveProcessPath`
  (running-process image via `ProcessImagePath.ResolveRunningPath` +
  `where.exe` fallback через IProcessRunner) извлекается в
  `internal static ProcessImagePath.ResolveNameToPath(string name,
  IProcessRunner runner, ILogger?)`; FirewallManager делегирует туда же
  (root-cause reuse, один источник правды, диффа ~30 строк).
- **process image → NT path**: `ProcessImagePath` уже несёт
  `QueryFullProcessImageNameW` P/Invoke — добавляем перегрузку с
  `PROCESS_NAME_NATIVE=1` (спайк-код), не дублируем DllImport.
- **DOS → NT path** (`C:\... → \Device\HarddiskVolumeN\...`): спайковый
  `DosPathToNtPath` через `QueryDosDeviceW`, чистая часть — в Protocol (§4).
- **internet-NIC picker**: живёт в `NetworkInterfaceDetector` (существующий
  файл): `GetInternetInterfaceAddresses(ownTunName, logger)` — enumerate
  `NetworkInterface.GetAllNetworkInterfaces()`, кандидаты = Up + IPv4
  unicast + непустой `GatewayAddresses`, минус own-TUN (по имени из
  settings), минус loopback, минус WG/AWG/Tailscale (**reuse существующего
  `IsWireGuardName`**). Выбор — pure `PickInternetInterface` (§4):
  Ethernet > Wireless80211 > прочее, детерминированный tie-break, лог
  выбора. v6 = global unicast выбранного NIC, если есть; иначе zero
  (spike proven v4-only работает).
- **Снапшот процессов**: Toolhelp32-код спайка как есть (это НЕ
  `IProcessScanner` — сканеру нужны profile-правила, драйверу нужно ВСЁ
  дерево pid/ppid/NT-path; разные задачи, не натягиваем интерфейс).
- **pid-recycle guard**: спайковый (parent новее ребёнка → parent=0), как
  pure post-processing в Protocol.

### 1.5 Thread-safety model

- **Один `SemaphoreSlim(1,1)` (`_gate`) сериализует всю control-плоскость**:
  Engage / Disengage / re-register / crash-sweep. Все публичные методы —
  `async`, ожидания I/O — overlapped-event через
  `ThreadPool.RegisterWaitForSingleObject` либо блокирующий
  `GetOverlappedResult(bWait=true)` на `Task.Run` (одинаково корректно;
  берём второе — проще, control-IOCTL миллисекундные; ponytail: без IOCP).
- **Pump-поток** (§2) единственный, кто делает DEQUEUE_EVENT; со своим
  OVERLAPPED. DeviceIoControl на одном handle из двух потоков с разными
  OVERLAPPED — легален by design.
- Состояние (`_engaged`, `_pumpHealthy`) — `volatile bool` + изменения
  только под `_gate`; события (`EngagedChanged`) — вне lock'а.
- `NetworkAddressChanged` handler: debounce 2 s (перезапускаемый
  `CancellationTokenSource`), затем под `_gate` re-detect NIC → если IP
  сменился → повторный engage-flow только REGISTER_IP_ADDRESSES (внутри
  manager'а допустим частичный шаг — это не публичный API).
- `Dispose`: cancel pump → под `_gate` best-effort RESET → close handle →
  снять sublayers → отписки. Never throws.

## 2. Inverted-call event pump (то, что спайк пропустил)

### 2.1 Нужен ли он для корректности? Нет — и это фиксируем.

Из ABI-дока и драйверных README/headers: split-решение принимается в ядре
(process-callout + config match), DEQUEUE_EVENT — уведомительный канал
(inverted call: драйвер комплитит НАШ pending IRP, когда есть событие).
Спайк вообще не слал DEQUEUE_EVENT — exclusion работал и переживал kill.
Следствия:

- **Смерть pump'а НЕ трогает engaged-состояние** (fail-open не значит
  "выключить работающее"). Лог `[SplitTunnel] event pump degraded` +
  `IsPumpHealthy=false` (виден в diag/tooltip).
- Зачем тогда pump: (a) не копить события в ядерной очереди драйвера на
  многодневных сессиях; (b) observability — `START/STOP_SPLITTING_PROCESS`
  это ЕДИНСТВЕННОЕ прямое доказательство "драйвер реально сплитит app X"
  (золото для «у меня Discord не исключается»); (c) `ERROR_MESSAGE` /
  `ERROR_START_SPLITTING` — ранняя диагностика деградаций.

### 2.2 Threading model: dedicated bg-поток, не async

Один `Thread { IsBackground = true, Name = "split-tunnel-events" }`.
Обоснование: цикл = вечно-pending DeviceIoControl + WaitForSingleObject —
это чистый blocking-I/O поток; async/Task ничего не даёт, а держать
pending overlapped поверх thread-pool с кастомным ожиданием — сложнее и
хрупче. Паттерн Mullvad такой же (их event-loop — отдельный поток).

```
loop:
  issue DeviceIoControl(DEQUEUE_EVENT, in=null, out=buf64K, &ovl)   // ERROR_IO_PENDING ожидаем
  WaitAny(ovl.Event, shutdownEvent)
    shutdown → CancelIoEx(handle, &ovl); GetOverlappedResult(discard); exit
    ovl      → GetOverlappedResult → bytes → ParseEventBuffer(buf[0..bytes]) → classify → log
  errors: ERROR_OPERATION_ABORTED → exit (нас отменили / RESET);
          любой прочий → счётчик; 3 подряд → pump degraded, exit (не спиним CPU)
```

- **Буфер**: один reusable pinned `byte[64 * 1024 + 64]` — `ImageNameLength`
  это USHORT (≤ 65535 байт), заголовки фиксированные; переполнение
  невозможно by construction.
- **Cancellation**: `shutdownEvent` (ManualResetEvent) + `CancelIoEx` на
  handle. `Thread.Join(2s)` в Disengage; не дождались → лог + бросаем
  (background-поток умрёт с процессом, handle всё равно закроем — pending
  IRP отменится закрытием handle).
- **Порядок в Disengage**: (1) signal shutdown + CancelIoEx + Join; (2)
  RESET; (3) close handle; (4) sublayers. RESET при живом pending
  DEQUEUE_EVENT легален (драйвер отменяет pended IRPs на reset), но
  детерминированный порядок проще дебажить.

### 2.3 Event parsing (pure, в Protocol)

Порт `parse_event_buffer` из `driver.rs` + layout из `events.h` (natural
alignment, x64):

- `ST_EVENT_HEADER`: `EventId u32 @0` (+4 pad), `EventSize SIZE_T @8`,
  `EventData @16`.
- `ST_SPLITTING_EVENT`: `ProcessId HANDLE @0`, `Reason u32 @8`,
  `ImageNameLength USHORT @12`, `ImageName WCHAR[] @14` (не-null-terminated).
- `ST_SPLITTING_ERROR_EVENT`: `ProcessId @0`, `ImageNameLength @8`,
  `ImageName @10`.
- `ST_ERROR_MESSAGE_EVENT`: `NTSTATUS @0`, `ErrorMessageLength @4`,
  `ErrorMessage @6`.
- Ids: `START/STOP_SPLITTING_PROCESS = 0/1`; `ERROR_FLAG = 0x80000000`;
  `ERROR_START/STOP_SPLITTING = 0x80000001/2`; `ERROR_MESSAGE = 0x80000003`.
  Reason bitflags: INHERITANCE=1, CONFIG=2, ARRIVING=4, DEPARTING=8.

Оффсеты пинятся **golden-vector юнит-тестом** (§4) и один раз сверяются с
живым событием на VM (W1.1 acceptance): запустить notepad из excluded →
в логе `START_SPLITTING pid=... image=...\notepad.exe reason=CONFIG|ARRIVING`.

Classification (pure `SplitTunnelPolicy.ClassifyEvent`): splitting-события →
Information-лог; `ERROR_*` → Warning-лог; unknown id → Debug + skip (forward
compat на бамп драйвера). Никаких управляющих действий по событиям в v1 —
только лог (upgrade-путь: late-bind нерезолвленных excluded по ETW, §5.4).

## 3. Fail-open design — полный перечень failure paths

Инвариант-фон, который делает fallback дешёвым: **W1.2 НЕ меняет
конфиг-генерацию** — sing-box правила `process_name → direct` для
excluded-апов остаются ВСЕГДА, engaged или нет. Драйверный bind-redirect
просто уводит excluded-потоки мимо TUN до того, как sing-box их увидит.
Поэтому "fallback на post-capture" = буквально "ничего не делать" — правила
уже стоят. Это же значит: **никакого специального "перегенерировать конфиг
при сбое драйвера" не нужно.**

| # | Failure path | Detect | Действие | Fallback-состояние |
|---|---|---|---|---|
| 1 | Файлы драйвера отсутствуют/битые (AV съел .sys, ручное удаление) | pre-check: `File.Exists` + sha256 против пина ДО CreateService | лог Warning, `EngageAsync=false` | post-capture; сеть не тронута (ни одного syscall к SCM ещё не было) |
| 2 | CreateService / StartService fail (policy, DSE, чужой LTSC-hardening) | Win32 err от SCM | лог с err-кодом, best-effort DeleteService если сами создали, `false` | post-capture |
| 3 | **Mullvad-collision**: сервис существует, binPath ≠ наш | OpenService + QueryServiceConfig | если path указывает на чужой install (`Mullvad VPN` в пути / файл существует и не наш) → НЕ трогаем чужой сервис, лог "real Mullvad detected", `false`. Если это НАШ старый путь (переехал install) → `ChangeServiceConfig` на новый (self-heal, как Mullvad `install_driver_if_required`) | post-capture (оба VPN живы, ничего не сломано) |
| 4 | Device open fail: `ERROR_FILE_NOT_FOUND` (не загрузился) / `ERROR_ACCESS_DENIED` (exclusive handle занят — живой Mullvad-daemon) | CreateFileW err | лог (в ACCESS_DENIED-ветке — явно про «другой агент держит устройство»), `false` | post-capture |
| 5 | Любой control-IOCTL fail (INITIALIZE / REGISTER_PROCESSES / REGISTER_IP / SET_CONFIGURATION), вкл. `FWP_E_SUBLAYER_NOT_FOUND` | Win32 err / overlapped err | лог шага+кода, **RESET** (вернуть драйвер в inert STARTED), close handle, `false` | post-capture; драйвер загружен, но без фильтров = невидим для сети |
| 6 | Sublayer add fail (BFE stopped, доступ) | FWPM err ≠ 0 и ≠ ALREADY_EXISTS | лог, `false` ДО каких-либо driver-IOCTL | post-capture |
| 7 | Финальный `GET_STATE != ENGAGED` | verify-шаг engage-flow | RESET + close + `false` | post-capture |
| 8 | **ABI mismatch на бампе драйвера** (мусорный state, INVALID_PARAMETER, неизвестные event id) | те же err-пути 5/7 + unknown-id в pump | как 5/7; unknown event = skip. Build-time защита: build.ps1 фейлит сборку при sha256-mismatch бандла (§6.2), т.е. незаметно новый .sys не приедет | post-capture |
| 9 | Event pump умер (3 подряд ошибок DEQUEUE) | pump-loop | лог Warning, `IsPumpHealthy=false`, поток выходит. **Остаёмся ENGAGED** (§2.1 — split в ядре не зависит от pump) | true-split продолжает работать (= spike-режим, live-proven); деградация видна в diag |
| 10 | Re-register IP fail при смене сети | NetworkChange-путь | retry 1 раз через 5 s; снова fail → `DisengageAsync` (excluded вернутся на post-capture маршрут через живой TUN) + лог | post-capture. Держать ENGAGED со stale internet-IP НЕЛЬЗЯ — excluded биндились бы к мёртвому адресу (это анти-fail-open), поэтому именно disengage |
| 11 | RESET fail при Disengage (драйвер wedged) | IOCTL err | лог Error; escalation: `ControlService(STOP)` (переживает ценой известного driver-бага про callbacks — на выключении приемлемо); teardown app продолжаем, никогда не блокируем Stop() | TUN уже снят VpnEngine'ом → маршруты ОС восстановлены; худший случай — фильтры драйвера доживают до перезагрузки, редиректя excluded на физ-NIC (они и так туда шли) |
| 12 | App crash без Stop (stale ENGAGED, потом IP сменился) | crash-recovery sweep §1.3 при следующем старте app | GET_STATE > STARTED && мы не engage'или → RESET + лог | чисто к моменту следующего connect |
| 13 | Исключение в ЛЮБОМ месте manager'а | try/catch по границе всех публичных методов | лог + best-effort RESET/close + `false`/no-throw | post-capture. Manager никогда не пропускает исключение в VpnEngine |

Микро-инвариант очерёдности: sublayers создаются ДО первого driver-IOCTL и
удаляются ПОСЛЕ RESET — так драйверные фильтры никогда не остаются в
удаляемом sublayer'е (иначе `FWP_E_IN_USE`-мусор).

## 4. Pure-decision extraction (testability, зеркало WedgeKillPolicy)

Всё, что можно тестировать без драйвера/ProgramData/сети — pure static в
`SplitTunnelDriverProtocol.cs`. Manager остаётся тонкой I/O-обвязкой.

| Pure unit | Сигнатура (эскиз) | Юнит-тесты (все — без live driver) |
|---|---|---|
| `BuildSublayerGuids` | `(Guid, Guid) → byte[32]` | golden vector: байты обоих GUID в LE-layout на своих оффсетах |
| `BuildAddresses` | `(IPAddress? tunV4, IPAddress? inetV4, IPAddress? tunV6, IPAddress? inetV6) → byte[40]` | оффсеты 0/4/8/24 по ABI; v6-null → нули; порядок tunnel-then-internet (частая ошибка — перепутать) |
| `BuildConfiguration` | `(IReadOnlyList<string> ntPaths) → byte[]` | header NumEntries/TotalLength; entry stride 16, оффсеты string-region-relative; blob UTF-16LE без NUL; 1 путь / 3 пути / пустой список; USHORT-переполнение длинного пути → ArgumentException |
| `BuildProcessRegistry` | `(IReadOnlyList<ProcInfo>) → byte[]` | entry stride 32; empty-path → off/len 0; смешанный список; round-trip через тестовый reverse-парсер |
| `ApplyPidRecycleGuard` | `(Dictionary<uint,ProcInfo>) → void` | parent новее ребёнка → parent=0; нормальная пара не тронута; parent отсутствует в map → не тронут |
| `ParseEventBuffer` | `(ReadOnlySpan<byte>) → SplitTunnelEvent` | golden vectors для всех 5 event id (byte-layout §2.3); unknown id → Unknown; буфер короче заголовка → malformed (не throw) |
| `DosPathToNtPath` core | `(string dosPath, Func<string,string?> queryDosDevice) → string` | обычный путь; нижний регистр диска; без ведущего `\`; не-drive путь (UNC) → null/reject; QueryDosDevice-фейл → null |
| `PickInternetInterface` | `(IReadOnlyList<NicSnapshot>) → NicSnapshot?` (record: name, desc, type, isUp, hasV4Gateway, v4, v6) | single-NIC; TUN отфильтрован по имени; WG/AWG/Tailscale отфильтрованы (reuse `IsWireGuardName`); ethernet предпочтён wifi; нет кандидатов → null; детерминизм при равных |
| `SplitTunnelPolicy.ShouldEngage` | `(isWindows, routingMode, routingAppsMode, hasExcludedApps, driverSetting) → bool` | матрица: split+exclude+непустой список+auto → true; include / full / пустой список / off / не-Windows → false |
| `SplitTunnelPolicy.ClassifyEvent` | `(eventId) → EventSeverity` | splitting → Info; error-flag → Warning; unknown → Debug |
| `SplitTunnelPolicy.ShouldReRegister` | `(oldAddrs, newAddrs) → bool` | смена v4 → true; идентичные → false; появление v6 → true |

Итого ~30-35 юнит-тестов, ноль моков, ноль ProgramData (учтён baseline
`dev-box-test-env-baseline`: эти тесты обязаны быть зелёными и локально).
Буферные тесты — главная ценность: они пинят hand-packed ABI, единственное
место, где молчаливая порча (сдвиг оффсета при рефакторинге) даёт
руническую ошибку драйвера вместо компайл-ошибки.

## 5. W1.2 — VpnEngine wiring

### 5.1 Hook points (ровно четыре, все в VpnEngine.cs)

Manager инжектится опциональным ctor-параметром
`ISplitTunnelDriver? splitDriver = null` (паттерн `IWindowsDnsHardening`);
`PlatformServices.CreateVpnEngine` создаёт реальный на Windows, тесты
передают fake. Ленивое создание — внутри manager'а ничего не трогает
систему до первого Engage.

1. **Engage — конец `StartAsyncInternal`, после успешного
   `pipeline.ExecuteAsync` (не-EarlyReturn ветка), рядом с Unix-DNS-блоком.**
   sing-box уже запущен (Phase 7), auto_route уложен, мониторы стоят
   (Phase 8). Гейт: `SplitTunnelPolicy.ShouldEngage(...)` по
   `settings.App.RoutingMode/RoutingAppsMode/RoutingAppsExclude` +
   yaml-параметру `true_split_driver: auto|off` (default auto; escape hatch
   для суппорта — выключить драйвер, не трогая режим; UI-тумблер не делаем
   до user-signal). Пути: `RoutingAppsExclude` имена →
   `ProcessImagePath.ResolveNameToPath` (§1.4); нерезолвленные — лог +
   skip (их продолжает вести post-capture правило; upgrade §5.4).
   Покрывает и failover-рестарты (они re-enter `StartAsyncInternal`) —
   engage идемпотентен.
2. **Re-engage — конец успешного `ApplyAsync`.** Если
   `_splitDriver?.IsEngaged == true` ИЛИ `ShouldEngage` теперь true →
   повторный `EngageAsync` с пере-разрезолвленными путями. Одним махом
   закрывает: изменение excluded-списка, смену TUN-IP (TunFingerprint
   forceRestart — рестарт in-place, БЕЗ прохода через StartAsyncInternal!),
   переключение include→exclude. `ShouldEngage`-false после apply (ушли в
   include/full) → `DisengageAsync`.
3. **Disengage — `TeardownInternal`, ПОСЛЕ `_singBox?.Dispose()`** (сразу
   за slipstream-stop). Порядок принципиален: пока sing-box умирает,
   excluded-потоки продолжают жить на NIC-биндах (0-gap до последней
   миллисекунды); к моменту RESET TUN уже снят → новые бинды excluded
   пойдут обычным default-route → тот же физ-NIC. Разрыва нет ни в одной
   точке. `Task`-мостик: `DisengageAsync` синхронно ждётся с таймаутом
   (5 s) — teardown-путь и так синхронный, manager never-throws.
4. **`Dispose`** — `try { _splitDriver?.Dispose(); } catch { }` в обеих
   ветках (running и partial-start), рядом с firewall-cleanup.

### 5.2 IP-change → re-register

Заявленный в goal «существующий network-change hook, который слушает
HealthMonitor» — **проверено: его нет** (desktop-Core не подписан на
`NetworkChange`; HealthMonitor чисто таймерный). Правка плана: manager САМ
подписывается на stdlib `NetworkChange.NetworkAddressChanged` пока engaged
(§1.5, debounce 2 s → re-detect → REGISTER_IP_ADDRESSES при изменении;
fail-path #10). VpnEngine не участвует — ноль нового wiring'а.

### 5.3 Контракт с W0.1 wedge-kill / crash-recovery

Ключевой факт (проверен по коду): HealthMonitor-восстановление
(`OnSingBoxCrashed` → `AttemptRestart` → `SingBoxManager.Restart()` /
relaunch-primitive) происходит **внутри живого VpnEngine, без
Stop()/StartAsync** → хуки 1/3 не срабатывают → **драйвер остаётся ENGAGED
сквозь всё down-window + рестарт**. Это не баг, а вся суть W1: excluded
живут через NIC, пока sing-box лежит/перезапускается/wedge-kill'ится.
После relaunch TUN получает тот же IP из того же конфига → re-register не
нужен. Контракт фиксируем тестом (§7.2 сценарий d) и комментом у хука 3.
Достигнут restart-ceiling → `FailoverRequested` →
`ExecuteProbeFailoverRestartAsync` → `TeardownInternal` (disengage) →
`StartAsyncInternal` (engage) — само закрывается хуками 1/3.

### 5.4 Kill-switch / Wave-39 scoping (open-q #1 — закрыто кодом)

- **Kill-switch (`CreateBlockRules`) — per-program**: правила создаются
  ТОЛЬКО для routed-процессов профиля (block_on_vpn_fail), excluded-апов в
  `_managedRules` нет by construction → MPSSVC-блоки и driver-permits не
  пересекаются. Live-тест W1.0 это подтвердил. Изменений не требуется;
  acceptance-пункт «routed апы fail-closed при kill» остаётся в W1.3 verify.
- **Wave-39 DNS-lockdown — глобальный блок UDP/53+TCP/53/853 с allow
  loopback/TUN**, НО: (a) DNS excluded-апов на 99% идёт через
  dnscache/svchost — svchost не excluded → его DNS едет в туннель → allow-TUN
  пропускает (caveat #1 драйвера работает «на нас»); (b) в down-window
  `DnsLockdownPolicy.Decide` уже fail-open (снимает блок при не-serving
  туннеле) — W0.1 это сделал за нас. Остаточный угол: excluded-ап со СВОИМ
  UDP/53 (некоторые игры) при живом туннеле + включённом (opt-in!)
  DnsLeakLockdown получит блок своего прямого DNS. Решение W1.2: **принять
  и задокументировать в W1.3 caveats** (рядом с dnscache-caveat, тот же
  корень); per-excluded-app allow-rules — только по user-signal. Кода — ноль.
- **Upgrade-путь для нерезолвленных excluded** (Discord из %LocalAppData%,
  запущенный после connect): ETW уже стоит (`EtwProcessMonitor` +
  `ProcessStarted` в `StartMonitorsPhase`) — по событию о старте
  excluded-имени дёрнуть re-engage с дорезолвленным путём. В W1.2 НЕ делаем
  (post-capture правило ловит такой ап и так — деградация мягкая);
  заводим follow-up chip после live-verify, если сценарий реально жмёт.

### 5.5 Uninstall-on-app-uninstall

`packaging/windows/uninstall.ps1` уже стопит/удаляет службу VPNRouter —
добавляем симметрично: `sc.exe stop mullvad-split-tunnel` (best-effort;
в норме драйвер уже в STARTED-inert после Disengage) + `sc.exe delete` +
заметка в лог скрипта. RESET перед stop из скрипта недоступен (app уже
удалён) — приемлемо: known-bug драйвера течёт callbacks до ребута, машина
и так в uninstall-сценарии. W1.4.

### 5.6 W1.2 тесты (fake driver, ноль Windows-зависимостей)

- engage вызван после успешного Start в exclude-режиме; НЕ вызван в
  include / full / пустой список / `true_split_driver: off`.
- disengage вызван в Stop() до firewall-teardown; вызван в Dispose.
- ApplyAsync: смена excluded-списка → re-engage с новым набором; уход в
  include → disengage.
- fake, возвращающий `false` из Engage → Start завершился успешно, статусы
  не искажены (fail-open сквозной).
- seam-паттерн и стиль — как `VpnEngineDnsLockdownLifecycleTests` /
  `VpnEngineSplitTunnelLifecycleTests` (существующие).

## 9. Open risks (что остаётся и как принято)

| Риск | Оценка | De-risk / acceptance |
|---|---|---|
| Event-pump correctness (единственный не-spike-proven код) | MED→LOW | pump выведен из correctness-контура (§2.1): его смерть не трогает split и не бричит сеть; parser pure + golden tests; live-валидация оффсетов первым же прогоном 7.2-a |
| ABI drift на бампе драйвера | LOW (частота бампов Mullvad низкая) | build-time sha256 gate (§6.2) делает бамп ФИЗИЧЕСКИ невозможным без ручного обновления пинов; процедура бампа = re-extract ABI-док + повторный 7.2-a на VM; runtime fail-path #8 ловит остальное |
| Real-Mullvad coexistence | LOW | guard #3/#4: чужой сервис не трогаем, занятый handle → post-capture; packaging-тест W1.4-f. Резидуальный: оба «наши» (наш stale переехавший install) → ChangeServiceConfig self-heal |
| Driver limitations как UX-жалобы (DNS via svchost / localhost-UDP / multicast / UWP) | принято | caveats выведены в badge-tooltip + README (W1.3); это ограничения bind-redirect-класса, «чинить» нечего — только честно показывать |
| Wave-39 vs excluded-ап со своим UDP/53 при живом туннеле | принято (opt-in фича × редкий паттерн) | задокументировано в caveats; per-app allow — по user-signal (chip после релиза) |
| Multi-NIC internet-pick на экзотике (docked laptop: ethernet+wifi оба с gateway) | LOW | pure `PickInternetInterface` детерминирован + лог выбора; «неправильный» из двух живых NIC всё равно даёт egress; починка = поправить одну pure-функцию по diag-логу |
| Kernel event queue при умершем pump'е на многодневной сессии | LOW | drivers-side поведение то же, что у Mullvad в проде; pump degraded — редкое состояние, диагностируемое; ребут/reconnect чистит |
| Орфан kernel-сервис после ручного удаления папки app | принято | demand-start без стартующего = inert запись SCM; uninstall.ps1 чистит нормальный путь |
| Оценки поехали из-за VM-harness | MED | буфер в §8; гочи W1.0 записаны в 7.2 как обязательный чек-лист |

Вопрос, где нужен человеческий взгляд ДО W1.2: **гейт `ShouldEngage` по
умолчанию auto-ON для всех существующих exclude-пользователей** (первый
connect после апгрейда молча ставит kernel-сервис). Альтернатива —
opt-in-тумблер на первый релиз. Техническая рекомендация: auto-ON (фича и
есть режим exclude; fail-open доказан), но это product-решение о моменте
появления драйвера у юзеров — подтвердить при cut.
