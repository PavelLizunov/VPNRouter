# v2.31.10 — TgProxy autostart observability (DBG-3)

## Триггер

Sister DBG-2 task (App-side `AutostartTgProxyAsync`) shipping into
v2.31.10-rN. Pre-fix the Service-side `VPNRouterService.AutostartTgProxyAsync`
emitted exactly two outcome lines:

- `[Service] TgProxy started on port {Port} (PID {Pid})` (success)
- `[Service] TgProxy autostart failed after retries` (failure)

Plus a single early-return: `[Service] TgProxy not installed, skipping autostart`.

When the autostart silently dropped, we had **no breadcrumb** pointing at:

- WHICH probe failed (PythonExe missing? proxy/ dir missing?)
- WHAT paths were checked
- WHAT command was about to be run
- WHETHER the Python process started but exited within milliseconds (which
  is the canonical failure shape for embeddable-Python/wheel issues — pyc
  cache corruption, `._pth` malformed, port already bound, tg-ws-proxy
  module import error)

This forced "redeploy with extra `printf` then send me the log" round trips
with users for every autostart bug. The same gap mirrored on the App-side
manual-Start path in `MainWindowViewModel.ToggleTgProxyAsync`.

## Симптом

User reports «TgProxy не запускается автоматически» / «иконка не зелёная
после ребута», `vpnrouter*.log` shows nothing actionable. Diagnosis loop
takes days because:

1. ask user to enable verbose logging
2. ship debug build with extra `Console.WriteLine`
3. user reproduces, mails log
4. find: it was a missing wheel / port collision / shadow-blocked Python
   that exited after 200ms

## Root cause (instrumentation gap)

Three high-traffic paths each emit one line on success and one on
catastrophic failure with zero structured context:

1. `TgProxyUpdater.IsInstalled()` — boolean only, no path probe surface.
2. `TgProxyManager.Start(port, secret, verbose)` — logs `python.exe {Args}`
   (full args including secret) once on launch. No post-spawn validation —
   if the Python process launches and exits 100ms later, the only
   subsequent log is the async `Process exited (exit code: N)` warning,
   which races with the spawn-success log line and confuses the trail.
3. `ResilientStarter.StartWithBackoffAsync` — only logs on retry
   (`attempt > 1`) and on final failure. First-try success is invisible.

Wired together in `VPNRouterService.AutostartTgProxyAsync`:

- Method entry: not logged.
- After `IsInstalled` true + secret present: not logged.
- ResilientStarter handoff: not logged.

## Fix strategy

### 1. `TgProxyUpdater.IsInstalled`

- Add `IsInstalled(ILogger? logger)` overload.
- Old `IsInstalled()` delegates to new with `logger: null` (back-compat,
  pin'd by `IsInstalled_ParameterlessOverload_DelegatesToLoggerOverloadWithNullLogger`).
- New overload emits one structured line listing both paths + per-component
  bool + overall bool:

  ```
  [TgProxy] IsInstalled: PythonExe at {Path} -> {Exists}, ProxySourceDir at {Path} -> {Exists}, overall = {True|False}
  ```

### 2. `TgProxyManager.Start`

- Build `redactedArgs` from `args` via new internal-static
  `RedactSecretInArgs` (regex `--secret\s+\S+` → `--secret REDACTED`).
- Log full PSI shape (FileName, redacted Arguments, WorkingDirectory,
  CreateNoWindow, UseShellExecute) right before `Process.Start`.
- Log spawned PID immediately after (was: same line as args in pre-fix).
- Add 2-second `WaitForExit(2000)` watchdog:
  - If process exited within window → log `ExitCode` + `StandardError.ReadToEnd()`
    tail explicitly. This is the line that catches Python embeddable
    failures.
  - If still alive → log `still alive after 2s probe` so success state
    is unambiguous.

The redaction guarantee is the privacy-critical surface — secret never
appears in any log line.

### 3. `ResilientStarter.StartWithBackoffAsync`

- Log BEFORE every attempt: `[Resilient] {Component}: attempt {N}/{Max}, delay={Delay}s`.
  First attempt has `delay=0`; subsequent attempts use `backoffSeconds[attempt-2]`
  so the printed delay matches what was actually waited.
- Log per-attempt success: `[Resilient] {Component}: attempt {N}/{Max} succeeded`.
- Log per-attempt failure (in addition to existing post-attempt warning):
  `[Resilient] {Component}: attempt {N}/{Max} failed-with-{Error}`.

### 4. `VPNRouterService.AutostartTgProxyAsync`

- Entry breadcrumb: `[Service] AutostartTgProxyAsync: entered`.
- Switch `IsInstalled()` call to logger-aware overload (`IsInstalled(Serilog.Log.Logger)`).
- After secret check passes + port chosen:
  `[Service] AutostartTgProxyAsync: secret configured (len {SecretLen}), port {Port} chosen, handing to ResilientStarter`.
  Note: `{SecretLen}` not `{Secret}` — only the length is leaked, never
  the value. Negative-pin'd by
  `VPNRouterService_AutostartTgProxyAsync_LogsEntryAndDecisions`.

### 5. App-side parity

DBG-2 sister hasn't merged its `AutostartTgProxyAsync` into
`MainWindowViewModel`. The existing manual-start handler in
`ToggleTgProxyAsync` is instrumented with the same shape so:

- `[VM] ToggleTgProxyAsync: start path entered`
- `IsInstalled(_logger)` (logger-aware)
- `[VM] ToggleTgProxyAsync: secret configured (len {SecretLen}), port {Port}, calling TgProxyManager.Start`

A `TODO(DBG-2 sister)` comment marks the spot to copy these patterns
verbatim into the future App-side autostart helper.

proxy/ dir) — output captured 2026-05-07:

```
[03:53:28 INF] === Repro 1: existing installation (this VM has tg-proxy installed) ===
[03:53:28 INF] [TgProxy] IsInstalled: PythonExe at C:\ProgramData\VPNRouter\tg-proxy\python\python.exe -> True, ProxySourceDir at C:\ProgramData\VPNRouter\tg-proxy\proxy -> True, overall = True
[03:53:28 INF] Repro 1 outcome: IsInstalled returned True

[03:53:28 INF] === Repro 2: synthetic missing-deps (rename proxy/ then probe) ===
[03:53:28 INF] (simulated: proxy/ dir moved aside)
[03:53:28 INF] [TgProxy] IsInstalled: PythonExe at C:\ProgramData\VPNRouter\tg-proxy\python\python.exe -> True, ProxySourceDir at C:\ProgramData\VPNRouter\tg-proxy\proxy -> False, overall = False
[03:53:28 INF] Repro 2 outcome: IsInstalled returned False
[03:53:28 INF] (In Service path the next log would be: '[Service] TgProxy not installed, skipping autostart')

```

Repro harness was a temporary `tools/log-repro/` console (deleted after
capture); the same probe runs in production through `VPNRouterService.AutostartTgProxyAsync`.

## Оценка

- Logging instrumentation only — no behavioural change to autostart, no
  WFP / network / process-lifecycle modifications.
- Risk: low. Pure additive log calls, all guarded with `?.` against null
  logger.
- Dependencies: none.
- Estimate: 1.5h actual.
