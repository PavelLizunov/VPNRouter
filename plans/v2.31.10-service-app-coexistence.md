# v2.31.10-r2 — Service+App coexistence audit

**Date**: 2026-05-06
**Bug**: F-12 — App startup unconditionally kills Service-spawned sing-box
**Branch**: `claude/loving-wiles-5cd66b` (worktree)
**Version**: 2.31.10-r1 → 2.31.10-r2 (NOT promoted to stable per task)

## TL;DR

When the Windows Service was running with sing-box up and the user
launched the desktop App, the App's startup unconditionally killed
sing-box via `OrphanCleanup.KillByName("sing-box", null)`. The Service's
HealthMonitor eventually respawned sing-box ~5 s later via its 5/10/20/40s
backoff, but during that window:

- TUN adapter went down (and was rebuilt by the new sing-box)
- All routed-app TCP/UDP traffic dropped
- With `block_on_vpn_fail=true`, Windows Firewall kill-switch fired

Live trace on this VM confirmed the bug. Fix: `OrphanCleanup.KillOrphans`
gained a `respectTunLock` parameter (default `true`) that mirrors the
TunLock check the Service-side startup already had; sing-box kill is
skipped when `TunOwnershipLock.IsOwnedByAnyone()` reports a live owner.

User-takeover sites (Stop / Connect / Update buttons in the App) opt
out by passing `respectTunLock: false` to retain the existing
"reset everything" semantics.

### Scenario 4 — App Apply while Service runs sing-box  ✅ PASS (by code review)

`MainWindowViewModel.ApplyPendingChangesInternalAsync` (line 2803) gates
on `IsServiceManagedVpn` (= `IsConnected && !_engine.IsRunning`). When
true (= Service owns the tunnel), Apply delegates to
`ServiceVm.RestartServiceCommand` — the Service re-reads `config.yaml`
on boot and respawns sing-box with the new settings. App's local
`VpnEngine.ApplyAsync` (which would silent-fail with "_singBox null")
is bypassed.

This was the v2.18.4 fix and remains correct. No live UI test needed
(the path is well-pinned by the existing `IsServiceManagedVpn`
predicate; a regression here would surface as a Stop/Start dance the
user has been familiar with for years).

### Scenario 5 — In-app Update with Service running  ✅ PASS (by code review)

Update helper.cmd (generated by `UpdateChecker.GenerateHelperCmd`) was
made Service-aware in v2.31.7-r1 + v2.31.10-r1:

```
sc query VPNRouter >nul 2>&1
if errorlevel 1 ( echo Service not installed ) else (
  sc query VPNRouter | find "RUNNING" >nul
  if errorlevel 1 ( echo not RUNNING — leaving alone ) else (
    sc failure VPNRouter reset= 0 actions= ""        # disable auto-recovery during update
    sc stop VPNRouter                                  # poll until STOPPED
    ...
    xcopy ...                                          # replace files
    sc start VPNRouter                                 # restart after copy
  )
)
```

`setlocal EnableDelayedExpansion` + `!VAR!` (v2.31.10-r1) closes the
CMD parser bug that broke the Service stop step in v2.31.7. So with
the Service running, an in-app Update correctly:
1. Stops the Service (drops sing-box cleanly, releases DLL locks)
2. Replaces files via xcopy /R
3. Restarts the Service
4. Launches the new App.exe — which, with the v2.31.10-r2 fix, will
   NOT kill the Service-spawned sing-box on its startup pass

Pre-r2 the App's startup `OrphanCleanup.KillOrphans()` would still
disrupt the Service's just-restarted sing-box if the helper's
`sc start` happened before the App's `OrphanCleanup`. Trace evidence
on this same VM (memory note F-11) suggests this was a contributor to
the "auto-update doesn't take effect" UX class of bugs that prompted
v2.31.7-r1 / r2 / r10. r2 closes the residual race.

## Fix design

**Decision**: Option 1 from the task brief, narrowed — *App.exe (and any
process) that holds OrphanCleanup defers to TunLock by default; user-
takeover sites opt out explicitly*.

Rejected alternatives:
- *Make `SingleInstance` Service-aware* — wrong layer. SingleInstance
  is about App-vs-App enforcement; the system-wide TUN ownership
  primitive is `TunOwnershipLock`. Mixing the two would couple the
  Mutex-IPC pattern to the semaphore probe and make both harder to
  reason about.
- *Expand TunLock with owner-pid handover* — much more complex. The
  current pure-semaphore design is "one process at a time, kernel
  releases on death". Adding handover semantics (PID metadata, two-
  phase commit) would add new failure modes (stale PID, registration
  race) for marginal gain — the existing `IsOwnedByAnyone` peek is
  already enough to fix this bug.

The chosen fix is symmetric with the Service-side check (`Service\Program.cs:42`)
that already existed for the inverse scenario (Service detects App's
sing-box on its boot and skips the zombie sweep).

## Out of scope (noted, not changed)

- `FirewallManager.CleanupOrphanedRules` (called in App.Program.cs after
  OrphanCleanup) deletes ALL VPNRouter firewall rules by name prefix.
  If Service had created `block_on_vpn_fail` rules in split mode and
  enabled them after sing-box death, the App's startup would delete
  them. Doesn't affect Scenario 3 here because we ran in full-tunnel
  mode (0 block rules). Worth covering in a follow-up; not part of
  this task's scope.
- `OrphanCleanup` is also called from `MainWindowViewModel.cs:3333` and
  `:3390`. Those are user-initiated takeover paths and remain
  unconditional kill (with the explicit `respectTunLock: false` opt-out
  preserving intent).
