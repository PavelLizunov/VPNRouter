# MTU / fragmentation robustness — исходники отгружаемого форка (не рассуждения)

Продолжение `sdr-research-realtime-games-nat-2026-07-02.md`. Вопрос пользователя:
«1420 не двигает ли обрыв — что если что-то шлёт 1500, и мы снова там же?».
Ответ получен чтением ТОЧНОГО отгружаемого форка (sing-tun v0.8.10 из Go-кэша +
`Leadaxe/sing-box-lx@c7a2592e/submodules/wireguard-go`), а не из памяти.

## Факты (file:line, проверено)

1. **MSS-клампинга в sing-box НЕТ.** Единственные `MSS` в sing-tun — константы
   парсера заголовка (`internal/gtcpip/header/tcp.go:90,142,232`), клампирующего
   кода нет. Значит MSS для TCP ставит **ОС клиента** = `TUN_MTU − 40` в SYN, в
   обе стороны. Программной страховки нет — всё держится на корректном TUN MTU.
2. **System-стек ДРОПАЕТ IP-фрагменты** (`stack_system.go:570-576`,
   `processIPv4UDP`): `MoreFragments` → «ipv4: fragment dropped»;
   `FragmentOffset()!=0` → «ipv4: udp: fragment dropped». Только НЕ-фрагментированный
   UDP NAT-ится и форвардится. **Фрагментация как fallback не работает** ни в одну
   сторону: если ОС раздробит oversized-UDP (DF снят) — sing-box выкинет куски.
3. **PMTUD-сигнализации НЕТ.** `ICMPv4FragmentationNeeded` (`icmpv4.go:113`) — только
   константа, ни одного call-site эмиссии. `rejectIPv4WithICMP` (`stack_system.go:675`)
   зовётся лишь с Port/Host-Unreachable. Приложение НЕ получает от туннеля подсказки
   «ужми пакет».
4. **wireguard-go `DefaultMTU = 1420`** (`device/tun.go:14`) — WG-стандарт; наш
   `AwgEndpointMtu=1280` (`ConfigGenerator.cs:58`) его же и придавливает. Device
   способен нести до `MaxContentSize` (~1950B на Windows, `constants.go:32`) — то
   есть 1420 не упирается ни в какой предел форка.

## Что из этого следует (ответ на вопрос)

Обрыв **жёсткий** (ни фрагментации, ни PMTUD — подтверждено). НО кто в него может
попасть — ограничено классом трафика:

- **TCP** (веб, загрузки, Steam-CM, control-каналы игр — бОльшая часть): ОС
  клампит MSS к `TUN_MTU−40` ДО сборки сегмента, в обе стороны. Физически не
  превысит. **Иммунен** (при отсутствии инверсии TUN>endpoint — ровно тот баг,
  что дал DoH-затык).
- **QUIC / HTTP3 / сам Hysteria2-транспорт**: DPLPMTUD (RFC 8899), сам ужимается
  до ~1200–1350; Hy2 вдобавок **фрагментирует UDP-over-QUIC на прикладном уровне**
  (реассембли на exit'е). **Иммунен.**
- **Единственный уязвимый класс: DF-UDP размером > TUN MTU, без PMTUD.**
  Реальные представители — SDR-класс (Dota 1328B, CS2). Игры **сами капают**
  размер датаграммы под совместимость с реальными сетями — ~1300 это потолок.
  **Ничего легитимного не шлёт 1500 DF-UDP по интернету** (сломалось бы на любом
  пути <1500 и без нас).

**Вывод: 1420 — не произвольное число, «двигающее обрыв в новый трафик».** Это
WG-стандарт (= `DefaultMTU` форка), и он покрывает ВЕСЬ уязвимый класс (игровой
UDP кончается ~1300). Между 1420 и 1500 в категории DF-UDP-без-PMTUD осмысленного
трафика нет — падать обратно в ту же точку нечему.

## Настоящий разрыв — НЕ «кто-то шлёт 1500», а underlay < 1500

Если реальный path-MTU у клиента/exit'а < 1500 (PPPoE 1492, мобилка ~1400,
туннель-в-туннеле), то даже endpoint 1420 → внешний зашифрованный пакет 1480+ >
underlay → фрагментируется/блэкхолится уже на ВНЕШНЕМ пакете. Вот это переменная,
и она per-network. «1420» безопасно только при underlay=1500.

## Рекомендации (робастно, не числом)

1. **Откатить 1280→1420** (WG-стандарт): endpoint 1420, TUN=min(user,1420), БЕЗ
   инверсии. Покрывает SDR + весь игровой UDP. (Мой r8-кэп 1280 — вредная
   пере-осторожность.) Проверка: `ping -f -l 1372 <ext>` через туннель (1372+28=1400).
2. **НЕ полагаться на «снять DF / фрагментировать»** — system-стек дропает
   фрагменты (факт 2). На этом стеке фрагментация-как-сеть-безопасности мертва.
   (Правка моей же более ранней идеи — снял бы её, не прочитав исходник.)
3. **Underlay<1500 (реальный разрыв):** (a) probe эффективного path-MTU
   (ping-f с уменьшением) → endpoint = pathMTU − WG_overhead(~80); либо (b)
   пользовательская MTU-настройка с гайдом «если игры/крупные загрузки рвутся —
   снизь MTU». Проверить, ставит ли форк DF на ВНЕШНИЙ WG-пакет (если да — внешний
   PMTU-блэкхол; если нет — underlay сам фрагментнёт, деградация но не обрыв).
4. **Для игр самый MTU-робастный транспорт — Hysteria2, а не AWG.** QUIC = DPLPMTUD
   + Hy2 фрагментирует UDP-over-QUIC → SDR-1328 проедет при ЛЮБОМ underlay path-MTU.
   AWG (сырой WG + фрагмент-дропающий system-стек) — наименее MTU-толерантный путь.
   Значит Fable-шный «роутить game-UDP через Hy2-сиблинг» — это не только против
   burst'а (H1), но и **единственный по-настоящему MTU-робастный путь для игр.**
5. **Верификация** — общая с SDR-диагностикой: tcpdump на exit + in-tunnel
   path-MTU-probe покажут, где режется и какой реальный MTU пути.

## Итоговая таксономия «класс × уязвимость к MTU»

| Класс | MSS/PMTUD-самозащита | Уязвим к нашему обрыву? | Фикс |
|---|---|---|---|
| TCP (веб/загрузки/Steam) | MSS-clamp ОС (TUN−40), 2-стор. | НЕТ (если нет инверсии TUN>endpoint) | endpoint≥TUN |
| QUIC/HTTP3/Hy2-транспорт | DPLPMTUD + app-frag | НЕТ | — |
| DF-UDP > MTU без PMTUD (SDR/игры) | нет | **ДА** — единственный класс | endpoint 1420 (покрывает ~1300); либо Hy2-путь |
| Мелкий UDP (<1200: RakNet, voice, DNS) | не нужна | НЕТ | — |

**Bottom line:** правильный фикс — endpoint/TUN 1420 (не 1280) + понимание, что
реальный риск — underlay<1500 (probe/настройка), + для игр Hy2-путь как
MTU-робастная альтернатива. Фрагментация-fallback на system-стеке невозможна —
не закладываться на неё.
