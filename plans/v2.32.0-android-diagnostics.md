# v2.32.0 — Android status-card diagnostics (AND-DIAG)

## Триггер

Android status card показывал только бинарную пару "Connected / Not
connected" + описание. На desktop же — runtime diagnostics (uptime,
LastHealthCheck, LastError, RestartAttempts). Запрос — поднять Android
до desktop-parity по surface'у.

## Симптом

User видит:

```
🟢 Connected
Traffic is routed through the VPN tunnel.
```

Не видит:

- Сколько уже подключён (десктоп показывает live uptime с момента сейфa
  state-flip'а в RuntimeStatus.cs).
- Что health-monitor только что прошёл / провалился / стал stale (десктоп —
  через `_lastHealthCheck` + chip).
- Что был silent disconnect с конкретной ошибкой (на Android это
  ACTION_TUNNEL_ERROR с EXTRA_ERROR_MESSAGE, но v2.31.x только логировал
  через `Android.Util.Log.Warn`, наверх не пробрасывал).

## Root cause

Surface не построен. На стороне data:

- Все три источника есть локально:
  - **Uptime** — можем зафиксировать `_connectionStartedAt = DateTime.UtcNow`
    в OnIntentChanged(true).
  - **Health-check** — sing-box пишет в
    `getExternalFilesDir()/singbox.log` (Phase 6.1 fix).
    Можем naivно дельтить размер / mtime каждые 30 с.
  - **LastError** — receiver MainActivity TunnelStateReceiver уже знает
    msg, но не пробрасывает. Добавить static event
    `TunnelErrorReported` и дёрнуть его перед SetIntent(false).

На стороне UI:

- `BuildSimplePageView` собирал status card как dot+title+desc, без
  заглушек под доп. строки. Расширить layout на 2 опциональных строки.

## Fix strategy

### 1. MainActivity.TunnelErrorReported event

```csharp
public static event Action<string>? TunnelErrorReported;

case ActionTunnelError:
    var msg = intent?.GetStringExtra(ExtraErrorMessage) ?? "(no detail)";
    Log.Warn(...);
    try { TunnelErrorReported?.Invoke(msg); } catch { }
    SetIntent(false);
    break;
```

Receiver всё ещё на binder dispatch thread → подписчики обязаны
marshal'ить в UI thread. На AndroidApp side делаем
`Dispatcher.UIThread.Post`.

### 2. AndroidApp diagnostics state + UI

Полей:

```csharp
private TextBlock? _statusHealthCheck;
private TextBlock? _statusErrorOneLiner;
private DispatcherTimer? _diagnosticsTimer;
private DateTime? _connectionStartedAt;
private string? _lastError;
private DateTime _lastErrorAt;
private DateTime _lastHealthProbeAt;
private long _lastHealthLogSize = -1;
private DateTime _lastHealthLogMTime;
private bool _lastHealthOk;
private bool _firstProbePending;
```

Константы (Phase в коде):

```
ErrorDisplayWindow   = 30s   // auto-clear lastError
HealthProbeInterval  = 30s   // probe cadence
HealthStaleThreshold = 60s   // stale если log не дёргался
```

Layout (внутри status card Border):

```
StackPanel Spacing=6
├─ statusHeaderRow (dot + title)         // title в формате "Connected · 1:23:45"
├─ statusDesc                             // existing description (остаётся)
├─ statusHealthCheck (small, muted/warn)  // hidden когда disconnect
└─ statusErrorOneLiner (small, danger)    // hidden пока нет error
```

### 3. DispatcherTimer pump

Один timer 1-секундный (`DispatcherPriority.Background`):

```
OnDiagnosticsTick:
  1. Если connected → перерисовать title с uptime
  2. Если due (Δ ≥ 30s от предыдущего probe) → RunHealthProbe → ApplyHealthCheckDisplay
  3. Если _lastError != null AND age ≥ 30s → clear + hide
```

Запускается в UpdateConnectionState(connected=true), останавливается
при disconnect (но если есть active error — продолжает крутиться до
истечения окна).

### 4. Health probe — log delta strategy

```csharp
var info = new FileInfo(extDir + "/singbox.log");
var size = info.Length;
var mtime = info.LastWriteTimeUtc;
var grew = _lastHealthLogSize >= 0 && size > _lastHealthLogSize;
var recent = (DateTime.UtcNow - mtime) < HealthStaleThreshold;
_lastHealthOk = grew || recent;
```

Почему log delta а не TCP probe:

| | Log delta | TCP probe |
|---|---|---|
| Network needed | нет | да (round-trip) |
| Per-protocol | works для всего | надо знать proxy host:port |
| Cost | 1 stat call | 1 connect+close |
| Idle false-negative | mtime fallback | время-зависим |
| Failure mode | возвращает stale, не блокирует | timeout = false alarm |

Log delta также corner-case'ит log rotation (size shrinks но mtime
свежий → recent=true).

### 5. Format choice

Auto-switch для uptime:

- < 1 час: `M:SS` (`0:42`, `12:05`, `59:59`)
- ≥ 1 час: `H:MM:SS` (`1:23:45`)

Совпадает с pattern'ом call timer'ов в Slack / WhatsApp.

## Test environment limitation (2026-05-07 session)

KYOCERA Balmuda + Android 12 has a **pre-existing Avalonia
accessibility crash** in
`Avalonia.Android.Automation.ToggleNodeInfoProvider.PopulateNodeInfo`
that fires whenever the OS queries the app's a11y tree. Both
`uiautomator dump` and (more painfully) the system's
`AccessibilityNodeInfoDumper` invocations from `screencap -p` triggered
on focus change crash the app process within 5–10 s of any tap. Logged
as `NullReferenceException` thrown from a
`PropertyInfo.SetValue` reflection call inside the Toggle automation
peer; reproducible on the prior `r2` APK before this AND-DIAG patch
landed (verified by stash + re-build), so it is **not introduced by
this change**.

Net effect on this session: I could capture the disconnected baseline
on first launch, but every subsequent UI interaction (tap Connect, tap
OK on consent dialog, scroll, screencap) eventually triggers the
accessibility query → crash → process death → static
`MainActivity.IntendedConnected` resets to false on relaunch. Result:
the connected and error states render correctly in code but couldn't
be photographed live in this session.

Mitigations I tried that did not work:
1. `am force-stop` + `am start` to force a fresh launch — works for
   ~5 s, then any subsequent screencap kills the app again.
2. Skip `uiautomator dump` entirely — didn't help; `screencap -p` on
   its own appears to wake the same a11y dumper code path.
3. Restart phone via SSH — out of scope for this iteration.

Path forward (follow-up, not blocking):
- File a separate task to debug
  `ToggleNodeInfoProvider.PopulateNodeInfo` (Avalonia 11.3 issue). Most
  likely we're feeding it a control with no `IsChecked` peer or null
  AutomationPeer.
- Or temporarily strip AccessibilityProperties.Name from the new
  RadioButton/CheckBox controls in BuildSimplePageView, see if that
  side-steps the crash.
- Or run the live verify on a different device (e.g. an emulator with
  a11y disabled).

The plan acceptance gate for connected + error states transitions to
"verified on follow-up". The diagnostics code itself is checked in,
builds clean, and is ready for the user-side live verification once the
underlying a11y crash is addressed.

## Оценка

Время: ~2 часа на код + plan + live test. Risk: минимальный — purely
UI / timer code, network не трогает, security periметра не трогает.
Side effects: один новый event (TunnelErrorReported) + один новый
DispatcherTimer + 4 новых TextBlock'а. Никаких изменений в
ConfigBuilder / VpnRouterService / libbox interop.

## Известные ограничения (v1)

1. **Перезапуск App при активном tunnel'е** — `_connectionStartedAt`
   ставится с DateTime.UtcNow в момент когда AndroidApp получает
   IntendedConnected=true (либо при attach, либо на следующий
   broadcast). Если service был up до открытия app, мы недооценим
   uptime (фактическое время подключения старше нашего fix'а). Чтобы
   точно — нужен второй intent extra (started_at_unix_millis) от
   VpnRouterService.java или persistence в SharedPreferences. Не делаем
   в v1, отложено до follow-up.

2. **Log delta может ложно-positive'ить при идле phone** — экран off,
   нет outbound traffic, sing-box ничего не пишет → mtime stale. Через
   60-120 с у пользователя замигает "Stale check" хотя tunnel жив.
   Workaround: increase `HealthStaleThreshold` до 120 с, либо
   complement'ить probe'ом из libbox stats API (Connections endpoint).
   v2 — на 2026-05-08+ если будут реальные complaints.

3. **Health-check не различает "tunnel работает но прокси упал"** —
   sing-box продолжит писать в лог retry-сообщения после падения
   upstream, и probe скажет OK. Точнее — нужен active TCP probe плюс
   log delta. Опять же — отложено до v2.
