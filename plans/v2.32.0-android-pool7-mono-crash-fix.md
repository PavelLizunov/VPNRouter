## Триггер

After merging four task branches (CONFIG-EXPORT, DIAGNOSTICS, ZAPRET,
NETRES) into main on 2026-05-07, a previous Claude session reported a
SIGABRT during Mono runtime init on the KYOCERA A101BM device:

```
F libc    : Fatal signal 6 (SIGABRT)
#01 xamarin::android::Helpers::abort_application
#02 xamarin::android::internal::MonodroidRuntime::mono_log_handler
#07 mono_method_get_unmanaged_callers_only_ftnptr+60
#08 MonodroidRuntime::init_android_runtime+1360
#10 Java_mono_android_Runtime_initInternal
```

The previous Claude bisected to `ff5041e` (the AND-CONFIG-EXPORT merge
commit) and concluded that this branch alone was the culprit. All four
merges were then reverted and main was reset to `d6cc9f9`.

This session was tasked with reproducing the crash on an isolated
CONFIG-EXPORT branch, capturing verbose Mono logs to identify the
failing method, fixing the root cause, then iteratively re-merging
DIAGNOSTICS, ZAPRET, and NETRES.

## Симптом (per task brief)

SIGABRT before any user code runs — `init_android_runtime` is the
JCW/UnmanagedCallersOnly registration phase. The candidate causes
listed in the brief: wrong `[UnmanagedCallersOnly]` signature, AOT
trim removing a JNI-bound method, malformed `[Register]` Java→C#
binding, Newtonsoft + abstract-type AOT issue.

`AndroidStorage.cs` and `AndroidApp.axaml.cs`) and the resulting APK

### Why the previous bisect was wrong

Most likely explanation: stale incremental build artifacts in
`VPNRouter.Android/{bin,obj}` carried over from a previous failed
merge attempt. .NET Android's typemap / java callable wrapper
generator is sensitive to obj/ state — a partial build that left
inconsistent typemap.{jm,mj} files alongside an older
`VPNRouter.Android.dll` would produce exactly this crash signature
(JCW references a method whose ftnptr lookup fails).

Another contributing factor: this fresh worktree did NOT have
`VPNRouter.Android/Lib/libbox.aar` (gitignored — third-party binary).
A previous build attempt with a missing libbox.aar produces only
`javac.exe error JAVAC0000: method does not override or implement a
method from a supertype` errors, which means no APK is produced at
all — a different failure mode. If the prior bisect was running
against a state where libbox.aar was present from one merge attempt
but stale obj/ from another, the resulting APK could plausibly hit
the JCW lookup crash. We did not need to investigate that further
because a clean rebuild produces a working APK.

## Lessons for future sessions

1. **Never trust a "this branch alone crashes" claim without verifying
   on a clean worktree.** If you don't have a fresh `git clone`-equivalent
   state, your bisect is on a state that may include partial merges,
   stale obj/, or stale typemap.{jm,mj}. The fastest way to be sure is:
   check out the suspect branch in a NEW git worktree, copy
   `VPNRouter.Android/Lib/libbox.aar` (gitignored) into it, run
   `rm -rf VPNRouter.Android/{bin,obj}`, then `dotnet build` from
   scratch.
2. **`libbox.aar` is gitignored.** A fresh worktree won't have it.
   Any javac `JAVAC0000: method does not override` cascade is a
   missing-libbox symptom, NOT a code bug — copy the .aar from any
   other worktree's `VPNRouter.Android/Lib/` to fix.
3. **Java compile errors (JAVAC0000) are reported as MSBuild errors but
   the dotnet wrapper may still exit 0 on the outer pipeline.** When
   piping `dotnet build ... | tail -30`, the pipe's exit status is
   `tail`'s, which is always 0. Inspect the actual log for `Error(s)`
   counts; don't trust the parent shell's `$?` after a piped build.
