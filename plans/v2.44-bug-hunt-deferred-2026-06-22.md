# v2.44 adversarial bug-hunt — deferred findings (2026-06-22)

Source: 4 parallel review agents over the v2.44.0 session code (Linux kill-switch,
desktop ConnStats, Clash-YAML parser, Android P4/P1). The low-risk, fully-testable
findings were fixed in **v2.44.1-r1** (see release notes). The items below were
verified real but deferred because they are cross-cutting and/or need device/VM
testing that an unattended session can't fully perform. Each needs a deliberate
decision + targeted testing before shipping.

## P1 — Android: unauthenticated clash_api on 127.0.0.1:9090 (security)

`VPNRouter.Core/Models/VPNConfig.cs` `ClashApi` exposes `external_controller` with
**no `secret`**. On Android, loopback is not UID-isolated, so any other installed
app can `connect("127.0.0.1", 9090)` and read connection metadata (destination
hosts/IPs) or issue control calls (`PUT /configs`, `DELETE /connections`). P1 (live
stats, v2.43.0) introduced the consumer; the exposure predates v2.44.0.

Fix (needs device test): set a random per-session `secret` on the clash_api block in
the Android config builder + send `Authorization: Bearer <secret>` from
`VpnRouterService.java pollStatsOnce()`. Confirm desktop ConnStats
(`ClashSingBoxApi`) either is unaffected (desktop loopback is same-user) or also
sends the secret. Risk: if the header isn't wired consistently, stats silently
break — must device-verify on the phone before ship. Consider unix-socket / abstract
namespace bind as an alternative to a TCP port.

## P1 — Linux/macOS kill-switch: empty processNames is an ambiguous "arm" signal

`LinuxFirewallManager.CreateBlockRules` (and the mirror `MacFirewallManager`) infer
full-tunnel from an **empty** processNames list. But `StartupPipeline` also passes an
empty list when the split-tunnel process scan times out (30s) or throws. So a
split-tunnel user with `block_on_vpn_fail=true` whose catalogue is slow/corrupt gets
the **global** egress kill-switch armed instead of the intended honest no-op — on the
next sing-box hiccup all egress (incl. never-tunnelled direct apps) is dropped.

Fix: plumb the already-computed `isFullTunnel` (StartupPipeline ~line 653) explicitly
into `CreateBlockRules` rather than inferring from list emptiness; only arm on the
deliberate full-tunnel mode. Touches the pipeline + BOTH firewall managers + the
`IFirewallManager` contract — cross-cutting, pre-existing (shared with the shipped
macOS path), so not a v2.44.0 regression. Add a regression test for the degraded-split
case (the current `FullTunnel_emptyList_arms` test pins the ambiguous behaviour).

## P2 — Linux kill-switch: residual brick if orphan-sweep delete fails

If the engaged marker survives a hard kill but `nft delete table` later fails because
the NOPASSWD sudoers grant is gone, the drop-policy table stays loaded and the host
has no internet — only a log line tells the user to run
`sudo nft delete table inet vpnrouter_ks`. Narrow, but a genuine brick path.
Fix: surface to the GUI (blocking modal with the exact command) and try an
interactive `sudo`/`pkexec` fallback during *recovery* specifically.

## P2 — Linux kill-switch: IPv6 server silently dropped from pass-list

`ReadServerIps` filters server IPs to v4 (`!ip.Contains(':')`); the inet table drops
all v6 egress except loopback. Fine for v4 Reality nodes (fail-closed, no leak), but a
v6-only server would be unreachable while engaged → reconnect brick until self-clear.
Fix: add `ip6 daddr` pass rules for v6 servers + v6 LAN, or log when a v6-only server
is dropped.

## P2 — Linux kill-switch: test gaps

No coverage for: orphan-sweep delete FAILURE branch, multi-server dedup / `ip daddr {}`
join, malformed current.json, runner-throws (vs exit-code) path, Dispose idempotency,
v6 server. Backfill in `LinuxFirewallManagerTests.cs`.

## P2 — Android: START-blocked-from-background is invisible to the user

P4 START on Android 12+ from a cold process hits
`ForegroundServiceStartNotAllowedException`, caught + logged but with no user-visible
feedback. Inherent Android limitation; optionally post a notification on the caught
exception so automation users see why "nothing happened".

# Round 2 (auto-failover + B0 telemetry) — 2026-06-22

Second adversarial pass (2 reviewers) over the failover machinery and the B0
connection-health telemetry that feeds it. Two trivial, isolated, observe-only
fixes were applied directly (ClashLogStream restart-latch; failure-rate [0,1]
clamp). The rest are in CORE failover logic where a wrong autonomous fix could
break failover or wipe settings, with no integration test to catch it — so they
are documented here for an integration-tested follow-up. All were VERIFIED real
against the code (not just agent claims).

## P0 — Auto-failover ResetCycle() has NO production call site (coupled with oscillation)

`AutoFailoverEngine.ResetCycle()` (clears `_tried` + attempt counter) is only
called from the unit test — `grep ResetCycle` over Core/App/CLI/Service finds no
production caller. Meanwhile `_failover ??=` (VpnEngine.cs:1090/1119) lives for
the whole engine lifetime and `Stop()` doesn't null it. So the `_tried` set and
the `MaxAttempts=3` cap accumulate across the ENTIRE app session: after 3
lifetime failovers, automatic failover gives up permanently ("Все серверы
недоступны") until app restart, even for servers that are healthy now.

**Coupling caveat (why not a one-line fix):** the obvious fix — call
`_failover?.ResetCycle()` on the confirmed-good connect (StartupPipeline.cs:1221
`OnConnected`) — REMOVES the only terminal state. Servers that flap (warmup
connect OK -> 15s post-start probe fails) would then loop the pool forever
(A->B->C->A...) with NO backoff, because the cap never trips once `_tried` is
cleared on each connect. A correct fix needs BOTH: (a) reset the tried-set on a
*sustained* good connect, AND (b) a re-failover backoff / rate-limit (e.g. "no
more than N failovers per M minutes") so flapping or a network-down condition
doesn't churn the whole pool. Needs integration testing on the VM with a
deliberately-flaky node. There is also no "it's the network, not the node"
suppression (if a direct warmup also fails, don't failover).

## P0 — VpnEngine has zero start/stop/failover synchronization (races)

No lock / SemaphoreSlim / `_isStopping` flag anywhere in VpnEngine. The
post-start probe fires failover on a threadpool thread and does `Stop()` +
`StartAsync()`; a user Disconnect at the same instant interleaves on `_singBox`
/ `_probeCts` with no guard, and the failover-driven `StartAsync` can re-populate
`_singBox` AFTER the user's Stop -> resurrected tunnel after disconnect. Also a
`_probeCts` cancel/dispose race (use-after-dispose). Fix: a single
`SemaphoreSlim(1,1)` (or lock + state machine) around start/stop/apply/
failover-reentry, plus an `_isStopping` flag the failover restart delegate
checks before AND after its awaited StartAsync. Architectural; integration-test.

## P2 — Auto-failover persists the resolver-aggregated server list (subscription leak)

`AutoFailoverEngine.HandleDeadConfigAsync` does `_store.Save(_settings)`
(AutoFailoverEngine.cs:202) on the LIVE settings. In subscribe mode
`VlessServersResolver.Resolve` has already set `settings.Vless.Servers =
subscriptionAggregated` (VlessServersResolver.cs:112), so the failover Save
serializes the aggregate into `vless.servers` YAML — the v2.30.0-r8 leak class
(subscription servers reappear as fake "manual VLESS" entries next launch). Fix:
mirror `StartupPipeline.PersistSanitizedActiveProfile` — reload fresh from disk
(`_store.Load()`), set ONLY `Vless.ActiveServer` + `App.ActiveSubscriptionServer`,
save that; leave the live `_settings` intact for the restart delegate. CAVEAT:
`ISettingsStore.Load` returns DEFAULTS on disk-read failure, so a naive
reload-then-save could wipe settings on a corrupt config — guard against
`Load()` returning a defaults sentinel before saving. Unit-test with a real
SettingsLoader temp-file round-trip, not just InMemorySettingsStore.

## P1 — Auto-failover ignores protocol when picking the next candidate

`PickNextCandidate` filters on structural usability + tried/active exclusion
only, never protocol. It can swap a VLESS+Reality active to a Hysteria2 / TUIC /
dns-tunnel candidate (dns-tunnel especially needs the slipstream sidecar, phase
6.5) -> the restart mishandles it or wastes a failover attempt against the cap.
Fix: prefer same-`Protocol` candidates; move protocol-specific required-field
validation (VLESS uuid, Hy2/TUIC password) into `IsCandidateUsable` so dead
candidates are skipped pre-swap.

## B0 telemetry (observe-only behind VPNROUTER_CONN_HEALTH=1)

- **FIXED:** ClashLogStream restart-latch (`Start()` now gates on `_loop is {
  IsCompleted: false }` so it can restart after Stop). Failure-rate clamped to
  [0,1] in ConnectionHealthState.
- **Deferred — hot-spin backoff (P0-2):** `RunAsync` resets `backoff = MinBackoff`
  right after `ConnectAsync` succeeds, BEFORE any message. A /logs socket that
  accepts-then-immediately-closes (sing-box restart storm) yields a 1s
  busy-reconnect loop that never escalates. Fix: have `ReceiveLoopAsync` return
  whether it processed >=1 message and only reset backoff then.
- **Deferred — classifier precedence (P1-1):** `Classify` tests the generic
  attempt marker `": outbound connection to "` BEFORE the fail marker `"using
  outbound/"`. Disjoint today, but a future sing-box wording with both tokens
  would be miscounted as a (successful) attempt — the dangerous direction
  (under-reports failures). Safer to test the unambiguous fail marker first.
  Reorder is count-neutral on current diag fixtures but re-run
  ConnectionHealthFixtureCountsTests to confirm before pinning.
- **Deferred — UDP attempt/fail asymmetry (P1-2):** UDP relay-open *failures*
  (`listen packet connection ... using outbound/`) are counted, but UDP
  *attempts* use "outbound packet connection to" which the attempt marker
  (`": outbound connection to "`) doesn't match -> denominator misses UDP
  attempts -> inflated rate in UDP-heavy sessions. Needs the exact sing-box UDP
  wording from a real log to fix correctly.
- **Deferred — global Snapshot Node mislabel (P2-2):** `Snapshot()` tags the
  all-nodes window with the *current* `_activeNode`; right after a failover
  switch the global rate is dominated by the old bad node but labelled with the
  new one -> could re-trigger failover off the new node on inherited stats. Have
  failover consume `SnapshotByNode()` only, or pass null node for the global.

# Live device finding — P4 EXT_START "config_json missing" (FIXED v2.44.1-r2, 2026-06-22)

Found during the on-device live sweep (A101BM, Android 12) of v2.44.1-r1. EXT_STOP
and TOGGLE-to-stop work (verified: tunnel physically drops). But **EXT_START (and
TOGGLE-to-start) never bring the tunnel up** — the receiver forwards correctly
(`P4: external-control 'EXT_START' -> service START`) and the service starts, but
then:

```
E VpnRouter: startTunnel failed: java.lang.Exception: config_json missing
   at VpnRouterService.startLibboxService(VpnRouterService.java:879)
   at VpnRouterService.startTunnel(VpnRouterService.java:669)
W VpnRouter: Phase 1.I: ACTION_TUNNEL_ERROR — Exception: config_json missing
```

**Root cause:** `VpnControlReceiver` sent the service `ACTION_START`, which (per
`onStartCommand`) expects the App to pass the freshly-built `config_json` as an
intent extra — that's the UI Connect path. A bare broadcast can't supply it, so
`startLibboxService` throws "config_json missing". (Not the Android-12+
background-FGS limit, as the release notes implied — the FGS start succeeded; the
config was the problem.)

**Fix (v2.44.1-r2):** the receiver now sends `ACTION_RESTART` for the START case.
`ACTION_RESTART` falls through to the service's last-good-config restore branch
(the same proven path Always-on / boot / swipe-recovery use): `loadLastGoodConfig()`
+ `startTunnel()`, rebuilding from the persisted `last_good_config_json`. That is
exactly what an automation-triggered start needs, and it matches the documented
"START requires a prior manual connect" (the first connect is what persists the
last-good config). One-const change in `VpnControlReceiver.cs`; reuses a
known-good code path. No last-good config (never connected) -> graceful
"user must launch app and tap Connect at least once" + stopSelf (unchanged).

Follow-up: the release notes' "background-start-limited on Android 12+" framing for
START is misleading — correct it to "START reuses the last-good config (requires a
prior successful connect)".
