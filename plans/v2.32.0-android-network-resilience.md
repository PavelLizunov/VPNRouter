# v2.32.0 — Android Network Resilience (AND-NETRES)

## Триггер

Android desktop-port (v3.0 alpha) уже умеет поднимать sing-box туннель из
Activity, но не выживает три платформо-специфичных stress-теста:

1. **Always-on VPN** (Settings → VPN → Always-on toggle): system-инициированный
   запуск сервиса после reboot или при подключении к новой сети.
   Pre-NETRES: `onStartCommand` с `intent.action != ACTION_START` падал в дефолтную
   ветку без обработки → service сразу `stopSelf`. Always-on флаг в системе
   стоял, но туннель не поднимался.
2. **Doze mode** (экран выключен 30+ минут, battery-saver): kernel
   урезает CPU фоновым процессам, sing-box застревает между
   ретрансляциями.
   Pre-NETRES: foreground notification был но без wake-lock — connect-init
   мог тихо повиснуть на screen-off.
3. **Network change** (Wi-Fi → cellular handoff): Phase 6.2 уже wired
   `ConnectivityManager.NetworkCallback` → `InterfaceUpdateListener`,
   sing-box re-binds upstream sockets. Это уже работает, нужна только
   user-facing toggle для ручного управления.

## Симптом

Пользователь:
- Включает Always-on в системных настройках, перезагружает телефон, ждёт
  подключения к Wi-Fi → VPNRouter не запускается, traffic идёт без VPN.
- Оставляет телефон с screen off на ~1 час → возвращается, открывает
  браузер → "no internet". Tunnel был, sing-box не reagiert.
- На метро / в дороге Wi-Fi пропадает, переходит на 4G → tunnel
  держится но новые соединения проваливаются (Phase 6.2 это лечит).

## Root cause

### 1. Always-on не обрабатывался

`VpnRouterService.java`:
```java
@Override
public int onStartCommand(Intent intent, int flags, int startId) {
    String action = intent != null ? intent.getAction() : null;
    if (ACTION_START.equals(action)) { ... startTunnel(); ... }
    else if (ACTION_STOP.equals(action)) { ... }
    return START_NOT_STICKY;
}
```

Always-on intent (`android.net.VpnService` / null после reboot) падал
в неявный else → метод возвращал `START_NOT_STICKY` → service
останавливался без запуска tunnel'а. Plus `START_NOT_STICKY` неправильный
policy для long-running VPN.

### 2. Doze без wake-lock

Между `boxService.start()` и моментом когда foreground notification
получает свой systemd-style "I'm important" слот, kernel может swap'нуть
process out, и Go-runtime в libbox потеряет CPU. Реальные user reports
на других sing-box-based приложениях: "first dial timeout after 30 min
screen-off, second dial works".

### 3. Network-change toggle отсутствует

Phase 6.2 уже работает корректно (Wi-Fi → cellular handoff). Не было
toggle для отладки конфликтов с libbox-internal interface monitor'ом.

## Fix strategy

### Step 1 — Always-on path в Java service

`VpnRouterService.java` `onStartCommand`:
```java
} else {
    // System-initiated start (reboot / Always-on / OEM restart).
    Log.i(LOG_TAG, "AND-NETRES: system-initiated start (action=" + action + ")");
    if (loadLastGoodConfig()) {
        startTunnel();
    } else {
        Log.w(LOG_TAG, "AND-NETRES: no last-good config saved");
        stopSelf();
    }
}
return START_STICKY;  // was START_NOT_STICKY
```

Last-known-good config persisted в `vpnrouter_settings` SharedPreferences
(тот же файл что C# `AndroidStorage` использует, чтобы не дублировать):

| Key | Value |
|---|---|
| `last_good_config_json` | full sing-box JSON, последний что успешно запустился |
| `last_good_per_app_mode` | "off" / "include" / "exclude" |
| `last_good_per_app_packages_lines` | newline-separated package names |

`persistLastGoodConfig()` вызывается из `startTunnel` ПОСЛЕ
`boxService.start()` — never overwrite good config с failing.

### Step 2 — Wake-lock + foreground hardening

```java
private PowerManager.WakeLock connectWakeLock;

private void acquireConnectWakeLock() {
    PowerManager pm = (PowerManager) getSystemService(POWER_SERVICE);
    connectWakeLock = pm.newWakeLock(PARTIAL_WAKE_LOCK, "VpnRouter:tunnel-init");
    connectWakeLock.setReferenceCounted(false);
    connectWakeLock.acquire(60_000L); // 60s safety timeout
}
```

`PARTIAL_WAKE_LOCK` — keeps CPU running, screen может спать. Acquired в
`startTunnel()`, released в finally (success или fail) + защитная
сетка в `stopTunnel()`. 60s timeout — fail-safe от leak'а.

`AndroidManifest.xml`: добавлен `<uses-permission android:name="android.permission.WAKE_LOCK"/>`.
Normal-protection level — granted at install, no runtime prompt.

### Step 3 — Battery-optimization deep-link

C#-side `OnReliabilityBatteryClicked` (AndroidApp.axaml.cs):
```csharp
bool isExempt = pm.IsIgnoringBatteryOptimizations(activity.PackageName);
var intent = isExempt
    ? new Intent(Settings.ActionIgnoreBatteryOptimizationSettings)
    : new Intent(Settings.ActionRequestIgnoreBatteryOptimizations)
        .SetData(Uri.Parse($"package:{activity.PackageName}"));
intent.AddFlags(ActivityFlags.NewTask);
activity.StartActivity(intent);
```

`AndroidManifest.xml`: добавлен `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`
permission. User должен подтвердить prompt — мы ничего сами не grant'аем.

### Step 4 — Auto-reconnect toggle

`fireUpdate(ConnectivityManager, Network)` в Java service:
```java
if (firstUpdateFired) {
    SharedPreferences prefs = service.getSharedPreferences(PREFS_NAME, MODE_PRIVATE);
    boolean autoReconnect = prefs.getBoolean(KEY_AUTO_RECONNECT, true);
    if (!autoReconnect) {
        Log.i(LOG_TAG, "AND-NETRES: auto-reconnect OFF — skipping");
        return;
    }
}
```

First update всегда forwarded (sing-box нужен initial bind), subsequent
updates — только если toggle ON. Default ON. Тoggle живёт в Reliability
section.

### Step 5 — Reliability section в Settings overlay

`AndroidApp.axaml.cs` `BuildSettingsReliabilitySection`:

| Row | Type | Behavior |
|---|---|---|
| Always-on VPN | Title + hint + button | `Intent(Settings.ACTION_VPN_SETTINGS)` deep-link |
| Battery optimization | Title + live status + hint + button | Status from `PowerManager.isIgnoringBatteryOptimizations`; button grants exclusion (если не excluded) или открывает list view |
| Auto-reconnect on network change | Checkbox-card | Default ON, persists в `auto_reconnect_on_network_change` SharedPreferences key |

Вставлен между Leak Protection и Updates (thematic clustering — "защита
туннеля").

## Оценка

- Java service changes: ~150 строк (persistence + wake-lock + Always-on branch)
- C# UI: ~200 строк (Reliability section + handlers + localization strings)
- AndroidManifest: 2 permissions (WAKE_LOCK, REQUEST_IGNORE_BATTERY_OPTIMIZATIONS)
- Risk: low. Pure Android system-API integration, всё gated через
  permission prompts (battery opt) или system Settings UI (Always-on).
- Breaking change: `START_STICKY` вместо `START_NOT_STICKY` — корректнее
  для long-running VPN service. Edge case: если service крашится
  систематически, `START_STICKY` вызовет infinite restart loop. Mitigation:
  существующий `LaunchFailureCounter` (SR-2) catches this в C# OnCreate path.
