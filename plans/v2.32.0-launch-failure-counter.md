# v2.32.0 — launch-failure counter (Chrome bad-flags-recovery analog)

## Триггер

`InstallHealthCheck` (v2.31.8-r1) ловит конкретный сценарий — mixed-version
DLL'и после прерванного auto-update. Но это не покрывает другие "App can't
even reach UI" loop'ы:

- Bad config: corrupt YAML после ручной правки или прерванного save.
- Missing dependency: сторонний AV удалил `hostfxr.dll` или нативную DLL.
- Avalonia / dispatcher init throw на экзотических Windows builds.
- ETW provider registration race.
- VS Code / DefaultProfile drift в CrashReporter installation.

Сегодня в любом из этих кейсов user видит ноль feedback: ярлык кликается,
ничего не появляется, кликает снова — то же самое. Recovery requires manual
visit к `vpn.ninitux.com/repair.cmd` + знание команды.

Chrome / Office / JetBrains IDE решают это через "3-strikes" counter:

- Каждый Main entry → bump persisted counter.
- App reaches "stable" milestone (window painted, dispatcher pumping) →
  reset counter.
- 3 consecutive failures → trigger graduated recovery.

## Симптом

User-side: «приложение не запускается, ничего не происходит». Нет диалога,
нет лога который пользователь способен найти, нет восстановления. Только
повторное скачивание installer'а (если найдут link).

Internal-side: `vpnrouter-launch-error.log` пустой потому что failure
происходит ДО любого Serilog config. CrashReporter может ловить, но не имеет
механизма "это уже третий раз — давай recovery".

## Root cause

Архитектурно: нет persistence layer'а который сохраняет факт "previous
launch failed". Каждый Main entry — fresh start. Нет escalation pattern'а.

InstallHealthCheck появился для one specific case (mixed-version DLLs).
Он включает loop-guard через marker file (`self-repair-marker`), но это
single-issue fix. Generic startup loop detection отсутствует.

## Fix strategy

### 1. `VPNRouter.Core/Services/LaunchFailureCounter.cs` (NEW)

JSON-backed counter в `%ProgramData%\VPNRouter\launch-counter.json`:

```json
{
  "consecutiveFailures": 3,
  "lastFailureUtc": "2026-05-07T10:30:45Z",
  "lastFailureType": "InvalidDataException",
  "lastSuccessUtc": "2026-05-06T18:42:11Z",
  "lastSelfRepairUtc": "2026-05-07T10:30:45Z",
  "lastConfigResetUtc": "",
  "lastSafeModePromptUtc": ""
}
```

API surface:

- `IncrementOnStartup(failureType?, path?) → int` — bumps counter,
  stamps `lastFailureUtc`, optionally records exception type.
- `MarkStable(path?)` — zeroes counter, stamps `lastSuccessUtc`.
- `RecordFailureType(type, path?)` — annotate без change counter
  (для wiring из `AppDomain.UnhandledException`).
- `RecommendAction(path?) → "none" | "self-repair" | "config-reset" |
  "safe-mode-prompt"` — peek + dispatch decision. Side effect: stamps
  per-tier cooldown when returning non-`"none"`.
- `ResetCooldown(minutes)` — override cooldown window (для тестов).
- `Read(path?)` — inspect state.
- `Reset(path?)` — wipe state file.

Threshold ladder:

| Strikes | Action | Effect |
|---|---|---|
| 3 | `self-repair` | Trigger `SelfRepair.Run()` (web reinstall). Process exits. |
| 5 | `config-reset` | Move `config.yaml` aside → `*.crash-recovery-{ts}`, fresh defaults на следующем Load. Process continues. |
| 7 | `safe-mode-prompt` | Append message в `vpnrouter-launch-error.log` + Console.Error: "manually run `repair.cmd` или `--safe`". Process continues. |

Loop-guard: каждый tier сохраняет `lastXxxUtc` при срабатывании;
повторный hit того же tier'а в пределах `CooldownMinutes` (default 10)
returns `"none"`. Это предотвращает self-repair re-fire каждый launch
если первый запуск installer'а сам провалился.

### 2. `VPNRouter.App/Program.cs` (EDIT)

Insertion point: ПОСЛЕ admin-elevation block (line 136 `}`), ДО binPath
self-heal (line 142). Это значит "very early" в Main, до DLL-load-heavy
operations (InstallHealthCheck, SingleInstance, etc.).

```csharp
// v2.32.0 — launch-failure counter.
try
{
    var recoveryAction = LaunchFailureCounter.RecommendAction();
    if (recoveryAction != "none")
        DispatchLaunchRecovery(recoveryAction);
    LaunchFailureCounter.IncrementOnStartup();
}
catch (Exception ex) { Console.Error.WriteLine($"[launch-counter] {ex.Message}"); }
```

`DispatchLaunchRecovery` — private static method в Program class:

- `case "self-repair"`: `SelfRepair.Plan() → Run() → Environment.Exit(0)`.
  Wrapped в `#if PLATFORM_WINDOWS` (SelfRepair execs `powershell.exe`).
- `case "config-reset"`: move `AppPaths.ConfigYamlPath` → `*.crash-recovery-{ts}`.
  Fall through (SettingsLoader recreates defaults). Cross-platform.
- `case "safe-mode-prompt"`: append message to launch-error.log + Console.Error.
  Fall through. Cross-platform.

### 3. `VPNRouter.App/Views/MainWindow.axaml.cs` (EDIT)

Subscribe to `Opened` event и call `LaunchFailureCounter.MarkStable()`:

```csharp
Opened += (_, _) =>
{
    try { LaunchFailureCounter.MarkStable(); }
    catch { /* counter is advisory; never fault on it */ }
};
```

`Opened` fires ПОСЛЕ ctor + DataContext binding + first frame paint. Это
правильная "stable" milestone — failures между ctor и Opened (XAML parse,
binding error, etc.) ещё считаются startup failures.

### 4. `VPNRouter.Tests/LaunchFailureCounterTests.cs` (NEW)

Pin contract:

1. `IncrementOnStartup` стартует от 1, накапливается, persists failure
   type.
2. `RecordFailureType` не меняет counter.
3. `MarkStable` zero'ит counter, stamps success UTC, preserves last failure type.
4. `RecommendAction` thresholds: <3 → none, 3 → self-repair, 5 → config-reset,
   7 → safe-mode-prompt (highest tier wins).
5. Cooldown: после non-none result повторный call возвращает none того же
   tier'а; после `ResetCooldown(0)` — refires immediately.
6. Escalation: 3-strikes self-repair → 5-strikes config-reset →
   7-strikes safe-mode-prompt → "none" когда все cooldowns active.
7. Reset() удаляет state file. Corrupted JSON → fresh state.
8. Threshold constants pinned.
9. Source-pin: `Program.cs` calls RecommendAction перед IncrementOnStartup;
   `DispatchLaunchRecovery` exists.
10. Source-pin: `MainWindow.axaml.cs` subscribes Opened и calls MarkStable
    в lambda.

## Оценка

~150 LOC core implementation + ~250 LOC tests + ~120 LOC plan = small
change. Risk: low (all writes wrapped in try/catch, never blocks
startup). No new network surface (SelfRepair triggers reuse existing
flow). Storage: ~500-byte JSON file in DataDir.

## Связь с другими планами

- `plans/v2.31.10-update-rollback.md` — local rollback safety net (Layer
  8) сработал через `UpdateBackup.HasFailureMarker`. Это OTHER recovery
  layer, специфичный для update-failed случая. LaunchFailureCounter —
  generic loop-detection поверх любых причин, including те что rollback
  не покрывает (corrupt config, missing dependency, AV interference).
- `plans/v2.31.10-helper-cmd-hardening.md` — helper.cmd parser bug
  v2.31.7 был triggering classic startup loop case. Counter дал бы
  recovery после 3-х падений, не дожидаясь user-reports через ~7 дней.
- `VPNRouter.App/Services/InstallHealthCheck.cs` — single-issue check
  для mixed-version DLLs. LaunchFailureCounter не дублирует — он fires
  для ANY startup failure (включая такие что health check пропустил).

## Расширения (не в этом PR)

- Wire `RecordFailureType` из `CrashReporter.Install()` unhandled-exception
  handler — чтобы `lastFailureType` populating'ся автоматически.
- Mac/Linux SelfRepair port (currently `case "self-repair"` Windows-only).
- UI-level "we noticed you've been having trouble launching" toast после
  successful MarkStable если предыдущий launch имел ConsecutiveFailures > 0.
