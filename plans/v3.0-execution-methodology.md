# v3.0 execution methodology

**Status:** active

**Audience:** DSH sessions executing `plans/v3.0-refactor-roadmap.md`

**Reading order:** `docs/agent-contract.md` -> this document -> roadmap -> task brief

The canonical repository contract always wins. This document explains how to execute v3.0 work; it does not grant merge, tag, deployment, or release authority.

## 1. Non-negotiable workflow

Every v3.0 task and every approved change over 30 lines uses the `phase-task-launcher` skill.

1. Start from current `origin/main` unless the owner names another accepted base.
2. Create a `dsh/<short-task-name>` branch before writing or committing the brief.
3. Add `plans/phase-<slug>-YYYY-MM-DD.md` with Why, What, How, risk, rollback, tests, and six tailored gates.
4. Commit and push the brief on the task branch, then wait for its actual PR checks before the implementation block.
5. Implement the smallest complete change. Behavior changes require regression tests; mechanical splits require a pre-change characterization baseline.
6. Run focused checks while iterating, then all applicable gates in section 4.
7. Perform independent review for non-trivial work and source-verify every finding before accepting it.
8. Fill the brief Outcome with observed evidence, commit, PR, test deltas, surprises, follow-ups, and rollback.
9. Commit without bypassing hooks, push only the task branch, update/open the PR to protected `main`, and wait for green checks.
10. Stop at review readiness. Merge, release, tag, deployment, and stable-cut authority require an explicit owner command.

A no-behavior documentation or comment edit of at most five lines may use an abbreviated brief. It still uses a task branch when the repository contract requires one.

## 2. Task brief

Use `.dsh/skills/phase-task-launcher/references/brief-template.md`.

A valid brief states:

- the concrete problem and user or maintenance value;
- exact files/symbols in scope and explicitly excluded scope;
- risk, blast radius, rollback, and dependencies;
- implementation sequence and tests to add or update;
- six gates, each marked PASS, FAIL, BLOCKED, or N/A with a reason;
- an Outcome based on executed checks rather than expected results.

Do not put secrets, live subscription data, credentials, or raw remote logs in plans.

## 3. Branch and PR discipline

- `main` is protected. Never push to it directly and never force-push.
- `origin` is the canonical GitHub remote in this checkout.
- Push with `git push -u origin HEAD`.
- After every push, run `tools/verify-last-commit-ci.ps1` when the environment supports PowerShell. If the control plane lacks PowerShell, use the exact PR checks as the authoritative remote substitute and record that limitation.
- Red or in-progress CI blocks the next implementation block. Do not stack known-red commits.
- Keep commits reviewable and scoped. The commit body explains why; do not add agent-attribution trailers.
- Do not alter remotes, mirror to Forgejo, merge the PR, or create tags/releases without explicit authority.

## 4. Six verification gates

### Gate 1 - Build

Run the smallest relevant build during iteration, then:

```powershell
dotnet build VPNRouter.sln -c Release
```

Android changes also require the Release APK build from `VPNRouter.Android/AGENTS.md` on a prepared worker with the required workload and AAR.

### Gate 2 - Tests

- Existing tests remain green.
- A bug fix adds a regression that fails without the fix.
- A behavior change covers happy, failure, and boundary paths where applicable.
- A mechanical extraction pins the relevant source/public surface before moving code.
- Use `[Fact]` for pure tests and `[AvaloniaFact]` for Avalonia objects or dispatcher work.
- Run the full discovered suite before handoff:

```powershell
dotnet test VPNRouter.Tests/VPNRouter.Tests.csproj -c Release --no-build
```

### Gate 3 - Documentation

- Fill the brief Outcome before final handoff.
- Update the nearest `AGENTS.md` only when the zone contract or durable architecture changes.
- Update `README.md` and `README.ru.md` only when public behavior, setup, compatibility, commands, or limitations change.
- Update `CURRENT_STATE.md` only for current release/platform facts.
- Append real deferred P0/P1 findings to `plans/OPEN-DEFECTS.md`.

### Gate 4 - Independent review

Run `bug-hunt` for non-trivial changes, especially changes over 100 lines or touching public API, process execution, files, networking, firewall, updates, security, or release tooling.

Give independent reviewers distinct angles. The SOL lead reopens every cited file/line, removes hallucinations and duplicates, fixes in-scope blockers, and records only source-confirmed survivors.

### Gate 5 - UI and remote verification

UI changes require deterministic headless screenshots and visual tests. A shipped candidate additionally requires the exact release-note scenario on fixed WINBRAT through repository verification tools.

Never run the VPN/UI scenario on `harness-test` or the development workstation. Use `docs/test-workers.md`; missing VM, identity, credentials, SDK, or resources is a blocker, not permission to use a fallback.

### Gate 6 - Characterization and integration

For god-file splits and mechanical refactors, the pre-change characterization surface must match after the change unless an intentional API change is separately specified and reviewed. Check all consumers, generated bindings, platform conditionals, and project files.

## 5. Test selection

| Change | Minimum evidence |
|---|---|
| Bug fix | focused regression plus affected suite |
| Pure refactor | existing focused suite; add characterization when coverage cannot prove equivalence |
| New Core behavior | unit tests plus integration at the nearest real boundary |
| ViewModel/XAML change | ViewModel tests, headless render, narrow layout checks, visual diff where baselined |
| Android change | shared tests plus Release APK build on a prepared worker |
| Release/tooling change | contract tests, syntax/parse checks, exact-SHA CI, and applicable remote gate |
| Packaging/workflow change | platform-specific contract tests and workflow validation |

Test names should state method, condition, and expected result. Prefer small fakes over new mocking dependencies. Avoid sleeps when an event, task, or injected clock can express the condition.

## 6. Parallel work

Parallelize only independent assignments with disjoint write scopes.

- Use DSH `subagent` calls for a small number of focused assignments.
- Use `workflow` only when the user explicitly requests a workflow or the task needs large fan-out.
- The lead owns architecture, decomposition, overlapping files, integration, source verification, and final acceptance.
- Workers do not commit, push, merge, release, or modify remotes. The lead owns Git integration; merge and release still require explicit owner authorization.
- Before launch, assign exact file ownership and required output. After completion, inspect `git status`, the full diff, and out-of-scope edits.
- If two workers touch the same file, stop parallel integration and reconcile sequentially; never select a winner by timestamp.

## 7. Resource and worker behavior

`docs/test-workers.md` is canonical.

- `harness-test` is control plane only: no SDK provisioning, platform build, or VPN/UI fallback.
- Target an exact commit SHA; do not test a mutable shared branch checkout.
- Run read-only CPU/RAM/disk/SDK/job preflight before heavy work.
- Allow one mutable scenario per worker.
- Do not mutate VM resources, lifecycle, networking, monitoring, or DSH services.
- Do not clean caches or system TEMP automatically. Report candidate paths with size and age, then wait for exact approval.
- Always clean only the deployment/test artifacts created by the current scenario.

## 8. Project invariants to include in reviews

The detailed list lives in `docs/agent-contract.md`, zone `AGENTS.md` files, and `docs/REVIEW_AGENT_PROMPT.md`. At minimum:

- `AppVersion.Version` exactly matches a release tag, including `-rN`.
- `process_name` values preserve filesystem casing.
- VLESS subscription servers are resolved before config generation.
- sing-box routing and DNS remain fail-closed.
- process handles, timers, cancellation sources, and event subscriptions are disposed safely.
- all user-visible text is localized through the owning string table.
- XAML uses semantic tokens and remains usable at narrow widths.
- no credentials, subscription URLs, UUIDs, keys, or raw live logs leave the trusted environment.

## 9. Release boundary

v3.0 development readiness is not release authority.

- Use `ship-rolling-candidate` only after an explicit candidate command.
- Use `post-ship-mcp-verify` after every candidate or stable ship.
- Use `cut-stable` only after explicit stable authorization and all hard gates.
- Require the exact 16-asset release contract, exact-SHA CI, sidecar verification, fixed-WINBRAT verification, two connection cycles, cleanup, and the open-defect gate where applicable.

## 10. Stop-the-line conditions

Stop and report when:

- a safety or release invariant is violated;
- required worker identity, credentials, SDK, disk, or network access is unavailable;
- a relevant test or CI check is red or still running;
- source verification cannot confirm a review claim;
- the task expands beyond the approved spec or requires a semantic choice;
- a destructive cleanup, resource mutation, merge, deployment, tag, or release lacks explicit authority.

## 11. Completion report

A handoff report includes:

- changed files and actual behavior/documentation delta;
- focused and full checks with observed results;
- review findings accepted, fixed, deferred, or refuted;
- worker/CI limitations and cleanup evidence;
- branch, commits, PR, and exact check state;
- remaining owner-authorized actions, if any.
