## 0. Constraints (set by user 2026-05-17)

> "Все что можешь запустить параллельно, запускай параллельно, даже тестерам не нужно пока давать этот релиз так как это пока очень сыро. Перед запуском продумай максимально правильную методологию работы, проверком, и документации всех фич, важно описывать все и вся, юзать все лучшие практики и все нужные и важные плагины claude-code которые там могут пригодиться и писать правильные тесты."

**Translation into hard rules:**

1. **No tester-facing releases during v3.0 dev.** Branch `v3.0-prep`. Cut only when v3.0 is integration-ready. No rolling `-rN` to public during this work.
2. **Parallel by default.** Every isolated task spawns its own agent.
3. **Methodology FIRST, code SECOND.** No code change without a brief, a verification gate, and an exit doc.
4. **Document everything.** Every feature touched gets a `plans/phaseN-<task>-YYYY-MM-DD.md` entry. No "obvious" tasks skip the doc — the doc IS the obviousness check.
5. **Best practices everywhere.** Modern .NET 8 patterns, async-first, no statics where DI fits, no string concatenation where interpolation works, etc.
6. **Use the right Claude Code skill.** Map per task — see §6.
7. **Write the right tests.** Per the test pyramid + characterization snapshots + contract tests for abstractions.

## 1. Branch strategy

```
main                                  ← stable cuts only (v2.x and eventually v3.0.0)
└─ v3.0-prep                          ← all Phase 2 + 3 work
   ├─ Phase 1 tasks land directly on main (low risk, small)
   ├─ Phase 2 god-file splits           ← per-task feature branches off v3.0-prep
   ├─ Phase 2 abstractions              ← per-interface feature branches
   ├─ Phase 3 Avalonia 11→12            ← own long-lived branch
   ├─ Phase 3 Newtonsoft→STJ            ← own long-lived branch
   └─ Phase 3 other items               ← short-lived feature branches off v3.0-prep
```

**Per-task feature branch lifecycle:**

```
1. brief: plans/phaseN-<task>-<date>.md committed to v3.0-prep BEFORE branch
2. branch: claude/phN-<task-slug>-<seq>
3. impl: code change(s)
4. tests: new tests pass; full suite green
5. docs: update README / CLAUDE.md / Strings.cs comments as needed
6. self-review: simplify + security-review skill where applicable
7. exit doc: append "Outcome" section to the brief
8. merge: --no-ff into v3.0-prep with summary
9. cleanup: delete branch
```

**No PRs in this repo's model — direct commits to branches.** Self-review via skills replaces PR-review-by-human, with the caveat that risky changes are flagged for explicit user approval before merge to `v3.0-prep`.

## 3. Verification gates (gate descriptions)

### Gate 1 — Build

`dotnet build VPNRouter.sln -c Release` must exit 0. Warnings tolerated only if they predate the change.

For Android changes:
`dotnet build VPNRouter.Android/VPNRouter.Android.csproj -c Release -p:EnableAndroidTarget=true -p:AndroidSdkDirectory=$env:ANDROID_HOME -p:JavaSdkDirectory=$env:JAVA_HOME` must exit 0.

### Gate 2 — Tests

**Hard rules:**
- ALL existing tests must remain green. Zero red.
- Behavior-changing tasks add at least 1 test per code path.
- Refactoring tasks (no behavior change) add at least 1 characterization snapshot test BEFORE the refactor begins, then verify identical behavior AFTER.

**Test pyramid for VPNRouter:**

```
Unit (xUnit [Fact])              ←── 80% of tests; pure data/converter/VM-list
   ↑
Integration ([AvaloniaFact] + Avalonia headless)  ←── 15%; VM ↔ View binding tests
   ↑
End-to-end (MCP computer-use)    ←── 5%; full app flow with VPN simulated
```

### Gate 3 — Docs

- Brief filled (sections "Why / What / How / Verification gate" non-empty)
- "Outcome" section filled before commit-to-main
- README.md + README.ru.md updated for user-facing changes
- CLAUDE.md (relevant sub-zone) updated for architecture changes
- Comments added explaining non-obvious code per project style

### Gate 4 — Self-review

For changes >100 LOC OR touching public API: run `simplify` skill on the diff.
For changes touching auth / TLS / process exec / file I/O: run `security-review` skill.

### Gate 5 — MCP verify (UI changes)

Per project Rule #1a from CLAUDE.md: any UI surface change → MCP screenshot + PASS/FAIL by feature point.

### Gate 6 — Integration cross-check (Phase 2+3)

For god-file splits: before-and-after characterization snapshot diff must be EMPTY (zero behaviour drift).

## 5. Test discipline

### When to write what

| Change type | Test type required |
|---|---|
| New abstraction (interface) | Contract tests: ≥1 happy path + ≥2 edge cases. Mock impl for fakes. |
| God-class split | Characterization snapshot BEFORE; diff = empty AFTER |
| Bug fix | Regression test that fails on `git stash` of the fix, passes after |
| New feature | Unit (logic) + integration (VM+View) + smoke (MCP if UI) |
| Refactor for clarity (no behavior change) | Existing tests should suffice; if not, write missing one |
| Performance-sensitive change | Benchmark before + after (BenchmarkDotNet or simple `Stopwatch` test) |

### Test naming convention

`MethodName_Condition_ExpectedOutcome` — strict:

✅ `Parse_PlaceholderPubkey_ThrowsPlaceholderConfigException`
✅ `GetActiveServer_NoSelected_FallsBackToFirstInSubscriptions`
❌ `TestParseFailure` (no condition, no outcome)
❌ `Should_handle_placeholder` (assertion-style, doesn't say which method)

### Mocking

**Avoid mocking concrete classes.** If you need to mock a Core service:
1. Extract interface (e.g. `IHttpClient`)
2. Make concrete impl an injectable
3. Mock the interface

Don't use Moq for fakes — write small inline impls per test class.

### Characterization snapshot tests (for god-file splits)

```csharp
[Fact]
public void MainWindowViewModel_DefaultState_MatchesBaseline()
{
    var vm = new MainWindowViewModel();
    var snapshot = SnapshotHelper.Capture(vm); // expose ALL public/observable props
    SnapshotHelper.AssertMatches(snapshot, "baselines/mvm-default.json");
}
```

Write baseline.json BEFORE the split. Run test AFTER → must match.

### Test file extraction discipline

Per Audit E: `UnitTest1.cs` is 6169 LOC across 42 classes. NEW tests go to dedicated files immediately. EXISTING tests get extracted as part of Phase 2 with names matching the class.

## 7. Communication protocol (multi-agent coordination)

When multiple agents work in parallel on Phase 1+:

### Agent contract

Each spawned agent MUST:
1. Read its brief in `plans/phaseN-<task>-<date>.md` (provided in spawn prompt)
2. Execute the task end-to-end (impl + tests)
3. Return a single-paragraph status (PASS / PARTIAL / FAILED + 2-3 sentence why)
4. Write the Outcome section to the brief BEFORE returning
5. NOT commit (integrator does the commit)
6. NOT push (integrator does the push)
7. NOT delete branches (integrator does cleanup)

### Integrator (parent session) responsibilities

1. Spawn N agents with their briefs already written
2. Wait for completion notifications
3. Read each agent's report
4. Cross-check: did any conflict with another agent's work? (run `git status` between batches)
5. Batch commit per logical group OR per agent (preference: per-agent for atomicity)
6. Push to remotes
7. Update todo list

### Conflict resolution

If two parallel agents both modified the same file:
1. STOP both, mark their briefs as "BLOCKED_BY_CONFLICT"
2. Manually reconcile based on which change is correct
3. Re-spawn the loser as sequential

For Phase 1, manually pre-analyze the parallelization plan (see §4 Tier P0 table). For Phase 2+, use worktree isolation.

### Per-task risk matrix template

Every brief includes:

```
Risk: LOW / MEDIUM / HIGH
Justification: <reason>
Mitigation: <what we did to lower it>
Rollback: <command/branch to revert>
Detection: <how we'd know if it broke in production>
```

### Project-level risks (v3.0 specific)

| Risk | Mitigation |
|---|---|
| v3.0-prep branch drifts from main for 8-10 weeks | Weekly rebase from main; cherry-pick critical fixes (CVE / user-reported P0) into both |
| Phase 1 dotnet test workflow exposes flaky tests in existing suite | Treat as Phase 1 follow-up: stabilize before Phase 2 starts |
| Avalonia 11→12 (3A) breaks VisualDiffTests | Behind feature branch; re-baseline PNG fixtures explicitly |
| Newtonsoft→STJ (3B) round-trip drift on edge YAML/JSON | New round-trip tests per migrated type; AB-test serialize/deserialize identity |
| MVM split (2B) breaks XAML binding paths | Characterization snapshot test BEFORE the split |
| User reports v2.x bug while v3.0-prep is in flight | Hotfix on main (cherry-pick to v3.0-prep) |

### Stop-the-line conditions

If ANY of these happen, halt Phase work and notify user:
- A regression test reveals an existing-but-undiscovered behavioural drift
- A CI workflow goes red and root cause is unclear
- User-reported P0 bug arrives that needs main-branch hotfix
- A "quick win" turns out to be >2× its estimate

## 11. Quality bars (best practices applied)

### Code

- **Async-first.** Every new public method that touches I/O returns `Task` / `Task<T>` / `ValueTask`. No `void` for I/O.
- **Nullable annotations strict.** `#nullable enable` in every new file. Use `?` for nullable, plain ref for non-nullable.
- **Records over classes for immutable DTOs.** `public sealed record FooBar(...)` when state never changes.
- **`sealed` by default.** Mark classes `sealed` unless extension is planned.
- **`readonly struct` for value types.** Avoid mutable struct footguns.
- **`Span<T>` / `Memory<T>` for high-throughput parsing.** Where we parse subscription bodies / sing-box JSON.
- **`System.Text.Json` source generators** for hot serialization paths (post-Phase 3B).
- **No magic numbers.** `const int RequestCodeQrScan = 0x0000C0DE;` style for everything.
- **CA-attributes** for cross-platform: `[SupportedOSPlatform("windows")]` on Win-only services.

### Tests

- **xUnit `[Fact]`** for unit tests; `[Theory]` + `[InlineData]` for data-driven.
- **`Assert.Equal(expected, actual)`** — expected first, NOT actual. Common footgun.
- **One assertion per concept.** Multiple `Assert.Equal` ok if they verify the SAME concept (e.g. all fields of a record).
- **Test method body MUST follow Arrange/Act/Assert structure** with blank lines between sections.
- **`Assert.Throws<T>`** for expected exceptions; never `try/catch + fail`.
- **No `Thread.Sleep` in tests.** Use `await Task.Delay` if absolutely required; prefer event-based.
- **Test names** in `MethodName_Condition_ExpectedOutcome` format (§5).
- **No magic test data.** Constants named `Known<X>` (e.g. `KnownBadPubkey`) at class top.
- **Cleanup after yourself.** `Dispose`, `try/finally`, `IDisposable` test fixtures.

### Documentation

- **XML doc comments on every public symbol.** Tooling enforces `1591`.
- **`<remarks>`** for non-obvious behavior or version-specific lessons.
- **`<exception>`** lists thrown types.
- **Code examples in `<example>`** for non-trivial public API.
- **CLAUDE.md cross-references** when adding new public types.

### Commits

- **Imperative present tense.** "fix bug" not "fixed bug" not "fixes bug".
- **`<scope>: <subject>`** format. Scopes: `core/app/cli/service/android/tests/ci/docs/build`.
- **Body explains WHY**, not WHAT (WHAT is in the diff).
- **Reference user-reports + audit doc paths.**
- **Multi-paragraph body** for changes >50 LOC.
- **`Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>`** trailer.

### CI

- **Pin actions to commit SHAs** not floating `@v3`.
- **Cache aggressively.** NuGet, Android workload, sing-box tarballs.
- **Workflows under 10 min wall-clock.** Split if longer.
- **`continue-on-error` flag is a smell.** Soft failures hide bugs. Fix the test or remove the workflow.

## Appendix A — Failure modes seen during methodology design

During the 6-agent audit that produced this methodology:
1. **One audit agent (D) recommended NOT introducing a DI container.** Validated — over-engineering for this codebase. Methodology aligns.
2. **One audit agent (F) found auto-draft trap.** Validated by user-reported v2.32.3-r1 ship incident. Spawned task chip exists to fix.
3. **Audit B catalogued 53 features.** Methodology requires each feature touched to update the catalog.
4. **Audit E found 9 untested services.** Methodology requires Phase 2D abstractions to unlock testing those before Phase 3 begins.

## Appendix B — Anti-patterns to avoid

Cataloging from project history:

1. **PowerShell `>` writes UTF-16 BOM + uppercase hex** — caught at v2.32.3-r1 ship. Use `sha256sum | awk` via git-bash for all SHA256 sidecars.
2. **`gh release create --prerelease`** without `--draft=false` may go to draft state. Always check `gh release view --json isDraft` after.
3. **Bind="false" on AndroidLibrary in .NET 8 Android** does NOT prevent binding generation for transitive types. Use Transforms/Metadata.xml `remove-node` to suppress.
4. **Static `HttpClient` initialized at class load** captures DNS at first use — refresh every 5 min via PooledConnectionLifetime config OR inject via IHttpClient.
5. **`async void` outside of UI event handlers** swallows exceptions.
6. **`.Result` on async** in `VpnEngine.cs:461` (known); never add another.
7. **CRLF/LF line ending churn on cross-platform commits** — `.gitattributes` is set; don't fight it.
8. **WorkflowDispatch inputs require `tag` parameter** for verify-release-integrity — discovered when retrying after Z:\kanareik fix.
