## Bug

`AppSettings.App.AutostartTgProxy` (and `AutostartZapret`) is read from
`config.yaml` into a bound property at `MainWindowViewModel.cs:2433` and
persisted at `MainWindowViewModel.cs:3165`, but **nothing ever invokes
`_tgProxy.Start(...)` based on the flag** in App-only mode. The only
manual-spawn site is `ToggleTgProxyAsync` at `MainWindowViewModel.cs:4317`,
which fires from the user-clicked Start button on the Telegram page.

End-user repro (pre-fix):

1. User enables "Autostart Telegram proxy" in Settings → Autostart.
2. Closes the App.
3. Logs out / in. App auto-relaunches via the HKCU\Run entry created by
   `VPNRouter.Core.Platform.AutostartHelper`.
4. Settings shows the toggle still ticked, but `tg-ws-proxy` isn't
   running. User has to click Start manually on the Telegram page.

The Service-side path works (`VPNRouterService.cs:93-96`,
`AutostartTgProxyAsync` at `:331-380`) — but only if the user installed
the Windows Service. A user who's running the App-only setup (HKCU\Run
auto-launch, no service) gets a silent gap.

## Fix

New partial in `VPNRouter.App/ViewModels/MainWindowViewModel.AutostartBootstrap.cs`:

```
BootstrapAutostartAsync()           // entry, called from ctor
├── 500 ms settle delay
├── ServiceVm.Refresh()
├── if (ServiceVm.IsRunning) return  // hand off to Service
├── TryAutostartTgProxyAsync()
└── TryAutostartZapretAsync()
```

Each `TryAutostart*` mirrors the Service-side method's checks:
- daemon installed (TgProxyUpdater.IsInstalled / ZapretUpdater.IsInstalled)
- daemon not already running (TgProxyManager.IsAnyRunning / ZapretManager.IsWinwsRunning) — idempotent
- settings populated (port, secret) — generates secret if empty (mirrors `ToggleTgProxyAsync` at `:4354-4358`)
- launches via the same `_tgProxy.Start()` / `_zapret.Start()` API as the manual path
- updates UI status fields (`TgProxyEnabled`, `TgProxyStatus`, `TgProxyLink`, `ZapretEnabled`, `ZapretStatus`)

Constructor wiring: fire-and-forget after `StartRuntimeStatusPolling()`:

```csharp
// MainWindowViewModel.cs ctor, ~line 2188
_ = BootstrapAutostartAsync();
```

## Service-vs-App ownership rule

When the Windows Service is running, it owns the autostart spawn at
boot — App defers. The `!ServiceVm.IsRunning` guard prevents two
processes (App + Service) from both trying to bind port 1443
(tg-ws-proxy) or claim winws.exe (zapret) simultaneously. Race
condition would manifest as "address already in use" on whichever lost
the race; user-visible failure mode would be one daemon mysteriously
not starting.

`ServiceVm.Refresh()` is called immediately before the gate to
re-poll the SCM so a Service that started concurrently with the App at
login (typical of slow logins or Service set to Automatic) gets seen.

## Why AutostartVpn is NOT bootstrapped here

App-side VPN bootstrap is strictly higher risk:
- Requires `VpnEngine.StartAsync(_settings, ct)` which pulls in
  subscription resolver (`SubscriptionResolver.ResolveAsync`),
  config-generator pass, leak-protection check, firewall rule install
  — all of which the Service already wires.
- Races with Service over the TUN ownership lock if Service is
  installed but happens to be stopped at moment of App launch.
- Writes to `current.json` at the same path the Service might be reading.
- Coordination already exists for the **manual** Connect path; reusing
  it for autostart needs careful sequencing with `LoadSettingsIntoUI`,
  `DetectServiceManagedVpn`, and `OrphanCleanup.KillOrphans` (the v2.31.10-r2
  coexistence fix).

The user-facing gap for AutostartVpn is also narrower in normal flow:
Simple-mode's `SmpAutostartChecked` setter ties VPN-autostart to
Service install (see `MainWindowViewModel.SimpleMode.cs:80-125`), so
the gap only manifests for users who manually edit `config.yaml`.

**Follow-up plan**: a separate iteration can add `TryAutostartVpnAsync`
mirroring the Service-side `AutostartVpnAsync` at
`VPNRouterService.cs:175-267` — including the TunOwnershipLock peek
(`:217-223`) so App and Service don't fight over the TUN adapter when
both are configured to autostart.

## Tests

`VPNRouter.Tests/AppAutostartTgProxyTests.cs` — 6 source-string pin
tests, same pattern as `ServiceAppCoexistenceTests`:

1. `BootstrapFile_ExistsAndDeclaresPartialClass` — partial class +
   namespace + method names.
2. `Bootstrap_ChecksAutostartTgProxyFlag_BeforeSpawning` — both
   `if (!AutostartTgProxy)` / `if (!AutostartZapret)` gates present;
   actual `_tgProxy.Start(TgProxyPort, TgProxySecret)` invocation
   present.
3. `Bootstrap_DefersToService_WhenServiceIsRunning` — `ServiceVm.IsRunning`
   guard with early return.
4. `Bootstrap_IsInvokedFromConstructor` — `_ = BootstrapAutostartAsync()`
   pattern in the ctor (regex match for fire-and-forget).
5. `Bootstrap_GeneratesSecret_WhenEmpty_MirroringManualPath` —
   `RandomNumberGenerator.GetBytes(16)` + `Convert.ToHexString` mirror
   the manual path's secret generation.
6. `Bootstrap_IsIdempotent_SkipsSpawnWhenAlreadyRunning` — calls to
   `TgProxyManager.IsAnyRunning(TgProxyPort)` and
   `ZapretManager.IsWinwsRunning()` for double-spawn prevention.

Why source-pin not behavioural? The bootstrap touches Windows-only
daemons (tg-ws-proxy, winws.exe) whose end-to-end behaviour can't be
asserted in unit tests without process mocking. The string pins catch
real refactor regressions: dropping the `!ServiceVm.IsRunning` guard,
removing the bootstrap call from the ctor, deleting the spawn
invocation, etc.
