# xUnit1051 cancellation-token sweep — 2026-05-21

## Context

`framework-cross-ref` research earlier this session confirmed that
xUnit1051 fires when test code calls a method that accepts a
`CancellationToken` overload but doesn't pass one. xUnit v3 (in use:
`xunit.v3` 3.2.2 per `VPNRouter.Tests/VPNRouter.Tests.csproj:44`)
exposes per-test cancellation via `TestContext.Current.CancellationToken`
— passing this enables orderly cancellation when the harness aborts
the test (timeout, parent CT). Tests doing real I/O (HTTP, subprocess,
sing-box probes) that ignore the test CT are genuine debt; pure-
computation tests are low-impact.

## Sweep pattern (mechanical)

Each call site like `await X.SomeAsync(args)` (or `args, CT.None`) becomes
`await X.SomeAsync(args, TestContext.Current.CancellationToken)`.

`TestContext` is in the `Xunit` namespace, which is already brought in
globally via `<Using Include="Xunit" />` in the .csproj.

## Refuse-to-proceed cases (skipped, warning preserved)

1. **Pre-cancelled token tests** — e.g.
   `VlessDeepVerifierBehaviourTests.VerifyAsync_PreCancelledToken_…`
   passes `cts.Token` (already cancelled) intentionally. **Don't touch.**
2. **Tests that explicitly use `CancellationToken.None` as a contract
   probe** (e.g. "happy path with no cancellation pressure") — left
   as-is when the intent is documented in the test name / comment.
3. **`Assert.ThrowsAsync<OperationCanceledException>(…)` wrappers** —
   the inner async lambda is meant to use a specific token; don't
   override.
