# v2.32.0 — SettingsValidator (defensive config-load gate)

## Триггер

`SettingsLoader.Load` ловит **синтаксически** битый yaml (труначен,
без BOM, неправильные отступы) — `Parse` бросает `InvalidDataException`
и v2.31.8-r9 fallback переименовывает в `config.yaml.broken-{stamp}`.

Но **семантически битый** yaml — `config_mode: nonsense`,
`tg_proxy_port: 99999`, `vless.servers[0].port: 0`, `subscription_url:
"not a uri"` — проходит насквозь, потому что YamlDotNet просто маппит
типы. Дальше эта мина срабатывает в нескольких местах:

- `NullReferenceException` / wrong-tunnel-mode silent leak (см. v2.28.2
  — `ConfigMode = ""` слил весь Apply-flow на manual instead of
  subscribe).
- sing-box check exit 1 на нелегальном MTU / порту / DNS strategy.
- `UnauthorizedAccessException` когда custom_config path указывает на
  несуществующий файл (а UI на этот мод залочен).

## Симптом

Реальные пользовательские bug-reports которые попадали в этот класс:

1. v2.28.2 silent leak: `_settings.App.ConfigMode = "subscribe"`
   персистился как `""` после неудачного hot-reload, следующий Start
   шёл по generated branch с пустым Vless.Servers и трафик утекал
   direct.
2. v2.31.6 spark-wraith «впн не хочет обновляться сам» — у user'а
   `tg_proxy_port` после ручного редактирования стал `0`, sing-box
   refused to bind, helper.cmd падал в loop без user-visible signal.
3. v2.31.8-r9 «приложение не запускается» — config.yaml оказался
   труначен в середине, App.exe крашился до UI. Пофикшено parser
   fallback'ом, но семантическая ветка (типо валидный yaml + типо
   значения, но мусор внутри) осталась незакрыта.

## Root cause

В `SettingsLoader.Parse` после миграции и null-coalesce defaults — нет
проверок что значения попадают в дозволенные диапазоны / sets.
Loader просто доверяет yaml. Migrator (`SettingsMigrator.Migrate_*`)
тоже не проверяет — он только smooth'ит schema_version diff.

```
file:
  VPNRouter.Core/Services/SettingsLoader.cs        — Load + Parse
  VPNRouter.Core/Services/SettingsMigrator.cs      — schema migrations
  VPNRouter.Core/Models/AppSettings.cs             — root model
```

## Fix strategy

Добавить чистую функцию-валидатор `SettingsValidator.Validate(AppSettings)
→ SettingsValidationResult { IsValid, Reasons[], Warnings[] }`. Никаких
side-эффектов, никакого I/O. Загрузчик решает что делать с результатом.

`SettingsLoader.Load` после `Parse` (и значит после миграции) зовёт
`Validate`. Если результат **invalid**:

1. Backup битого файла → `config.yaml.invalid-{yyyyMMdd-HHmmss}`.
2. `Save(CreateDefaults(), configPath)` — пишем фабричные defaults.
3. `Console.Error.WriteLine` с одной high-priority строкой:
   `[SettingsValidation] config.yaml rejected: <reasons>; backup at <path>; reset to defaults`.
4. Заполняем static `SettingsLoader.LastRecoveryNotice` — App / Service
   читают его один раз через `ConsumeRecoveryNotice` и поднимают сигнал.

App-сторона: новый `SettingsRecoveryNoticeText` `[ObservableProperty]`
+ `HasSettingsRecoveryNotice` + `DismissSettingsRecoveryNoticeCommand`,
binding в MainWindow.axaml через тот же warning-banner pattern, что
v2.29.0-r7 receipt warning. Bilingual через
`Strings.SettingsRecoveredFromBadConfig(string backupPath)`.

Service-сторона: после `_currentSettings = SettingsLoader.Load()` в
`ExecuteAsync` — `WriteEventLog(recovery, EventLogEntryType.Warning)`
если `ConsumeRecoveryNotice` не пуст. У службы нет UI, EventLog —
единственный operator-visible signal.

### Инварианты (FATAL — триггерят reset)

| # | Поле                                          | Правило                                    |
|---|-----------------------------------------------|--------------------------------------------|
| 1 | `app.config_mode`                             | ∈ {generated, subscribe, custom}; пусто = invalid |
| 2 | `app.routing_mode`                            | пусто или ∈ {split, full}                  |
| 3 | `app.theme`                                   | пусто или ∈ {light, dark}                  |
| 4 | `app.tg_proxy_port`                           | 1..65535                                    |
| 5 | `app.subscription_url`                        | пусто или parseable absolute URI            |
| 6 | `app.subscriptions[i].url`                    | пусто или parseable absolute URI            |
| 7 | `vless.port` (legacy single-server)           | 1..65535                                    |
| 8 | `vless.servers[i].port`                       | 1..65535                                    |
| 9 | `tun.mtu`                                     | 576..65535                                  |
| 10 | `dns.strategy`                                | пусто или ∈ {ipv4_only, ipv6_only, prefer_ipv4, prefer_ipv6, default} |
| 11 | `monitoring.health_check_interval`            | > 0                                         |
| 12 | `monitoring.process_scan_interval`            | > 0                                         |
| 13 | `monitoring.max_restart_attempts`             | >= 0                                        |
| 14 | `update.channel`                              | пусто или ∈ {stable, experimental}          |
| 15 | `profile_sources[i].url`                      | пусто или parseable absolute URI            |

### Инварианты (WARN-only)

- `config_mode == "custom"` + active path не существует на диске —
  warn, не reset (USB unplugged / temp permission glitch).

## Не делаем

- НЕ валидируем VLESS UUID / Reality keys / TLS fingerprints —
  отдельный validator (`LeakProtection.ValidateConfig` уже это
  частично делает на уровне сгенерированного sing-box JSON).
- НЕ валидируем `subscription.servers[i]` глубже porta —
  `VlessServersResolver` сам отфильтрует placeholders типа
  `your.server.com`.
- НЕ блокируем загрузку при WARN-only — пользователь не может
  потерять весь конфиг из-за временно отсоединённого USB.

## WFP / network safety

Pure code change. Не трогает sing-box, не трогает WFP, не зависит от
3rd-party software. Бэкапит исходный yaml перед reset так что
forensic recovery возможен.
