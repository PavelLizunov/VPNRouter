# v2.32.0 — SR-4: Settings load robustness

## Триггер

Audit SR-4 из родительского stability sweep: `SettingsLoader.Load(path)` сегодня
*почти* never-throws, но имеет 3+ места где YamlDotNet может бросить или
downstream код dereference'нет null sub-section. Сестринская задача SR-1
покрывает семантику (плохие значения); SR-4 — структурную robustness
(missing fields, partial migrations, weird YAML, locked files).

Урок v2.31.8-r9 показал что один corrupt config.yaml (truncated mid-write,
manual edit mistake, accidental BOM) уронил `MainWindowViewModel..ctor` и
дал «приложение не запускается» без UI / banner / clue.

## Симптом (то что user видел до SR-4)

- Garbled config.yaml → app crashes на launch без сообщения.
- Partial config.yaml (`vless:` без children) → NRE в downstream сервисах.
- File locked другим процессом → IOException uncaught → crash.
- Type-coercion fail (`tg_proxy_port: "abc"`) → YamlException uncaught → crash.
- Future schema field → silent drop (это OK, но не было покрыто тестом).

## Root cause

`SettingsLoader.Load`:

- ловил только `InvalidDataException` от Parse() → backup как `.broken-{ts}`,
- НЕ ловил IOException от `File.ReadAllText` → uncaught,
- НЕ ловил FormatException / YamlException от type-coercion → uncaught,
- НЕ ловил последний-ресорт unexpected exception → uncaught.

`Parse()` имел inline `??=` блок ~12 строк который покрывал только
top-level subsections + Vless internals + Tun.RouteExcludeAddress.
Не покрывал:

- AppSettings.CustomGroupApps (Dictionary)
- AppSettings.CustomCategories
- AppConfig.{CustomConfigs, SubscriptionServers, Subscriptions, CustomDirectRules, CustomRules, UserFreeSources}
- VlessTransportConfig.Headers (within entries inside Servers list)
- Per-entry VlessServerEntry.{Reality, Tls, Transport}
- SubscriptionEntry.Servers (per entry)
- CustomCategory.Apps (per entry)

YamlDotNet С# init'ы (`= new()`) **перезаписываются null'ом** когда YAML
имеет explicit empty value (e.g. `vless:` без children, или `subscriptions: ~`),
поэтому defaults в model declaration недостаточно — нужен post-deserialize
null-safety sweep.

## Fix strategy

### 1. Новый `AppSettingsSane.EnsureSane(this AppSettings?)` extension method

Файл: `VPNRouter.Core/Models/AppSettingsSane.cs` (новый).

- Walk полного object graph AppSettings.
- Replace любой null sub-object / collection с fresh default.
- Idempotent: only fills nulls, never overwrites populated values.
- Tolerates null receiver (returns fresh `new AppSettings()` через `??=`).
- Recursively walks Vless.Servers, App.Subscriptions[].Servers и каждый
  VlessServerEntry для Reality/Tls/Transport/Transport.Headers.
- Strips out null sequence entries (YamlDotNet emits null'ы для `- `
  без значения).

### 2. `SettingsLoader.Load` — full try/catch wrapper

```csharp
public static AppSettings Load(string? path = null)
{
    try { return LoadCore(path); }
    catch (Exception ex)
    {
        // Last-resort safety net.
        try { Console.Error.WriteLine($"[SettingsLoader] FATAL: ..."); } catch { }
        return CreateDefaults().EnsureSane();
    }
}
```

`LoadCore` структурирован тремя независимыми try-блоками:

1. **Read step** (`File.ReadAllText`): catch всё → defaults, **don't backup**
   (file unreadable, нечего backup'ить — следующий launch может попробовать
   снова после освобождения lock'а).
2. **Parse step** (`Parse(yaml)` + `EnsureSane()`): catch всё → backup как
   `config.yaml.unloadable-{ts}` (renamed было `.broken-{ts}`, унифицировали)
   + defaults.
3. **WriteExample step** (когда file отсутствует): catch всё → defaults
   in-memory без на-диск файла, non-fatal.

### 3. Parse() integration

Старый ~12-строчный `??=` блок заменён одним вызовом
`settings = settings.EnsureSane();`. EnsureSane — точно тот же null-safety
contract, плюс расширенное coverage. Idempotent → можно звать дважды
без ill effect (Parse зовёт, потом Load зовёт ещё раз для belt-and-braces).

### 4. Тесты `SettingsLoaderRobustnessTests.cs` (14 cases)

Файл: `VPNRouter.Tests/SettingsLoaderRobustnessTests.cs` (новый).

Все тесты используют unique temp dir per case (`IDisposable` cleanup) —
параллельный run без конфликта с реальным `%ProgramData%\VPNRouter\config.yaml`.

`AssertSane(s)` хелпер проверяет что **все 22 reference-typed properties**
на AppSettings tree non-null после Load.

## Risk

Minimal:
- Pure C# refactor + tests, no WFP / network surface.
- EnsureSane idempotent — calling extra times safe.
- Old `.broken-{ts}` файлы остаются на disk (форматирование не изменилось,
  только новые backup'ы пишутся как `.unloadable-{ts}`).
- Outer try/catch — last-resort safety net; LoadCore catches everything
  expected. Если outer блок ever fires в проде — это знак что есть unhandled
  failure mode, и log позволит диагностировать без crash.

## Notes

- `Console.Error.WriteLine` — Core layer не имеет прямого доступа к Event
  Log / toast (это App / Service surface). Caller (Service) может attach
  Serilog Console sink → файл / EventLog. Future SR может добавить
  опциональный `Action<string>` log callback на SettingsLoader, но текущая
  реализация достаточна.
- WFP/network safety: pure C# refactor + tests. Safe.
