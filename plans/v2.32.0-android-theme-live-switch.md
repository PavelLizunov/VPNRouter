# v2.32.0 — Android theme live-switch (handbook §6 / Phase 8.2)

## Триггер

`plans/vpnrouter-android-handbook.md:479-484` Phase 8.2 — known gap:
"switching dark↔light persists but UI brushes are read at
BuildSimplePageView and don't react". User-flagged on the v3.0 Android
alpha — kebab > Theme > Light/Dark flips the persisted preference and
fires `RequestedThemeVariant`, but the visible UI keeps the old colors
until app restart. Desktop has had instant theme switch since v2.16.0
via XAML `{DynamicResource X}` — Android port is the only platform
that still requires a relaunch.

## Симптом

1. Cold-launch in Light theme.
2. Tap kebab → Theme → Dark.
3. Active segment in the popup repaints (StyleSegmentButton already
   does manual brush reassign), but EVERYTHING else — status card
   surface, config row button, form card, CTA buttons, advanced card,
   chips, mascot — stays light.
4. App needs full restart to look correct.

## Root cause

`VPNRouter.Android/AndroidApp.axaml.cs` `BuildSimplePageView()`
constructed every Border / TextBlock / Button via object initializers
that snapshot brushes from `Application.Resources` once:

```csharp
var card = GetBrush("SurfaceBaseBrush");      // resolved against current
                                              // ActualThemeVariant once
...
var statusCard = new Border { ... Background = card, ... };
```

`GetBrush` reads the resource for the current variant and caches the
`IBrush` instance into a local var. Avalonia has no link from the
property-set value back to the resource dictionary, so a subsequent
`RequestedThemeVariant` change fires a re-resolution of the merged
ThemeDictionaries but doesn't push new brushes into the already-set
properties.

Desktop dodges this entirely because the equivalent XAML uses
`Background="{DynamicResource SurfaceBaseBrush}"` — `DynamicResource`
installs a binding that resolves through the visual-tree resource host
and re-resolves whenever the resource-or-its-source-variant changes.

## Strategy chosen — **Option B (DynamicResource via code-behind)**

Three options were on the table per the task brief:

- **A. Walk-and-reassign**. Track every brush-set property in a
  dictionary, walk on theme change, re-fetch each brush, reassign.
  Brittle (every new control needs to be added to the registry, and
  state-flip helpers like `SetVpnChipState` need parallel logic).
- **B. DynamicResource bindings via code**. Use Avalonia's
  `Avalonia.Markup.Xaml.MarkupExtensions.DynamicResourceExtension`
  (which implements `IBinding`) and bind it via the standard
  `AvaloniaObject.Bind(prop, IBinding)` overload. Same mechanism as
  desktop XAML — single source of truth.
- **C. Rebuild SimplePage on theme change**. Heaviest. Loses form
  state (text-input contents, scroll position, popup expanded state).

**Picked B.** It's a direct port of the desktop pattern, avoids the
state-loss surface of C, and avoids the manual-tracking surface of A.

### Implementation

1. Added top-level `internal static class StyledElementResourceExtensions`
   with one extension method:

   ```csharp
   public static T BindToken<T>(this T element, AvaloniaProperty prop, string key)
       where T : AvaloniaObject
   {
       element.Bind(prop, new DynamicResourceExtension(key));
       return element;
   }
   ```

   `DynamicResourceExtension` implements `IBinding`; `Bind(prop, IBinding)`
   subscribes to the resource observable that re-fires when
   `RequestedThemeVariant` flips and re-resolves the merged dictionaries.

2. Refactored every brush touch point in `BuildSimplePageView`,
   `BuildLogOverlay`, `BuildAppPickerOverlay`, `BuildAppRow` and the
   `_serverList.ItemTemplate` factory to call `BindToken(prop, "KeyName")`
   immediately after construction in place of `Background = GetBrush(...)`.

3. Refactored helpers that used to take baked `IBrush`:
   - `MakeChip(label, IBrush bg, IBrush fg)` →
     `MakeChip(label, string bgKey, string fgKey)`
   - `MakeMenuItem(label, IBrush fg, onClick)` →
     `MakeMenuItem(label, string fgKey, onClick)`
   - `MakeSegmentButton` / `StyleSegmentButton` — both go through
     `BindToken` (each call replaces the prior LocalValue binding,
     so toggling active state cleanly switches between the two
     resource keys).

4. Removed `GetBrush(string)` (now dead code; every call site uses
   `BindToken`). `GetRadius(string)` stays — radii live outside
   ThemeDictionaries so they're theme-invariant and a one-shot lookup
   is correct.

5. State-flip surfaces that pick a different KEY per state were
   updated to re-bind on each transition:
   - `UpdateConnectionState` — `_statusDot.Fill` re-binds to
     `SuccessSolidBrush` (connected) or `TextMutedBrush` (disconnected).
   - `SetVpnChipState(state, force)` — chip Foreground+Background
     re-bind to one of the three pairs (Off / Connecting / On). Added
     a `force` parameter so `ApplyTheme(string)` can re-issue the
     bindings even when the chip state hasn't changed (a pure theme
     flip needs to retain the active state but pick the new variant's
     brush).

6. `ApplyTheme(string mode)` now also:
   - Calls `_mascotImage.Source = LoadMascot()` — the mascot is a
     bytes-based `Bitmap`, not a brush, so it can't ride DynamicResource;
     `LoadMascot()` returns the inverted Bgra8888 variant when
     `ActualThemeVariant == ThemeVariant.Dark`.
   - Re-fires `RepaintThemeSegment()` and `RepaintLanguageSegment()` so
     the active segment chrome moves to the new selection.
   - Calls `SetVpnChipState(_vpnChipState, force: true)` and
     `UpdateConnectionState(MainActivity.IntendedConnected)` to re-issue
     the state-driven bindings (the variant change alone wouldn't move
     them — they pick a key per state).

### Token categories migrated

| Category | Tokens used | Where |
|---|---|---|
| Surface | `SurfaceAppBrush`, `SurfaceBaseBrush`, `SurfaceRaisedBrush`, `SurfaceSunkenBrush` | mainScroller, statusCard, _formCard, configRowButton, advCardButton, menuPanel, log overlay, app picker overlay, _menuFeedback, _ctaConnect, _ctaConnecting, _appPickerSearch |
| Text | `TextPrimaryBrush`, `TextSecondaryBrush`, `TextMutedBrush` | every label TextBlock; chips Off-state foreground; section headers; menu items; row labels in app picker + server list ItemTemplate |
| Border | `BorderSubtleBrush`, `BorderDefaultBrush`, `BorderAccentBrush` | statusCard, _formCard, configRowButton, advCardButton, menuPanel, dividers, segment buttons |
| Accent | `AccentBgSubtleBrush`, `AccentFgBrush`, `AccentSolidBrush`, `AccentOnSolidBrush`, `AccentBorderBrush` | mascot wrapper, flag icon, advanced-card chevron circle, _ctaConnect (outline), _ctaDisconnect (solid), _appPickerSaveBtn, segment active state |
| States | `SuccessBgBrush`, `SuccessFgBrush`, `SuccessSolidBrush`, `WarningBgBrush`, `WarningFgBrush`, `DangerFgBrush` | _statusDot connected fill; VPN chip Connecting + On states; serverInputError text |
| Radii | `RadiusXs`, `RadiusSm`, `RadiusMd` | unchanged — theme-invariant, still resolved via `GetRadius` |

### Mascot — separate path

`LoadMascot()` already had the per-theme inverted variant logic; it
just wasn't being re-invoked on theme change. New `_mascotImage` field
stores the `Image` control so `ApplyTheme(string)` can flip its
`Source` to the freshly-resolved Bgra8888 buffer.

### Sub-optimal alternative considered: `Application.Current.FindResource`

The handbook hint suggested "Application.Current.FindResource calls
per state change" as one option. That would require a custom
`PropertyChanged` notification on `RequestedThemeVariant` and a manual
walk to re-resolve every property. DynamicResource subsumes that —
Avalonia already maintains the resource observable and the binding
infra wires it up automatically. Strictly fewer moving parts.

## Оценка

Implemented in one session (~2 h). Net diff: ~150 LOC migrated,
helper class added (~25 LOC), one helper signature change
(`MakeChip`, `MakeMenuItem`), `GetBrush` removed.

Risk: Low. Same mechanism as desktop's well-exercised
`{DynamicResource X}`. Worst case if Avalonia's Android backend has
a quirk — graceful degradation (the initial-state values are still
present in the cache; bindings either work and recolor on theme
change, or fail and the visible state stays where it was on launch).
