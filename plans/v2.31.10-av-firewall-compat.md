# v2.31.10 — AV / Firewall compatibility (RU/CIS market)

## Триггер

VPNRouter ships unsigned binaries (`VPNRouter.App.exe`, `VPNRouter.Service.exe`,
`VPNRouter.GUI.exe`, `sing-box.exe`). RU/CIS audience runs a long tail of AV
products beyond Defender — Comodo, Avast/AVG, Kaspersky, Bitdefender, ESET.
sing-box.exe в particular is a known false-positive trigger (`Wacapew.C!ml`
ML-heuristic family) per upstream reports on similar Go-binary projects.
Need a compat matrix + a recommendation set so we can put exclusion guidance
in the README and decide whether to invest in code-signing.

## Симптом

Hypothetical / observed:
- Defender quarantines `sing-box.exe` mid-test → VPN dies → wintun routing
  collapses → "VM looks dead" or hard-crash for end-user.
- Comodo Free Firewall blocks any network adapter install → wintun TUN never
  comes up → VPNRouter hangs in starting state.
- AV product blocks named-pipe IPC `VPNRouter.App.SingleInstance.v2` → fresh
  launch attempts deadlock because the SingleInstance handshake never
  completes.
- AMSI / behavior-monitor flags the `iwr -useb https://… | iex` install
  bootstrap or the in-app `SelfRepair` spawn pattern as `Trojan:Win32/ClickFix`.
- SmartScreen blocks first-run of unsigned downloaded EXE (Internet zone MOTW).

| Method | Coverage |
|---|---|
| **Live test** on Windows 11 LTSC 2024 26100 VM, VPNRouter v2.31.10-r1 | Defender across 3 modes (baseline / cloud-on / no-exclusions) + Windows Firewall outbound-block |
| **Doc-only research** (vendor KBs, GitHub issues, Comodo forums) | Comodo, Avast, Bitdefender, Kaspersky, ESET — install too risky on a dev VM (Comodo has known wintun-install incompatibility; live install would also disable Defender via WSC and would not represent realistic test surface without a fresh VM per product) |

Rationale for skipping live 3rd-party AV install on this VM: Comodo Free
Firewall has a documented hard incompatibility with wintun — it cannot
filter wintun traffic AND triggers errors during virtual-adapter install
(see Comodo forum [VPN-block thread](https://forums.comodo.com/t/comodo-firewall-doesnt-filter-wireguard-vpn-tunneling/319238?page=2)). winget is not present
on LTSC and a 206 MB MSIX bootstrap dropped mid-stream from this VM's NAT,
making clean installer download fragile. Live testing all five AV products
would need ~5 fresh VM snapshots, which is out of scope for this iteration.

## Required exclusions (when AV blocks)

For 3rd-party AVs that quarantine or block, the user needs to add **all
four** of these as path exclusions, plus one application allow rule:

| Exclusion type | Path / target | Why |
|---|---|---|
| Path | `C:\Program Files\VPNRouter\` | Install dir; all unsigned EXEs live here |
| Path | `C:\ProgramData\VPNRouter\` | Runtime dir; sing-box runs from `\bin\sing-box.exe` here, config + cache + logs are here |
| Process | `sing-box.exe` | Process-level exclusion stops behavior monitoring on the long-running TUN process |
| Process | `VPNRouter.App.exe` | Same — UI process |
| Firewall application rule | `C:\ProgramData\VPNRouter\bin\sing-box.exe` Allow Inbound + Outbound | Both directions; sing-box accepts TUN packets (inbound from kernel) and proxies (outbound to upstream VLESS server) |

## Defender false-positive (`Wacapew.C!ml`) submission flow

If a future Defender signature update flags `sing-box.exe`, here is the
canonical Microsoft submission process:

1. Get the file: `C:\Program Files\VPNRouter\app\sing-box.exe`
   (sha256: `139847AB3B7BB3562A4DB6421A18069BD92D78CA2B0C031DDEA93840202CC296`
   for v2.31.10-r1 shipped build)
2. Open https://www.microsoft.com/wdsi/filesubmission
3. Sign in with a Microsoft account (free)
4. Submission form:
   - **Submission type:** Software developer
   - **File:** upload sing-box.exe (≤ 50 MB cap; we're 42.73 MB ✓)
   - **Detection name:** the exact threat name from the Defender event
     (e.g. `Trojan:Win32/Wacapew.C!ml`)
   - **Source:** GitHub release URL
     (`https://github.com/SagerNet/sing-box/releases`)
   - **Description:** "VPNRouter ships sing-box (https://sing-box.sagernet.org)
     — open-source proxy platform. Reproducible from upstream Go source.
     False-positive on ML heuristic for unsigned Go binaries."
   - **"Do you believe this file contains malware?"** → **No**
5. Wait 24–72 h for Microsoft analyst response. If accepted, the
   signature is removed from cloud DB; clients pick it up on next
   `Update-MpSignature` cycle (typically <24 h)

Reference: [Microsoft FP submission docs](https://learn.microsoft.com/en-us/troubleshoot/sharepoint/security/false-positive-malware-detections),
[Defender for Endpoint FP guidance](https://learn.microsoft.com/en-us/defender-endpoint/defender-endpoint-false-positives-negatives).

## Code-level findings worth tracking

### F1: SelfRepair.cs inline `iwr | iex` bootstrap may trip ClickFix heuristic

`VPNRouter.App/Services/SelfRepair.cs:122-137` builds an inline PowerShell
command and spawns `powershell.exe -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -Command "..."`.
The bootstrap does `Invoke-WebRequest … -OutFile $tmp; & $tmp` — exact
shape of the `Trojan:Win32/ClickFix.DCW!MTB` family that already fires
on dev tooling in this VM's threat history.

**Severity:** medium. Defender currently doesn't flag this for our binary,
but the heuristic is inherently noisy and may fire on a future signature
update for an arbitrary subset of users.

**Mitigation options** (any of):
- (a) Write the bootstrap to a tempfile (`Path.GetTempFileName()`-style)
  and run via `-File` instead of `-Command`. Tempfile-based exec is far
  less likely to trip ClickFix because the entire script is on disk and
  AMSI scans the whole file rather than a one-line download-and-execute
  string.
- (b) Inline the install.ps1 logic directly into SelfRepair (no IWR);
  currently install.ps1 is the source of truth for install layout, so
  duplicating risks drift.
- (c) Sign the embedded helper via Authenticode (longer-term — see F4)
- (d) Use `Start-Process powershell.exe -Verb RunAs -File <path-to-script>`
  pattern that repair.cmd already uses successfully for self-elevation
  (no inline command-string)

Recommendation: **(a)** is the smallest fix. ~10 lines change to
`SelfRepair.Run()` — drop bootstrap to `%TEMP%\vpnr-self-repair-<ts>.ps1`,
spawn `-File`. Same UX, much smaller AMSI surface.

### F2: Install dir not in default Defender exclusion list

The exclusions on this VM (`C:\ProgramData\VPNRouter` + `C:\Project\VPNRouter`)
were added during dev. **Real users** running `iwr install.ps1 | iex` get
no exclusions. They survive currently because Defender's signature DB
doesn't flag our binaries, but if a Wacapew false-positive fires:

- `C:\Program Files\VPNRouter\app\sing-box.exe` (install copy) → quarantined
  → first launch of VPNRouter.App.exe finds missing sing-box and fails
  before it can copy to ProgramData
- Even after recovery, the install copy stays missing → next auto-update
  may break (xcopy from install copy → ProgramData)

**Mitigation options:**
- (a) install.ps1 adds Defender path exclusions during install (requires
  admin already). One-line `Add-MpPreference -ExclusionPath` for
  `C:\Program Files\VPNRouter` and `C:\ProgramData\VPNRouter`. Pros:
  zero-touch UX. Cons: privacy/policy concerns for some users; Tamper
  Protection blocks this on managed devices.
- (b) Don't add exclusions but document them in README + show a one-shot
  hint in app if `Get-MpThreatDetection` returns a hit on our paths
- (c) Sign binaries (F4)

Recommendation: **(b)** — README documentation plus a Tools-page section
"Antivirus blocking VPNRouter?" with a copy-paste exclusion script. (a)
is too invasive for users who don't have an issue.

### F3: User-facing error when sing-box dies

If sing-box gets quarantined mid-session, VpnEngine sees the process
exit and treats it as a crash. User sees "VPN не работает" / generic
error. They have no way to know it's an AV that ate the binary.

**Mitigation:** when SingBoxManager detects the binary is missing on
restart attempt, show an explicit dialog: "sing-box.exe не найден.
Возможно, его удалил антивирус. Добавьте `C:\ProgramData\VPNRouter\bin\sing-box.exe`
в исключения и перезапустите VPNRouter." with a "Open antivirus
exclusion settings" link that opens Windows Security exclusion page
(`ms-settings:windowsdefender` shell deep-link).

Recommendation: low-priority polish; not blocking. Tag for v2.32 if AV
reports start flowing in.

### F4: Code-signing decision

Cost-benefit for an EV code-signing certificate ($300–500/year, ~1 day
to procure + integrate into CI):

**Pros:**
- Eliminates Defender Wacapew FP by design (signed Go binaries virtually
  never trip ML heuristics)
- Removes SmartScreen "Don't run / More info" prompt on first launch
  (note: Smart App Control "Enforced" mode will still need EV +
  reputation build-up time)
- Eliminates 3rd-party AV "unsigned" PUA detection (ESET, Kaspersky in
  particular)
- User confidence — "verified publisher: Pavel Lizunov" in UAC dialog
  vs. "unknown publisher"
- Signed sing-box.exe specifically would address the dominant
  false-positive trigger surface

**Cons:**
- $300–500/year recurring cost
- EV cert requires hardware token (USB/HSM) — slows CI signing pipeline,
  needs build-host integration (Azure Trusted Signing or YubiKey)
- Sign all 4 EXEs each release (~14× per year at current rolling-rN
  cadence). Re-signing sing-box.exe means **dropping upstream
  reproducibility** — people who hash-check our sing-box against
  SagerNet's get a mismatch
- Re-signing every -rN release is annoying; need automation

**Recommendation:** **DO sign**, but only the three VPNRouter binaries
(App, Service, GUI). **Don't re-sign sing-box.exe** — leave it as the
upstream-reproducible, byte-identical SagerNet artifact. The Wacapew
FP risk on sing-box is real but transient (clears on next sig update);
the upstream-reproducibility property is much higher-value for security-
conscious users and saves us from being on the hook for sing-box bugs.
Document this trade-off in README.

For sing-box specifically, register it for FastTrack reputation
[via Microsoft's analyst flow](https://learn.microsoft.com/en-us/defender-endpoint/admin-submissions-mde)
on every release that introduces a hash bump.

**Priority:** start the EV cert process now (1-day procurement + ~3 days
build pipeline integration). Schedule for v2.32.

### F5: Comodo + wintun hard incompatibility — explicit error path

If a CIS user installs VPNRouter, they will hit a vague hang because
wintun adapter creation silently fails under CIS's NDIS filter. We
should detect this and show a clear error.

**Mitigation:** in VpnEngine.StartAsync, after wintun adapter creation
fails, check for CIS service presence:
```
Get-Service | Where Name -match 'cmdguard|cmdagent|HipsDaemon'
```
If found → show explicit error: "Comodo Internet Security blocks the
TUN adapter. VPNRouter cannot run alongside CIS. Either temporarily
disable CIS protection or uninstall CIS."

**Priority:** low. CIS user-base is small; Bitdefender + Avast cover
most of the real CIS-market block surface. Tag for v2.32 if any user
reports surface.
