# AWG server forwarding gate for Phase 1.1

Purpose: unblock `plans/goal-codex-awg-fulltunnel-dns-distribution-2026-06-30.md`
Phase 1.1 without guessing in the client. The WINBRAT client can complete the
AmneziaWG handshake for `main-brat`, but no TCP/DoH payload returns through the
tunnel. DNS-bootstrap loopback is already gone (`DNS query loopback = 0`), so
the next proof must come from the VPS.

## Client evidence

- Client endpoint: `main-brat`
- Client tunnel address: `10.66.0.22/32`
- Peer endpoint: `93.95.226.167:51822`
- WINBRAT TUN run: `endpoint/wireguard[proxy]` is selected, but hostname,
  `curl --resolve`, and `https://1.1.1.1` time out.
- WINBRAT SOCKS/no-TUN harness: `received handshake response` and keepalives
  are logged, but TCP payload still times out.

This points at server-side peer routing / forwarding / NAT, not at the
DNS-bootstrap loopback that the client fix addresses.

## Read-only VPS check

Run as root on `93.95.226.167`:

```bash

sysctl net.ipv4.ip_forward

awg show || wg show

iptables -S FORWARD

nft list ruleset 2>/dev/null | sed -n '1,220p' || true
```

Expected:

- `net.ipv4.ip_forward = 1`
- the `main-brat` peer is present and its server-side `AllowedIPs` is exactly
  `10.66.0.22/32`
- forwarding permits `awg0` traffic
- NAT masquerades traffic from the AWG client subnet out through the real egress
  interface

Important mismatch to check: the older VPS spec used example
`AllowedIPs = 10.13.13.2/32`, but the current client uses `10.66.0.22/32`.
If the server still has the old address, handshake can succeed while inner IP
payload is unroutable or dropped.

## Packet proof while WINBRAT tests

Keep these running while the client repeats the SOCKS or TUN curl probe:

```bash
tcpdump -ni any '(udp port 51822) or host 10.66.0.22 or host 1.1.1.1 or host 94.140.14.14'
```

Interpretation:

- UDP/51822 handshake only, no `10.66.0.22` inner traffic: server peer/routing
  is not accepting decrypted client payload.
- `10.66.0.22 -> 1.1.1.1:443` appears on `awg0`, but no egress packet on the
  public NIC: FORWARD/NAT problem.
- egress packet leaves public NIC, but no reply: upstream firewall/provider or
  wrong source NAT.
- reply returns to public NIC but not to `awg0`: reverse forwarding/conntrack
  problem.

## Candidate server fix

Do not apply blindly; first compare with the actual interface names and existing
firewall manager. The shape should be:

```bash
sysctl -w net.ipv4.ip_forward=1
printf 'net.ipv4.ip_forward=1\n' >/etc/sysctl.d/99-awg-forward.conf

# Replace eth0 with the real default-route interface.
ip route get 1.1.1.1

# Ensure the peer allowed IP matches the current client address.
# In awg0.conf / wg config:
# AllowedIPs = 10.66.0.22/32

iptables -C FORWARD -i awg0 -j ACCEPT || iptables -A FORWARD -i awg0 -j ACCEPT
iptables -C FORWARD -o awg0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT || \
  iptables -A FORWARD -o awg0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
iptables -t nat -C POSTROUTING -s 10.66.0.22/32 -o eth0 -j MASQUERADE || \
  iptables -t nat -A POSTROUTING -s 10.66.0.22/32 -o eth0 -j MASQUERADE
```

After any server change, rerun the WINBRAT Phase 1.1 checks. The gate passes
only when both are true on a real tunnel:

- VLESS and AWG: `DNS query loopback = 0`
- AWG: hostname curl succeeds through the tunnel, not just handshake/keepalive

a peer purely by key, and an empty keepalive packet carries no inner IP
header to check against `AllowedIPs`, but a real encapsulated packet
(source `10.66.0.23`) gets silently dropped post-decrypt if the server's
peer entry doesn't have that exact `/32` allowed. Both client addresses
(`10.66.0.22/32` Iceland, `10.66.0.23/32` Germany) look templated/adjacent,
which is circumstantial support for a shared provisioning-script bug across
both VPS's rather than two unrelated one-off misconfigurations — but this is
not server-confirmed; only the owner has VPS access to check.

**Conclusion**: this reproduction does NOT close Phase 1.1 the way the
session handoff expected (it predicted `loopback=0` AND `httpCode=204` on
this server). The DNS-bootstrap fix is doubly confirmed (VLESS pass +
2 independent AWG handshake-layer passes, all 0 loopback). End-to-end AWG
payload delivery remains unconfirmed on any real server tested so far —
gate-before-delete therefore still holds the game-DNS-off-proxy carve-out
pending owner direction (correct creds for a server with verified-working
AllowedIPs, or owner-side server inspection).
