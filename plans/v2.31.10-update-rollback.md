# v2.31.10 — local rollback safety net for failed auto-updates

**Status**: implemented in worktree `claude/mystifying-herschel-952fdf`,
ready for merge into v2.31.10-r3 (or whatever -rN follows the
[r2 merge runbook](v2.31.10-r2-merge-plan.md)).

**Scope**: Windows. macOS (.app bundle) and Linux (.deb / .tar.gz)
already have their own atomic-replace patterns (`ditto`, `cp -rfT`)
that don't suffer the same partial-copy failure mode. The Windows
helper.cmd does file-by-file `xcopy /R` and is what bit users in
v2.31.7 — that is where this rollback is most useful.

## Triggers

1. Helper.cmd parser bug history (v2.31.7-r1 → r10): `%SVC_TRIES%`
   pre-expansion in nested `if/else` aborted helper mid-flight, leaving
   `app/` with mixed-version DLLs. Repaired only by manual
   `repair.cmd` from `vpn.ninitux.com`.
2. Network-dependency of `SelfRepair`: pulls `install.ps1` from web. If
   the very VPN that just got damaged was carrying user's traffic,
   `vpn.ninitux.com` may be unreachable until they bypass the broken
   tunnel.
3. AV / AMSI surface of `iwr | iex` style bootstraps (Task C / F1
   audit, see `plans/v2.31.10-av-firewall-compat.md`). Defender's
   `Trojan:Win32/ClickFix.DCW!MTB` family fires on patterns we cannot
   avoid in a one-liner installer. Local file copy has no such surface.

## Goal

Auto-update can NEVER leave the user with a broken/missing install.
Even if helper.cmd parser mis-expands, even if network drops mid-copy,
even if AV quarantines the new SelfRepair fallback — there must always
be a working binary on disk.

## Design — state diagram

```
            ┌──────────────────────────┐
            │  App running (healthy)   │
            └────────────┬─────────────┘
                         │ user clicks Update
                         ▼
┌────────────────────────────────────────────────────┐
│  ApplyUpdateWindows()                              │
│   1. TryWriteInstallReceipt()                      │
│   2. UpdateBackup.CreateSnapshot(installDir)       │  ← LAYER 8 (NEW)
│      ─ recursive copy app/ → app.bak.tmp/          │
│      ─ atomic rename app.bak.tmp → app.bak/        │
│   3. File.WriteAllText(helperPath, cmd)            │
│   4. Process.Start("cmd.exe /c helper.cmd")        │
│   5. Environment.Exit(0)  ← from caller            │
└────────────────────────────────────────────────────┘
                         │
                         ▼ helper.cmd takes over (detached)
┌────────────────────────────────────────────────────┐
│  helper.cmd (extern)                               │
│   • wait parent PID                                │
│   • sc stop VPNRouter                              │
│   • taskkill sing-box.exe                          │
│   • xcopy %SRC%\* %DST%\ /E /Y /Q /R /I            │
│   • set XCOPY_EXIT=!ERRORLEVEL!                    │
│   • IF non-zero: > %DST%\.update-failed echo …     │  ← NEW marker
│   • sc start VPNRouter (if was running)            │
│   • start "" %DST%\VPNRouter.GUI.exe               │
└────────────────────────────────────────────────────┘
                         │
                         ▼ new App.exe launches
┌────────────────────────────────────────────────────┐
│  Program.Main — InstallHealthCheck phase           │
│                                                    │
│  health = InstallHealthCheck.Check()               │
│  marker = UpdateBackup.HasFailureMarker(...)       │
│                                                    │
│  if !health.IsHealthy || marker:                   │  ← LAYER 8 entry
│      r = UpdateBackup.RestoreSnapshot(installDir)  │
│      if r.Restored:                                │
│          ClearFailureMarker; relaunch self; exit   │
│      else:                                         │
│          fall back to SelfRepair (network)         │
│  else:                                             │
│      ClearFailureMarker; schedule DeleteSnapshot   │
│      (30 s grace, background Task.Run)             │
└────────────────────────────────────────────────────┘
```

## State invariants

| State | `app/` | `app.bak/` | `app/.update-failed` | Action on next launch |
|---|---|---|---|---|
| Pre-update | populated, healthy | absent | absent | normal startup |
| Mid-update (snapshot done, copy in progress) | being mutated | populated | absent | (process is mid-flight; no startup yet) |
| Post-update healthy | new version | populated | absent | clear marker, schedule snapshot delete in 30 s |
| Post-update partial-fail | mixed DLLs | populated | present (xcopy non-zero) | RestoreSnapshot → relaunch |
| Post-update parser-fail | mixed DLLs | populated | absent (helper aborted before marker) | InstallHealthCheck.Check detects mismatch → RestoreSnapshot → relaunch |
| After 30 s grace, healthy | new version | absent | absent | normal startup |
| Snapshot itself corrupt | new version (mixed) | empty/truncated | maybe | RestoreSnapshot refuses (file count guard) → SelfRepair fallback |

## Disk-space considerations

- `app/` is roughly 50–60 MB (≈ 270 files including managed + native +
  PDB + sing-box.exe).
- `app.bak/` is the same size while it lives.
- Peak disk usage during update: 2× app/ + the staged update under
  `%ProgramData%\VPNRouter\update-staging\` (already present pre-Task-E).
  So pre-update peak is roughly **3× app size** = 150–180 MB.
- Cleanup window: 30 s after the FIRST healthy post-update launch.
  Reasonable upper bound on how long we hold the doubled space.
- Failure mode if disk is full: `CreateSnapshot` returns a non-Success
  result, the caller logs and proceeds. The user experience degrades
  to pre-Task-E (no rollback available, falls back to `SelfRepair` on
  next launch if needed).

## Why preferable to network-fetched SelfRepair

| Concern | SelfRepair (network) | UpdateBackup (local) |
|---|---|---|
| Works offline | no | yes |
| Time to recover | 30–90 s | ≈ 5 s |
| AMSI / AV surface | yes (`-File` PS1 still scanned) | none |
| Can recover when VPN is the broken thing | only if vpn.ninitux.com is reachable directly | always |
| Triggers UAC prompt | usually yes (install.ps1 elevates) | no (in-process file copy) |
| Idempotent | partly (10-min marker) | yes |
| Loop-safe | partly (10-min marker, then surfaces error) | yes (RestoreSnapshot consumes the snapshot, so a second hit falls through to SelfRepair) |

`SelfRepair` is **NOT** removed — it stays as the second-line fallback
for the rare case where `app.bak/` itself is missing or corrupt
(e.g., user manually deleted the folder, disk-full at snapshot time,
or someone restored from a backup that lacked the snapshot).

## Architectural issues uncovered

1. **`xcopy /R` is already in helper.cmd** (line ≈544 of `UpdateChecker.cs`,
   `xcopy "%SRC%\*" "%DST%\\" /E /Y /Q /R /I`). The `/R` flag overwrites
   read-only files; it is NOT a "fallback retry". So the prompt's
   "does helper.cmd already use `xcopy /R` fallback" question is
   answered: there is `/R` for read-only handling but no retry-on-
   failure semantics. Our `.update-failed` marker write is the new
   first-class failure detection — pre-Task-E the only signal was the
   `update-installed-version` receipt comparison after relaunch, which
   misses the case where the new binary's `AppVersion.Version` happens
   to match the receipt (e.g. failed install OF the same `-rN` we just
   tried, on a partial xcopy).

2. **`installDir` derivation**: `appDir = AppContext.BaseDirectory`
   ends in `app/`. We need its parent for the snapshot location. On a
   default `C:\Program Files\VPNRouter\app\` install this is trivial.
   On a portable / dev install where the user runs from a flat layout
   (no `app/` wrapper), `Path.GetDirectoryName` of the appDir gives
   the user's chosen folder, and we'd write `app.bak/` there as a
   sibling of the binaries — still works, but the symmetry breaks.
   Acceptable for now — production installs are always `app/`-layout.

3. **Snapshot at `update-staging/` siblings, not `app/` siblings?**
   We considered putting `app.bak/` under `%ProgramData%\VPNRouter\
   update-staging\app.bak\`. Rejected because:
   - `RestoreSnapshot` uses `Directory.Move` which is atomic only on
     the same volume. `%ProgramData%` and `Program Files\VPNRouter\`
     can be on different volumes (rare on default Windows but common
     on developer systems with separate D: drives).
   - File copy across volumes is not atomic — if the App crashes
     mid-copy, the user could end up with no `app/` and a partial
     copy, which is strictly worse than the corrupted state we set
     out to fix.
   - The 50–60 MB transient cost is acceptable on Program Files.

4. **macOS / Linux parity**: not implemented. macOS `ApplyUpdateMac`
   already uses an "old-bundle-aside-then-ditto" pattern that gives
   us a similar safety net inline. Linux `pkexec`-driven `cp -rfT`
   has its own atomic-on-failure semantics through the rsync-style
   path. If we ever see a Linux/macOS variant of the v2.31.7 partial-
   xcopy bug, we revisit.

## Live-verify scenarios (post-merge)

Cannot easily simulate xcopy failure on a clean dev VM (xcopy `/R`
rarely fails when source/dest are both writable). The following
manual scenarios cover the contract:

1. **Healthy update path** (positive control): trigger an in-app
   update from `vX.Y.Z-rN` to `vX.Y.Z-r(N+1)`. Confirm:
   - `app.bak/` appears alongside `app/` while the helper.cmd runs
   - 30 s after relaunch, `app.bak/` is gone
   - No `.update-failed` marker at any point
2. **Forced rollback path** (manual injection): immediately after
   `app.bak/` is created, kill the helper.cmd before xcopy completes,
   manually edit one of `app/`'s DLLs to break it, write
   `app/.update-failed` with arbitrary text, relaunch App. Confirm:
   - `[health]` line in stderr says "rollback ok: restored ..."
   - `app/` content matches the snapshot from before the corruption
   - `.update-failed` marker is gone
   - SelfRepair did NOT fire (no PowerShell window)
3. **Empty-snapshot guard** (safety): manually create an empty
   `app.bak/` (just `Directory.CreateDirectory`), break a DLL in
   `app/`, relaunch. Confirm:
   - `[health]` line says "rollback declined: ... empty/truncated"
   - SelfRepair fires as fallback
   - `app/` is untouched by RestoreSnapshot

These are documented as live-verify scenarios for the user to run
after the merging session ships -r3. Not part of automated suite —
xcopy mid-flight kill / manual marker injection is too brittle to
script.
