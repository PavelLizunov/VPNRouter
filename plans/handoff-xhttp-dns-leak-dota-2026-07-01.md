## НАХОДКА A: xhttp по-прежнему не подключается из приложения (сервер вроде
починен, клиент — нет)

Хронология:
1. Сервер `93.95.226.167:9443` (`main-brat`, VLESS+Reality+xhttp,
   `path=/U4YILqMxZg2N6sIKQFLt4w`) изначально отвечал
   `v2ray-xhttp: unexpected status: 404 Not Found` буквально на КАЖДЫЙ запрос
   — подтверждено логом (`C:\Project\logs\VPNRouter-diagnostics-20260701-003612.zip`,
   `singbox-tail.log`): 17.5 сек network warm-up, десятки разных доменов
   (api.anthropic.com, api.steampowered.com, msftconnecttest...), 0 успехов.
   TLS+Reality handshake при этом проходит (это реальный HTTP-ответ от
   сервера, не таймаут) — значит сервер жив, просто конкретный path не
   смаршрутизирован на его стороне. Клиентская часть (`ConfigGenerator.cs`
   BuildOutbounds, `VlessUriParser.cs` xhttp-ветка ~line 78-99) проверена
   независимо: сгенерированный JSON с точно таким же `path` проходит
   `sing-box-lx check` чисто — путь передаётся byte-exact из URI, без
   искажений при кодировании. **Вывод на тот момент: чисто серверная
   проблема, не баг VPNRouter.**
2. Владелец сообщил: "Пофикшено со стороны vps получилось подключиться" —
   т.е. на VPS что-то починили и подключение в моменте прошло.
3. **НО следующим сообщением владелец уточнил**: "в xhttp из приложения не
   подключило, хотя с iphone проблем не было" — то есть с ДРУГОГО клиента
   (iPhone, не VPNRouter — какой именно клиент неизвестно) этот же сервер
   работает нормально, а из VPNRouter (Windows) — по-прежнему нет.

**Свежей диагностики под ЭТО конкретное состояние ЕЩЁ НЕТ.** Диагностика из
п.1 (404) относится к состоянию ДО фикса на VPS и как объяснение ТЕКУЩЕГО
провала уже не годится — нужен новый снятый diag-бандл сразу после свежей
попытки подключения именно xhttp-сервера из приложения.

**Первый шаг**: попросить владельца ещё раз попробовать подключиться к
xhttp-серверу из VPNRouter и сразу снять диагностику (Настройки → экспорт
диагностики, либо просто `C:\ProgramData\VPNRouter\logs\singbox.log` —
свежий tail). Посмотреть НОВУЮ ошибку — не факт что это снова 404, могло
поменяться. Если ошибка другая — разобраться что именно. Если что-то похожее
на протокольное несоответствие (не HTTP-статус, а TLS/stream-level obscure
error) — сравнить как sing-box-lx строит xhttp-запрос (`mode=auto`,
`x_padding_bytes`, `no_grpc_header`, host-header — см. `VlessUriParser.cs`
xhttp-ветка) с тем, что послал бы стандартный Xray-core клиент (вероятно то,
чем пользуется iPhone) — возможна несовместимость реализации xhttp в
sing-box-lx (форк `Leadaxe/sing-box-lx`) относительно апстрима. **НЕ трогать
AWG-ядро/lx-патчи вслепую** — xhttp это отдельная ветка кода от AWG.

## НАХОДКА B: реальная утечка DNS под AWG full-tunnel (P1, есть скриншот-доказательство)

Подключение на момент теста: `main-brat`, AmneziaWG+obfs, `93.95.226.167:51822`,
`routing_mode: full`, статус в UI "Подключено [full]".

Скриншот браузерного IP/DNS-leak-теста:
- **IP** = `93.95.226.167` (Iceland, 1984 ehf) — корректно, IP не течёт.
- **DNS Addresses** — 3 сервера, ВСЕ `195.2.238.4` / `195.2.239.4` /
  `195.2.238.58`, подписаны "Russia, Trytek LLC", 300/300 hits каждый.
  Это НЕ то что сконфигурировано (`vpn-dns` = AdGuard/пользовательский DoH
  через `detour="proxy"`, `local-dns` = 1.1.1.1 через `dns-direct`) —
  реальная утечка DNS-запросов мимо туннеля на что-то похожее на локальный
  ISP-резолвер, при этом сам HTTP-трафик (IP) корректно идёт через VPN.

Текущие toggles в момент теста (`C:\ProgramData\VPNRouter\config.yaml`):
`strict_dns: true`, `force_ipv4_only: true`, `flush_dns_on_start: true`, но
**`dns_leak_lockdown: false`** — firewall-backstop (блокировка порта 53 на
не-TUN интерфейсах) выключен, поэтому даже если бы что-то попыталось утечь
мимо туннеля, ничего бы это не поймало и не заблокировало as a hard failure.

Это **ровно тот вопрос**, который уже был явно поставлен как Phase 1.3 в
`plans/tz-codex-awg-dns-leakprotection-audit-2026-06-28.md`, пункт 1
("Строгий DNS"): "с AWG `dns.final=vpn-dns`, `detour=proxy` — резолвится ли
вообще hostname DoH-сервера, или это `DNS query loopback`... нужно
перепроверить на ЖИВОМ AWG-туннеле" — теперь есть живое воспроизведение
реальной утечки, аудит нужно закрыть максимально приоритетно, это P1 по
факту (see `plans/OPEN-DEFECTS.md`).

**Первый шаг**: повторить browserleaks-style DNS-leak-тест на живом
AWG-туннеле, ОДНОВРЕМЕННО снимая `singbox.log` (grep `dns:` — куда реально
уходят DNS-запросы, отрабатывает ли `route.rules[protocol=dns,
action=hijack-dns]` вообще для трафика через AWG `endpoints[]` block, или тут
есть путь резолва в обход `dns.servers[]`, специфичный для wireguard-типа
endpoint на Windows — например какой-то системный DNS-резолв, который TUN не
перехватывает так же надёжно как для VLESS-outbound). Смотреть
`ConfigGenerator.cs` BuildDns + `BuildAmneziaWgEndpoint` +
`LeakProtection.cs`. Возможный quick-mitigation для владельца прямо сейчас
(не фикс, а обход): включить `dns_leak_lockdown: true` в настройках —
если утечка реальна, лочдаун её как минимум заблокирует (ценой возможной
потери интернета вместо утечки — fail-closed).

## НАХОДКА C: Dota2 — "Задержка: ОШИБКА" на ВСЕХ регионах под AWG (Roblox стабилен)

Скриншот диалога выбора региона матчмейкинга Dota2 при активном том же
AWG-подключении: ВСЕ доступные регионы одновременно (Зап./Вост. Европа,
Россия, Восток/Запад США, Дубай, Индия, Перу, Бразилия, Аргентина,
Юж.Африка, ЮВ Азия, Чили, Австралия) показывают "Задержка: ОШИБКА" —
не отдельные далёкие регионы, ВСЕ сразу. Диалог: "Не удалось вычислить
задержку. Проверьте интернет-соединение."

Владелец: "roblox с awg работает стабильно, возможно это как-то связано с
dns" — сам подозревает связь с находкой B. Одновременный провал ВСЕХ
регионов (а не таймаут по одному-двум) больше похож на системный сбой на
раннем этапе (DNS resolve упомянутых matchmaking-хостов) чем на россыпь
независимых сетевых таймаутов. Если Dota2 резолвит имена региональных
серверов и это резолв либо утекает по тому же нерабочему пути что и в
находке B, либо утёкшие DNS-ответы ведут на IP, которые потом фризит
российский TSPU для не-российского трафика (см. memory `roblox-277-rca` —
"RU TSPU замораживает foreign IP tcp+udp" — тот же паттерн, другая игра),
это объяснило бы одновременный провал разом.

Существующий трек по игровому UDP: `plans/tz-codex-dota-awg-game-udp-2026-06-29.md`
+ `plans/OPEN-DEFECTS.md` P2 (`WSAENOBUFS` под game UDP нагрузкой) — **но, по
всей видимости, нужно сначала закрыть находку B (DNS leak), потом
перепроверить Dota2** — вероятно одна и та же причина, а не два разных бага.
Не чинить WSAENOBUFS вслепую, пока DNS-гипотеза не проверена или не
исключена.
