# v2.31.10 — VPNRouter coexistence with WireGuard / AmneziaWG

**Date**: 2026-05-06
**Worktree**: `funny-liskov-3f39cb`
**HEAD**: v2.31.10-r1 (prerelease, shipped before this audit)
**VM**: Windows 11 LTSC 2024 in VirtualBox; default route via NAT 10.0.2.2

## Триггер

Real-world user pattern: AmneziaWG to corporate gateway 10.9.1.1 + VPNRouter on
top, both running concurrent wintun TUN adapters. Prior session
(`memory/wireguard_killswitch_wfp.md`) accidentally killed VM internet by
activating WG with `AllowedIPs = 0.0.0.0/0`; rescue procedure documented but
never repeated under controlled conditions. Open question: how does VPNRouter
behave when (a) coexisting with another wintun, (b) the other wintun has a WFP
kill-switch, (c) VPNRouter is torn down with the other still up.

## Test methodology

Five scenarios run on `funny-liskov-3f39cb` worktree. Each scenario verified
internet via `Invoke-RestMethod 'https://api.ipify.org?format=json'` before and
after, and snapshot of route table + adapter state. DANGER scenarios (#3, #4)
wrapped in `try { ... } finally { rescue }` so cleanup runs unconditionally.

Rescue pattern (proven during this audit):

```powershell
Get-Service | Where Name -match '^(WireGuardTunnel|AmneziaWGTunnel)\$' | ForEach-Object {
    Stop-Service $_.Name -Force -ErrorAction SilentlyContinue
    Set-Service $_.Name -StartupType Manual -ErrorAction SilentlyContinue
}
```

Evidence saved to `plans/coexistence-evidence/` (current.json snapshots, log
slices, JSON state dumps, screenshots).

## Detailed findings

### Scenario 2 — auto-excluded WG subnet

vpnrouter log line, exactly as designed:

```
2026-05-06 17:05:00.127 +03:00 [INF] [VpnEngine] Auto-excluded WG/AWG subnets: 10.99.99.0/24
```

`current.json` confirmed (`plans/coexistence-evidence/02-current-with-wg-lan.json`):

```json
"inbounds": [{
    "type": "tun",
    "tag": "tun-in",
    "interface_name": "VPNRouter-TUN",
    "address": "172.19.0.1/30",
    "auto_route": true,
    "strict_route": false,
    "route_exclude_address": ["10.99.99.0/24"]
}]
```

Adapter was `wg-lan`/`10.99.99.2/32` → widened to `/24` by
`NetworkInterfaceDetector.CalculateSubnet()` lines 132-135. Working as designed.

### Scenario 3 — WireGuard kill-switch behavior

WG service `WireGuardTunnel$wg-killsw` came up. Internet DIED (`Invoke-RestMethod`
returned `The remote name could not be resolved: 'api.ipify.org'`). Ping to
gateway 10.0.2.2 returned `DEAD`.

VPNRouter Connect clicked during WFP-blocked period. From `vpnrouter*.log`:

```
2026-05-06 17:08:20.184 +03:00 [INF] [VpnEngine] Auto-excluded WG/AWG subnets: 10.99.99.0/24
2026-05-06 17:08:25.715 +03:00 [INF] [VpnEngine] sing-box started (PID 6892)
2026-05-06 17:08:25.802 +03:00 [INF] [VpnEngine] VPN Router is running
2026-05-06 17:08:39.076 +03:00 [INF] [VpnEngine] TUN ready after 13360ms (attempt 4)
```

Compare to normal startup (scenario 1, no WFP block): TUN ready after 1308ms,
1 attempt. Under WFP block: 4 attempts, 13.3s. **No FATAL log entries, no
HealthMonitor restart-loop, no panic in singbox.log.** sing-box gracefully
absorbs the network noise and continues retrying.

Once VPNRouter `auto_route` claimed default route, sing-box was apparently able
to make outbound VLESS connections through `VPNRouter-TUN` despite WG's WFP
filters blocking traffic on the physical Ethernet adapter. This is consistent
with how WG kill-switch works: WFP `Block all except FROM tunnel adapter` rule
exempts TUN-sourced packets; sing-box's TCP socket is bound to the physical
interface but routed via TUN/VPNRouter's exclude list. Net effect on user:
*VPNRouter still functions even when WG kill-switch is up*.

This is an interesting edge case — depending on perspective, either a feature
("VPNRouter survives a misconfigured WG") or a leak ("WG kill-switch user
expects no traffic; VPNRouter's TUN bypass routes around it"). For the user's
stated problem domain (AmneziaWG to corp + VPNRouter on top), the feature
interpretation is what's wanted. No bug here.

### Scenario 4 — AmneziaWG kill-switch behavior

AmneziaWG 2.0.0 MSI installed via direct GitHub download
(`https://github.com/amnezia-vpn/amneziawg-windows-client/releases/download/2.0.0/amneziawg-amd64-2.0.0.msi`).
Note: the URL `https://updates.amnezia.org/awg-windows/AmneziaWG.msi` from the
task brief returned 404; GitHub releases is the working source.

AmneziaWG adapter description was `WireGuard Tunnel` (because AWG forks WG's
Windows client) — caught by the `WireGuard` keyword in
`NetworkInterfaceDetector.WgKeywords`. **AmneziaWG WFP behavior is identical to
WireGuard**: same WFP filters, same kill-switch semantics, same rescue
procedure works.

sing-box was already running (PID 6892) when AWG came up. PID stayed stable
through 25s of WFP-blocked observation. No restart, no FATAL.

### Scenario 5 — VPNRouter teardown with WG active

Click sequence:

1. Pre: `sing-box PID=6892`, `VPNRouter-TUN Up`, `wg-lan3 Running`, `wg-lan3
   adapter Up`.
2. Click Disconnect button on VPNRouter App (relative coords 270, 545).
3. Post (after 8s settle):
   - sing-box: STOPPED ✓
   - VPNRouter-TUN: GONE (cleaned by `TunDiag` in Stop path) ✓
   - wg-lan3 service: **Running** ✓
   - wg-lan3 adapter: **Up** ✓
   - Internet: works (`104.194.156.93`)

`TunDiag.RemoveLeftoverAdapters()` correctly targets only `VPNRouter-TUN` /
`sing-box-tun*` by name; doesn't touch arbitrary wintun adapters. Confirmed
by absence of any disable/remove side effects on `wg-lan3`.

## Recommendations

### 1. Should VPNRouter detect existing wintun adapters and warn user? — **NO** (already does the right thing)

`NetworkInterfaceDetector.IsWireGuardInterface()` already auto-detects WG and
AmneziaWG by description+name keyword match. Detected subnets get added to
`route_exclude_address` automatically. Auto-detect log line is shown in
vpnrouter.log. No additional warning needed — the "warning" is the audit log
itself, and it already fires.

If we wanted to be extra-safe, we could surface this in the App's status
banner: "Detected coexisting VPN: WireGuard (10.99.99.0/24) — excluded from
TUN routing." But that's polish, not correctness.

### 2. Should we extend `Auto-excluded WG/AWG subnets`? — **MARGINAL**

Current keywords: `WireGuard`, `Amnezia`, `AWG`, `WG Tunnel`. This already
catches WG client, AmneziaWG, and most third-party WG-derived clients (because
they typically inherit "WireGuard Tunnel" in `InterfaceDescription`).

What it doesn't catch:
- **Tailscale** (`InterfaceDescription = "Tailscale Tunnel"`). Tailscale uses
  `100.64.0.0/10` by default (CGNAT), which is non-routable for normal traffic
  — low risk that VPNRouter's TUN steals Tailscale traffic. But user might be
  on a tailnet using a different range.
- **OpenVPN TAP-Windows** — different driver, won't generally conflict at the
  wintun level.
- **Cisco AnyConnect** — uses its own IPSec, not wintun, doesn't trigger
  `route_exclude_address` issue.

**Suggested follow-up (low priority)**: add `Tailscale` to `WgKeywords`. Low
risk, helps a small population. Not worth a bump for v2.31.10-r2 — fold into
next stability cycle.

### 3. Should we set explicit route metric for VPNRouter-TUN to win over WG? — **NO**

sing-box's `auto_route: true` already handles route precedence by setting
appropriate metric on the TUN adapter at startup. Manual metric override would
fight with sing-box's own logic.

What we observed: when both VPNRouter-TUN and Ethernet have RouteMetric=0,
ifMetric is what tiebreaks, and Windows naturally prefers TUN for VPN-routed
processes (because sing-box installs per-process route hints via the TUN
inbound).

In scenarios 2 and 5, no routing conflicts arose. The auto-excluded subnet
mechanism is the right abstraction.

### 4. Should we detect WFP block patterns and show a user-actionable error? — **NO** (out of scope)

Sing-box doesn't FATAL-loop under WFP block, just retries TUN initialization
slowly. Not a graceful-degradation bug. If we wanted to be helpful, we could
add a `vpnrouter doctor` check that lists active `Get-NetFirewallProfile` rules
including WFP, and flags `WireGuardTunnel$*` services in Running state — but
that's a "diagnostic helper," not a fix.

The actual user-actionable failure mode for "AmneziaWG to 10.9.1.1 + VPNRouter
on top" is when the AWG handshake fails (legitimate endpoint, but unreachable
right now): then AWG installs its WFP rules, internet dies, and VPNRouter is
running but its outbound VLESS gets the same WFP block. Recovery path: either
stop the AWG service (rescue), fix the AWG config, or wait for AWG handshake
timeout to clear filters.

VPNRouter cannot fix this in the user's stack — fixing it means
deactivating the user's intended kill-switch. Best we can do is document the
diagnostic in `vpnrouter doctor` (future work, not v2.31.10).

## No concrete bug fix in v2.31.10

The audit found no bugs in VPNRouter's coexistence behavior. Five scenarios
passed; the auto-detect + route-exclude mechanism (introduced before v2.27.x
per code archeology) works for both WG and AmneziaWG. The rescue procedure
documented in `memory/wireguard_killswitch_wfp.md` was confirmed effective
twice (scenarios 3 and 4).

**v2.31.10-r1 stands as-is.** No `-r2` bump needed for this audit's findings.

## Side observations (out of scope, captured for posterity)

1. **Windscribe self-update interrupted MSI install of AmneziaWG.** Our
   `msiexec /i amneziawg.msi /quiet` triggered a side-channel that revived an
   in-progress Windscribe installer (parent PID 9252, since terminated), which
   spawned `Windscribe_2.21.7_amd64.exe /VERYSILENT` and ended in a "Windscribe
   Install Error" dialog plus a "Uninstall Windscribe?" prompt. UI clicks for
   VPNRouter automation got captured by the Windscribe modal. Mitigation in
   the audit: `FindWindow` + screen-coord click on the dialog's `No` button.
   Not a VPNRouter issue.

2. **Tailscale present on this VM (ifIndex=14, "Tailscale Tunnel")** was
   never auto-detected. See recommendation #2.

3. **AmneziaWG MSI URL drift**: brief said `https://updates.amnezia.org/awg-windows/AmneziaWG.msi`,
   actual location is GitHub releases. If we ever ship per-platform doctor
   advice, link to `github.com/amnezia-vpn/amneziawg-windows-client/releases`
   instead of `updates.amnezia.org`.
