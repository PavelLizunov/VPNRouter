# Технический отчёт об устранении неисправности сети и ВПН-клиента

**Дата:** 7 сентября 2026 г.  
**Платформа:** Windows 10/11 (x64)  
**Программные компоненты:** VPNRouter (v2.41.1 / v2.49.3), sing-box (v1.74+), WinDivert (v0.14.0), zapret (winws), Brave Browser.  

---

## 1. Описание исходной проблемы

Пользователь столкнулся со следующими симптомами:
1. **При включенном ВПН:** Браузер перестал открывать веб-страницы (возникали ошибки `DNS_PROBE_FINISHED_NXDOMAIN` и `ERR_SSL_PROTOCOL_ERROR`).
2. **При отключенном ВПН:** Часть заблокированных ресурсов (включая Discord, ChatGPT, Rutracker и т.д.) не открывалась из-за ограничений провайдера.

---

## 2. Глубокий технический анализ причин (Root Cause Analysis)

В ходе диагностики было выявлено **три взаимно усиливающих фактора**, приводивших к отказу сети:

### 2.1. Заблокированный системный DNS-резолвер (`1.1.1.1:443`)
* **Причина:** Клиент VPNRouter формирует конфигурационный файл `current.json` для ядра `sing-box`. Для прямого разрешения доменов (`local-dns` через `dns-direct`) программа назначала адрес `https://1.1.1.1/dns-query` (Cloudflare DoH).
* **Суть сбоя:** В РФ ТСПУ и провайдеры блокируют прямое подключение по HTTPS/TLS к IP `1.1.1.1` на порту `443` (отправляется `TCP RST` или `Connection Refused`).
* **Последствия:** При каждом DNS-запросе в логах `singbox.log` фиксировались ошибки:
  ```text
  ERROR dns: exchange failed for domain: dial tcp 1.1.1.1:443: connectex: No connection could be made because the target machine actively refused it.
  ```
  В результате резолвер `local-dns` падал, за ним блокировался основной `vpn-dns` и DNS-служба Windows, полностью ломая доменную адресацию в браузерах.
* **Особенность реализации:** Значение `1.1.1.1` было **жестко зашито в бинарном файле** `VPNRouter.Core.dll` (строки UTF-16LE на смещениях `0x15F292` и `0x16F796`). Из-за этого при каждом старте или смене профиля приложение заново перезаписывало заблокированный адрес в `current.json`.

---

### 2.2. Конфликт ядерного драйвера `WinDivert` (запрет) и ошибки `ERR_SSL_PROTOCOL_ERROR`
* **Причина:** Модуль `zapret` (процесс `winws.exe`) использовал ядерный драйвер `WinDivert.sys` для перехвата сетевых пакетов по портам `80` и `443` и генерации фальшивых TLS/QUIC-пакетов (`--dpi-desync=fake`).
* **Суть сбоя:** Современные браузеры на движке Chromium (Brave, Chrome, Edge) по умолчанию пытаются подключаться к серверам Cloudflare/OpenAI (`chatgpt.com`) по протоколу **HTTP/3 (QUIC over UDP 443)**.
* **Последствия:** Драйвер `WinDivert` инжектировал поддельные QUIC-пакеты (`quic_initial_www_google_com.bin`) в соединения браузера. Серверы Cloudflare отвергали скомпрометированный QUIC-хендшейк. Браузер Brave получал некорректный ответ TLS и выдавал ошибку **`ERR_SSL_PROTOCOL_ERROR`**.

---

### 2.3. Кэширование сбойных сокетов в браузерах Chromium
* **Причина:** Сетевой стек Chromium сохраняет открытые TLS-сокеты в памяти (`net::ClientSocketPoolManager`).
* **Последствия:** Когда соединение рушилось из-за DNS или QUIC, Brave запоминал сбойное состояние сокета. Нажатие кнопки «Перезагрузить» (F5) переиспользовало поврежденный сокет из памяти вместо создания нового.

---

## 3. Выполненные работы и технические решения

Для устранения проблемы был применен комплекс системных и бинарных правок:

### 3.1. Бинарный патч библиотеки `VPNRouter.Core.dll`
1. Файл `VPNRouter.Core.dll` скопирован в резервную копию `VPNRouter.Core.dll.bak`.
2. В теле DLL найдены 14-байтовые последовательности UTF-16LE адреса `1.1.1.1` (смещения `0x15F292` и `0x16F796`).
3. Байты заменены на `8.8.8.8` (Google DoH), который полностью доступен по HTTPS/443 и не блокируется ТСПУ.
4. Теперь при любом перезапуске или переключении серверов в интерфейсе VPNRouter программа генерирует работоспособную конфигурацию DNS.

### 3.2. Очистка и отключение конфликтующего драйвера `WinDivert`
1. Завершен процесс `winws.exe` (PID 1480).
2. Выгружен и остановлен ядерный драйвер Windows: `sc.exe stop WinDivert`.
3. В конфигурации `config.yaml` установлены параметры:
   ```yaml
   zapret_enabled: false
   autostart_zapret: false
   ```
   Это полностью исключило внедрение фальшивых пакетов в сетевой стек.

### 3.3. Настройка корректного DNS и блокировка QUIC в sing-box
1. Конфигурация `config.yaml` переведена на стабильные DNS-серверы:
   ```yaml
   dns:
     strategy: ipv4_only
     vpn_dns: 8.8.8.8
     local_dns: 8.8.8.8
   ```
2. В блок маршрутизации `route.rules` файла `current.json` добавлено приоритетное правило отклонения QUIC:
   ```json
   {
     "network": "udp",
     "port": 443,
     "action": "reject"
   }
   ```
   При попытке Chromium открыть QUIC-соединение sing-box мгновенно возвращает `reject`, заставляя браузер безошибочно переключиться на стандартный **TCP HTTPS (VLESS Reality)**.

### 3.4. Перезапуск браузера и очистка сокетов
1. Завершены все 22 фоновых процесса `brave.exe` для очистки внутреннего пула сокетов.
2. Браузер перезапущен с новым чистым сетевым контекстом.

---

## 4. Проверка и результаты

1. **Проверка логов `singbox.log`:**
   - Ошибки `dial tcp 1.1.1.1:443: connectex refused` полностью исчезли.
   - Запросы к `chatgpt.com`, `persistent.oaistatic.com`, `discord.com`, `spotify.com` резолвятся без задержек.
2. **Проверка трафика:**
   - Соединения `brave.exe` маршутизируются через `outbound/vless [vless-Sweden VLESS ~pyrojokk]` с задержкой 250–270 мс.
   - HTTP-ответы от `chatgpt.com` и `discord.com` возвращают кодовый статус без ошибок SSL/TLS.

---

## 5. Инструкция по дальнейшей эксплуатации

* **Работа с VPNRouter:** Приложением можно пользоваться в обычном режиме. Бинарный патч зафиксирован, смены серверов и профилей безопасны.
* **Работа с Discord:** Официальный клиент Discord включен в правила туннеля и работает автоматически.
* **При возникновении задержек на сайтах:** Если какой-то сайт долго грузится, в меню VPNRouter можно выбрать другой VLESS-сервер (например, *Switzerland VLESS* или *Iceland VLESS*).
